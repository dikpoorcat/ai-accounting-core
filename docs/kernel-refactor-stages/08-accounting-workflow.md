## 已确定的使用方式

- 泛化开始默认最早待处理月，展示银行、工资、普通业务、税务、资产、融资六类完整清单；明确事项直接处理。
- 已到期且条件齐的事项优先；缺资料时继续其他独立事项。未知期限不推定逾期，普通未结款项不自动成为付款指令。

- 外部网站代办不在本阶段范围内。

## 实施设计

### 工作清单

`workflow(company_id, as_of, period?)` 是公司级工作起点；`period_readiness(company_id, period, as_of?)` 读取明确月份。两者与看板共用期间状态，退出固定九步和重复判断。

清单分资料与核算、关账、实际办理、文件交付；六类业务分别保留资料状态、核算状态、计数、问题和精确来源。分类来自注册定义和明确检查器职责，不解析错误文案。

自动选月只使用实际业务、资料、正式入账及已建立事项。闭期资料真实问题由开放期承接，不据此代填更正入账月；闭月申报和文件待办保持公司级可见，不把核算月份拉回闭月。空公司没有可靠月份时返回空状态；无开放待处理月时以最近已处理月作展示背景。选月不得逐月完整核验，不从政策或公司成立月补造空月。

### 实际办理与核对

`external_completion` 保存实际事件、义务精确版本、实际日期、不可变凭据及真实原采用来源。实际申报资料可以先于工资发布保存；不补造计算引用或以空集合表示无业务。

`external_basis_review` 引用办理事实与正式账务精确版本，保存核对依据，通过统一预览和发布形成无分录结果。实际完成与核对状态分别返回；后续账务变化只使核对过期，不撤销真实办理。真实补报另存接续事实，复核不伪装为再次申报。

季度税务办理和季度财务报表报送拆开，退出 `quarterly_tax_and_reports`；财报依赖对应期间核算及关账，保留空月覆盖规则。实际申报、扣税、缴款不互相推定，不增加关账门槛。

### 恢复与合同

规范 `needs_information` 和 `fact_issues`；已知下一步以类型明确的 `resolution` 返回命令、事实类型或候选。技术故障不变成业务追问。原请求重试沿用原幂等键；内容改变后重新预览并使用新键。

新增只读 `request_result(company_id, submitted_request_id)`，从现有请求与审计读取 `committed` 或 `unknown`。校验两者一致，损坏拒绝；未知不能解释为失败，不增加请求表或聊天状态。

公司任务保存稳定 `error_code`，公开安全、直白说明；覆盖四类 worker、启动恢复和显式重试，保留尝试次数上限。目录操作继续使用 `operations`。

响应版本：context 2；brief/funds/employees/assets 7；看板业务详情 5；期间准备/季度报表 4；浏览器任务 2；workflow/完整 period_readiness 1。关账内容 4、核对页面 1 保持。金额继续整数分和 HTTP 整数分字符串，生成合同与全部消费者当期接通。

### 协议与说明

版本化 `agent_operating_protocol` 统一开始、查证、追问、回答范围、执行、反馈、恢复与切公司。Skill 负责模式和资料阅读，默认提示遵守协议；启动 Skill 只准备环境。直接改写漂移的旧接口、PostgreSQL 和重建操作指引，保留原审查及历史阶段记录。

## 实施顺序

## 实际结果与提交

### 实现结果

工作清单复用期间检查，六类资料与核算、关账、实际办理和文件交付各自保留状态。公司级任务含全部活动及失败任务；手工备份无虚构月份。当前事实、原件和任务目录组成选月来源，闭期已发布但仍未处置的原件也会进入第一开放月，未知期间不能漏过。选月与随后期间读取共用原件解析缓存。

季度税务与财报已拆开。办理事实保存原提交依据和真实凭据；账务核对通过独立无分录结果表达一致、差异和无法核对。后来核算使旧核对过期，真实补报精确接续且不能倒置实际日期。已保存但错误的办理事实必须在原编号修订，或有依据地撤去；不允许另建根绕过已有登记。关账核对摘要继续保留未结事项计数，冻结内容合同仍为 4。

请求回执读取使用已有 request/audit，响应丢失沿原请求键重放。四类任务和启动恢复保存稳定错误码，公开返回不包含原异常；明确的请求形状错误与程序内部错误分别处理。公司开发合同更新任务错误码列和外部事实表，目录合同不变。

当前后端生成 35 份合成响应，覆盖空公司、开放／冻结月份、资料问题、实际办理与核对状态。工作清单和完整期间读取纳入同一模型／Schema／TypeScript／Ajv链，新增嵌套金额的 int64、未知值、浮点及布尔拒绝检查。页面及运行协议、操作 Skill、默认提示和当前运行说明同步更新，不再保留固定九步或旧季度别名。

### 独立 AI 对话验收

使用 GPT-6 Sol、高推理的独立智能体，通过测试专用持久 MCP 连接调用真实 `finance_local_schema` 和 `finance_local_command`。环境只含新建合成甲、乙公司，鉴权保存在进程内；没有业务模拟接口，也没有把测试调用日志加入产品。

57 次实际 MCP 调用走通“开始 → 查已有公司及资料 → 问起始月／缺少账户 → 接收负责人回答 → 保全证据和逐项处置 → 登记、预览、发布 → 更新清单”。随后模拟中断，明确要求切乙公司直接处理另一笔，智能体重新读取 Schema、公司上下文和工作状态，新建乙公司自己的现金身份。收款人未知仍为空；未把“其他事项没有新确认”扩成无业务。

在甲公司的证据写入已提交后，测试中转器故意丢失一次响应。智能体以原载荷和原请求键重放，返回同一回执；数据库仅一行请求及一行审计。原件方向填写错误后，也实际走过资料修订、旧定位失效、业务录入更正和无影响复核，原凭证没有重复。最终甲、乙各一笔 10,000 分支出、各一张凭证，账户不同，没有关账；甲的事实为修订 2，乙为修订 1。

实际对话、完整调用及只读数据库核验留在忽略目录 `.tmp/stage8-agent-eval-01/`。其中 `dialogue.md`、`tools.jsonl`、`verified-state.json` 分别保存对话、工具和最终状态。智能体曾多问一句“公司实际支出还是备用金内部消费”；最终按明确答复处理，没有据此创建新业务规则。本轮证明这些实际路径已走通，不把一次对话当作所有会计场景的正确率证明。合成 MCP 服务已关闭。
