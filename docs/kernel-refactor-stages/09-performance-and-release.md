## 实际完成的八组优化

1. **精简老板看板及整条读取链。** 独立月度核对模块及专用请求、缓存退出默认页面；资产不再返回未展示的历史状态和来源标签，同时清理对应查询、组装与合同。简报只消费金额时，不构造资金页专用的对账展示和历史账户标签。两关闭月的金额窄路径返回值字节28,784→5,266、结果解码6→0；全量金额、未知状态及必要核验保留。
2. **限定SQL范围并修正索引驱动。** 银行事实定位从重复扫描全公司角色改为fact ID索引；员工、报表头及冻结采用定位同类排查。直接采用部分索引避免累计readiness引用扩大候选，主120资产VM下降11.5%，返回行和解码量不变。报表4932个命名头改用JSON对象key/value，VM266,763→222,267，特殊输入保留原退路。
3. **分开全量汇总和按页明细。** 默认装载20条明细，续页、筛选、详情和精确直跳分别读取，不先拉全量对象找目标。全量业务金额独立计算；仅为命中卡片装载必要展示资料，后续已退出字段进一步删除专用装载。资产启用身份、开放成员、冻结来源和完整核验仍按职责检查。
4. **同一快照内复用核验与精确定位。** 发布、范围、manifest和权限检查去重；缓存按请求key查缺，不遍历全部已缓存月份。目录精确key查找及唯一目标哈希复用，使描述遍历119,186→59,847、目标哈希12,119→239。owned连接复用SQL准备程序；成功数据与业务证明不跨请求快照缓存。
5. **减少已核数据的重复汇总和编码。** 资金摘要直接消费同快照已核资金效果，省去JSON→SQLite及未使用分页序号的组装；金额消费者不建立未消费的事件字典和展示统计。报表复用已取得的期末金额和精确checkpoint基准，余额summary仅处理变化key；未知、异常形状、非owned与固定历史规则保留完整回退。
6. **统一HTTP响应校验和序列化。** 看板响应在Service统一校验一次、dump_json一次，HTTP直接发送bytes；内部已确认的重复投影校验收敛，独立边界仍严格校验。后期热态诊断序列化约0.1–0.3ms，此项是减少重复处理的工程优化，不作为500ms主要瓶颈的证据。
7. **前端按需加载与局部刷新。** context和主请求并行，共享已加载context或pending promise，watcher避免相同选择重复请求。详情展开才加载，筛选和分页刷新对应集合；相同选择刷新保留隐藏挂载组件，公司、期间、错误及版本失效时清空重读。凭证列表、税务局模板和老板必要待办保留。
8. **收敛读取容器和临时对象生命周期。** 标准ChainMap按原优先序展平，checkpoint基准同快照只遍历一次。递归closure捕获prior map形成自引用环，改显式stack；weakref测试证明请求结束立即释放，未关闭GC或调用强制回收。相关统一回归321项通过、五页业务输出相等；未证明旧慢样本由GC造成。
