For assets, the four selected-but-unindexed keys are:

1. `Read("fact", "asset_consumption", "*", following_month)`. `_required_asset_work` uses the *calculation* consumption outcome to identify the latest consumed month/completed count; it never refers to the fact counterpart. The existing main48 private trace includes 1,128 such fact versions.
2. `Read("calculation", "asset", "*", following_month)`. Acquisition facts define the cards; activation and consumption calculations, and reimbursed-card calculations, supply the rule's posted checks. The ordinary asset-page card query and formal publication verifier independently select asset calculations where their own purposes require them. The existing main48 trace includes 48 asset calculations.
3. `Read("calculation", "reimbursed_asset_batch", "*", following_month)`. The rule walks the batch *fact* member list and checks every member's reimbursed-asset card against its *reimbursed_asset* calculation. No batch calculation value or ID is read by this readiness rule. Zero such calculations appeared in the main48 private trace; this is not evidence that a real bundle cannot have one.
4. `Read("calculation", "opening_identity_binding", "*", following_month)`. Asset/loan readiness applies the current binding *fact* via `_assignment_data`. Neither rule uses a binding calculation row. Zero appeared in the main48 trace; it must still be tested with a nonempty correction bundle before any change.

These four were selected into `Context` solely because `required_work` eagerly materialized all declarations; `Context.trace` then reported their IDs as if the business rule used them. The current declaration removes the four reads and their eager selections together. The retained 27 selections and formal source gates are unchanged.

## Frozen and formal source duties

`Periods.collect_current_readiness` unions all declarations, selects and validates typed inputs in the caller snapshot, runs each evaluator, and records `Context.trace()` IDs under `close_requirements.readiness`. `Periods._manifest` writes this map into each new immutable close. `read_indexes._close_references` expands every saved readiness ID into close-reference rows; `integrity._check_closes` checks every saved readiness ID against independently validated source sets. Readers of an **existing** close read its saved original list; they do not regenerate that list from today's readiness declaration. Search of the sealed source found no direct consumer of the `assets_and_financing` map by name except its registration and work-area annotation; report readers explicitly use `financial_reports`, not the asset map. This supports preserving all old close bytes and fixed-v1 behavior while changing only what a new *current* check actually traces.

The formal close path does not rely on these four readiness keys as its only publication/content gate: `Periods._manifest` calls `verify_close_integrity` **before** `check_readiness`. `_verify_close_integrity_snapshot` independently collects all current calculations through the month, voucher owners and all stored close-reference IDs, then `_check_sources` validates calculation/fact dependency and seals, source digests, original typed fact rows/child order, publication and evidence. `Periods.completeness` separately rejects a current-month `fact_current` without `calculation_current` as unpublished, with its existing derived-asset disposition exception. This must be exercised for asset acquisition, asset consumption, batch owner and opening-binding cases; this static proof does not replace fault tests. Full company verification and repair must continue to compare their own authoritative full sets, not trust a reduced readiness trace.

The public readiness/page behavior has a narrower caveat: selecting an otherwise unused key today still constructs a typed fact/calculation, and malformed storage can make that page fail early. It does **not** itself perform the full digest/source-chain proof supplied by the formal close verifier. The parent clarified that accidental rejection from loading an unused body is not by itself sufficient reason to keep that work, but all business checks and actual source gates must remain. A reduced declaration would intentionally make the readiness trace describe actual rule use; this is a new-close output change even when `issues` are identical, and cannot rewrite any prior root or released v1 reader.

## Validation and limits

- New real Engine/QueryReads tests pass: five tests cover a nonempty reimbursed batch, three successive consumption months with no unused fact decoding, loan identity correction, a closed-period opening binding, and formal close rejection for an unpublished asset and a damaged authoritative asset source. They compare the former and current readiness issues and assert the changed trace IDs. Five related existing asset, identity and opening tests pass; Ruff passes. The wider grouped regression and fixed-v1 verification remain the release checks.
- In fixed-r29 main48, private ABBA complete brief responses differ only at `/data/generated_at`. Each 31-read run asks `Store.facts` for 4,273 IDs including 1,128 consumption facts; each 27-read run asks for 3,145 IDs and zero consumption facts. SQL returns 86,003 → 81,443 rows, 26.96 → 26.21 MB, and 4.0193M → 3.8981M sampled VM instructions. The required consumption calculations remain selected. Hot diagnostic CPU is approximately 2.20 s old versus 2.22–2.27 s new, so this is a confirmed physical-read reduction and more accurate trace, not a demonstrated whole-page latency improvement.
- Existing formal full verification, repair, backup and fixed-v1 paths continue to read authoritative saved source and manifest content independently. The changed current readiness trace cannot be applied retrospectively to a saved close. Its exact new-close root may differ even with identical business issues; no historical root is rewritten.

The released `content-v1` descriptor hashes the model class sources, reference declarations, independent v1 history/storage rules and named v1 close readers. It does not hash the current module-level `domains.assets.required_reads` function. No model class or v1 reader was edited here, so this candidate does not call for rewriting an existing descriptor; the normal fixed-v1 contract check must still run in the grouped validation.
