# r26 主 48 月简报父进程来源交集

固定 r26 主 48 月已完整核验。真实浏览器默认完整简报 30 次中位 896.2 毫秒，全部超过 500 毫秒。另用真实 HTTP 完整简报做一次**非计时**插桩：响应 200、882,716 字节；父进程 `Dashboard.brief` 约 770 毫秒、线程 CPU 约 734 毫秒，报表问题和财务位置在该次父进程消费时均已完成，两个等待各不足 0.1 毫秒。插桩与其它负载并行，不能作为纯页面时延。原始记录见 `.tmp/stage9-r26-brief-attempt-scope.json`、`.tmp/stage9-r26-parent-source-overlap.json`；纯浏览器记录见 `.tmp/stage9-release-main-48-browser-pure-r26.json`。

同一父快照内，`_funds(summary_only=True)` 的历史开办／银行直接采用对 47 个闭月分别读取 97 个主体；`_long_term_assets` 的两组资产及项目采用各读取 47 个闭月、每次 48 个主体。三组逐月主体集合互不相交，141 个精确 `close_accounting` 切片都是首次调用；已认证的家庭根、桶和过滤器位置仍由共同 `QueryReads` 复用。`_open_items` 的历史与当前清偿范围各首次取得；随后的财务位置和准备检查分别命中已有历史范围一次。删去这些首次读取会改变来源证明，不能把 141 次函数调用算作 141 次重复正文解码。

父进程准备检查请求 1,987 个事实版本，其中仅 8 个已由默认凭证明细的 typed 缓存提供。资金、工资、资产分支所请求计算对应的事实，与准备检查分别交 3、50、96 个 ID；它们先前做的是来源原文摘要／封签或结果验证，准备检查仍需当前类型模型。149 个交集事实均已走 `Store.facts` 的 C 侧 JSON 构造与严格类型验证，其完整正文合计约 143 KB。让先前 `fact_data_many` 的 Python 解码结果序列化后供 `Store.facts` 使用，须在每次读取事务增加独立数据槽，仍保留事实元数据、证据与类型验证；通常会为未重用的来源额外序列化。收益规模不足以支持这项多层改造，故不实施，也不借原始 JSON 绕过年月解码。资产内部有 47 个计算 ID 从无状态元数据再取得状态字段，默认凭证明细约 101 个 ID 有同型二次查询；目前未量得足以改变整页关键路径的净收益。

下一组只需集中判别两件事：一是在相同已认证闭月桶上，三个不同主体范围的 Python 过滤及逐范围 publication 对照究竟处理多少重复条目；二是资料与查重 worker 是否在父准备检查时造成实际等待。逐次记录精确范围、首次物理桶、成功缓存命中、CPU／VM／字节及完整响应。父、worker 分属不同事务，不能把 worker 的证明写入父 `QueryReads`。已否决的第四概况 worker 原型在 12 月完整响应等价时，中位时间 392.4→399.3 毫秒、总进程 CPU 1109→1156 毫秒；48 月不能凭父串行函数数目推定扩 worker 会更快。报告开放贡献 937 份交集已成功复用，历史清偿范围也已命中；不再重复添加同类缓存。
