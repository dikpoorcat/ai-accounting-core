# 报表上下文与未冻凭证的期间定位（r29 固定候选）

这组补齐先前 A 类排查遗漏：`Reports.closed_period_coverages` 只消费报表档案／接续档案，却先将全部历史 `financial_reports.facts` 约 19,000 个 ID 建成 `first_close`，再把全集送入 SQLite `json_each` 才筛两种少数类型。此前 `_report_profiles` 已按少数类型定位，因此误以为所有档案消费者都已覆盖；context 的独立季度覆盖入口没有经过它。另有完整报表在已认证 `frozen_flows` 排除多数月后，仍先扫描本年全部凭证版本，再以月份集合排除。本组不改变财务来源、业务字段、合同、固定 v1 规则或 DDL。

| 调用范围 | 原因与处理决定 |
| --- | --- |
| `Dashboard.context` → `Reports.closed_period_coverages`，及单季度 `closed_period_coverage` | 先从权威 `subject.kind`／`fact_revision` 定位截至最晚季度末的两种档案 `(id,period)`；全部 close header 和 `financial_reports` readiness 块仍逐月认证，`facts` 列表完整作类型／非空检查，仅输出与档案候选相交的首次采用期。随后在 Python 按原 `(max(fact_period,first_close), fact_period,id)` 排序；实际命中档案正文仍按原摘要核验。晚关账首次采用旧档案、未来事实、并列最新和缺关账问题规则不变 |
| `_report_references` 及 `_report` 完整报表／CLI／MCP／导出 | 完整公开回执仍需要全部来源 ID；保持全量认证与返回。`_report` 的 issues-only 分支已有少数类型候选 `retain_ids`，不复用 context 集合代替完整报表 |
| `_frozen_unused_classification_ids` | 此消费者用精确未消费分类候选与 flow 根证明旧分类覆盖；当前同快照可能复用完整引用列表。它不使用档案候选，不能套用本次 `retain_ids` 或把窄集放进完整引用缓存；本组保留，后续有独立工作量证据再判断 |
| `_report_profiles`、`_report_tax_and_carry_refs` | 两者已按少数类型／期间先定位，再与认证采用 ID 相交；未发现同一晚筛全集 join，保持不动。明确 carry 选择与无 profile 时的税确认正文证明仍走原入口 |
| 未冻凭证候选：`_report` 的有／无 `party_balances` 两分支 | 至多枚举本报表年内实际未被成功 `frozen_flows` 采用的月份，以现有 `voucher_period` 索引逐月定位版本；无 party 余额时，原来查询前年科目行的 `UNION` 分支完整保留。空月返回空，当前／已关／冲正的后续权威 voucher 选择和来源核验原样执行 |
| 关账、完整核验、修复、备份及 fixed v1 | 仍从完整权威 close/source 独立重建；本组只改普通报表／context 的当前选择范围，不让少数档案集合替代完整核验。历史 close 解码由既有 `content_history_context` 固定规则执行，未改 v1 私有格式或 descriptor |

固定 r28 的主 12 月已独立完整核验。只读私有 ABBA 在同一合成库的受控只读快照上比较：四个季度 coverage 响应逐字段相同，整个 `closed_period_coverages` SQL VM 23,200→5,100，两次各自稳定，少数档案元数据 1 行、认证来源相交后 11 行；原始数据见[覆盖对照](stage9-coverage-profile-scope-main12-r28.json.gz)。报表实际执行参数含 11 个已冻月、1 个开放月；未冻凭证候选前后 1,026 个 ID 的**多重集和摘要相同**，VM 149,800→4,100；无 party 余额时的历史科目 `UNION` 在产品代码与定向测试均保留，SQL 计划及 ABBA 见[凭证对照](stage9-report-voucher-months-main12-r28.json.gz)。这些 VM 是读取工作量，不是浏览器时延或 48／120 月通过记录。

产品窄改已落 `reports.py`；26 项季度覆盖与 bounded 报表定向通过，Ruff check 通过。随后收紧两项新增工作量测试：1,000 个无关引用现由一次真实 `save_facts` 写成已注册、合法 typed 正文、可在 `fact_revision`／`subject`／类型表精确核到的非档案税确认事实，另修订其中一个；close readiness 实际引用这 1,000 个版本，原闭期选择会从物理行读到它们，季度输出与独立旧口径仍相同。最小凭证测试也使用生产相同列序的 `voucher_period(period,voucher_id,id)` 与 `voucher_line_account(account,version_id,line_no)`，确认 1,000 个冻结月版本增长后未冻候选不变，并覆盖前年科目例外及空月。收紧后的两项定向再次通过，Ruff check 通过。原季度 5／6 月、晚采用、未来事实、坏已选档案正文和缺目录边界由同组既有测试继续覆盖。

r29 固定源码摘要为 `7fc64f629149f7960e8f11453bcb69469d47decfb374275e4f77ad26dd99a940`。它与 r28 的公司、目录、content-v1 三份合同逐字节相同；主 12／48 月合成库分别已有 r28 固定读取器独立完整核验，r29 诊断**不宣称重新完成完整核验**。使用 r29 固定只读源码、同一默认六入口原生插桩，与 r28 完整响应逐字段比对：两档各仅 8 个 `generated_at`／`checked_at`／`read_version` 差异，业务字段完全相同；每页 SQL 返回行和字节均未变。context VM 在 12 月 25,900→7,800，48 月 97,700→20,400；reports VM 在 12 月 1,147,300→1,001,600，48 月 1,461,400→1,315,700。报表单项下降均为 145,700 VM，两个规模仍需浏览器纯计时验证。原始 [12 月工作量](stage9-default-main12-r29-work.json.gz)／[响应](stage9-default-main12-r29-work.responses.json.gz)／[差异](stage9-default-main12-r28-r29-diff.json.gz) 和 [48 月工作量](stage9-default-main48-r29-work.json.gz)／[响应](stage9-default-main48-r29-work.responses.json.gz)／[差异](stage9-default-main48-r28-r29-diff.json.gz) 已归档；r28 原始对照见[前组记录](grouped-open-fact-range-r28.md)。这是带插桩的单进程工作量对照，简报 worker 未运行，不能写作六页纯浏览器达标。r29 25 文件受影响组两片 JUnit 为 171＋173＝344 项通过、无失败或跳过，源码前后清单一致；[组回执](group-r29-result.json.gz)及[两片 JUnit](group-r29-shard-1-junit.xml.gz)、[第二片](group-r29-shard-2-junit.xml.gz)已归档。主 12 月[独立完整核验](stage9-release-main-12-verified-r29.json.gz)及[切公司样本核验](stage9-release-main-12-switch-verified-r29.json.gz)均为 complete／verified、无 limitations；[主 48 月独立完整核验](stage9-release-main-48-verified-r29.json.gz)也为 complete／verified、无 limitations（121,593 事实、50,519 计算、49,245 凭证、47 次关账、337 原件）；正式纯浏览器性能验收仍待结果。
