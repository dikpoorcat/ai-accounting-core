# 报表来源计数的范围排查

触发条件：季度页的正式计划已包含精确事实 ID，页面只消费分类、所得税确认两项计数，却按全部业务种类建立临时分组树。来源 ID 随历史增长时，分组工作随之增长；ID 本身仍是必须保留的完整计划内容。

| 位置／调用方 | 实际消费 | 决定 |
| --- | --- | --- |
| `Reports.browser_report_details` → 季度页、默认／按需准备、开放／冻结报表 | 只消费两个确定种类的计数 | 使用两个条件计数，仍逐个精确 ID 经 `fact_revision → subject.kind` 取权威种类，不改用 typed 表推断 |
| `dashboard_reads` 的凭证摘要与分类 | 消费全部种类及冲正分组 | 保留分组 |
| `duplicates` 的业务及原件竞争查询 | 各分组用于判断不同重复关系 | 保留领域分组 |
| `engine` 的变更传播原因计数 | 按主体归因，种类参与结果 | 保留 |
| CLI／MCP 正式报表、导出、关账准备和固定 v1 | 不经过页面这两个计数；仍构造各自完整计划与依据 | 保留 |

只读实验使用固定 r29 和独立完整核验过的 12／48 月主样本，原 SQL 与候选交替执行，来源连接与种类权威相同。48 月 19,746 个 ID，两项结果均为分类 19,729、所得税确认 16；VM 约 375.2k → 256.7k，不再使用临时分组树。局部 SQL 交替中位数约 43.7 → 40.1 毫秒，仅作定位，不是整页验收。12 月同样比较，完整原始数据单独保存。

12 月 4,938 个 ID，VM 约 93.9k → 64.2k，局部交替中位数约 7.79 → 6.94 毫秒。另试精确 ID 驱动、强制 `subject_kind` 覆盖索引，48 月 VM 反增至 552.9k，中位数约 48.8 毫秒，因此不采用。它也不能与此前已否定的“按种类取全候选后用 Python 求交集”混为一个试验；typed-only 方案因无法保持原权威语义同样未采用。

定向测试首轮 2 通过、1 失败：新增长测试误在非季末登记所得税确认，被真实入口正确拒绝。改为仅季末登记，重跑该新增场景 1 项通过；新增 12 个月、48 个档案修订及 4 个季度确认后，原计划计数和实际 VM 保持不变。旧正常／空季度断言保留，Ruff 通过；没有为修夹具重跑已通过的大组。

[原始诊断及测试回执](grouped-r30-root-diagnostics.json)已归档。未减少默认内容、来源集合或来源核验。当前修改尚未成组验证，500 毫秒仍未通过。
