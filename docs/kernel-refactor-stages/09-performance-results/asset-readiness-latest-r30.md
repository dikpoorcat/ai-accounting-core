# 资产准备检查最新结果私有原型（未采用）

本原型只读固定 r29 合成样本，不改生产读取器、关账根、合同或测试库。目标是区分 `asset_consumption` 全历史结果水合与业务实际消费的最新结果。原始记录：[12 月](asset-readiness-latest-main12-r30c.json)、[48 月](asset-readiness-latest-main48-r30c.json)。其中的 CPU 和墙钟数值仅为诊断，不是页面验收。

| 样本 | 历史当前结果 | 每资产最新结果 | 原选择返回字节 / VM | 仅最新值的私有选择返回字节 / VM |
| --- | ---: | ---: | ---: | ---: |
| 12 月 | 66 | 11 | 56,700 / 3,800 | 31,739 / 3,400 |
| 48 月 | 1,128 | 47 | 970,056 / 63,300 | 422,438 / 57,300 |

私有选择保留原 `Context.trace` 的 ID 和次序；正常样本的 `required_work` 问题与之相同。这仅证明正常输入的范围和输出相同，**没有**证明旧结果原文损坏、缺成员、修订或身份纠错的等价拒绝范围。原型另测了一个更强的 owner/member 元数据证明分支：12 月另返 102,827 字节，48 月另返 1,701,641 字节；复制的合成 owner 删除一名成员会被该分支拒绝。这个附加分支不是现有路径必然要付出的成本，不能拿它否定其他等价方案。

直接用 SQLite `json_extract` 取结果标量还有独立语义边界：测试原文 `{"values":{"asset_id":"a","asset_id":"b"}}` 时，Python `json.loads` 取得 `b`，SQLite `json_extract(...,'$.values.asset_id')` 取得 `a`。仅把当前 Python 解析替换为 SQL 标量，无法凭正常样本 parity 证明同一结果。此处只是私有原型的失败条件，不等于既有产品读路径已经发生缺陷。归档重复键原文见 [样例](asset-readiness-duplicate-key-r30.json)。

决定：不落地该资产原型；继续按实际调用链审查现有 SQL JSON 读取是否先有足以约束原文编码的证明。不得把保留旧 trace ID 误写成已校验旧正文，也不得把附加 owner 证明的成本算作必需基线。
