全页捕获 SQL 合计约 **970.3k → 1,195.8k VM**、**26,131 → 26,961 行**、**9.73 → 10.95 MB**。计数查询解释大部分 VM 增长，但并行负载下的 execute/fetch 墙钟不能作严格耗时分摊。`read_open_contributions` 的 1,004 份当月来源在 12／48 月相同；第一次 `_party_delta` 请求 938 份、零缓存命中，归并后是 51 行。第二次 `_report` 请求 1,003 份，其中 937 份已在同一事务成功核验，实际只补另外 66 份，约 11.2k／11.6k VM。两处分开处理的往来行与利润／现金行精确键交集为零；这不是对 937 份再查一次来源正文或封签的隐藏重复。完整报告与来源证明仍须保留。

浏览器只消费 `classification_count` 和 `income_tax_confirmation_count`；公开 `ReportPlan.report_fact_ids`、计划摘要、CLI／MCP 与导出仍需全量 ID。关账时五种 `Read(kind)` 可见类型，但 `financial_reports.facts` 冻结为经根认证的**无类型 ID 列表**。`_closed_report_fact_sources`、`_report_references` 继续只传 ID；报表只对最新 profile、本报表需要的税／carry 与命中凭证分类核验原文，未持有全部历史 19,746 个 ID 的已认证类型。当前计数的 `fact_revision → subject` 是权威头身份查询，却不是所有旧事实的原文／封签核验。把逐 ID 查询搬到计划构造处只移动工作；按“总数减少数类型”、typed 子表或可修复目录推分类数会漏旧年／未采用来源及合法错类、缺行、显式 carry 边界。现有冻结格式和无新投影约束下**没有已证明能缩减该精确范围的上游取数方案**，故不做新 AB 或生产变更。不能把“尚无安全方案”写成算法已达下界。

完整逐 SQL、首次真实绑定参数与 EXPLAIN、分段及两消费者计数已无损压缩归档：主 12／48 月原始及详细 JSON、归并 JSON 见[归档清单](stage9-r30-report-sql-family-archives.json)。清单分别记录原字节和 gzip 字节的 SHA-256，解压后逐字节一致；原始 `.tmp` 文件仍留存。已采用的两项条件计数及先前负试验见[来源计数范围](report-count-scope-r30.md)。新 `.tmp/stage9-r30-report-process-io.py` 仅已备好，**尚未运行**；当前没有进程 I/O、物理盘读取或页命中证据，不能把同 VM 查询的取行增时归因为缓存或磁盘。
