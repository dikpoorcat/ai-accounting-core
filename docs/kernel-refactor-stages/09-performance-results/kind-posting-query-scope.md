# 按类型读取当月凭证的扫描范围

## 问题与证据

**候选未采用，原增长问题尚未解决。** 起点为固定 r37。本组核对公共凭证选择器在明确入账月时仍先枚举历月同型计算的问题。三个私有写法没有同时改善工资与资产；不把局部 VM 降低当成整页收益。生产及测试完整清单已核对，仍与 r37 相同，无新增回归或页面验收结论。

相同公司规模为 50 人、每月 1,000 笔，12／48 月均只返回本月 50 份工资。真实参数下的执行计划均为：先从 `calculation_kind_period` 按 `kind` 搜索，再按计算编号找凭证，最后才判断凭证月份。最初候选分别为 600／2,400 个，目标入账月均仅 50 个。

| 原样查询 | 12 月 VM | 48 月 VM | 两档返回量 |
| --- | --- | --- | --- |
| 工资依据编号 | 11,467 | 33,066 | 50 行，3,300 B |
| 工资度量 | 17,624 | 39,223 | 50 行，99,660 B |

同时捕获的空类型分支仅 45／49／124 VM。修复不能使这些空分支反而遍历整月。原始探针只在每库调用一次真实员工页取得参数，随后运行相关原样 SQL、候选计数及 EXPLAIN；不把它作为独占计时。

## 修改范围与保留路径

| 位置或调用方 | 处理决定 |
| --- | --- |
| `selected_voucher_sql`：有 `kinds`、精确 `posting_period`，且未被业务编号／凭证编号范围接管 | 原有类型路径保留。统一强制按入账月驱动的三个私有写法未采用，不增加按样本调节的阈值、类型特判或新索引。 |
| `Journal` → 简报工资汇总、员工工资及劳务读取 | 同时比较来源编号与度量。首个候选在 48 月工资路径改善，但 12 月回退；不存在类型仍是小成本，不是主要问题。 |
| 资金页按账户取得的精确凭证集合、按业务编号的详情 | 精确集合／业务编号优先级不变，不改成月份全范围。 |
| `dashboard._assets` → 资产页当月取得度量 | 也经 `month_journal.select(kinds=...)` 进入本分支。原排查只关注资产身份与历史成员，遗漏了取得度量。补查真实资产页后确认：当前月只有一笔取得，强制按月扫描导致显著回退。简报另有资产汇总路径，不把资产页对照冒称简报也读取同一取得明细。 |
| 上下文、资产身份与历史成员、报表完整计划计数 | 这些具体路径不进入本组类型与入账月分支，保留原路径；不能外推到整个资产页或全部性能问题。 |
| 只有类型、没有精确月份；只有下限或跨度范围 | 保留原类型索引路径。宽期间与类型选择谁更窄取决于实际数据，本组没有足够证据统一改写。 |
| CLI、MCP、业务详情和公开报表 | 通过共同选择器时沿用其参数边界；入口、响应、完整来源身份与拒绝行为不改。 |
| 关账、完整核验、修复和备份 | 正式采用、凭证拥有者、无影响复核及内容核验保留。普通候选定位不能替代完整核验。 |
| 固定 `report_projection_v1` 与 `position_v1` | 使用独立历史选择规则；当前月份定位改法不回写固定版本实现。 |

不能用计算的业务所属月代替凭证入账月。1 月业务在 3 月更正时，3 月选择仍须取得更正与关联冲正；旧冻结凭证及其原采用保持不变。

## 私有对照与采用决定

全部试验使用固定 r37 和 12／48 月合成库的真实 SQL 与参数，在只读事务中执行。每档先捕获员工页的 5 条查询，后补简报 6 条、资产 2 条。首个候选按类型存在性、实际入账月、类型过滤定位凭证；类型存在性只保证全库没有这种类型时能早退，不能保证稀疏类型有利。

| 真实调用，原样 → 首个候选 | 12 月 VM | 48 月 VM |
| --- | --- | --- |
| 工资依据，50 行 | 11,467 → 17,894 | 33,066 → 17,894 |
| 工资度量，50 行 | 17,624 → 24,051 | 39,223 → 24,051 |
| 资产依据，1 行 | 344 → 13,578 | 776 → 13,578 |
| 资产度量，1 行 | 462 → 13,696 | 894 → 13,696 |

员工与简报工资结果一致；全部首个候选对照的逐列多重集相同。依据编号查询没有排序承诺，消费者会转为集合；度量查询仍有原显式排序。空劳务／项目类型返回零行，VM 只有少量变化。

另外两种写法取消重复凭证定位，分别直接按月份驱动、把类型过滤放在凭证编号关联之前。结果仍一致，但工资依据 VM 分别为 40,135／38,225，工资度量为 47,238／44,373，两档都比原样差。不是连接次数少就更好，SQLite 实际执行顺序与范围才是判断依据。

首个候选曾短暂写入工作区，随后撤回；未创建新测试文件。原始脚本、SQL、实参、EXPLAIN、逐列数据及审查记录共 15 份已归档，[清单同时记录源码未变的核对结果](kind-posting-r37-manifest.json)。既然没有保留代码且已经出现明确工作量反例，本组不再扩写法、不进行纯计时、不重复运行整组回归。

本组结论仅是**通用强制按月驱动不可采用**，不是原增长已修复或已排除。120 月、跨月更正、冻结采用及其他组合在这些候选下未做动态验证；没有进入生产，无需为被拒绝候选补齐整套验证。若以后提出不同设计，仍须同时考虑短历史、密集工资、稀疏资产及确切来源证明，不能重跑本次三个失败写法。
