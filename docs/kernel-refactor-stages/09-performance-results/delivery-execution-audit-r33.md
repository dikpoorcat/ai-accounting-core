# 第 9 阶段交付执行入口审查（r33，只读）

本页核对可执行入口与现有结果，不记录一次新的验收。仓库仍是 `draft / 0`；r33 是隔离的 `released / 1` 候选，19 文件受影响组 192 项通过，不是正式三合同、最终运行包或整页性能通过。[主阶段状态](../09-performance-and-release.md)、[正式切换顺序](formal-v1-switch-audit-r32.md)与[待验清单](release-gaps-r31.md)是交付状态依据。以下操作只可在新建合成根、**同一最终固定源码及其生成产物**上执行，开发候选的成功不能拼成最终验收。

| 交付动作 | 现有可执行入口与已证范围 | 最终正式版仍需取得的证据 |
| --- | --- | --- |
| 新建、登录与发布 | `scripts/package_local_kernel.py` 不带 `--skip-validation` 时归档、重定位、逐文件 SHA 核对，再用包内 `runtime/python.exe -I` 执行 `tools/verify_local_package.py`。该自检用包内 CLI 建合成公司／负责人、登记对象和事实、预览、正式发布、同请求幂等及身份纠错；另核包内合同、模板、运行依赖和默认路径。两次旧开发包自检已有通过记录。 | 冻结 catalog、company、content 正式 v1 后用**全新输出目录**构包，保存 ZIP、manifest 和自检回执；验证新建、重开、draft／旧体系拒绝及包内同版升级门禁。旧包是 `draft / 0`，不能复用。 |
| 工资确认、页面与账面核对 | 包自检 `verify_reserve_business` 对工资政策／确认、银行与备用金、当前和冻结来源、五个看板路由、七个鉴权查询及整数分传输作真实 CLI／HTTP 核对；关闭后与恢复后内容比较。页面 HTTP 合同检查不等于浏览器完整渲染或 30 次性能样本。 | 在最终包复跑合成业务自检；另用最终前端和隔离常驻服务完成五页默认内容、按需详情、切公司及整页独占计时。对照已核验业务响应，不把 HTTP 200 计作页面验收。 |
| 密码批准、单月关账、更正 | `verify_local_package.py` 的 `approve_close` 从真实关账核对响应生成 native 安全请求、以合成负责人密码执行并检查状态；单月 `preview_close`／`close`、自动备份、冻结报告及闭期冲正后原冻结月份不变均有脚本断言。包自检还调用隔离的 Tk 表单／私有传输。 | 最终包中运行相同链路，保存批准、关账、当前与冻结核对及恢复后校验回执。不得把批量批准或跨月关账引回接口。 |
| 实际办理、任务恢复与备份恢复 | 包自检的 `verify_stage8_workflow` 通过公开 CLI 完成外部义务、实际办理和独立复核；`request_result` 验证幂等及跨公司不可见。`verify_stage8_job_recovery` 制造合成备份失败、检查持久任务尝试／错误，再显式 `retry_job` 至成功。多处 `backup` → `jobs` 成功 → `restore_company` → 完整核验及业务／冻结结果相等。 | 最终包复跑完整任务链，保存失败、中断、重试、ZIP 核验和恢复报告；失败任务或 pending 不算交付备份。正式 v1 的历史保留、同版升级与启动拒绝仍需最终包实证。 |
| GPT-6 Sol 实际 MCP 中断接续 | `tests/kernel/stage9_package_agent_harness.py` 用**包内**解释器开 stdio MCP、合成服务和 native 批准 relay，逐请求保存真实/交付响应；`lose_next_write_response` 模拟已提交但客户端丢响应。既有 `.tmp/stage9-package-agent-draft-2` 有 38 个 MCP 请求、1 个 native 请求、`tools.jsonl`、请求／响应和恢复核对；`ready.json` 明示目录及公司均 `draft / 0`。包自检本身的 stdio 握手与查询也是另一个自动检查，不能冒充代理自主接续。 | 用**最终正式包**重新提供隔离合成公司，由实际 GPT-6 Sol 按 schema→先查后问→工资确认／发布→关账密码批准→丢响应查回执→更正→办理→任务恢复→备份恢复完成真实 MCP 对话，保留完整工具回执与包 SHA。旧 relay 的公司由宿主先 seed，不能声称代理经 MCP 执行了公司新建；公司新建由包内 CLI 自检覆盖。如要求代理本人新建，需在最终回放另设该步骤。 |
| 大原件与边界 | `scripts/benchmark_stage9_evidence.py` 可用 `--source` 固定清单、全新 `--root`／`--output`，分别 `--size-mib 240`、`1536`、`--profile mixed`；每件最多 20 MiB。脚本实际执行原件登记、完整核验、便携备份、恢复及恢复后核验，比较原字节，并在各阶段并行读取完整准备简报、记录父进程及三 worker RSS。`--foreground browser` 配合 `--node`／`--playwright-module` 才测浏览器渲染；默认 `http` 不包含渲染。旧 240 MiB 候选与约 1.5 GiB 开发库诊断已有记录，后者仍是 `draft / 0`，均非最终验收。 | 最终源码在**两个不同新根**独占依次运行两档，分别保存 source manifest、原件/包 SHA、核验／恢复、前台样本、内存与失败记录。1536 MiB 运行前脚本检查至少约 `4×1536 MiB + 512 MiB` 临时空间；与浏览器 30 次纯计时分开。 |
| 20 MiB／10 万行／5,000 项 | `scripts/benchmark_stage9_boundaries.py --full` 在新合成根使用真实登记入口验证 20 MiB 正好接受、再多 1 字节拒绝，银行 100,000 行接受／100,001 行拒绝，5,000 事实一次提交／5,001 拒绝且物理行、请求、审计无半写。r10 `boundaries-release-r10.json` 属隔离候选。脚本明确要求其**自身位于所选固定源码**，仅用当前工作区脚本加 `--source` 指向别处会被拒绝。 | 从同一最终固定源码副本中的脚本执行 `--full --source <该源码> --workspace <本仓库> --root <全新.tmp根>`，用仓库虚拟环境，保存 `report.json` 和源码清单；与两档原件可顺次独占运行，无须共用业务库。校准模式不能当边界验收。 |

执行顺序：源码和受影响回归稳定、规模及纯浏览器条件满足后，导出 v1 候选并一次冻结三份正式合同，`--check` 及正式工厂核对；随后正式源码重验非空合成历史和隔离升级／恢复，构建未跳过自检的独立包，再安排实际 GPT-6 Sol MCP 回放及两档原件／边界的最终固定源记录。若合同、源码、前端产物或运行条件随后变化，受影响证据须重测。定期备份、跨公司配对和真实换库仍按原计划延后，不纳入本次合成包演练。
