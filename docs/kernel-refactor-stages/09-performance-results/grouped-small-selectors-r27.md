# 少数类型来源与重复解码小表：r27 受影响组

本组先在 r26 固定源码、已完整核验的主 12／48 月合成库上定位，随后封存 r27 候选。r27 与 r26 released 候选的两库结构指纹及 content-v1 相同；本次未改 DDL。私有对照不是整页浏览器验收。真实季度网页使用按需准备，员工默认及单人详情分别测量。

| 根因 | 触发、位置和证据 | 集中处理与边界 |
| --- | --- | --- |
| 大采用集合定位少数类型 | `Reports._report_profiles` 及税确认／接续定位把上万条认证采用 ID 传入查询逐个匹配，只返回 1／4 行。主 48 月默认报表两条查询各约 237k VM | 从权威类型和期间先取候选，再与原有认证 ID 集合求交；最新期并列、显式接续、命中正文和摘要、公开完整采用 ID 保留。共用 `_report` 的页面、CLI/MCP、导出及准备检查一起接通。分类属于高基数且有冲突语义，没有证据就不套用此方法；固定 v1、完整核验和维修规则不改 |
| 内联小表被循环解码 | `adopted_head_metadata` 的 `limits` CTE 保存各闭月真实发布上界。SQLite 默认内联后，每个工资候选重新扫描 JSON 小表；kind 过滤本来在窗口前，不能误称扫描所有业务类型 | 只物化这张请求内小表，仍使用原期间、发布上界、末次采用和行数语义。主 48 月工资 2,400 个头逐行一致，约 1.13M→765.4k VM；员工默认及单人详情完整响应一致。其他同形 CTE 与调用方另按执行计划审查，不批量加物化 |
| 类型合法，但缺少原始摘要核验 | 新增损坏用例把报表档案／税确认／接续事实改成另一合法值；原代码只做类型解码，可能接受修改。此前把“完成类型解码”误认为“来源已核验”，遗漏了实际消费点 | 复用 `verify_sources`，在选中依据被消费前核对原文、封签和来源；成功证明只在同一只读事务内复用。覆盖完整报表／导出、准备、上下文季度导航及浏览器未选中的接续候选。无档案时的早退原会漏掉已采用税确认：合法字段改值反例修前未拒绝，修后对该分支实际 required report facts 核摘要并保留原空问题结果。固定 v1、完整核验、维修与备份仍独立从权威来源检查 |

**含最终来源证明成本**的同合同私有整页对照：主 12 月默认 deferred 季报 VM 1,331,500→1,222,100、返回行 25,758→26,283、返回值字节 10,029,432→10,043,655；主 48 月 VM 2,280,200→1,815,400、行 26,588→27,113、字节 11,253,419→11,267,642。两者 typed fact 解码均 417→417；多出的 525 行／14,223 字节是精确来源正文证明，净少 109,400／464,800 VM。因当前开发工作树 bundle 与 r26 固定样本指纹不同，对照在 `.tmp` 复制 r26 固定源码、只叠加本组 `reports.py` 和消费者 helper 改名；未改固定源或数据库。排除自然变化的 `checked_at` 及源码派生的 `read_context.read_version` 后，两库完整业务响应逐字段相同。原始小工作量数据见 [报表整页工作量](grouped-report-small-selector-proof-r27.json.gz)，早期未含证明的结果和失败 SQL 形状留在 `.tmp/stage9-report-scope-ab-r26-results.md`；CPU／墙钟均不作为 500ms 验收。

反例覆盖缺 ID、错类型、未来、未采用的更新档案、最新并列、无档案、命中 profile／tax 正文合法改值、context 季度 coverage 的建账月改值、显式接续与未选接续选项的正文损坏。报表稀少类型和来源保护定向 5 项、显式接续／导出 1 项通过，相关 Ruff 通过。更正前的错误判断是把 `reads.fact_versions` 的类型化装载当作不可变事实正文摘要证明；它并不核摘要，已在所有实际消费这三类报表事实的路径补精确证明，非命中来源不因候选定位而扩大核验。

员工 48 月角色来源第一次核对 2,450 个事实，之前同快照已经装载的只有 50 个；第二次 50 个中与第一批交集 29。主要成本是必要的身份来源认证，保留。工资头与劳务头两次选择的业务范围不同；劳务查询为空不能作为取消该能力的依据。

资产页另外两次 owner 选择有 48 项交集，底层块却已经做到每个 `(期间,目录,块)` 只装一次。私有“窄选择＋剩余主体”四次完整响应相同，VM 约降 10%，但物理块和解码不减；生产实现需要多层显式传递采用证明，暂不落地。complement 自身的损坏对照尚未做；不能把 prefetch 的损坏结果挪用过来。跨请求相同来源不复用。

## 验证安排与状态

生产修改、工作量增长测试与异常分支先收敛；再固定一份源码，统一运行受影响的报表、员工、资产（若有改动）、读取、历史和页面回归。生成及接口形状不变，不因没有新前端修改重复整套前端测试。完整核验与实际整页计时按新固定候选执行，计时前停止建库、回归和插桩。

当前：r27 固定的 33 文件受影响组已结束，404 项通过、1 项失败，源码前后未变。失败是损坏测试污染正常场景；已拆开共享正常场景与反例，保留全部业务断言，两个受影响文件 18 项通过、Ruff 通过；[修复记录](r27-scenario-repair.json)确认生产源码与固定 r27 不变，未重复运行其余已通过项；原记录见 [成组结果](read-group-r27.json) 和 [失败日志](r27-group-shard-2.log)。主 12 月 [完整核验](main-12-release-r27-verified.json) 通过；r27 主 48 月尚未再做完整核验。120 月工作量、r27 浏览器整页时延、固定 v1 普通页面的动态读取仍未验证；不能把 r26 私有同合同工作量写成 r27 验收。
