固定源码 `.tmp/stage9-build-source-r24-release`，已完整核验的主 48 月合成库，2019-12。通过真实 HTTP 请求简报 complete/default 100、资金与资产 deferred/default 100；只读插桩原始数据：`stage9-r24-close-accounting-scope-r2.json`。后台仍有构造负载，wall 不作纯计时。插桩自身会增加开销。三页均 HTTP 200、正文大小与先前真实 HTTP 诊断一致；资金和资产原始正文 SHA 也相同，简报的时间字段令原始 SHA 随请求变化。

每页每月有且仅有一次已认证 `accounting` family 的 SQL 装载，共 47 次、1.87 MB。每个调用仍各做当期采用 publication 与当前凭证两项精确关系查询：简报和资产各 141 次、资金 47 次。这些为所给范围的完整来源对照；不能因 family 或桶缓存命中而省略。资金仅有一个全月的待收付范围；简报另外有资料和资产两组，各范围不重叠。资产前两个 48 个对象范围不重叠，第三个 96 对象范围包含第二个 48 对象并增加另外 48 个；因此有 2,256 次同期间对象 filter 重探、106 个桶重复请求和 508 条缓存桶条目重访，但第三组仍有 324 个新桶首次核验，不能用此前结果冒充其完整新范围。

`may_contain` 在每个调用重新 SHA-256 对象 ID 并算 8 个模位置；47 月的已认证 filter 位长全为 12072。每页只有 193、97、144 个不同对象，因此纯位置计算远多于业务上不同输入组合。固定 filter 和上述真实探针顺序的 ABBA 微计时原始 `stage9-r24-filter-probe-micro-r3.json`，以原逻辑与按 `(subject,bit_count)` 同请求预计算位置后逐位核验对比：简报 35–36→约 10 ms，资金 18→约 5 ms，资产 35–37→约 9 ms；各次完整真假序列 SHA 相同。r1/r2 探针误把重复计算放在字典推导中，已保留但不用于收益判断。

固定 r24 的私有运行时真实 HTTP ABBA `stage9-r24-filter-probe-http-ab.json` 仅在每个请求线程内复用纯位置，三页四次响应规范化 SHA 分别全同（只排 `generated_at`）。资金 A 365/337、B 324/347 ms；资产 A 465/500、B 427/442 ms；简报 A 818/1041、B 871/890 ms。后台负载、进程调度和工作进程等待波动较大，不能把这些数字作纯浏览器过线声明。值得考虑的最小生产改法是 QueryReads 同快照保存纯 `(subject,bit_count)` 位置，再传给当前 `read_accounting`；每个闭月仍用其已认证 filter 逐位判断，且始终运行 publication/voucher 的完整精确源关系对照。直接读取、关账、维修、备份与固定 v1 原入口保持独立核验；不跨请求缓存。尚未改生产。
