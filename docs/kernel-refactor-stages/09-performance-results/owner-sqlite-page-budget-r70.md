# 必要数据库页重复驱逐

## 问题和排查范围

r69 已降低银行及工资定位的扫描量，但简报、员工和报表的原生读取仍超过 500 毫秒。定位 SQL 的 VM 下降与延迟改善不一致，不能只按执行步数判断。常驻只读池原有每连接 64 MiB 的 SQLite 页缓存；必要来源分散在大库索引和记录页中。

对固定 r69 源码和同一已核验主 48 月合成根，分别用 64、128、256、256、128、64 MiB 做正反对照。每一配置都新建池，各读取预热 3 次、计时 5 次；六个读取全部执行，计时没有与回归、建库或插桩并行。业务结果全字段相同，只排除合同中明确的三个生成时间：context.generated_at、brief.data.generated_at、reports.checked_at。

这是物理数据库页缓存，不存上一事务的业务判断或响应。所有请求继续读取新快照、检查版本和来源。未修改数据、SQL、冻结合同、计算或必要核验，也不改变垃圾回收规则。

| 同类位置／调用方 | 决定 |
| --- | --- |
| 常驻服务五页与上下文的共享 `ResidentReadPool` | 统一提高物理页预算，并核对每次借出连接的实际预算；默认仍最多四个连接。 |
| CLI／MCP 普通业务执行、写事务、完整核验、关账、修复、备份恢复 | 不增加业务结果缓存，也不改这些路径的连接与核验职责。 |
| 固定版本历史 | 仍按其版本解码和核验；SQLite 页缓存不替代内容证明。最终运行包未验证。 |
| 员工历史候选增长 | 独立修正实际扫描范围，不能用增加缓存掩盖历史增长。 |

## 实施和验证状态

`resident_reads.py` 设置预算、限制连接数量为整数 1–4，并对借出连接读回 `PRAGMA cache_size`。预算被改变的连接关闭，不继续使用。已有文件权限、结构、身份、只读配置、事务结束和跨公司检查不放宽。

新增回归验证超界或非整数连接预算拒绝、预算变化后连接失效、替换连接和实际身份读取；现有提交可见性、跨线程、跨公司、并发上限、内容损坏和文件替换测试一起运行：**11 passed，13.30 秒**，Ruff 通过。回执为 `.tmp/stage9-resident-page-budget-r70.{log,xml}`，静态检查另有独立日志。
