# 银行准备诊断并入材料 worker：未采用

常驻服务的默认完整简报由父进程和资料、查重、报表三个 worker 分别持有只读事务。父进程在 `Periods.collect_current_readiness` 末尾对本月全部当前计算执行严格存储 JSON／摘要门禁，然后以两条 JSON1 查询形成银行未对账问题；材料 worker 此前已在自己的受控快照核验其中多数结果。现有 r33 双向成功证明仅在**同一连接、同一受控只读事务**复用，不能跨进程传给父进程。

私有变体只把银行的完整结果 ID 门禁和两条原 SQL 接在材料 worker 的 `read_completeness_summary` 后面，在该 worker 的同一 `QueryReads.snapshot` 内运行；父进程在原位置消费银行问题，问题仍列入 `snapshot_issues`。材料结果和银行问题合包返回，不传递证明对象。三个 worker、文件身份和前后 `data_version` 守卫、整组失败回退、串行关账与准备、固定 v1 均未改动。原始资料、固定 r33 源码和合成库未被修改；[探针、五份原始 JSON 的无损 gzip 与 SHA-256](bank-material-worker-negative-r33-archive.json)保存了各次对照。

12 月材料成功证明 999 个 ID、银行本月范围 1,016 个，交集 999；48 月分别为 999、1,052、999。变体只需对银行新增的 17／53 个结果在 worker 内再次严格解析，父进程的其余内容和来源核验继续执行。所有 complete 对照的整份响应仅排除动态 `data.generated_at` 后相同，正式 worker guard 均接受。开放月 `deferred`、前一闭月 `complete` 两个控制组也响应相同，且未启并行 worker。未建立无银行账户的独立开放月样本；该边界**未验证**。

无插桩样本各臂只有两次正式请求，12 月 B 的中位改善约 24.5 ms，48 月仅约 6.5 ms；不是浏览器 30 次验收，也不能由并行背景下的插桩 CPU 推导稳定端到端收益。插桩对照中，合包使父进程首次等待材料的墙钟增加，虽然父进程后段不再重复解析；主 48 月报表 worker 仍为较长路径。净减少的是 345 次严格解析、约 270 KB SQL 返回值及 3,200 VM，不是整个本月结果的搬运量。

**决定：未采用。** 简单合包还有错误顺序差异：原银行内容错误在材料、查重和报表问题核对之后、银行原位置才抛；合包的单个 `try` 会使父进程取材料时提前抛出。若以后有足够大且稳定的收益，须在同一 worker 回执中分别保存材料成功结果与银行错误，并在父进程原银行位置消费／抛错，`finish` 仍要确认两者已消费；本轮不为微弱收益增加第二管道或生产分支。r33 已实施的双向复用继续仅适用于串行、同事务路径；默认常驻简报跨 worker 重复仍存在，但本次证据不足以扩大它的信任边界。

源与验证口径：本私有读取候选使用固定 r33，读取由固定 r32 已独立完整核验的主 12／48 月合成库。两版 schema、catalog/company 和 content-v1 合同及固定来源清单一致；**本记录不是 r33 对两库的独立完整核验**。A/B 工具记录了完整响应哈希、每进程 SQL 行／字节／VM 与解析次数；native 仅用 `perf_counter`、`process_time`，没有 SQL、解码、`tracemalloc` 插桩。native 开始／结束 UTC 及每臂时间见归档清单和原始文件。
