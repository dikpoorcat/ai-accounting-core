# 资金汇总与明细同源读取

r30 固定源码的只读诊断见 `.tmp/stage9-funds-shared-summary-page-scope-r30.md` 及其中的原始 JSON。资金 `account_summary`、`bank_summary`、`investment_summary` 各自计算完整汇总；当同一资金请求也返回 `movements`、`statements`、`investment_events` 明细时，原实现又让 `_sql_page` 重跑对应的同一事件来源。主12/48样本的当月 movement 均是504行；汇总与分页分别约238k/229k SQLite VM。主样本500条银行流水的汇总与分页各约87k VM。投资历史成本是另一范围，不属于可合并的当前事件来源。

本组限定在 `dashboard_funds.py`：请求相应明细时，同一只读快照内用 `source_rows AS MATERIALIZED` 供完整汇总、全局/筛选计数、游标存在性与 `limit+1` 明细页消费；账户筛选只限明细，全局汇总不缩小。汇总只在首返回行附带一次，不把每条事件搬进 Python，也不跨请求保留。原独立 `_sql_page` 已退出生产，`_finish_sql_page` 统一处理计数和游标。简报 `summary_only`、未请求该明细的资金调用及历史投资成本继续原职责。所有金额、方向、日期、多个 effect、冲正、内部转款、银行对账来源和实际投资办理仍来自原事件 SQL，不以余额投影替代。可见银行匹配与明细事实仍执行原有定向证明。

实施前的私有 movement AB 在默认页与非空账户筛选页逐行一致，组合 VM 从467/469k降至253/255k。以固定 r30 来源做的局部旧／新 SQL 对照，在非空合成银行40行、投资12笔中保持完整汇总、来源页行与分页元数据相同：银行13.5k→9.5k VM，银行空末页12.9k→8.6k VM，投资含历史成本26.6k→17.1k VM。**这些是局部 SQL 诊断，不包含后来 G 组增加的原文解释证明，也不是 r31 整组通过。**旧分页实现只保留于诊断，生产不维持另一份。另以80条无关历史资金事实增加来源规模，本月24条完整明细结果保持一致，同源 SQL VM 增幅受限。私有脚本 `.tmp/stage9-funds-r31-fixed-compare.py` 在新建的非空银行与投资合成库上，将完整 `funds` 返回同固定 r30 模块逐字段比较，默认、单集合、筛选、`summary_only` 两项均通过；不读取或改动固定 r30 样本。G 组之前，新增和旧有界读取两文件12项、固定源码对照2项、原资金对齐文件18项、银行损坏来源3项通过；这些定向不代替后来的固定组与五页时延验收。
