The HTTP client timing includes local transport and receiving the complete body; Python JSON parse after receipt was 0.2/4.7/1.2/0.7/1.2/0.3 ms in route order. Browser Ajv/DOM work is **not** measured. The server's own `http_reply_write` interval is in raw `dispatch[].http_events`, but browser `responseEnd` and final render still require a separate browser trace. Authentication was 8–10 ms and catalog bind 9–12 ms on the five company routes. Most server time is inside business read and verification. Parent thread-time on Windows has coarse 15.6 ms resolution and cProfile wall includes wait; neither is a pure latency proof.

The current browser harness stamps `__stage9RefreshStart` on click and `__stage9RenderedAt` after required network responses and two ready frames, but exports only their difference for pure timing. A private diagnostic harness can export each required `PerformanceResourceTiming.startTime/responseStart/responseEnd` relative to that same click, the last required `responseEnd`, the first observed `aria-busy=false`, and final two-frame render timestamp. That separates click→send, network/server, and responseEnd→render without weakening the existing checks. If responseEnd→render is material, add marks around the existing frontend response parse/validation and state commit in a **private diagnostic copy**, keeping the product default content and assertions intact. Correlate server dispatch timestamps by request path/company/period and a diagnostic request id; do not subtract separate-run HTTP and browser samples as though they were one trace.

Inclusive cProfile call trees (profile overhead; nested numbers must not be added): brief parent `_funds` about 279 ms and `period_readiness` 258 ms, with `QueryReads.close_accounting` 141 calls about 246 ms; the report worker wait appeared as about 206 ms in this sample. Assets had six selected-accounting reads about 345 ms, asset-card sources 234 ms, five owner-event selects 227 ms, and 141 `close_accounting` calls 222 ms. Quarterly reports had `party_balance_rows` twice about 480 ms, `_party_delta` 185 ms, two open-contribution reads 159 ms, and classification/fallback reads about 110 ms. Three-month quarterly readiness remained in the actual route. The default all-pages native meter's complete readiness on every page and 25 MB should **not** be attributed to these deferred HTTP routes.

Brief parallel workers were separately profiled with `.tmp/stage9-r24-main48-brief-worker-profile.py`, output `.tmp/stage9-r24-main48-brief-worker-profile.json`. Three cProfile trials confirmed response parity excluding `generated_at`: materials 487–521 ms, duplicates 535–597 ms, reports 1115–1310 ms, all with profile overhead. Report worker `check_report_readiness` 760–864 ms followed by `_position` 249–331 ms; it waited 68–80 ms for parent-supplied obligations. Parent work and workers overlap, so they cannot be summed into page latency. Parent `LocalService._dashboard_brief` was 1219–1433 ms under profiling and parallel load. The no-profile HTTP brief sample was 785 ms. A separate prepared `close-review` was deliberately not rerun; an unprepared ordinary close-review was only about 35 ms and is **not** a substitute for the browser's prepared review.

The r24 main12 browser log records `dashboard_period_not_found` during a request and two `WinError 10053` writes to an aborted socket after the five pages' 150 successful samples and a measured 2016-03 company switch. The server log omits request path/query and request chronology, so it does not prove which request received the period error or why the socket closed. The harness records API response errors by path/status and failed requests by path/company/period, but a successful server response whose client later aborts may not reach those arrays. To resolve this without changing product logic, run one diagnostic switch using a private wrapper around `DashboardHandler.do_GET/reply` that records only path, safe query (`company_id`, `period`, `year`, `quarter`), status and monotonic times, correlate with Playwright `requestfailed`/`response` events, and omit bearer tokens. A normal navigation abort must be demonstrated for that exact request; the existing log cannot establish it.
