本轮接续 r66 的实际失败结果。仓库仍为 draft/0；r67 已在隔离源码中固定候选，清单摘要为 `33a25cb6d16243bbe85d1ed5d6f469d77f7f747754cb766ec9cbeb3c5cce10f2`，没有新的五页浏览器验收。11 文件集中定向组实际为 **132 passed／2 failed，171.58 秒**；运行前后源码清单相同。两项失败是固定 v1 缺发布记录时的错误分类，后续最小受影响组四项通过。员工和资产虽减少历史正文，定位 SQL 却放大扫描，使主 48 月原生读取退化到约五秒；这轮实现不能收口。下面按根因记录，定向通过不代替最终验收。

## 名单、金额与显式历史混在一起

触发：默认员工页只显示本月名单和金额，却对全部历史工资认证采用身份。主 48 月 r66 实际装载 2,400 个工资头和 2,350 个冻结采用叶，员工原生读取为 823–837 毫秒。

决定：名单用每个人的一条精确采用见证；本月和开放段工资仍保留完整作用域。未付和实际支付读取既有、独立核验的清偿汇总。身份纠错范围按保存的纠错计划及逐项记录核对；归属与冻结债权不一致时回到完整路径。打开某个人的历史、完整核验和备份继续核验其实际需要的完整内容。

修改：`dashboard.py`、`dashboard_reads.py`、`settlement_freeze.py`。全量名单和汇总保留，默认分页仍为 20 条，没有新增缓存或冻结根。

实证：2 人、3 个月合成样本中，默认严格采用身份范围为 2 个主体，原路径为 6 个；完整响应相等。新增作用域组 22 passed，93.14 秒。主 48 月固定候选随后暴露定位扫描退化：员工 4,947–5,154 毫秒，资产 4,163–4,758 毫秒。SQL 输入精确不能证明实际读取有界；定位查询修正前不把少装载历史正文写成性能完成。无冻结基线和固定 v1 仍走完整路径。

## 报表分类头聚合没有实际收益，撤回

触发：冻结报表根指定 4,932 个分类来源，读取全部头部后只判断整批存在、范围及摘要是否一致。范围确实全部必要，头部逐行返回不是输出要求。

曾尝试保留所有指定 ID 的核验，用 SQL 返回完整性、范围及摘要比较的汇总。实际主 48 月对照显示，原完整头读取为 187,600 VM，聚合为 409,700 VM；报表相关读取总耗时没有降低。额外物化试验为 424,600／439,500 VM，也不保留。决定恢复原完整头读取和严格集合比较，不能以少返回行掩盖更多扫描。

试验修改：`report_flow.py`。首轮 35 passed／1 failed，新增数字 ID 负例暴露 SQLite 类型亲和性差异；修正类型比较后补跑新增及组合单例，20 passed。原有两模块的 17 项首轮已通过，未把局部补跑改写为整组 36 通过。原试验、失败及主样本负收益都保留；恢复后的相关整组另行记录。

## 已核发布记录与完整期间检查重复

修改范围限定为 `publication.py` 与 `query_reads.verify_publication_periods`。只在同一拥有的只读快照、当前读取规则下复用已有精确成功 ID；未核部分仍完整核验。独立完整核验、关账、修复、固定 v1 和新请求不借此放宽规则。
