# 第 2 阶段：依赖、写入检查与内容核验

**状态：完成（2026-09-20）。**

承接[整体架构](../kernel-refactor-architecture.md)与[路线图](../kernel-refactor-roadmap.md)。处理审查第 5、8、9、10、13、23、40、41、42 项，以及实际读取记录、历史依赖保全和私有通道验证。完成后提交 Git，停在本阶段。

## 1. 目标与边界

统一依赖选择、写入检查和失效传播；补齐权威内容与派生数据的核验；提供原子、有限的维修路径。保留现有业务用法、五页布局和信任链，不增加逐项证明流程。真实公司数据不用于开发验收。

公司库增加 v13，只追加读取修复计数；目录库仍为 v3。v1–v12 冻结合同不改。历史读模型、工资确认、身份和备用金改造按后续阶段实施。同账户直接改文件的风险保留，不增加操作系统隔离工程。

## 2. 实施设计

### 2.1 依赖与删除

共享来源、类型、作用域及严格截止期间的选择规则，接通数据库、批量读取、同批排序与覆盖、失效和测试辅助。精确版本保留历史含义；跨类型读取仍真实跨类型，双通配继续拒绝。事实作用域包含 claim，计算作用域不包含。持久对象使用保存的作用域；事实变化合并旧持久作用域和新声明作用域，不重建历史依赖。

Context 的输入集合私有只读，实际读取记录统一生成依赖和 checked_lanes。空命中仍有作用域依赖；具体类型空读检查对应 lane，跨类型空读检查三 lane。

删除预览返回三个完整 epoch 和 checked_lanes。预览及锁内最终检查共用删除计划，重新核对精确事实、计算、关账及下游；pending 下游覆盖月份、通配、自定义作用域、claim 和截止期。实际删除按精确 ID 并检查行数，审计原因与预览对象一致。检查三 lane，成功推进目标 lane，撤去核算结果时同时推进 accounting；保留幂等、编号、历史和回滚。

读取成本按精确版本／主体、业务作用域、跨类型月份、具体类型全集分别验证。不加统一硬上限或静默截断；检查扫描、装载和 SQL 数量随匹配集合变化，而非无关历史变化。

### 2.2 内容与投影核验

全量核验直接扫描权威源，不依赖反向目录取得全集。检查原件、原始事实主子字段及摘要、封存关系、计算原始结果及摘要、发布与凭证关系、完整有序凭证行及总额、冲正、关账原文摘要和精确引用。事实复用原始存储解码，在当前模型校验和补默认值之前核对摘要，不另建类型合同。

普通凭证与原计算完整行比较；冲正与 reverses_id 原凭证逐行互换借贷比较。开放期旧版本、闭期冲正及替代、无行结果、review_no_impact 复用旧凭证、批次和成员均保留原语义。

monthly_account 和 monthly_cashflow 从有效凭证版本生成；balance 和 opening_account 从当前正式发布计算的保存结果生成。按总借方、总贷方和整数分核对全科目，期初不混入当期流水；零行规则统一，溢出拒绝。新关账前执行独立全科目核验，同时核对既有冻结清单原文、历史链和精确依据；缺上年可比资料不能豁免。

历史关账先确定采用依据，再比较金额；已有明确来源的不一致属于错误。已知旧格式缺少期初采用依据时，报告覆盖不足，保留未建立语义，不猜、不以差额倒推、不覆盖旧关账。该限制传递到核验、备份和恢复结果，不能包装成完整通过；未知结构继续拒绝。

### 2.3 维修与版本

保留 rebuild，只重建四张金额投影；新增只读 verify_integrity 和仅修四张引用目录的 repair_read_indexes。新命令接入现有 CLI、MCP 和 Schema，不增加网页维修按钮。

维修通过现有授权、幂等、审计和统一写事务。权威源错误阻止维修，目标派生表的已知差异不阻止。目录维修只对固定触发器白名单临时解除限制，恢复完整原始引用和空源标记后按原 SQL 还原触发器；提交前核对完整结构、外键和目录。任何失败连同计数、请求和审计回滚。不提供外部 SQL 或持久维修开关。

state.read_repair_revision 初始为 0，仅实际维修变化时在同一事务加一；无差异和幂等重放不增加，不成为第四业务 lane。页面 snapshot_version 与按需准备 read_version 使用它，响应形状和 context／funds 的 schema_version 2 不变。代发和报表导出在生成计划的同一读快照捕获计数，在写事务幂等检查后、保存任务前再次检查；公共计划与参数不加字段。关账继续锁内重建并检查内容。

普通连接不全库扫描或自动修复。发布核验本次实际来源与影响；显式核验、备份和恢复执行全量检查。迁移使用第 1 阶段的增量合同，独立新库与升级库的 SQL 原文完全一致。

### 2.4 文件权限与授权边界

复用现有平台能力。Windows 文件 owner＋SYSTEM 私有 DACL，目录带继承，按句柄核验并拒绝重解析路径；现有 POSIX 分支目录 0700、文件 0600，检查 owner 和符号链接，不改变全局 umask。应用自有目录、数据库、临时库、边车、服务日志和锁统一处理，只收紧已知对象。

外部备份父目录保持原样，只保护应用创建的临时目录和 current／previous ZIP，复制轮换后复核。恢复输入可在共享位置，恢复目标和暂存空间必须私有；不能落实权限时明确报错。完整常驻身份链仍为当前 Windows 能力，不宣称其他平台已完整支持。

合成服务实际验证同账户可以读取受保护 capability，并经私有接口走到真实密码重认证；错误密码共用持久节流，正确密码才可创建批准。批准写入数据库后，错误期间或 epoch 被拒绝，正确单月关账才消费批准。窗口展示由测试替身接收请求，密码、批准签发和消费使用正式代码。原生窗口不是独立隔离边界，同账户文件控制风险不在本阶段消除。

## 3. 验证及完成条件

依赖选择、空命中及失效；三 lane 删除竞态与新下游；完整行内容损坏；四表投影错漏与独立期初；冲正、无行和旧凭证复用；目录 occurrence／空标记；维修故障回滚与幂等；分页和导出维修竞态；v13 新建、升级及未知结构拒绝；平台权限、备份轮换和恢复均需有针对性验证。

运行受影响后端回归、前端版本失效测试、生成检查、类型检查和构建，记录局部及全量核验成本。规划基线为四组 51 项、删除及业务三组 36 项通过，两组重叠不相加。备份旧英文错误断言与实际先行目录检查不一致，按稳定错误分类验证，不能减弱检查。

## 4. 实际结果与提交

### 4.1 已交付

依赖选择与实际读取记录统一；删除在写锁内重新核对精确对象及三个 lane；普通与资产批次发布共用来源和投影检查。四张金额投影与四张引用目录分别维修，旧事实、依赖和关账保持原样。公司 v13 使用第 1 阶段的增量合同，只增加读取修复计数，目录 v3 和公司 v1–v12 合同未修改。

CLI／MCP 已接入只读 `verify_integrity` 和写命令 `repair_read_indexes`，原 `rebuild` 接入同一维修事务。页面、按需准备及导出提交使用维修版本；context／funds 仍为版本 2。备份与恢复回执保留 `verification`，历史缺少采用依据时明确返回 `limited`；不把新字段强加给旧 ZIP 清单。

Windows 私有文件和目录、既有文件收紧、边车、服务锁、备份轮换及恢复均使用合成路径验证。链接路径在解析前拒绝，已有边车在 SQLite 打开前检查，新边车在写入前建立私有权限；外部备份父目录不收紧。POSIX 权限分支保留，但本机不运行 POSIX 专项，也不宣称完整常驻身份链已支持其他平台。
