# 基础修订：新库起点与未来升级

## 目标与边界

状态：完成。依据[整体架构](../kernel-refactor-architecture.md)和[路线图](../kernel-refactor-roadmap.md)，通用运行层已切换到独立的新库体系，创建、打开、备份、恢复、CLI、MCP 和看板入口已接通，未来升级能力已验证。本阶段随代码、测试和文档一起提交，停止在阶段 3 之前。

沿用审查 §1.1 信任链，复用前两阶段的共同定义、响应合同、事务、依赖、版本检查、内容核验、维修、权限和密码批准。期间、身份、备用金、工资及关账表示的业务改造仍归后续阶段。本阶段不操作真实资料、现有数据库、备份或运行服务。

## 数据库合同

- 系统标识 `ai-accounting-kernel/2`，类别 `catalog` / `company`，SQLite `application_id=0x41414332`。
- 开发基线为 `draft` / 版本 0；正式版本为 `released` / 版本 1 起，阶段 9 才冻结。开发库只接受当前完整指纹，不升级、不转正式版、不自动重建。
- 不可修改的 `schema_meta` 保存系统、类别和状态；`user_version` 保存结构版本；`schema_history` 保存实际安装历史和指纹。稳定身份不再包含结构版本。
- 新合同放在 `schema_contracts/<kind>/draft.json`。开发基线和正式 v1 为完整合同，正式 v2 起为父合同约束的增量。旧合同、迁移桥和 v10 特例退出运行层，由 Git 保留历史。
- 窄职责 `SchemaBundle` 配套模型、合同和迁移步骤。生产只使用固定包内工厂，测试以独立合成合同走同一加载、规划、执行和核验，不再跳过自定义模型的结构检查。
- 迁移匹配精确来源，锁内复核；明确动作、数据核验、结构和外键检查在同一事务内完成。失败全部回滚，外键恢复失败关闭连接。不补造未经的中间历史。
- `db-contracts:generate` 只生成开发合同文件，`db-contracts:check` 只比较；构建摘要和运行包覆盖新合同。

## 入口与备份

- 已有库先用正常 SQLite 只读事务核对标识、类别、状态、版本、完整结构、历史和身份；正确读取 WAL，不使用 immutable。未确认前不改已有权限、不补标识、不升级、不恢复任务、不操作旧服务。
- 无目录库但有公司、操作或服务运行痕迹的根拒绝初始化；已有空文件不是新建目标。新库在独占暂存文件内完成创建、核验和落盘，原子发布后才创建服务锁、日志及元数据。
- 开发启动器、MCP 配置、Vite 使用 `data/kernel-draft`；独立包使用自己的开发根。CLI 使用明确 `--root` 或 `FINANCE_DATA_ROOT`。
- 备份 ZIP 格式为 2，保留成员、大小、摘要、身份、滚动及幂等保护；增加 `database_format` 和数据库字节数。manifest、库内登记和实际结构必须一致。
- 当前只恢复相同开发指纹。未来已知正式旧版本按源合同核验，在暂存副本迁移并复验后发布；开发与正式版之间、旧系统和未知来源均不转换。恢复不覆盖已有目标，不改来源备份。
- 外部备份完整检查在目录写事务外进行；调度和恢复再次核对摘要，避免检查后替换。

## 接口

统一格式信息为 `{family, kind, status, version, fingerprint}`。`company_context`、备份和核验结果使用顶层 `database_format`，身份仅保存稳定标识。`schema.database_formats` 声明两种库；服务元数据和 health 使用新协议并核对目录格式。凭据使用新命名空间，不导入旧凭据。

context / funds 保持现有响应形状及接口版本 2。格式、结构及备份错误使用稳定错误码，不变成业务追问。调用方和运行说明当期接通。

## 实际结果

通用运行层、最终业务回归和独立包验收已完成。以“基础修订：建立新库起点与未来升级能力”提交，准确提交身份以包含本文记录的 Git 提交为准。

已落地的变化：

- 两类数据库采用独立系统标识、不可变格式登记和 `draft / 0` 精确合同；身份不再携带结构版本。旧合同、升级链和 v10 特例从运行代码与包内退出，历史留在 Git。
- 生产模型与合同通过固定 `SchemaBundle` 配套。合成正式合同走相同加载器、规划器和事务执行器，验证公司结构演进、目录独立升级、身份及历史保留、失败回滚和外键恢复；未向生产登记虚构正式版本。
- 创建通过私有暂存库核验后原子发布。打开、绑定及服务连接先验证新格式和完整结构，安装历史与身份处于同一读取快照；WAL 中已提交的标识和结构正常可见。
- 备份格式 2、目录格式、公司上下文、schema、服务协议及凭据命名空间已接通。恢复先在目录写事务外核验来源，再从同一个文件句柄复制并核对摘要，恢复私有副本，复验后发布；失败可重试，不覆盖已有目标。
- 开发启动器、仓库 MCP 配置及 Vite 改用 `data/kernel-draft`。CLI 要求明确根或环境变量；独立包默认自己的开发根，Vite 经只读 `service-info` 核验连接资料。
- 开发合同生成、只读检查、SQL 差异、构建摘要、CI 和打包清单改用新合同；上下文、资金页维持响应版本 2，其他业务领域改造仍按后续阶段推进。

验收中已修正的缺陷包括 Windows 原子发布前的文件同步方式、并发锁读取导致的错误、恢复来源替换竞态，以及格式字段把浮点或布尔值当作版本号的问题。备份错误按稳定错误码返回中文，不透传内部异常内容。

并发服务验证发现，SQLite 最后连接关闭时删除 WAL/SHM，会与下一连接的权限检查及辅助文件创建发生竞态。连接现在使用 SQLite 的 `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` 保留私有辅助文件，正常自动检查点和显式检查点仍有效；文件消失只做有限重试，现存文件的权限、所有者和链接检查不放宽。依据见 [SQLite 连接配置](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html)。隔离验证 1200 次、最终源码验证 400 次真实登录请求与并发连接开闭均无错误。恢复入口也在路径规范化之前拒绝文件链接，避免目录层绕过备份层已有检查。

正式批次入口的回归还暴露了资产处置无法发布的问题：已计提月份新增处置时，批次预览只收集计算依赖，遗漏明确读取的待计算事实。现按已有事实与计算依赖共同形成发布范围；启用或折旧批次均能携带处置完成发布，不改变卡片无独立凭证、版本检查、幂等及失败回滚规则。这是正常业务验收发现的缺陷修复，不提前实施阶段 3 的资产历史架构。

完整核验对报销资产卡片采用关系的调用也已修正：只有已核对凭证集合中的实际批次拥有者，才向采用核验提供凭证依据。合法关账通过，伪造资产、结果摘要或无凭证拥有者仍拒绝；不将一般依赖成员当成拥有者。

旧升级专项由新体系的合成迁移、旧格式拒绝及回滚测试替代。原有正常业务测试继续核对金额、累计、更正、冻结、依赖、修复和批准；资产测试改为正式批次入口，员工摘要移出的明细通过真实按需接口读取，并分别核对当前清偿与历史冻结。资金页仅修正已确认来源显示内部采用术语的问题，待确认说明保留，五页布局不变。

性能夹具的合成计算编号改为当前完整内容标识公式。空待办性能测试直接观测准备检查，保留 240／2400 条历史和原 VM 步数预算；原来的整次关账预览包含有意执行的累计内容核验，不能代表空待办查询成本。关账预览的历史读取优化仍归阶段 3，整页 500 毫秒目标仍归阶段 9，本阶段未宣称完成这两项。默认回归本机用时约 36 分钟，CI 作业时限调整为 60 分钟，业务和性能断言不放宽。
