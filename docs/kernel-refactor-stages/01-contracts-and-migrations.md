# 第 1 阶段：业务定义、接口合同与迁移基础

**状态：原前提下完成（2026-09-20，提交 `f411820`）。新基线未实施。**

本阶段在保留目录库 v3、公司库 v12、既有接口和旧结构升级能力的前提下，处理审查第 2、4、14、20 项及生成 SQL 属于结构合同的问题。下文保留当时目标、实际实现、验证数字和已知差异，不能作为新基线已经验收的依据。

现行[整体架构](../kernel-refactor-architecture.md)与[路线图](../kernel-refactor-roadmap.md)以全新开发、全新库为前提。共同定义、响应生成链和通用迁移机制继续复用；通用旧库、旧包兼容在基础修订退出，响应别名与领域适配在对应阶段整理。以下旧兼容要求只记录当时工作，不再约束新设计。

## 1. 目标和边界

消除发布与读取之间重复维护的共同业务定义；建立能真正接通消费者的响应合同；允许已知数据库通过明确、原子的步骤演进已有结构。

信任链、现有业务用法、核算规则和五页布局保持不变。目录库仍为 v3，公司库仍为 v12，冻结快照不回写。身份、工资确认、政策来源校验、备用金简化和新历史读模型按后续阶段推进。本阶段不修改真实公司资料或数据库。

## 2. 具体设计

### 2.1 迁移基础

保留 `upgrade`、`verify_schema` 入口。内部版本步骤绑定数据库类别、源版本和指纹、目标版本和指纹、明确执行动作及数据核验。版本步骤来自包内代码，不接受外部 SQL，不推断 ALTER，不为未知结构修复缺失对象。

支持明确的加列、重命名、索引与触发器替换；原生 ALTER 无法表达的约束变化通过专用单表复制替换完成，明确列映射和相关约束恢复。所有动作在同一次升级事务内完成。需要关闭外键时，在事务外调整，取得写事务后重新核对精确源；失败回滚，结束恢复并读回外键开启状态。

保留旧版本的历史说明标记、引用目录回填条件和已记录 v10 形态。旧历史行保留，不补造未经过的中间版本记录。新步骤逐步核验，最终核对完整 SQLite 对象 SQL 原文、外键及数据保留情况。

现有全量合同只读。后续增量合同保存父版本及指纹、对象 `add/remove/replace` 和目标指纹，加载后还原完整对象并验证。对象键不得重复或交叉，父合同、操作对象及指纹错误均拒绝。已记录 v10 形态只作为允许的源，不成为标准合同或增量父版本。只读差异工具展示对象和原／新 SQL；增量合同描述目标，迁移步骤负责到达目标。

本阶段用隔离测试合同验证新能力，不创建生产 v13 或目录 v4。

### 2.2 共同业务定义

新增窄职责的科目定义模块，集中现有名称、六组精确报表映射、已知位置科目集合，以及四种具名税种的控制科目。科目值、匹配范围和缺名回退原样保留；计算器仍决定金额、借贷方向和税务处理。

现有资金模块集中四类清偿付款对应科目和余额类别到页面账户类型的映射。事实声明、发布与清偿查询共同引用；工资与备用金付款的额外费用行使用事实已有资金科目。实际账户身份仍来自业务身份和冻结结果，不从科目反推。

工作流模块集中五类外部义务的依据类型、工资人员核对及个税未开始状态排除规则。枚举、适用性检查、读取、准备及详情共同引用。周期与适用性继续由政策和公司事实决定；会计债权债务与外部办理义务不合并。

全部定义调整保持生成 DDL 不变。构建摘要正常变化，不缩小构建内容范围；通过既有核算等价机制识别没有会计影响的复核。

### 2.3 完整响应切片

本阶段完整迁入 `dashboard_context`、`dashboard_funds`，包括期间、准备度、分页、来源、候选和问题类型。以当前后端实际输出为准，不照抄已落后的 TypeScript 或测试夹具。

| 接口 | 保留分支 |
| --- | --- |
| context | 空目录、公司无月份、公司有月份；空目录原有省略字段继续省略 |
| funds | 无期间 `data=null`、默认 `preparation=complete`、网页 `deferred`、各集合和账户筛选分页 |

Python `TypedDict + TypeAdapter` 是单一来源。省略字段用 `NotRequired`，未知值用可空类型，不默认补字段或丢字段。原生金额复用 int64 整数分，HTTP 按显式金额类型序列化为字符串；计数、行号和版本仍为数字。来源和问题中的已知金额也要显式建模，真正开放的非金额扩展不能隐藏货币字段。

从同一模型生成 HTTP JSON Schema、TypeScript 类型和 Ajv standalone 校验器。生成工具固定 `json-schema-to-typescript 16.0.0`、`ajv 8.20.0`；CI 使用 Node 24.19.0。金额字符串为 `^(0|-?[1-9][0-9]*)$`，校验器通过 BigInt 检查 int64 范围，不经过 Number。

服务读取返回边界统一验证，CLI/MCP 保持原生整数，HTTP 使用类型化序列化。`schema.response_schemas` 先公开这两个原生响应合同。响应合同失败返回 `response_contract_mismatch` 和 HTTP 500，只提供字段路径，不把程序错误变成业务追问。

前端用补齐公司参数后的最终 URL 同时请求和验证。context/funds 使用生成类型及运行时收窄，停用这些端点按字段名猜金额的转换和校验；其余端点继续原校验，后续逐阶段迁入，第 7 阶段收口。

`schema_version` 保持 2，快照、读取和集合版本维持原职责。对外字段结构、必填性、空值、金额编码或状态含义改变时增加接口版本。

生成产物纳入仓库。`contracts:generate` 更新产物；`contracts:check` 在临时目录生成并逐字节比较，不改源码。CI 同时检查 Python→Schema 与 Schema→前端产物；构建只检查，不隐式重新生成。

## 3. 实施步骤与验收

按迁移基础、共同定义、共享合同和消费者的顺序完成集成，再验证、修正和记录结果。互不依赖的代码和测试可以分工处理，最终统一集成。

| 范围 | 必要验收 |
| --- | --- |
| 业务定义 | 四类付款合法方向出账和查询一致；错误资金行仍报警；四税种和五义务一致；科目分类、名称回退及本月非零累计零行为保留 |
| 冻结与构建 | 目录 v3／公司 v12 默认 DDL 和冻结合同逐对象相同；旧冻结结果可读；代码整理仍可识别无会计影响复核 |
| 迁移成功 | 实际执行器完成加列、索引／触发器替换、约束复制替换；与独立目标库比较完整结构、数据和引用 |
| 迁移失败 | 在关键步骤注入故障，结构、数据、版本和历史一起回滚；外键恢复；未知近似结构拒绝 |
| 增量合同 | 父链展开一致；缺父、错误指纹、重复或无效操作拒绝；打包不得漏父合同 |
| 响应 | 空目录／月份、complete／deferred、各集合分页筛选、旧快照失效；保留实际字段，不以旧夹具定义合同 |
| 金额 | 未知与零、超过 JS 安全整数、int64 两端；浮点、布尔、越界、负零和前导零拒绝；普通计数不字符串化 |
| 消费者 | 当前后端合成响应经过真实校验器和页面；公司切换及过期请求隔离；格式错误明确失败，不追问业务事实 |
| 生成 | 模型变化但产物未更新时检查失败；检查命令不写仓库；类型检查和前端构建通过 |

运行受影响的后端回归、前端测试、类型检查和构建；测量新增响应校验成本。本阶段产生的问题当期修复，不积压到第 9 阶段。

## 4. 实际结果与后续影响

### 4.1 已交付

- `kernel/account_definitions.py` 统一科目名称、六组报表分类和四种税种科目；`domains/money.py` 统一四种付款科目和账户类型；`workflow.py` 的五类义务定义由枚举、依据读取和业务详情共同使用。没有改变核算金额、科目值、借贷方向或五页布局。
- `kernel/migration_steps.py` 提供明确版本步骤和单表复制替换，`migration_contracts.py` 还原并校验增量合同，`versions.py` 统一执行事务和旧版本兼容桥。未来公司 v13／目录 v4 起不接受新的全量快照。旧历史记录、v9 说明标记和 v10 引用回填条件保留。
- `kernel/response_contracts.py` 完整定义 context、funds 及其嵌套响应。`LocalService.dispatch` 校验原生结果，HTTP 使用同一合同序列化金额。普通程序错误和合法业务问题继续分开，错误路径中的未知字典键也会脱敏。
- 前端通过生成类型和预编译校验器读取这两个接口，使用最终请求 URL 校验公司、月份、快照和分页。旧兼容分页的 `total_count` 仍表示筛选数量，集合分页的 `total_count` 仍表示完整数量，没有把二者误当成同一含义。
- 生成器、依赖锁、CI、消费者和阶段文档同时落地。源码内所有冻结 JSON、目录 v3／公司 v12 的默认 DDL 均保持原样；没有修改真实公司数据。

### 4.2 开发入口

在仓库根目录使用 `npm run contracts:generate` 更新 Python→HTTP Schema→TypeScript／校验器；使用 `npm run contracts:check` 只检查同步情况。`npm run build` 和 `npm run build:release` 检查后再构建。没有新增 HTTP 端点，原生合同通过现有 `schema` 命令的 `response_schemas` 读取。

只读结构比较：`.tmp-kernel-venv/Scripts/python.exe scripts/diff_kernel_contracts.py business 11 12`。它仅展示包内两份完整合同的 SQL 差异，不操作数据库。

`tests/kernel/response_samples.py` 在临时目录建立合成公司，生成当前后端的 15 类响应。前端使用这些响应做验证；后端集成测试每次重新生成临时样本并调用实际 Node 校验器，不以静态旧夹具代替当前合同。

### 4.3 验证结果

合并回归覆盖 21 个后端测试文件：业务定义、查询、工作流、报表、工资与备用金付款、迁移、冻结合同、无会计影响复核、资金分页与筛选、历史来源、按需准备、空库回放、传输和本次响应合同。**286 项全部通过**。最终收紧冻结分支必填项并补齐样本后，响应合同专项 **27 项通过**；迁移新增专项共 **53 项通过**。受影响代码和测试的 Ruff 检查通过。

新增测试覆盖原生金额与 HTTP 金额、未知与零、超过 JS 安全整数、int64 两端、浮点和布尔误入、缺字段／多字段／错误版本、真实业务问题详情、错误路径脱敏、HTTP 500，以及模型变化后生成检查失败且不改文件。迁移测试覆盖独立目标库比对、保留数据和引用、并发改结构、关键步骤回滚和外键恢复失败关闭连接。

前端本阶段专项 **42 项通过**（原有公司／月份切换、资金筛选、按需准备 36 项，加生成合同与实际消费者 6 项）。15 类当前后端样本通过预编译校验器，实际 FundsView 的银行页、账户筛选和无月份分支通过渲染验证。`npm run contracts:check`、类型检查及 `npm run build` 均通过。隔离副本修改 Schema 后，生成检查按文件名报错且不改已有产物；同步状态下检查也不改文件。

完整前端测试为 **107 项：101 通过，6 个失败计数**。其中是下节记录的 5 个既存断言及 1 个父套件失败，没有本阶段新增失败。

读取成本用临时数据库的 500 条资金明细测量，响应约 947 KB（含现有重复别名）：100 次原生校验的中位数为 **4.8 ms**，HTTP 再校验并序列化的中位数为 **10.4 ms**。两处合计约 15 ms。该样本的原有资金读取中位数约 679 ms；这是最大明细页样本的观察值，不代表整页 500 ms 目标已经完成，整页性能仍按第 9 阶段处理。

Ajv 生成时共享被引用的校验函数，避免重复展开。最终校验器源码约 530 KB，构建后的主 JS 为 480 KB（gzip 约 82 KB）；构建没有大块体积警告。
