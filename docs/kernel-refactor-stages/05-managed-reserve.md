## 目标与合同

备用金只表达实际支出和实际退回公司，支持银行、现金和公司平台账户。备用金自身不建账户，不管理余额、容量、可退额度、内部消费或成本分配。

新增 `managed_reserve_expense` 和 `managed_reserve_refund`，使用通用登记、预览、发布与录入纠错入口。前者借管理费用、贷实际资金账户；后者借实际资金账户、贷管理费用。实际日期属于所属月；金额为正整数分。三个资金账户字段恰好一个非空，核对对应实体类型；平台必须采用精确原行，银行和现金不填写平台原行。交易方可选，未知不虚构。

退款不要求原支出编号，不读取历史成本，不产生退款权利、义务或额度占用。无历史支出或退款超过已记支出均不构成拒绝理由。真实资金保护、期间规则、身份纠错、内容核验、冻结和投影修复沿用内核已有机制；直接撤去实际资金仍返回 `immutable_fact`，身份纠错不能把实际收付终止为零。

工资混合付款保留整笔银行金额、完整净薪分配、工资来源及防重复核销，备用金金额改为 `reserve_expense_fen`。删除范围和备用金平台账户依赖；实际退入的确认、同月及已有日期约束保留。银行差额不能代替实际退入依据。银行余额只按全额减少一次。

退出旧范围、接续、成本资格、容量、FIFO、原债结清和专用命令。普通费用回收及公司平台收付、融资和内部划转继续保留。备用金内部资料沿现有有依据的不入账处置保存；公司平台原行仍要求完整且唯一处理。

新业务接入身份、发现、银行对账、平台原行、资料、期间贡献、现金流、关账和页面。查重规则升为 2，覆盖同一原行跨备用金、普通资金业务和工资付款的重复；费用确认与实际付款分别处理。强候选核对、弱线索不打断，缺失交易方不当成相同对象。

沿现有通用响应字段展示，不新增备用金专用响应结构：context 2；brief、funds、employees、assets 4；business_status 3；季度报表、期间准备及关账合同 2。CLI、MCP、命令 Schema、读取、前端和运行说明当期接通。剩余响应全面生成化仍归第 7 阶段。

## 验收场景

- 三渠道支出、退款、原件方向和唯一采用；独立退款、多次退款、无历史来源与超过已记支出，费用净额允许为负。
- 工资全额、净薪与备用金守恒、实际退入依据、原有工资合法场景及重复核销；普通平台与普通费用回收三渠道继续可用。
- 强弱候选、跨类型和批内重复、核对失效、缺失交易方、错误账户和原行硬限制。
- 开放期纠错和撤去、闭期连续更正、身份纠错、冻结原文、幂等、过期预览、整组回滚。
- 当前及期间投影、修复版本、损坏拒绝、银行对账、报表现金流和公司切换；整数分及 HTTP 大额金额。
- 多期合成样本验证退款不扫描历史成本；公司合同更新且目录合同不变，运行包中无退役入口。
- 后端回归、两类合同检查、前端测试、类型检查和构建；独立包走通身份登记、三渠道收付、工资混合付款、发布、更正、关账、备份恢复。

### 验证中发现并修正的问题

1. 查重初版把资金坐标相同但核销内容不同的付款升级为强疑点，可能误拦合法业务。已收紧为完整同类签名或精确原行，增加对应回归。
2. 真实资金页准备检查返回的资料问题含 `category`，共享响应模型原先遗漏该可选字段，会误报响应合同错误。已准确声明并更新生成产物；未知金额字段仍拒绝，响应版本按本阶段约定保持。
3. 全回归中的一条历史回放测试仍通过旧展示档案入口登记往来方。已改用统一实体档案，并继续核对关账只采用关账前版本、后补名称和说明不进入冻结内容。
4. 银行奖励测试把同一收款补充归属确认写成另一笔收款，被新查重正确拦截。现通过有依据的录入纠错补齐原业务，仍验证缺少归属确认不能发布、实际日期和金额不变、余额只增加一次。
5. 独立包新增金额断言最初把工资明细科目 `560201` 和备用金费用科目 `5602` 当成一项读取。已分别核对两个科目的合成预期，再核对管理费用总额；没有改动核算结果来迁就测试。
