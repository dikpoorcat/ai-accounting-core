# 关账前资料与应收应付核对

架构由公司业务说明、月度资料清单和已有记账组件组成。清单只保存来源覆盖、金额归属和处理依据，正式核算仍由类型化业务组件完成，不接受自由分录。

## 固定流程

1. `finance_get_company_notes` 读取公司业务说明。
2. `finance_register_evidence` 留存原件，随后独立调用 `finance_register_period_materials` 保存清单。后续提问、中断或入账失败不会删除这次已提交的登记。
3. AI 核定业务性质、金额及必要所属期，通过现有工具入账，或查找已入账组件。
4. `finance_update_period_material_inventory` 记录处理结果，提交预期清单版本、幂等键及刚核对的 MD 哈希。
5. `finance_get_period_material_completeness` 逐项验证。第 5 项流程、材料完整性确认、关账预览、正式关账和完整代发均复用该结果。
6. 已提供材料通过核对后，负责人只需明确确认是否还有**尚未提供**且影响本月的资料。正式关账仍使用原有负责人审批流程。

不存在“设为完成”的接口。链接必须指向本公司有效正式凭证中的具体组件，提供其 `facts_hash`、匹配金额，必要时明确子往来键和核算事实。内核核对业务类型、原确认金额、实际入账月份和所属期；应收应付后来部分核销或结清不减少原确认容量。一个组件的金额不能重复分配。

本月应确认业务在下月记账、仅将所属期写成本月，不能完成本月清单。工资、社保、劳务、资产和借款继续使用原领域检查。正常以后月份结算不阻止本月关账；已导入的所有以后月份收款和付款都通过组件及核销来源核查归属，没有后续流水时不要求等待。

## 原资料覆盖

CSV/XLSX 从留存原件解析。`columns` 将列字母映射为 `amount` 或 `context`；`header_row` 指明表头终止行，`total_rows` 指明合计校验行。不同工作表可使用 `sheet_columns`、`sheet_header_rows` 和 `sheet_total_rows`。隐藏行、列和工作表同样读取并记录。未映射列、缺失或无法解析的金额、公式无缓存结果、合计不符均保留为阻断项。金额不默认为零。

原件中无法读取的明细金额仍生成待核对项。查阅补充依据后，可在该项的 `amount_fen` 和 `basis` 明确记录确认金额与依据；原值和解析问题保留，合计按补齐后的金额重新核验，正式确认仍须足额关联。横杠不自动视为零。

例如报销表 A 列为人员、B 列为金额，第 5 行为合计：

```json
{
  "evidence_id": "原件编号",
  "columns": [{"column": "A", "role": "context"}, {"column": "B", "role": "amount"}],
  "total_rows": [5]
}
```

同一原件重复登记关联已有项；重新映射不会删除旧项。`splits` 将一项明确拆为多个金额，子项总和必须等于原金额；每个子项可分别入账或转入其他期间。多项也可分配到同一组件，累计金额不能超过组件原确认金额。

处理结果包括 `recognize`（入账或关联已有确认）、`duplicate`（关联本清单中同一业务的原项并说明依据）、`other_period`（原子转入对应开放期间）、`supporting`（无核算金额的背景证据）和 `no_accounting`（明确为预测、余额校验、非本公司业务或确认前取消，并保存依据）。未知信息保留 `pending`。移到未来期间但尚未确定归属，仍会阻止当前期间关账。

PDF、图片及文字使用 `passages` 登记页码或原文位置与摘录。AI 须阅读全部材料并登记未决事项；本版不提供通用 OCR，也不能自动证明自由文本已被正确理解。已登记但未归入任何清单的证据会独立列为缺项。

## 公司业务说明

位置为 `FINANCE_STORAGE_DIR/<统一社会信用代码>/业务说明.md`，首次登记清单时创建。公司摘要返回路径。文件使用普通中文 Markdown，包含“长期规则”“按月确认”“待澄清事项”。

AI 通过 `finance_update_company_notes` 使用预期文件哈希写入；发现用户修改后重读、合并，再提交。具体业务回答只记录实际适用范围，不自动成为长期规则。MD 本身不更改账务；正式核算采用的负责人确认仍留存为不可变证据，并通过现有类型化事实表达。MD 改变后须重新查阅核对，普通管理资料补充继续走现有管理入口，不改凭证。

关账快照包含清单版本、来源覆盖、有效组件事实、核对时 MD 的内容及哈希。清单写入与正式关账使用同一公司事务锁；正式关账在锁内重算。预览后新增资料、清单变化或来源删除、更正、冲正，不能被旧完整性确认覆盖。

已关账月份保留当时采用的说明与资料范围。以后新增资料或修改管理说明不会重新打开历史月份，后续代发仍校验原清单所关联的正式来源及余额；当前开放月份继续按最新资料和说明核对。

## 代收代付

`pass_through.recognition_basis` 默认为 `received`，保持旧请求收到款项时确认的行为。明确证据证明收款前权利义务已成立时，使用 `credit` 和实际确认日或 `recognition_period`：固定模板借记“其他应收款—代收代付”、贷记“其他应付款—代收代付”，不生成收入、费用或资金流水。

后续收款用 `receivable_settlement` 核销 `receivable` 子往来，付款用 `payable_settlement` 核销 `primary` 子往来；均支持现有部分核销及余额保护。受益人和用途仍为可选管理资料。公司承担的个人报销使用 `expense/payment_basis=person_advance`；“报销款”这一银行摘要不决定分类。

完整代发读取清单中标记为 `export_category=reimbursement`、`salary` 或 `labor` 的已知来源和人员，复用正式来源金额；清单已核对通过时不要求另换固定代发表模板。未核定项、漏选尚未结清来源或漏人均不能生成完整文件；已结清来源不重复导出。人员及代发类别用于付款范围，不升级为凭证必填项。

## 迁移、备份及回放

`0006_material_completeness` 是 v4 基线之后的前向迁移，新增版本化清单表与受控代收应收科目。历史版本记录不可更新或删除；没有改写旧基线，也没有迁移或修补生产凭证。

公司便携 ZIP 包含单独校验哈希的 MD 文件，导入时安装到该公司的业务数据目录；已有不同内容会返回冲突。空库回放导出来源映射、拆分、处理依据及 MD，重新读取原件，再经公开清单接口重新关联新库组件。原库已经失效的来源不能靠刷新哈希变成完成；MD 尚未核对则停止该回放步骤。回放中断后可恢复已提交的登记。旧库仅有笼统“材料已齐”而无原资料清单时，不能靠复制旧确认关账，须先按原件补齐回放清单。

同一版本同时包含代发原表模块的 `0007_mybank_payment_sources` 前向迁移。回放包保留最新代发原表的证据引用，目标库重新解析原件，不复制原库的逐人计算结果。
