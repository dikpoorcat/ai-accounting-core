# 直接采用引用索引与开发结构调整

公司合同仍为 `ai-accounting-kernel/2`、`draft / 0`。目录合同没有变化。这项开发改动不进行正式合同冻结，不切换服务入口，也不自动调整已有资料根中的数据库。

## 索引定位范围

`close_reference_direct_adoption` 使用 `(reference_type, reference_id, path, close_period, position)`，仅包含 `adopted_results[*].fact_id` 和 `adopted_results[*].calculation_id` 两条路径。当前看板 `_adopted_heads_sql` 的事实、计算两条候选定位路径显式使用它，避免相同身份在累计 readiness 引用中的重复命中。

索引只定位候选。候选仍需通过原有发布、关账和所选来源核验；事实与计算两种身份入口、实际引用类型枚举、缺失来源候选和发布高水位判断均保留。索引不决定采用结果，也不替代完整引用目录核验。完整核验比较不可变来源与目录的全部引用多重集；页面局部读取只核验其实际消费的来源，不能据此宣称整个目录无损伤。

`close_reference_lookup` 仍用于其他身份与路径的引用查询，原主键仍用于按关账期间核验全部成员及配对，`close_reference_related` 仍服务相关身份查询。上述索引均保留。固定 v1 来源解释和相关 SQL 没有改动。

## 原数据与历史保留

显式根升级要求服务停止并取得资料根锁。所有公司的来源核验和经过验证的独立便携 ZIP 备份先于任何公司结构修改。目录另行备份并比较负责人及公司定位数据。备份后的来源指纹必须与计划一致，写入前、取得写锁后和目标复验均绑定目录中的公司、数据库及纳税人三项身份；目标结构的跳过核验同样绑定身份。

每家公司整个剩余计划处于同一个写事务内；取得写锁后再次核验完整来源结构和内容。第一步维持原表复制及外键恢复流程，索引单步不关闭外键。每步完成后核验精确目标结构，并在追加该步收据之前比较来源全部原表值和保留业务历史摘要，因此既有 `schema_draft_history` 行也处于数据保留核验范围。原 `schema_history`、身份、业务、审计、冻结历史和既有开发收据保留原值。

执行器仅为实际经过的步骤追加连续收据。曾由923调整到c9的库保留第一项收据并追加第二项；直接安装c9的库从第一条收据开始记录本次索引调整；直接安装当前目标的库没有调整收据。任一步失败回滚该公司整个计划。根操作保留已完成公司的精确前缀和全部来源备份，重试核验并跳过已达目标的公司。

滚动备份只允许沿这两项精确声明保全923或c9的原 ZIP，并按其原合同重新核验结构、内容、证据及身份。普通备份核验和恢复仍要求明确选择匹配合同，不能将旧 ZIP 重标为当前结构。

## 验证与审查边界

本组验证使用新建的小型合成公司，包括923双步、c9单步、已有收据保留、目标新建、混合来源根及重试、失败回滚、同结构身份竞态与备份后的他公司文件替换、两种来源 ZIP 滚动，以及累计 readiness 引用增长的 SQL 工作量和旧查询多重集对照。固定 v1 的合成核验、ZIP 和目录维修测试强制阻断当前看板候选 SQL，确认这些路径不依赖新入口。它不构成固定 v1 看板支持的声明。

正式 `offline_upgrade.py` 本轮仅做代码审查：根锁前及锁内的内容检查绑定目录三项身份，实际迁移的来源与目标内容回调也绑定身份；已达目标的公司跳过 DDL，末尾再通过 `check_root_current` 核验结构与三项身份。因此跳过前换入并保留到末尾的同结构他公司文件会使最终检查拒绝返回成功。跳过分支没有另做一次完整内容核验，本组也没有执行正式升级链或验证任意外部文件替换在检查后不再发生。
