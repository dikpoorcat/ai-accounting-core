# 内核重构路线图

## 1. 本轮前提与执行方法

本文把[内核架构审查](kernel-architecture-review.md)的已确认事项排成实施阶段；全局架构、信任边界和不变量以[内核重构架构](kernel-refactor-architecture.md)为准。原审查保留为历史问题来源，不随本轮改写。

新前提文档修订、基础修订及第 3–5 阶段均已完成。第 5 阶段的实际改动、回归、多期观察及独立包记录见[阶段 5 文档](kernel-refactor-stages/05-managed-reserve.md)。阶段 6–9 尚未开始。

本轮按全新系统、全新数据库设计，可复用正确的既有实现，不要求兼容旧数据库或旧接口。旧公司 v1–v13、目录 v1–v3 不再是新系统的升级来源。取消旧库兼容不等于取消正常业务历史：新系统仍须保留不可变事实、历史计算、实际依赖、冻结关账、真实清偿与开放期／闭期纠错，并从首个正式版本起支持可信前向升级。本轮不包含真实资料重录、真实公司换库或现有资料根清理。

阶段 0、1、2 的交付和数字保留为原前提下的实际完成记录，不能当作新数据库基线已经验收。基础修订及阶段 3–5 已通过本轮验收；后续另行细化和实施阶段 6–9。每次只推进一个阶段，按“细化设计 → 实施 → 验证 → 修正 → 更新文档 → Git 提交 → 停止”执行，不自动进入下一阶段。

每阶段开始时才在 `docs/kernel-refactor-stages/` 创建当期细化文档，写清目标、结构与接口变化、调用方、实施步骤、验收、实际结果和遗留边界；不预建未来文档。技术选择由实施者决定；影响业务处理或实际使用体验的选择，应先提出具体方案，再请负责人决定。各阶段当期接通受影响的 CLI、MCP、页面、操作协议与测试，不把调用方或已发现缺陷积压到阶段 8、9。验证范围随风险确定，不设置固定全量门禁。

开发期使用明确的新 family／kind 与单一 draft 标记。创建、打开、读取、备份和恢复均严格匹配实际完整结构指纹及库内登记指纹；同一结构可完成关账、备份和恢复测试。只使用临时合成库，不承诺跨阶段升级；结构不匹配即拒绝，不自动重建、不补写当前指纹。需要新结构时由测试显式创建另一临时资料根。基础修订即用隔离的正式测试合同验证迁移执行器，不等交付末期才验证未来升级。阶段 9 冻结新谱系公司／目录各自首个正式 v1，此后结构变化使用前向版本与增量合同；draft 库不作为正式版升级来源。

原审查的公司样本、计数、耗时和测试结果只代表当时观察。不得以零使用样本删除能力，也不得将历史最小耗时包装成当前结论。保留既有保护与同账户信任边界，随相关改动验证，不另建逐项证明工程。定期备份与跨公司配对继续作为未来项。

## 3. 分阶段计划

阶段 1 已完成共同业务定义、受控前向迁移、增量合同与可审阅 SQL 差异，context／funds 共享响应合同及 CLI、MCP、前端消费者接通；当前仓库记录的提交为 `f411820`。其余读取合同仍需在对应阶段接入。该阶段保留旧结构升级和历史 v10 支持的验收，属于原前提，不继续约束新基线。

阶段 2 已完成共同依赖选择、实际读取记录、失效传播、三 lane 删除审阅与锁内版本检查；接通来源内容核验、四表金额投影与四表引用目录维修、独立期初核对、维修版本、导出竞态检查和现有文件权限。公司库 v13、目录库 v3；旧关账依据不足时的有限覆盖以及旧格式核验也属于原前提。新基线复用通用机制，移除不再支持的旧格式分支后重新验证，不直接沿用“已完成”结论。

详细实现、当时验收和既有测试差异分别见阶段 1、2 文档，数字保留在本文完成记录。

### 基础修订：新数据库起点与通用机制

**状态**：完成，本轮回归和独立运行包验收通过。具体实现与最终验收结果记入[基础修订实施文档](kernel-refactor-stages/foundation-revision.md)，本文不重复测试数字。

**交付**

- 建立独立 family／kind 标识、新 draft 基线和统一识别入口；明确拒绝旧公司、旧目录、旧备份及未知结构。备份外层格式与库内身份、结构指纹交叉核对，不隐式升级或改写被拒绝文件。
- 将旧谱系合同、迁移桥和识别特例退出运行包；Git 历史保留旧源码及合同。新谱系保留精确 SQL 结构合同、源／目标指纹、唯一声明的前向步骤、事务回滚、数据校验、安装历史和后续增量合同能力。
- 复核阶段 1、2 的通用实现：业务定义、共享响应合同、依赖与 epoch、删除检查、权威内容核验、投影／目录维修、读取版本、文件权限和授权边界。保留原始存储解码，不用当前 evaluator 重算覆盖历史依据。
- 按新的接口与数据库合同接通当期消费者。开发期间没有旧接口兼容承诺，但每个完成阶段都应可以通过 CLI、MCP、页面运行验证。

**验收**：旧谱系、伪造版本、缺标识和结构偏差均被拒绝；同指纹 draft 可关账、备份、恢复；隔离正式测试合同覆盖新增结构、已有表变化、跳版本、未知来源及故障回滚。内容损坏阻止维修与备份，派生数据可受控修复且版本可见，业务 epoch 与维修版本职责清楚。接口、金额精度、调用方和权限测试随改动通过。

**边界**：只处理通用层。旧关账采用适配归阶段 3，旧身份路径归阶段 4，旧备用金模型归阶段 5，旧工资／资料／政策兼容归阶段 6；不把全仓库旧兼容删除挤进本阶段。不触碰真实资料根，不在此冻结正式 v1，不增加同账户隔离工程或额外工资密码确认。

### 阶段 3：期间、历史读取与关账内核

**状态**：完成。期间规则、发布链、直接关账、投影、读取和当期消费者已接通；回归、性能对照及独立包通过。实际数字、发现并修正的问题及成本边界见[阶段 3 文档](kernel-refactor-stages/03-periods-history-close.md)，不把后端耗时称为整页达标。

**交付**

- 已决定开放月份按所属月入账，不提供任意分离；闭期迟到及冻结更正明确指定开放入账月，原有合法所属月纠错保留。
- 统一当前有效、历史还原、当时冻结与开放期增量口径；建立按入账期、类别、对象归集的余额变动读取，独立期初不混入本期发生额。
- 新关账明确保存实际采用的精确结果、必要引用与冻结链，区分凭证拥有者、无行状态和批次成员。完整依据沿不可变依赖追溯，不能把依赖出现等同于采用。
- 退出旧 manifest、旧期初／资产采用推断等兼容分支；新结构从首次关账就完整保存采用依据。正常业务历史、已发布结果与冲正链继续保留。
- 整理未结事项汇总、批量关系读取与复用失效条件，减少跨请求推导、重复校验及逐条装载；分别测量累计链与独立业务的关账、核验、读取和存储增长。

**验收**：同口径看板／报表一致；当前还原与冻结入口清楚；账户历史查询随目标范围装载，完整核验保持有效。跨月更正、累计归零、独立期初、无行结果和精确采用均有测试。第 30、34、37、38 项以端到端测量证明减少实际工作量，主页面未结 KPI 继续可用。

**边界**：不等待身份或备用金重写。以少量明确的保存结果、余额和精确引用合同完成公共能力；后续各域在当期声明并测试接入，不引入泛化框架。不得降低校验保护，不假定全部增长均为二次，不重试第 24 项已回退方案，不在失效条件未定义前增加跨请求缓存。

### 阶段 4：身份、查重与事实发现

**状态**：完成。基线 `d810a8b`，对象登记、原子纠错、查重、分页及消费者已接通；回归、性能对照和独立包通过，实际结果见[阶段 4 文档](kernel-refactor-stages/04-identity-and-discovery.md)。

**交付**：建立登记前查找、明确复用、身份候选与有依据纠错；名称与稳定身份分离。纠错覆盖开放期重算、工资累计、个税、清偿和冻结后的更正，保留旧事实与冻结记录，不把别名当作修复，不放开普通 amend 自由改身份。增加现实业务疑似重复候选，保留幂等、领域唯一性和防重复核销；优化 `find_facts` 筛选、排序、游标和批量装载。

**验收**：人员身份分裂、同月冲突、既有清偿与闭期更正有明确影响预览和处理结果；候选用代表性样本测误报／漏报后确定规则，不仅凭姓名、外部编号、原件或金额相同就自动合并或拒绝。稳定业务身份唯一性和防重复核销仍有效。小页、无期间与人员筛选限制实际工作量，CLI、MCP、页面接通。

**边界**：已批准强候选先核对，AI 先查资料，仍无法判断才问负责人；弱线索不打断。当前名单按纠正后身份展示，详情保留旧身份及纠错过程，已关账内容原样。不增加逐笔批准或页面布局，真实业务冲突不用技术默认值解决，普通修改不能任意改身份。备用金简化和工资确认分别留在阶段 5、6。

**状态**：完成。起点 `ac91752`，三渠道直接收付、工资拆分、旧模型退出及当期消费者已接通；回归和独立包通过，实际结果记入[阶段 5 文档](kernel-refactor-stages/05-managed-reserve.md)。

**边界**：不建立公司钱包，不管理账外余额，不把旧债务结清或退款权利当作实际退款，不借新结构保留旧容量机制。
