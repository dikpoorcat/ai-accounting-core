# 内核重构路线图

## 1. 用途与执行方法

本文把[内核架构审查](kernel-architecture-review.md)确认的问题排成可执行阶段。全局架构、信任边界和不变量只以[内核重构架构](kernel-refactor-architecture.md)为准，本文不重复定义。

执行遵守以下约定：

1. 按阶段 0 至阶段 9 顺序推进，每次只实施一个阶段。阶段 1 已完成，本次工作结束；阶段 2 至阶段 9 后续按当次任务推进。
2. 每个实施阶段开始时，才在 `docs/kernel-refactor-stages/` 建立一份细化文档，文件名为 `<两位阶段号>-<英文主题>.md`。本阶段不创建空文件或模板。
3. 细化文档要把当期问题落实为数据结构、命令、读取契约、迁移、调用方、测试和回退边界。普通技术选择由实施设计解决；只有影响业务处理或产品体验的实质选择，才拿出具体方案请负责人决定。
4. 每个阶段结束时，CLI、MCP 和页面必须保持可用，当期变更涉及的调用方与测试必须同时接通。验证范围按改动风险确定，不设置脱离改动范围的固定全量门禁。
5. 原审查中的公司样本、计数、耗时和测试结果只代表当时的历史记录，不得写成当前运行结论。新阶段只记录当期实际完成的验证。
6. 信任模型沿用架构文档和原审查 §1.1 的信任链。实施时保留既有保护，但不为每次改动另做一套逐项保护证明。
7. 不因生产样本为零而删除能力。定期备份与跨公司配对继续作为未来项，不混入本轮阶段。

每阶段按“细化设计 → 实施 → 验证 → 修正 → 更新文档 → 结束本阶段”执行。阶段文档写清目标和边界、具体改法及接口和数据变化、实施步骤与验收场景，以及实际结果、遗留问题和后续影响。缺陷在当期解决，不留给阶段 9；整体设计发生变化时，直接改写架构文档，本文同步调整阶段安排。

## 3. 分阶段计划

### 阶段 0：架构与路线图定稿

**状态**：完成。

**交付**

- 完成 `docs/kernel-refactor-architecture.md`，统一目标架构、边界和实施原则。
- 完成本文，固定阶段顺序、验收条件、问题归属和明确不做的事项。

**验收**

- 两份文档互相一致，没有把方向性建议写成已实现能力。
- 原审查 §5.1 的 1–45 及 10b 共 46 项均有唯一主阶段或明确的保留、排除、未来状态。
- 各实施阶段都有明确交付与验收条件，前置依赖没有循环，可以逐阶段细化和实施。
- 未决定的产品选择保留待决定状态，没有写成负责人已经批准。
- 阶段 1–9 没有被提前实施，也没有创建空的阶段细化文档。

**前置依赖**：原审查结论与负责人已经作出的业务取舍。

**边界**：只改两份主文档；不改代码、数据库、真实资料和原审查，不运行实现测试，不提交 Git。

### 阶段 1：业务定义、接口合同与迁移基础

**状态**：完成。具体实现、验证结果和既有测试差异见[阶段文档](kernel-refactor-stages/01-contracts-and-migrations.md)。context／funds 已完整接入，其余读取合同仍由后续阶段逐步迁入。

**交付**

- 集中科目、税种和资金科目等重复业务定义，明确仍由计算器控制的封闭边界，先消除发布与查询的双份映射。
- 为读取响应建立共享、可验证的合同来源，保留 HTTP 金额字符串、MCP 整数分以及运行时数据校验。
- 建立已有表受控前向演进和可审阅的迁移写法；目录 v1–v3、公司 v1–v12 的冻结合同和已发布快照继续只读，保留已知历史 v10 形态的升级支持。
- 把 SQLite 生成 SQL 原文属于结构合同的事实纳入迁移设计，文本变化按新版本处理。
- 接通受影响的 CLI、MCP、前端类型、运行时校验和测试；同时核对科目扩展对页面的影响，以及“本月非零、累计为零”等展示口径。

**验收**

- 同一业务含义不再由发布、查询、报表和义务判断各自维护；已有付款类型的资金科目映射有直接一致性验证。
- 一次后端读取合同变化能让前端类型和运行时校验同步失败或同步更新，金额精度边界没有退化。
- 已知旧结构能通过前向迁移升级，未知结构仍拒绝；迁移失败原子回滚，旧合同指纹保持不变，迁移差异可直接审阅。
- CLI、MCP 和页面通过同一合同工作；受影响的迁移、接口和展示测试通过。

**前置依赖**：阶段 0 完成。

**边界**：不把全部科目和税种一律数据化，不把精确匹配一律改成前缀匹配，不回写冻结快照，不在本阶段重做身份和历史读模型。

### 阶段 2：依赖、写入检查与内容核验

**状态**：未开始。

**交付**

- 统一依赖匹配语义，贯通 `reads()`、`scopes()`、实际读取、`context.used`、`checked_lanes`、epoch 校验和下游失效传播；测试辅助不再另写一套选择规则。
- 按权威来源区分可恢复的引用目录与必须保留的历史依赖，为可恢复目录提供受控验证和修复路径。保留 `read_index_source` 的统一摘要锚及 close 来源的轻微冗余。
- 补足正式事实、有效计算、凭证行、凭证版本、投影和关账冻结结果之间的内容核验；投影修复若改变可见结果，消费者必须看到版本变化，并完成全科目交叉核验。
- 让删除预览、事务内当前版本检查和最终删除覆盖同一组 lane 与同一审阅对象。
- 为关键读取职责明确允许的范围、实际工作量和失效行为，不把跨类型读取误改成字面量 `kind='*'` 筛选。
- 对目录库、公司库、边车文件和备份沿用现有平台文件权限能力，统一创建、打开和恢复时的权限基线。
- 准确记录私有通道尚未完成运行攻击验证，以及同账户进程能控制文件时的授权边界。

**验收**

- 期间域、通配域、主体域和具体类型域的真实引擎行为均有机制级与业务结果验证；漏记读取会被测试发现。
- 引用目录可从对应冻结源受控核验或修复，历史作用域与当时实际读取记录不被当前代码重算覆盖。
- 内容核验能发现总额变化，也能发现总额不变但科目或行内容变化；有效版本、历史版本和独立期初处理清楚。
- 投影修复前后如读取结果变化，CLI、MCP 和页面的快照版本随之变化；关账前完成全科目写模型交叉核验。
- 已复现的 material lane 删除竞态被阻断，并核对其他 lane 的实际影响。
- 文件权限基线在支持的平台按现有能力执行；文档和界面不声称已获得同账户隔离。

**前置依赖**：阶段 1 的合同和迁移基础。

**边界**：不删除历史依赖，不把所有目录当投影重建；不声称库内自洽能抵御同时改写全部记录；不增加操作系统隔离、另一设备、新签名备份或额外工资密码确认。私有通道按本阶段实际核对结果记录，未完成实测不得声称已经验证。

### 阶段 3：身份、查重与事实发现

**状态**：未开始。

**交付**

- 建立身份登记前查找、明确复用、候选提示和有依据纠错的统一能力，展示名称与稳定身份分离。
- 设计身份纠错对开放期重算、累计依赖、代发、已关账结果和更正链的影响；不把别名本身当作历史已修复。
- 增加现实业务疑似重复候选，保留幂等、领域唯一性和防重复核销；候选只提供线索，不自动判重。
- 优化 `find_facts` 的筛选、排序、游标和批量装载，使无期间、小页和人员筛选能限制实际工作量。

**验收**

- 登记前可以按有用条件找到既有身份；纠错有明确依据、影响预览和开放期／闭期处理路径。
- 身份候选和业务重复候选分别用代表性样本测误报与漏报，再确定阈值；姓名、编号、原件或相同金额不能单独触发自动合并或自动拒绝。
- `find_facts` 保留全部筛选与游标语义，返回量增加时不再逐行完成相同装载工作，小结果集可提前停止。
- CLI、MCP 和页面能展示候选、影响范围和处理结果，调用方不需要猜测身份关系。

**前置依赖**：阶段 1 的合同；阶段 2 的依赖和版本检查。

**边界**：不自动合并身份，不预定别名表，不恢复备用金退款额度。身份模型、查询结构及收款账号与资金账户的技术分层由实施者决定；检索用法、弱候选展示和纠错后的页面呈现如有实质取舍，拿出具体方案请负责人决定。

### 阶段 4：工资、资料与期间规则

**状态**：未开始。

**交付**

- 将本月工资方案、变更通知或明确无变化的复用依据贯通到正式工资发布，保留负责人确认控制。
- 为闭期后补录资料产生的问题安排明确承接和阻断责任；关账和完整代发继续使用同一完整性检查器。
- 统一政策来源 URL 的核算语义和可核对要求，处理历史兼容。
- 清理 `material_revision.processed` 死列及相关接口语义。原审查样本中的 `expected == received` 只表明计数自洽，不是逐项覆盖证明。
- 明确所属期、入账期、迟到业务和闭期更正的合同；阶段开始时保留当前语义，再根据具体方案决定是否允许两个开放月之间主动分离入账期。
- 把 `tax_import` 中新增个人扣款成分无法映射的问题提前到能采取行动的检查环节，并保留明确拒绝。

**验收**

- 未经当月负责人确认或不满足复用条件的工资不能正式发布；确认依据和工资结果的版本关系可核对。
- 归属已关账月份的迟到资料问题不会静默停留在 `file_status`，也不会以全局文件状态误伤合法未来月份。
- 调用方能从合同理解两个期间及更正条件，管理归集字段不会替代核算所属期。
- 政策来源和 `tax_import` 映射问题在 CLI、MCP、页面均以结构化、可处理的结果呈现。
- 资料完整性、工资发布、期间边界和导出映射的当期测试通过。

**前置依赖**：阶段 1 的合同和迁移；阶段 2 的版本、依赖与内容核验。

**边界**：不擅自增加开放月份间主动分离入账期；不因 `tax_import` 在历史生产样本中未使用而删除它；不以文件级总状态阻断所有月份。

### 阶段 5：备用金简化

**状态**：未开始。

**交付**

- 将备用金收敛为两类清楚业务：实际转入时计管理费用，实际退回公司时按回款冲抵管理费用。
- 让业务事实直接表达“备用金支出”或“备用金退款”，不再通过范围间接决定会计性质。
- 为已有范围、成本资格、容量、占用、接续和历史记录设计前向迁移与兼容读取；新业务路径不再要求这些资料。
- 保留工资付款中净薪与备用金的明确拆分。既有业务更正或转换使用专用入口，处理相关引用与下游，不扩大普通修改权限。
- 接通真实收付证据、重复识别、凭证、看板、CLI 和 MCP。

**验收**

- 一笔转入和一笔部分退款可独立完成登记、预览、发布、查询和展示，金额只取实际收付。
- 新路径不计算备用金余额、最大金额、可退额度，不要求范围、成本来源目录、逐笔分配或 FIFO。
- 工资拆分合计等于实际银行流出，工资不能被重复核销；实际退款与工资付款分别按真实资金事实处理。
- 旧记录仍可按其历史语义读取和更正，迁移不会把旧容量关系伪装成新模型事实；旧债务结清或退款权利不能自动认作实际退款。
- 相关调用方和测试改为新业务语言，不再向负责人追问内部消费和剩余额度。

**前置依赖**：阶段 1 的迁移与合同；阶段 2 的核验；阶段 3 的重复候选能力。

**边界**：不建立公司钱包模型，不恢复账外余额管理，不用新结构继续维护旧容量机制。

### 阶段 6：历史读取与关账表示

**状态**：未开始。

**交付**

- 统一当前结果、历史还原、当时冻结和开放期增量的读取口径，增加按实际入账期、类别和对象归集的余额变动投影。
- 新关账直接记录本期实际采用的精确结果和必要引用，完整依据沿不可变依赖追溯；旧 manifest 及关账格式保留明确适配。
- 分别测量累计链与独立业务的关账、验证、读取和存储增长，用于细化新表示及索引，并验证减少重复保存和展开的效果。
- 基于阶段 2 的内容核验与版本机制，处理投影修复和历史基线，避免把投影错误冻结成权威。
- 减少跨请求重复推导、读路径重复校验和关系逐条装载，整理未结事项汇总读模型；明确复用与失效条件，结构调整后再评估缓存。

**验收**

- 重要账户级历史查询不再依赖扫描全部历史；有效版本、冲正和独立期初衔接正确，相同口径在看板与报表得到相同结果。
- 当前还原与当时冻结有不同但明确的读取入口，CLI、MCP 和页面不会混用。
- 新旧关账均可读取，跨越表示变化的期间能够接续；精确历史采用关系、冻结结果和阶段 2 的内容核验保持成立。
- 第 30、34、37、38 项的方案以端到端测量证明减少实际工作量；未结事项 KPI 继续在主页面可用。

**前置依赖**：阶段 1 的迁移和合同；阶段 2 的核验和版本机制；阶段 5 的备用金新模型。

**边界**：不为减行数丢失历史采用依据，不假定全部关账增长都是 O(n²)，不重试已回退的 `close_rows` 两段式方案，不在定义失效条件前直接加入跨请求缓存。

### 阶段 7：老板核对与看板

**状态**：未开始。

**交付**

- 将阶段 1 的共享读取合同完整接入看板，修复清偿事件 `state` 标签及相关展示漂移。
- 在同一版月度关账预览中呈现负责人能理解的业务摘要、试算结果、资料状态和实际采用的政策、工资依据及来源，再由现有密码重认证批准。
- 采用整月统一批准，不增加逐笔勾选或逐笔认领流程。
- 将正式流程限定为单公司逐月关账；正式 CLI、MCP、页面和操作说明移除批量关账入口，测试准备、回放和验证可保留内部批量能力。
- 对审计调用来源说明和专门的可读变更流水提出具体产品方案，由负责人决定是否纳入；不把两项写成已批准新增能力。

**验收**

- 负责人看到的内容与密码批准所绑定的 digest 和 epochs 是同一版本；状态变化后旧批准不能继续消费。
- 看板能显示实际采用依据、未决状态和月度关账内容，金额和 issue 展示选择有明确、一致的合同。
- 页面不再暴露正式批量关账，单公司逐月流程端到端可用；测试专用能力不进入正式操作协议。
- CLI、MCP、页面和前端测试同步采用共享合同；科目扩展和“本月非零、累计为零”的场景有验证。

**前置依赖**：阶段 1 的读取合同；阶段 2 的版本和内容核验；阶段 4 的政策与工资依据；阶段 6 的历史读取。

**边界**：保留密码重认证、摘要和版本绑定；不把哈希当作人类可理解内容；不增加逐笔认领。审计入口来源和独立变更流水只有在本阶段明确选择后才实施。
