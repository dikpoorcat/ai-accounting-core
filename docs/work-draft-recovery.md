# 事项工作稿恢复

工作稿保存尚未登记的候选输入、来源、剩余问题及已收到的回答，让同一资料根内的服务重启后可以接续。公司、月份和事项由当前会话、明确选择及工作清单确定；工作月份不替代资料实际所属期。正式事实、采用、待重算、完成和批准仍以当前内核为准。

## 四个入口

MCP 使用 `finance_local_command(command=..., payload=...)`，CLI 使用 `finance-local call <命令> --input <请求.json>`。先取接口概要，再按需选择命令与响应合同。

| 命令 | 必须明确的字段 | 行为 |
|---|---|---|
| `list_work_drafts` | `company_id` | 可筛选 `period`、`work_area`，默认100条、最多500条，沿 `cursor` 续读；只列月份和事项，不自动选最新稿。 |
| `read_work_draft` | `company_id`、`period`、`work_area` | 返回完整正文、`revision` 和提示；不存在时明确返回。 |
| `save_work_draft` | 上述范围、`expected_revision`、`draft` | 初建显式传 `null`，更新传读取的版本；整稿原子保存，只返回结果和新版本。 |
| `delete_work_draft` | 上述范围、`expected_revision` | 删除同版有效稿，不影响正式业务。 |

`work_area` 沿用 `bank`、`payroll`、`transactions`、`tax`、`assets`、`financing`。目录从当前身份命名空间的服务文件名发现范围，不解析所有正文，不承诺文件已经验证。目录项可能随后被并发删除，以精确读取为准。

## 正文和保存节点

正文各项可省略，省略保持省略：

| 字段 | 内容 |
|---|---|
| `candidates` | 每项包含稳定 `id`、现有目标 `command` 和原始 `payload`；允许缺正式必填字段。 |
| `source_refs` | 证据、来源、业务、事实版本和原位置引用。 |
| `questions` | 稳定 `id`、`question`、可选原话 `answer` 和来源引用；回答只适用原展示范围。 |
| `resume_note`、`next_step` | 接续位置与下一步说明。 |
| `pending_requests` | 正式命令、完整原 `payload` 和原 `request_id`。 |
| `result_refs` | 正式请求、业务、事实版本或任务编号，恢复时继续核对内核。 |

保存只检查结构、合法JSON、目标业务入口和已提供的事实类型，不调用完整业务模型补默认值。通用候选不能绕过专用登记入口；类型尚不明确时保存问题和笔记。金额使用整数分，小数使用十进制字符串。候选仍未经过完整业务验证，不能成为登记或批准依据。

以下合成例子尚缺正式字段，可以保存，不可直接登记：

```json
{
  "company_id": "<当前公司编号>",
  "period": "2026-03",
  "work_area": "transactions",
  "expected_revision": null,
  "draft": {
    "candidates": [{
      "id": "office-service-candidate",
      "command": "save_fact",
      "payload": {"kind": "expense", "data": {"amount_fen": 12800}}
    }],
    "questions": [{
      "id": "creditor-kind",
      "question": "这笔费用是供应商应收，还是员工垫付？"
    }],
    "resume_note": "先查已有来源，仍有歧义再确认。"
  }
}
```

收到新资料或负责人回答、完成一批核对、准备追问或正式提交时保存。更新用当前版本，冲突先重读并合并；保存成功才说明已保存，结果未确认时重读。工作稿不捕获模型内部思考，保存节点之间的内容也不承诺恢复。

## 中断后接续

1. 重读接口概要，绑定公司并核对清单；范围未知时列出草稿供选择，不猜最新工作月份或改推进顺序。
2. 读取当前稿，再用 `work_context` 核对当前事实、来源及正式进度。文件和业务库各自读取，不宣称同一事务快照。
3. 复用已保存候选、回答和可核查来源，必要时续读原文或历史依据；只问仍会改变处理的缺项。
4. 正式写入前保存完整命令、原载荷和原请求键。未判明请求不能随候选编辑丢失；恢复先查 `request_result`。`unknown` 不等于失败，需要重放时保留原载荷和原键，不自动换键重做。移除旧待判明请求时，服务核对当前公司、数据库和原请求的已提交回执，并要求留下结果引用；仅填写一个结果引用不能清除未知请求。回执证明原键已提交，不证明工作稿载荷摘要，正式重放仍由原入口核对幂等内容。
5. 处理条件或预览失效时重新准备和核对，旧预览不构成持续有效的批准。正式处理走原入口，成功后保存结果引用，事项完成后重读清单。

准备和预览没有正式回执；目录操作使用 `operations`，安全批准与关账按现有流程，后台任务查询精确 `jobs`，排队成功不等于交付或实际办理完成。

## 文件和故障边界

资料根 `.work-drafts` 复用现有私有权限、文件锁和原子替换，绑定目录实例、公司、数据库和工作范围，路径由服务派生。每范围只留最新版，没有独立索引、历史版本库或跨请求业务状态缓存。

完整UTF-8封装最多8MiB，包含身份、版本、摘要和正文。不设总配额、过期或自动淘汰，明确删除才清除。程序更新不删除稿；当前入口变化时保留原输入并提示核对合同。公司ZIP不包含工作稿，换根不自动接续。

每次保存产生新唯一版本，防止并发覆盖和删除重建后的旧版本误用。替换前失败保留旧稿；替换后同步或响应失败时文件可能已更新，报告结果未确认并重读，删除后响应丢失同理。不承诺硬件断电或磁盘损坏恢复。

损坏、身份不符或格式不支持时保持原样，正常读、写、删除均拒绝，需要另行明确处理；本轮没有强制删除、自动修复或清空。密码、恢复码、会话及批准令牌不进入稿，原件、完整解析和已登记事实从现有入口读取。

## 合成验证和比较

临时合成公司覆盖不完整及专用候选、回答、重启、公司／期间隔离、跨月引用、版本冲突、删除重建、损坏、超限、权限和写入故障。正式提交仍应完整验证，工作稿不得改变业务版本、正式进度或ZIP格式。

比较基线是已完成读取链的 `ece2a8d`。独立对话使用同一模型和推理设置，记录恢复完整性、重复追问、工具次数、返回字节、草稿读写、SQL和耗时。插桩工作量与纯计时分开，不估算模型令牌，不预设提速倍数。

## 2026-10-09 验证结果

最终相关回归305项通过、2项平台跳过，耗时152.76秒；Ruff与差异格式检查通过。范围包括工作稿文件、服务、CLI／MCP／HTTP合同、原请求恢复、读取链、私有权限及公司备份。跳过的是通用权限夹具无法创建链接和Windows不适用的POSIX模式检查；本轮新增的实际悬空链接检查通过。完整模块清单、构建身份、分阶段指标及合成恢复证据见 [比较记录](work-draft-recovery-results.json)。

验证没有修改公司或目录数据库结构、看板、AGENTS.md，没有写入真实业务、重启现有服务、提交或推送Git。测试服务使用临时合成公司，验证后已停止。

### 实际 AI 对话

两版各进行一次独立对话，使用相同的继承模型和推理设置，没有覆盖设置。两笔办公服务资料于3月收到，已归属2月，第二笔缺债权人类别。首次对话两版都只追问该缺项；收到负责人“第二笔也是供应商”的回答后先停止，不登记或发布。新版保存候选和回答，基线没有对应保存入口。随后重启各自合成服务，并用没有旧对话历史的新智能体恢复。

| 恢复结果 | 读取链基线 | 加入工作稿 |
|---|---|---|
| 成功保存的接续点 | 无法恢复 | 恢复当前版本 |
| 两笔候选及原请求键 | 重新从原件构造，原候选键不可恢复 | 两笔均恢复 |
| 负责人补充回答 | 无法恢复 | 恢复原话并核对适用范围 |
| 重复询问第二笔债权人类别 | 1次 | 0次 |
| 正式登记、发布 | 未执行 | 未执行 |

新版另指出整月资料覆盖尚未确认；这是整月完成范围的问题，与两笔候选已经回答的债权人类别分别记录，不能据此宣称所有问题都已消失。两版均继续核对当前来源和正式进度，没有把工作稿当作登记结果。

### 分开计时的脚本比较

脚本通过实际 MCP → ServiceClient → HTTP → LocalService，分别顺序执行纯计时和工作量两组运行。每个版本每组一次，热读连续3次；恢复阶段包含首个业务调用的进程冷读成本。工作量与毫秒来自独立运行，不能当作同次请求的关联采样。

| 基线，首次资料读 | 2 | 8522 | 220 | 1 | 0／0 | 360.93 |

热读单次中位数116.59毫秒。其余耗时为阶段合计，均包含工具传输成本，不是文件系统微基准。正式登记仍独立读取核验证据；丢失响应后通过原请求编号核对并用原载荷、原键重放，最终只有一条正式费用事实，仍未发布。工作稿恢复没有免除正式核验。

SQL计数是执行的语句数，不表示扫描行数或虚拟机工作量。文件读写计数是Python对专用JSON／临时文件的打开事件，按读写标志归类，排除锁和目录；一次保存包含临时写与发布后同步打开，因此两次保存对应4次写打开。计数不表示文件字节或逻辑保存次数。
