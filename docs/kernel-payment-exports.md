# 新内核的银行代发文件

代发文件是根据已确认应付款生成的付款指令。**生成、重试或下载文件均不代表已经付款**，不会创建银行流水、付款事实或资金凭证。实际银行扣款按实际付款所属月份，通过 `payment` 类型化事实及其核销分配入账，不从工资月份或文件交付日期推定付款月份。

## 第四步完成银行代发

先办当前工作月份，再按八步推进。第2步确认工资方案、适用劳务及个税并登记必要输入，第3步办理社保、公积金，第4步统一办理银行代发，在本步完成本月本次工资、奖金、劳务、报销及代付款的范围确认、必要事实核算、文件生成和交付。完整范围的必要核算、文件核验和交付完成后，继续本月下一步；后月份的实际付款登记不作为本月继续办理或关账的前提。后月份付款信息先保全并保存待办，到付款所属月核对复用，用户明确插办的除外。申报按覆盖期判断归属，不能仅因办理日在后月份而推迟本期必要扣税依据的核对。后续账务、报表及税费事项与银行代发无关，不作为代发的前置条件，也不设置“等后续核算再回补代发”的流程。

第2步确认不因尚未完成第3步而阻止。第4步复用仍有效的确认，关键输入或范围变化只核对变化部分；核对工资、个税与实际个人社保／公积金依据，完成工资净额核算及正式发布，再核销属于当前工作月、已核对但等待工资源核算的个税、社保公积金付款，不回头重复确认已核对缴款。实际缴款和正式入账分别说明。工资、奖金、劳务的净额来自有证据的确认扣税及适用的实际个人承担额，不采用理论计算数，零税也须明确依据。工资实际申报税额与已采用扣税不同且影响代发时，先明确并正式采用 `payroll_disbursement_basis`，保留未付差额，不能按猜测净额生成。

第四步先核对本次拟付款事项和已收资料，在本步补齐相关事实并正式核算，再读取完整候选、核对范围，主动接续预览、同版本确认、持久任务核验和交付，不另等生成请求或关账。模板、收款资料、本项报酬税依据、实际个人承担额、申报差额处置或本次来源核验缺项时，保留具体代发待办，先查已有来源，每轮只问本步同一事项最多3个独立问题，继续第四步其他可办工作并等待补齐，不转到后续阶段补核算。补齐后自动接续，不重复索取已有有效确认，也不降低正式计算和发布门槛。

## 发现来源、金额和收款人

公共命令通过 `finance_local_command` 调用 `export_sources`、`save_payee`、`preview_export`、`confirm_export`；按运行时 `finance_local_schema` 读取准确合同。候选读取和正式导出使用同一组来源资格、付款义务和用途规则，覆盖工资、奖金、劳务、员工及负责人报销、个人代垫、期初报销应付款、期初工资净工资，以及代收代付的转付和退回义务。

`export_sources(period, limit=100, cursor=None)` 是只读命令，按归集月份发现来源，每页默认100条、最多500条，按稳定来源身份排序。返回来源身份、业务类型、核算月份、归集月份、用途、逐项未结义务及核算状态。候选包含已发布、未发布和待重算来源；未发布来源不填写推测金额。读取候选不要求银行模板、收款账号或整月资料齐备，也不表示正式导出核验已经通过。须读取全部分页并与已收资料及拟付款事项核对，候选为空不能证明没有尚未登记的业务。

候选游标绑定公司、数据库、归集月份、核算／材料／管理三个数据版本及读取修复版本，不能跨公司、月份或不同快照拼接。版本变化时重新从首屏读取。保存了 `payment_period` 的来源按这个管理月份归集，未设置时按来源的核算月份归集；归集月份和用途不改变原业务归属期、金额或凭证，跨月归集保留请求月份和实际来源月份。

金额来自正式计算所产生的付款义务及实际剩余余额，真实付款、代垫、抵销和退回等已核销金额按精确义务关联计入余额。已计提的 `labor_accrual`、`labor_project_cost` 先在原来源补充并采用 `remuneration_tax_basis`，重新预览和正式发布原业务后接入净额代发；未确认扣税的毛额应付仍阻断，不能只在导出时减税。

真实报销使用“报销”用途。`pass_through` 向最终收款人的转付义务使用“代付款”，退回义务向原付款人支付并使用“代收款退回”；代收债权不能导出为付款。期初工资只取净工资部分，不把期初个税、社保或公积金款项混入代发。已保存的明确 `payment_category` 继续作为用途，不改写业务性质或历史文件。供应商费用、税款、社保缴款和借款不因都是应付款而自动纳入本次范围，也不根据收款人名称或账户猜测其业务性质。

相同收款人与用途合并成一行，文件最多2,000行。`preview_export` 接收归集月份、已经留存为证据的银行模板摘要，以及可选的业务来源 ID；不接收外部金额、自由分录或覆盖应付款的行数据。

收款姓名、账号和其证据由 `Exports.save_payee` 独立追加版本。账号始终按文本保存，保留前导零。缺少收款资料时返回明确缺项；不产生空账号、默认账号或零金额付款。

## 选定范围与完整范围的核验

显式提供 `source_ids` 时，不论是工资、奖金、劳务、报销、代付款或混合范围，都使用 `selected` 范围，核验所选业务及其直接、传递采用依据，包括实际付款、代垫、抵销、退回等精确关联义务且影响余额的处理。已结清但明确选择的来源仍参加核验。相关人员、金额、期间、正式发布、待更正及失效结果逐项检查，缺收款身份和账号仍阻断；无直接或传递关联的整月资料、税费和普通账务不阻挡本次选定付款。文件只代表本次范围，不声称整月完整代发。

选定范围复用同一资料完整性检查器。相关原件整份解析并核验未处理行、隐藏内容、控制合计、金额、期间、重复资料和竞争来源。可见文字签章页脚中由解析器补造的空金额位置，复用当前来源精确版本已有的 `no_accounting / not_company_business` 空金额处置；必须有明确理由且无核算链接，不按关键词跳过原行，也不豁免真实不明金额、公式错误、隐藏内容或控制合计。相关原件核验范围内或未知归期的未处理行、闭期承接问题、金额／期间差异及失效结果仍阻断，混合原件的未选行也不豁免；明确属于其他未来期的行只在所属期处理。工资原件按所选薪资及其关联依据的期间核验，混合范围中的报销月份不额外扩大工资原件检查范围。不能裁切原件或减少来源来掩盖相关问题。

省略 `source_ids` 时，选取该归集月份所有符合代发资格的未付义务，并保持整月完整检查。关账始终核验整月；选择含报销或代付款的范围，不再因此切换为整月检查。

## 预览、确认和文件任务

1. 完整读取候选，核对本次范围后，预览在一致数据库快照中读取付款义务、余额、收款资料和管理说明，显式来源使用选定范围，省略来源使用整月范围；范围内未发布业务、待更正结果和资料缺项继续阻断。
2. 确认检查核算、材料、管理三个版本及预览摘要，在一个短事务中保存冻结计划和 `payment_export` 文件任务。`confirm_export.output_directory` 可省略，提供时是导出父目录；默认使用公司内部 `exports`，每个新任务的成果目录由程序分配。确认阶段不读写任意外部文件，也不改变核算版本。
3. `run_export_jobs` 在事务外读取已留存模板并生成四列 XLSX：收款方名称、收款方账号、金额、附言／用途。姓名、账号、精确到分的金额和用途全部写为文本，并回读核验。
4. 任务成果目录同时保存 `银行批量代发.xlsx` 和 `代发核对.json`；后者记录任务、原预览摘要、来源计算版本、收款资料版本、文件校验值和生成语义。按 `jobs` 成功结果定位并核验后，用会计 Skill 的桌面复制脚本交付两份成果；相同内容复用，不同内容自动另名保留。

同一请求 ID 重试返回同一任务，旧任务仍沿用原保存的精确输出路径，不改写原载荷或改用新默认目录。文件任务采用进程锁；数据库写事务只用于领取任务和记录完成结果。文件生成失败可以重试，崩溃遗留的 `running` 任务可以恢复。如果文件已经发布但完成状态尚未落库，重试会核对任务身份、摘要和实际单元格后复用文件。已有无关目录或内容不一致的文件不会被覆盖。

计划一经确认便保留原金额、用途和收款资料。已有任务须核对是否完整覆盖本次来源、金额和收款资料，仍适用时可以复用；新来源、金额、用途或账号变化时，重新预览并生成新任务，不改写历史任务。候选为空、范围已经保存或旧任务成功，都不能代替本次文件交付的核验结果。核对当前版本后再用于银行操作，无未付余额时不生成空文件。
