# 新内核的银行代发文件

代发文件是根据已确认应付款生成的付款指令。**生成、重试或下载文件均不代表已经付款**，不会创建银行流水、付款事实或资金凭证。实际银行扣款发生后，仍通过 `payment` 类型化事实及其核销分配入账。

## 选取金额和收款人

八步流程第2步确认工资方案、适用劳务及个税并登记必要输入，第3步办理社保、公积金，第4步单独办理薪资代发。第2步确认不因尚未完成第3步而阻止；第4步复用仍有效的确认，关键输入或范围变化只核对变化部分。核对工资、个税与实际个人社保／公积金依据，完成工资净额核算及正式发布，再核销已核对但等待工资源核算的个税、社保公积金付款，不回头重复确认已核对缴款；实际缴款和正式入账分别说明。随后主动调用代发表预览、同版本确认、持久任务核验和交付，并跟踪实际银行代发，不自动执行银行付款。按明确归集月及工资、适用劳务 `source_ids` 生成，标明 `selected` 范围，不声称全月完整代发，也不混入无关报销。有效已有任务及产物先核验复用，避免重复生成；无未付余额不生成空文件。

模板、收款资料、本项报酬税依据、实际个人社保／公积金依据、申报差额处置或本次来源核验缺项时，保留具体代发待办，先查已有来源，每轮只问当前阶段同一事项最多3个独立问题，继续本阶段其他可办工作并等待。第4步薪资代发按第2、3步取得的真实依据办理，不回到第2步重复确认，不补默认值，也不降低正式计算和发布门槛。其他真实后阶段依赖按[会计工作流程](local-kernel.md#工作清单外部办理与恢复)保留具体待办，按八步顺序推进，不跳过中间阶段；取得依据后说明回补及返回位置。已有适用依据可直接复用，补齐后按当前阶段或回补点自动接续，不另问是否允许继续。工资、奖金、劳务的净额来自有证据的确认扣税及适用的实际个人承担额，不采用理论计算数；零税也须明确确认。工资实际申报税额与已采用扣税不同且影响代发时，先明确并正式采用 `payroll_disbursement_basis`，保留未付差额，不能按猜测净额生成。

公共命令通过 `finance_local_command` 调用 `save_payee`、`preview_export`、`confirm_export`；按运行时 `finance_local_schema` 读取准确合同。`preview_export` 接收归集月份、已经留存为证据的银行模板摘要，以及可选的业务来源 ID。不接收外部金额、自由分录或覆盖应付款的行数据。

显式提供 `source_ids` 且全部是工资、奖金或劳务来源时，使用 `selected` 薪资范围：核验本次来源及其直接、传递采用依据，包括个税、社保、公积金支付依据和实际核销工资余额的付款来源。相关人员、金额、期间、正式发布、失效结果及来源完整性逐项检查；无直接或传递依赖的普通业务和无关材料不阻挡本次薪资代发。文件只代表本次选定来源，不声称整月完整代发，不新增公共参数或响应字段。

选定范围仍使用同一资料完整性检查器，相关原件整份解析，核验隐藏内容与控制合计，并保留重复资料及竞争来源关联范围。混合原件中本次归集月、来源月核验范围内或未知归期的未处理行（含未选薪资及普通业务）、由本次期间承接的闭期问题、金额／期间差异及失效结果仍阻断；明确属于其他未来期的行只在所属期处理，不新增跨期门禁。不能裁切原件或减少选定来源来掩盖相关问题。省略 `source_ids` 时，选取该归集月份全部未付工资、奖金、劳务和明确归属员工的报销，并保持原整月完整检查；指定来源中包含员工报销时也保持原整月完整检查。关账继续核验整月。供应商费用不会因为收款人名称或账户看似个人而变成员工报销。

金额来自当前正式计算所产生的应付款及其剩余余额，已核销的真实付款自动扣除。相同收款人与用途合并成一行；文件最多 2,000 行。工资、奖金、劳务、报销具有明确的默认用途，也可使用已保存的 `payment_category` 管理说明。

保存了 `payment_period` 的来源按这个管理月份归集；未设置时按来源的核算月份归集。归集月份和用途都不改变原业务归属期、金额或凭证。跨月归集保留请求月份和实际来源月份，按上述薪资选定范围或整月范围核验各自来源、期间及相关原件，不把归集月当作业务所属月。

收款姓名、账号和其证据由 `Exports.save_payee` 独立追加版本。账号始终按文本保存，保留前导零。缺少收款资料时返回明确缺项；不产生空账号、默认账号或零金额付款。

## 预览、确认和文件任务

1. 预览在一致数据库快照中读取应付款、余额、收款资料和管理说明，按来源选择确定薪资选定范围或整月范围，复用同一资料完整性检查器；范围内未发布业务、待更正结果和资料缺项继续阻断。
2. 确认检查核算、材料、管理三个版本及预览摘要，在一个短事务中保存冻结计划和 `payment_export` 文件任务。确认阶段不读写任意外部文件，也不改变核算版本。
3. `run_export_jobs` 在事务外读取已留存模板并生成四列 XLSX：收款方名称、收款方账号、金额、附言／用途。姓名、账号、精确到分的金额和用途全部写为文本，并回读核验。
4. 输出目录同时保存 `银行批量代发.xlsx` 和 `代发核对.json`；后者记录任务、原预览摘要、来源计算版本、收款资料版本、文件校验值和生成语义。

同一请求 ID 重试返回同一任务。文件任务采用进程锁；数据库写事务只用于领取任务和记录完成结果。文件生成失败可以重试，崩溃遗留的 `running` 任务可以恢复。如果文件已经发布但完成状态尚未落库，重试会核对任务身份、摘要和实际单元格后复用文件。已有无关目录或内容不一致的文件不会被覆盖。

计划一经确认便保留原金额和收款资料。之后新增付款、更正业务或修改账号，不会改写历史任务；需要反映新状态时重新预览并生成新任务，核对当前版本后再用于银行操作。
