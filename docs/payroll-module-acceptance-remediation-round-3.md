## 2. P0 阻断整改

### R3-001：按员工和税年线性化累计个税确认

对应前轮：R2-001。

当前确认只对查询到的后续税月状态槽执行 `FOR UPDATE`。当员工本税年尚无状态行时，空范围不产生锁；两个事务可分别插入一月和三月，两个批次都基于看不到对方的累计状态入账。

必须实现：

- 为 `(org_id, employee_id, tax_year)` 建立真实可锁定的顺序域，可使用持久化 guard/年度状态行；不得依赖空范围锁、进程锁或单连接顺序。
- 预览只提供早期提示；确认必须在同一数据库事务内先取得顺序域锁，再重读已入账状态、验证计算版本并写批次、状态槽、事件和凭证。
- 同一员工同一税年不同税月并发确认必须只有一个可按其快照成功；另一个在取得锁后必须重算或稳定返回 `LATER_PAYROLL_TAX_STATE_EXISTS`/`STALE_PAYROLL_CALCULATION`，不得双双 `posted`。
- 多员工批次以确定顺序取得全部年度锁，避免死锁；任一员工冲突时整批原子失败。
- 冲正与合并奖金确认使用同一顺序域，避免确认与冲正互相越过。

最低测试：同步屏障控制的一月/三月双连接并发、同月普通工资/合并奖金并发、确认/冲正并发、多人反向锁顺序，以及失败事务无残留批次、槽、事件和凭证。

### R3-002：在数据库中约束税务状态槽和奖金依赖的业务形状

对应前轮：R2-002、R2-001。

当前复合外键只保证同企业。直接 SQL 已成功让员工 A 的合并奖金引用员工 B 的普通工资，并把员工 A 二月状态槽的普通批次指向员工 B 五月单独计税奖金、最终批次指向另一普通工资。正式状态槽也可任意插入、改月和删除。

必须实现：

- 规范保存工资行所属员工、支付税年税月和批次类型所需的关系键，使 PostgreSQL 能验证依赖，不得依赖 JSON 或服务层先查。
- 合并奖金依赖必须指向同企业、同员工、同实际支付税年税月、状态为正式的普通工资行/批次。
- 状态槽的 `regular_batch_id` 必须指向该员工该税月普通工资；`final_batch_id` 只能是该普通工资或合法依赖它的同员工同税月合并奖金。
- 单独计税奖金不得进入综合所得状态槽。
- 正式状态槽禁止任意改员工、税年、税月或删除；只允许有数据库可验证前置条件的普通工资 → 合并奖金 → 冲正恢复转换。
- 删除 `service.py` 中以请求 JSON 决定唯一依赖或冲正顺序的逻辑；JSON 仅作不可变审计快照。

最低 PostgreSQL 测试：跨员工、跨月、错误奖金类型、草稿/拒绝批次引用、任意槽增删改、合法合并与恢复，以及两个连接争夺最终批次。

### R3-003：冻结逐险种代扣权利并绑定工资行正式事实

对应前轮：R2-003。

正式工资后仍可增删改 `payroll_withholding_entitlements`。实测工资行个人社保为 0 分时，事后插入并放大养老权益到 100 分，再成功分配并支付 100 分。当前守恒只相对于可变权益金额成立。

必须实现：

- 工资确认事务在批次转正式前生成完整逐员工、逐组、逐险种权益；转正式时延期验证权益集合与不可变工资行快照及社保、公积金、个税总额逐项一致。
- 批次正式后禁止权益 INSERT、UPDATE、DELETE；不得允许把权益移入或移出正式批次。
- 支付分配只能引用正式、未冲正工资行的既有权益；逐项未冲正累计不得超过权益金额。
- 分配记录采用可追溯冲正或追加式状态，禁止事后改金额、改权益或物理删除。
- 权益为零时不得通过省略/新增分项改变守恒；明确规定零金额险种是否存行，并在模型、迁移和服务中一致。

最低 PostgreSQL 测试：正式后权益增删改、工资行为零后伪造权益、改变险种/组/员工、超额与并发分配、支付冲正后再支付，以及确认时权益和工资行合计不一致。

### R3-004：统一最终业务事件状态机和退款冲正语义

对应前轮：R2-005。

当前最终事件更新触发器没有约束 INSERT，可直接插入 `status='reversed', reversed_by_event_id=NULL`。另一方面，完整“客户预收 → 全额退款 → 冲正退款”在服务层先返回 `posted`，提交时因尝试把原事件从 `reversed` 改回 `posted` 被触发器拒绝。

本轮裁决：

- `BusinessEvent.status='reversed'` 只表示该事件被显式冲正，不得再用来表示销售、预收、工资付款等事件已经退款或结清。
- 全额退款保持原业务事件 `posted`；退款、核销、余额和经济状态由退款事件及规范关系表达。冲正退款通过新的冲正事件和核销恢复完成，不得执行 `reversed → posted`。
- PostgreSQL 在 INSERT 和 UPDATE 提交点同时验证：最终事件具有合法事件类型、正式完整凭证；`reversed` 必须有同企业、已正式、明确反向引用原事件的冲正事件。
- 最终事件的事实、日期、规则版本、规则轨迹、请求哈希和状态禁止任意修改；唯一允许的状态变化是满足完整关系的 `posted → reversed`。
- 迁移必须识别旧数据中“退款导致 reversed”的事件，明确安全转换或以诊断拒绝；不得静默改变历史含义。

最低测试：直接插入无链接 reversed、伪造普通事件作为 reversal、跨企业/自引用/循环链接、重复冲正、正常冲正，以及预收/销售全额退款后冲正退款的 PostgreSQL 提交级回归。

## 3. P1 必须整改

### R3-005：把三类更正版本链接入写入、选择和审计

对应前轮：R2-010。

数据库已有 `supersedes_id`，但员工资料、政策和期初状态的服务仍先按同起始日或重叠区间拒绝，构造模型不写替代关系，生效查询也不筛版本链叶节点。三个公开 successor 请求均被拒绝，三表替代计数均为零。

必须实现：

- 请求 Schema、服务写入和查询完整接入 `supersedes_id`；验证同企业、同员工/政策维度、直接 predecessor 存在且未被其他 successor 替代。
- 只允许新版本与明确祖先重叠；非祖先版本仍执行有效期排斥。
- 生效选择只返回给定业务日期上的唯一叶节点；不得以 `first()` 或“多条即模糊”替代版本链解析。
- 同期间期初更正使用新物理行；历史正式批次保持旧 ID 和旧快照。
- 查询返回 predecessor/successor 链；已有下游正式工资时，新版本不得静默重算，必须先按依赖冲正后重建。
- 加入链分叉、跨维度替代、环、自替代和删除祖先的数据库约束。

最低测试：资料、政策、期初三类同期间 successor 成功；跨企业/员工/维度、分叉和环拒绝；叶节点选择；历史批次保持旧引用；新版本下游冲正保护。

### R3-006：把工资事件来源改为可验证的一对多规范链

对应前轮：R2-012。

一笔法定缴款核销两次部分发薪时，轨迹含两个工资支付来源，但规范关系因每事件每种链接仅一行而把 `source_payment_event_id` 写成 `NULL`。关系表还允许把工资发放事件标成法定缴款链接，或把来源指向工资计提；正式后可任意增删改。

必须实现：

- 每个直接来源支付事件建立独立关系行或等价关联实体，不得用 `NULL` 代表“多个来源”；唯一键须允许一笔缴款关联多个来源并防止重复边。
- PostgreSQL 验证链接种类与事件类型、批次、开放项类别和来源事件类型匹配；工资发放、三类法定缴款及冲正分别有明确形状。
- 来源支付事件必须属于同企业、同工资批次/兼容批次，并真实参与本次开放项核销；不能挂任意同企业事件。
- 正式事件的关系边不可增删改；冲正创建自己的关系边并保留原链。
- 查询从规范关系返回全部批次、员工、资料、政策、来源支付和冲正事件；JSON 轨迹只作快照。

最低测试：两笔部分发薪后一次缴款保留两个来源；错误事件类型、链接类型、批次、开放项和来源拒绝；关系增删改拒绝；混合不兼容批次与完整冲正链。

### R3-007：冻结已保存工资批次的证据链

对应前轮：R2-013。

正式批次的 `payroll_batch_evidence` 可被直接删除，查询证据数从 1 变为 0；也可事后插入或替换。已取代与已冲正批次因此不能保证稳定证据数组。

必须实现：

- 预览事务先构建草稿及证据边，再把批次封存为 `calculated`；从封存起证据边禁止 INSERT、UPDATE、DELETE。
- 修改事实或证据必须生成新的 superseding 草稿，旧草稿、正式、已取代和已冲正批次保持原证据集合。
- 确认事件复用同一证据对象并验证集合完全一致；不得确认时悄悄增加、减少或替换证据。
- PostgreSQL 约束证据、批次和事件同企业；正式事件证据链也不可变。

最低测试：封存草稿及正式/取代/冲正批次的证据增删改攻击、重新预览生成新版本、确认集合一致、跨企业和重复证据。

### R3-008：并发冲正必须正确重放幂等结果

对应前轮：R2-004。

两个连接并发提交同键同载荷冲正时，一个返回 `posted`，另一个等待原事件锁后返回 `EVENT_IS_NOT_REVERSIBLE`。第二个事务未在取得锁后重新读取幂等事件。

必须实现：

- 冲正请求在取得原事件锁后重新读取 `(org_id, idempotency_key)` 并比较请求哈希；唯一冲突也必须回读。
- 同键同哈希返回同一冲正事件和凭证；同键异哈希稳定返回 `IDEMPOTENCY_PAYLOAD_MISMATCH`。
- 幂等判断、原事件可冲正检查、冲正写入和状态转换在同一事务中线性化。
- 对工资确认、工资付款和三类法定缴款执行相同并发矩阵，不得只修冲正特例。

最低测试：五类写入和冲正分别覆盖双连接同键同载荷、同键异载荷、不同键争用同一原事件及事务回滚后重试。

### R3-009：以不可变匹配历史支持付款冲正后的银行流水重记账

当前工资付款冲正后，银行流水仍指向已冲正原事件；使用新幂等键和同一真实流水记录正确付款会返回 `BANK_TRANSACTION_ALREADY_MATCHED`，导致纠错闭环中断。

必须实现：

- 建立银行流水与业务事件的规范匹配历史，保存原匹配、冲正事件和后续新匹配；不得为重记账简单清空历史指针。
- 每条流水同一时点只能有一个当前有效匹配；原付款冲正后，其匹配变为“已被该冲正失效”，允许新事件取得新的有效匹配。
- 查询同时返回当前匹配和完整历史；幂等重放不得重复创建匹配边。
- 迁移现有 `matched_event_id` 时保持可追溯，发现矛盾或多重有效匹配则拒绝升级。

最低测试：付款 → 冲正 → 同流水正确重记账；两事件并发争同流水；历史查询；重复冲正；收入、费用等非工资银行事件回归。

### R3-010：计算哈希中的政策快照必须与实际选用规则一致

对应前轮：R2-011。

实测 2026 年 12 月所属期、2027 年 1 月支付的工资，计算轨迹使用 `income-2027`，但 `policy_snapshot.parameters.income_tax.version` 仍为 `income-2026`。哈希证据与实际计算规则自相矛盾。

必须实现：

- 按各自适用日期分别组装社保公积金、综合所得个税和年终奖规则快照，不得复制一个外层政策的嵌套参数后只覆盖部分展示字段。
- 计算器输入、请求哈希、规则轨迹、批次查询和审计日志必须引用同一规则 ID、版本、有效期和官方来源。
- 快照生成后不可变；确认时重新解析规则并与草稿快照/哈希比较，变化则返回 `STALE_PAYROLL_CALCULATION`。

最低测试：跨所属期/支付年、规则生效首日和失效次日、无奖金规则、combined/separate，以及快照任一规则版本与轨迹不一致时确认拒绝。

### R3-011：迁移预检覆盖开放项金额与状态的完整一致性

对应前轮：R2-014。

`0001` 存量可存在 `original=100, settled=100, status='open'`。当前升级预检只验证核销合计和超额，未检查状态；该污染可升级到 head，而新触发器不会自动校验未更新旧行。

必须实现：

- 新增迁移在安装约束前扫描每个开放项的原额、有效核销合计、累计核销、余额和状态。
- 明确并验证 `open/partially_settled/settled/reversed` 等状态与金额组合；任何不一致以稳定诊断终止，revision 保持旧版本且不得半升级。
- 对 head 已存在但污染的数据同样先预检；不得假设只从 `0001` 升级。
- 升级后对全部旧行触发一次延期一致性验证，证明约束不是只保护未来 UPDATE。

最低 PostgreSQL 测试：全额已核销但 open、零核销但 settled、部分核销错误状态、累计字段不符、冲正核销组合、正常旧数据，以及失败后的 revision/数据原样保留。

### R3-012：MCP 预校验错误不得回显原始输入值

真实 FastMCP 在进入工具函数前执行 Pydantic 参数校验；当前脱敏包装捕获不到这一层。额外字段值 `SECRET-123456` 会出现在 `ToolError` 的 `input_value` 中。

必须实现：

- 在 MCP 协议/调用处理边界统一格式化预校验、工具内部、数据库和未知异常。
- 参数错误只返回稳定错误码、字段路径和不含输入值的原因；不得返回 `input_value`、请求片段、SQL、连接串、堆栈或异常 `repr`。
- 保持 Schema 严格和可发现，不得通过关闭 Pydantic 校验或恢复开放字典脱敏。
- 日志如需原始异常，必须与 MCP 响应分离，并对工资、员工、银行和证据字段执行敏感信息策略。

最低真实 STDIO 测试：额外字段、错误类型、超长字符串、伪 SQL/连接串、身份证/银行卡样式和嵌套政策错误；响应不包含哨兵值且包含可定位字段路径。

## 4. 工作包与文件所有权

### 工作包 A：税务顺序、奖金依赖和规则快照

范围：R3-001、R3-002、R3-010。主要修改税务状态模型、工资确认/冲正服务和规则快照。工作期间独占 `service.py` 对应段落，并与工作包 B 共同评审迁移约束。

### 工作包 B：数据库不可变性、事件状态机和迁移

范围：R3-003、R3-004、R3-011。独占 `models.py`、`ledger.py` 和新 `0004` 迁移；负责 PostgreSQL 直接 SQL 攻击测试及元数据无漂移。

### 工作包 C：版本链、来源链和证据链

范围：R3-005、R3-006、R3-007。先由 B 确定关系及触发器，再取得 `service.py` 独占权接入写入和查询。

### 工作包 D：幂等、银行匹配与 MCP 边界

范围：R3-008、R3-009、R3-012。在 A、B、C 合并后实施，避免同时修改支付、冲正和 `mcp_server.py` 共享路径。

### 集成工作包

扩展真实 STDIO PostgreSQL 17 生命周期：每一步从 MCP 和数据库双向核对规则快照、计算哈希、凭证、开放项、逐险种权益、银行匹配历史、证据、来源链、审计和冲正关系；加入失败注入与回滚后检查。不得以直接调用 `FinanceService` 代替 STDIO。

推荐顺序：B 先给出关系和迁移契约；A 与 B 在不共享文件时并行；C 接入规范链；D 收口事务与协议边界；最后执行集成工作包。调度者必须显式交接共享文件所有权。
