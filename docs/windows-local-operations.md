# Windows 本地运行速查

本机使用 `finance-local` SQLite 服务。一个资料根目录对应一个常驻服务；目录库索引多家公司，每家公司有独立业务库。当前开发库属于 `ai-accounting-kernel/2` 的 `draft / 0` 合同，连接时核对类别、版本和完整结构指纹。旧 PostgreSQL、Alembic 及旧 SQLite 库不是本系统的启动或升级来源。

## 启动与登录

在本仓库会话说“启动”，会按 `$accounting-startup` 只准备本地服务、验证 MCP 与负责人登录并打开页面。开始处理真实资料需另说“开始记账”或明确交办业务。

手工启动仓库环境：

```powershell
.\deploy\windows\start_accounting.ps1 -DataRoot D:\会计资料
```

未传 `-DataRoot` 时先使用 `FINANCE_DATA_ROOT`，否则使用仓库 `data/kernel-released`。原开发目录和凭据不自动导入；目录名称不改变当前draft／0结构状态。本轮按用户决定保持现有5173、资料根和身份，不进行正式合同冻结、正式包交付或运行入口切换；已有released隔离测试不授权转换当前库。`-NoBrowser` 只连接服务并返回身份状态；默认打开页面。服务在本机回环地址自动选端口，重复启动复用同一资料根的现有服务。独立运行包可在包目录执行 `finance-local.ps1 --root D:\会计资料 serve`。入口细节见[本地会计工作台启动](local-kernel-startup.md)。

负责人在页面发起设置或登录，密码和恢复码只在本机安全窗口输入。MCP 使用 `finance_local_security` 请求、查询或取消窗口；成功发起窗口不等于完成登录。取消后结束该次尝试。不要把秘密放进业务命令、聊天或终端参数。

页面可打开只表示服务可用。操作前仍要确认 `finance_local_schema` 与 `finance_local_command` 可连接，以及负责人已登录。开发工作区的 Python 命令使用仓库 `.tmp-kernel-venv`，不使用系统 Python。

## 工作与请求恢复

第2步确认工资方案、适用劳务及个税并登记必要输入，第3步核对社保、公积金实际承担额及申报缴款，第4步单独办理薪资代发。尚未办理第3步不阻止第2步确认；第4步复用仍有效的确认，不因阶段切换重复确认。进入第4步并核对工资、个税及实际个人社保／公积金依据后，核算工资净额并正式发布，再主动接续 `preview_export`、同版本 `confirm_export`、`jobs` 成功核验及交付，跟踪实际银行代发，不自动银行付款。使用明确的工资、适用劳务 `source_ids`，标示 `selected` 范围，不混入无关报销；缺项继续第4步其他可办工作并等待，正式计算、发布门槛不变，代发按本次来源及其直接、传递采用依据核验，相关原件整份检查。已有有效产物先核验复用，无未付余额不生成空文件。具体条件见[银行代发文件](kernel-payment-exports.md)。

泛化“开始记账”先调用 `workflow(company_id, as_of)`；指定核算月份时传 `period`，`as_of` 使用实际日期，申报覆盖期单独核对。聊天开场说明公司、期间和当前事项，展示八步完整清单：流水与基础资料；工资劳务与个税；社保公积金；薪资代发；账务补齐与报表准备；财报报送；所得税及其他当期适用申报；收尾核对关账。第5步包含普通业务、资产、融资和影响报表的税费计提；银行在开始收集识别，收尾再次核对完整覆盖、匹配与余额。六类资料与核算状态仍作为完整性检查维度，实际办理和文件交付分别说明。空公司没有可靠月份时不补造起点；有依据的无业务不推定外办不适用。完整步骤见[会计工作流程](local-kernel.md#工作清单外部办理与恢复)。

每个已展示事项完成后重读 `workflow`，展示结果、完整进度及当前阶段下一项工作；完整清单不作为整月资料问卷。当前缺资料或待确认时，继续本阶段条件满足的独立工作并等待答复。后阶段已有资料仅先保全、解析、归期和准备草稿，不提前追问、要求结果确认或正式发布。真实后阶段依赖记录子待办和回补点，按八步顺序推进，不跳过中间阶段；切换前不提前追问，进入对应阶段后正常办理，取得结果时说明回补事项及回补后的返回位置；用户明确插办结束后返回原阶段。已有确认及负责人主动提前提供的明确确认，核对适用范围后复用，不逐项增设允许继续审批。普通重算不一律重新询问，关键事实或范围变化才重新确认。财报核算与报表检查通过后可在开放期冻结导出并记录报送，默认最后关账；原报送快照、采用依据与回执保留，不新增外部事项的关账门槛。中断或切公司后，结合真实状态、适用确认及工作稿中的当前阶段和回补点恢复，未决问题和已有结果均保留。详细安排见[会计工作流程](local-kernel.md#工作清单外部办理与恢复)。

每条写命令使用稳定 `request_id`。响应丢失后，能恢复原载荷就用原键重试；只有编号时调用 `request_result(company_id, submitted_request_id)`。`committed` 返回原动作和保存的结果，`unknown` 只说明当前公司库没有该请求与审计记录，不能据此断定业务失败或另记一笔。改变请求内容或预览失效时重新核对，并使用新键。

`needs_information` 的 `fact_issues` 指向缺少的字段、精度和可复用来源；只在明确下一步时使用 `resolution`。提问前先查证原件、已有记录和负责人此前答复，得到唯一明确答案时采用并保留来源，不因字段未单独填写或接口提示缺项就机械追问。每轮只问当前阶段同一事项最多3个独立问题，包括仍影响处理的缺失、冲突、歧义和必要决定或批准；不以子项打包更多问题。说明已知情况，不把猜测当事实或把推理当授权。技术故障和内容损坏不转成业务追问。

## 数据库结构与故障

普通连接会核对目录库及公司库的系统标识、结构合同和实际 SQLite SQL 原文，只接受当前支持的精确结构，不自动升级、删除、重建或补标识。本轮字段清理使用新建合成公司验证，现库退出后续使用，现库、原件和备份继续保全，现有服务不切换；生产包不提供此前开发结构到本轮结构的迁移或兼容路径。保留的通用机制与历史验证见[开发结构合同](development-database-upgrades.md)。已有文件即使没有业务行也不是可覆盖的新建目标。遇到 `schema_fingerprint_mismatch` 或不支持的库，保留原文件并按诊断处理；真实空库重放须另行明确目标和范围。

`verify_integrity` 只读检查权威内容、发布链及派生数据。确认为派生数据差异后，显式使用 `rebuild` 或 `repair_read_indexes`；两个入口都先核对权威源，在同一事务内恢复所有必要派生目录、金额／冻结派生及已登记读取模型，再完整核验。实际变化才推进读取修复版本一次，失败全部回滚；不修原始源、不更改业务 epochs 或冻结源，普通只读连接不自动维修。不要用 SQL 手工改账或绕过合同检查。

后台备份和文件任务通过 `jobs(job_id=...)` 查询。失败返回稳定 `error_code` 和安全说明，处理明确原因后可对失败任务调用 `retry_job`；自动尝试有上限。`last_error` 是本机诊断内容，不作为公开结果或负责人追问。目录中的公司创建与恢复由 `operations` 查询。

## 页面与安全窗口

页面保持经营简报、资金、员工、资产、财务报表五页。普通记账关账先预览，再由负责人在同版核对内容上通过原生密码窗口批准，最后执行 `close`；页面浏览与窗口批准都不代替正式提交。按已确认重建文档重放时默认使用[专用批量关账](replay-batch-close.md)，在显式启用的公司、数据库及月份范围内接续，不逐月请求密码。报表、申报或付款的文件生成也不代表已对外办理。

页面开发构建和本机运行步骤见[启动说明](local-kernel-startup.md)。旧 `restart_dashboard.ps1`、Docker 容器和 `company_cli check-schema` 不是当前入口。
