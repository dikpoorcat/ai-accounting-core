## 1. 第四轮独立验收结论

第四轮交付的常规门禁全部通过：全量 139 passed，其中非 PostgreSQL 99 passed、PostgreSQL 40 passed；覆盖率 84%；`ruff`、`pip check`、`compileall`、`git diff --check` 和隔离迁移检查均无代码错误。银行匹配镜像、精确反向凭证、状态槽覆盖、正式关系双父保护、迁移污染预检和 MCP 未知异常脱敏已有实质改善。

但常规测试通过不是验收充分条件。独立直接 SQL、双连接与真实 STDIO 审计仍可复现以下阻断问题：

- 正式法定缴款来源边建立后，可通过修改其支撑 `Settlement` 使规范边失真并成功提交。
- 已被正式事件引用的 `Evidence` 内容仍可原地修改，SHA-256 和存储路径证据链不可信。
- 普通业务冲正可以在没有继承原事件证据的情况下正式提交。
- 工资冲正事件可删除规范 reversal 来源边后再正式提交。
- 两个并发事务可写入同一维度、有效期重叠且互非祖先的版本。
- 已有正式下游工资时，新 profile/policy correction 会与旧累计税态或旧普通工资依赖静默混用。
- 部分并发确认仍抛裸 `IntegrityError`；相同幂等键的并发与顺序返回语义不一致。
- 同企业、同政策和同缴费机构的兼容多批次法定缴款仍被一律拒绝。
- 仓库中的真实 STDIO 回归没有按任务书证明工资付款冲正后复用同一工资流水的完整链路。

因此第四轮验收结论为 **不通过**。R5 全部关闭前，不得把工资模块标记为完成、可投产或可作为法定工资结果使用。

## 2. 本轮开发纪律

- 新增线性迁移 `0006`；不得回写 `0001` 至 `0005` 掩盖存量升级问题。
- 数据库不变量必须防御所有支撑关系的 INSERT、UPDATE、DELETE；只保护最终目标表不算闭包完整。
- 延期触发器必须在 `commit` 点测试；并发测试必须使用两个独立连接、同步屏障和真实同时提交。
- 不得使用会跨事务存续的会话级 advisory lock；连接池复用时容易遗留锁。可使用事务级 PostgreSQL advisory lock、专用 guard row 加 `FOR UPDATE`，或数据库原生排他约束，但必须证明锁域稳定且不会死锁。
- 所有服务写入口使用一致的幂等信封：规范请求哈希、savepoint、唯一冲突回读、同载荷重放、异载荷稳定 mismatch。
- 不得通过放宽证据、来源、版本、开放项或冲正约束来让测试通过。
- 不得增加自由分录、自由科目或 Agent 自选会计处理接口。
- 不得删除、跳过或改弱现有测试；不得修改、清理、暂存或提交其他 Agent 和用户的无关改动。

## 3. P0 数据完整性阻断项

### R5-001：来源边不变量必须覆盖支撑 Settlement 的反向变化

第四轮的 `finance_assert_payroll_event_link` 会读取工资付款和法定缴款的核销关系，但只在来源边、事件和部分开放项变化时重验。已建立正式来源边后，直接把支撑 `Settlement.payment_event_id` 改为另一事件仍可提交：来源边声称法定缴款核销该开放项，而支撑 settlement 已不再属于该缴款。

必须实现：

- 对 `Settlement` 的 INSERT、UPDATE、DELETE 建立反向延期验证，分别收集 OLD/NEW 涉及的企业、付款事件和开放项。
- 重验所有以该 settlement、付款事件或开放项为证明的正式 `PayrollEventLink`，不能只重验开放项余额守恒。
- 正式来源边的支撑 settlement 不得移动付款事件、开放项或企业；合法冲正必须通过规范冲正关系把原 settlement 标为 reversed，并创建可审计的反向关系。
- 触发顺序要允许服务的合法付款、法定缴款和冲正事务在提交时形成最终一致状态，不能依赖语句执行顺序。
- 迁移到 `0006` 时扫描全部正式来源边，按 head 规则重新证明其 settlement；污染数据必须以稳定错误拒绝升级。

最低 PostgreSQL 测试：

- 建立正式法定缴款后移动 `Settlement.payment_event_id`、`open_item_id`、`org_id`，均在 commit 失败。
- 删除支撑 settlement、标记 reversed 但没有规范冲正、替换为另一 settlement，均失败。
- 正常发薪、两次部分发薪、法定缴款、付款冲正和法定缴款冲正均成功。
- 从污染 `0005` 升级 `0006` 被拒绝且 revision、数据原样保留。

### R5-002：Evidence 内容必须成为不可篡改证据对象

第四轮冻结了 `event_evidence` 和 `payroll_batch_evidence` 的关系边，但没有冻结 `evidence` 行本身。已实测正式工资事件入账后仍可修改 `Evidence.sha256`、`storage_path` 和 `metadata_json` 并提交。

必须实现：

- Evidence 一旦被 sealed/final 业务对象引用，其内容字段禁止原地 UPDATE 或 DELETE；至少覆盖 SHA-256、来源、文件名、媒体类型、大小、存储定位和影响证据含义的元数据。
- 若允许补充不改变原证据含义的处理信息，建立独立追加式版本/审计实体，不得覆盖原始证据行。
- Evidence 的 SHA-256 必须具有确定含义；同企业重复文件的去重规则由数据库唯一性和服务返回共同定义。
- 所有引用 Evidence 的正式对象均纳入保护，不得只覆盖工资事件。
- `0006` 升级扫描证据组织和引用闭包；不能证明归属或内容摘要有效的数据必须拒绝升级。

最低 PostgreSQL 测试：正式工资、普通收入和费用事件引用证据后，修改每个受保护字段及删除 Evidence 均失败；未引用草稿证据可按明确契约编辑；创建新 Evidence 并在新草稿中引用成功；并发替换与删除失败。

### R5-003：版本有效期约束必须抵御并发写偏斜

`0005` 的递归延期断言只能看到本事务快照。两个连接可各自插入同员工、有效期重叠、互非祖先的初始 profile，分别强制执行延期约束后同时提交，两条均成功。政策和期初版本存在同类风险。

必须实现：

- 为 profile、policy、opening state 的版本维度建立持久并发锁域。锁键至少包含 `org_id` 和员工/政策维度；所有初始版本与 successor 写入先取得同一顺序的事务锁。
- 优先选择 guard 表行锁或可证明正确的排他约束。若使用 `pg_advisory_xact_lock`，必须稳定映射 UUID/维度、使用事务级锁，并测试连接池复用、哈希冲突处理和多员工固定锁序。
- 数据库仍需验证祖先闭包、非祖先重叠、分叉、自环、环和跨维度 predecessor；服务层预检不能替代数据库约束。
- 并发同载荷应重放或返回同一已存在版本；异载荷返回稳定版本冲突，不得由提交先后产生两个叶节点。
- `0006` 安装约束前全量扫描 `0005` 存量的重叠非祖先版本。

最低双连接测试：两个重叠初始版本、同 predecessor 两个 successor、不同祖先扩期相撞、profile/policy/opening 三类、反向提交顺序、死锁重试和连接池复用。最终数据库只能存在一个合法结果。

## 4. P1 必须整改项

### R5-004：版本 correction 与正式下游之间建立激活屏障

当前服务允许对已被正式工资使用的 profile 和 policy 登记重叠 successor。后续工资或同月 combined 奖金会选择新叶版本，却继承旧批次的累计税态或普通工资依赖，形成不可解释的混合计算链。

必须先在文档和 Schema 中选定并实现一种确定策略：

1. 推荐策略：允许登记 correction 草稿，但在所有受影响正式下游及其后续累计税态冲正前不得激活或用于计算；或
2. 简化策略：存在受影响正式下游时直接拒绝登记，并列出必须先冲正的批次。

无论选择哪种：

- profile、policy 和 opening state 使用同一原则；不得一类拒绝、一类静默启用。
- 普通工资、combined/separate 奖金和后续月份累计税态均计算受影响闭包。
- 计算与确认保存实际使用版本 ID，并证明全部依赖来自一致的有效版本世代。
- 旧草稿可以保留历史引用，但不得被确认；正式批次只有完成规范冲正后才能重建。
- 查询必须能解释 correction 状态、阻塞它的正式批次以及允许激活的条件。

最低测试：历史普通工资后更正 profile/policy/opening、同月 combined 奖金、跨月累计税态、separate 奖金、先冲后重建以及多个员工受同一政策影响。

### R5-005：正式工资冲正与普通冲正都必须有完整证据和规范来源边

两条独立绕过已经复现：

- 普通 `service_cash_sale` 冲正可在未继承原事件证据时正式提交。
- 工资付款冲正可在 draft 阶段删除 reversal `PayrollEventLink`，再转 posted 并提交，最终来源边数量为 0。

必须实现：

- 所有最终 reversal 事件都必须继承原事件的 supporting evidence 集合；新增冲正原因证据使用明确的 `reversal_reason` 类型。
- 工资计提、工资付款、社保、公积金和个税事件的 reversal 必须恰有规范 reversal 来源边，指向原事件、相关批次和适用的原开放项/来源关系。
- `finance_assert_final_event_evidence` 不得对非工资计提事件直接跳过通用 reversal 证据验证。
- 事件从 draft 转 posted、来源边/证据边变化、原事件/原批次变化均须在 commit 重验。
- `finance_get_event` 和 `finance_get_payroll_batch` 返回同一规范冲正链，不从 JSON 或描述文本推断。

最低测试：普通收入/费用/退款冲正缺继承证据、工资五类事件缺 reversal 边、多一条/错原事件/错批次边、正常服务冲正、直接 SQL 绕过及存量污染升级。

### R5-006：所有工资写入口统一并发幂等信封

两个不同工资批次并发确认使用同一键时，一边成功，另一边可能在共同法定机构创建处抛 `uq_counterparty_identity` 的裸 `IntegrityError`。工资试算同键异载荷的并发路径返回 `PAYROLL_PREVIEW_CONFLICT`，顺序路径却返回 `PAYROLL_IDEMPOTENCY_PAYLOAD_MISMATCH`。

必须实现：

- 工资试算、确认、发薪、三类法定缴款和冲正统一计算规范请求哈希。
- 用 savepoint 包住可能触发唯一冲突的完整写入闭包，包括 Counterparty、批次、事件、开放项、来源边和银行匹配的 get-or-create。
- 捕获唯一冲突后回滚到 savepoint，按企业与幂等键回读：同 hash 返回原结果，异 hash 固定返回 `PAYROLL_IDEMPOTENCY_PAYLOAD_MISMATCH`。
- 对业务唯一键但非幂等键的争用，返回稳定领域错误，不得向服务调用方抛 SQLAlchemy/psycopg 异常。
- MCP 继续只暴露脱敏稳定错误码，但不能用 `INTERNAL_ERROR` 掩盖可分类的并发业务冲突。

最低双连接矩阵：每个写入口的同键同载荷、同键异金额/日期/银行/分配/批次、不同键争同一对象、共同机构首次创建、失败事务重试和反向提交顺序。

### R5-007：支持可证明兼容的多批次法定缴款

当前服务把所有法定缴款来源压成单一 `payroll_batch_id`。两份同企业、同政策、同机构的正式工资批次合并缴纳同类社保时也返回 `STATUTORY_PAYMENT_MIXES_INCOMPATIBLE_PAYROLL_BATCHES`。

必须实现：

- 每个来源开放项保留自己的 `payroll_batch_id`，不得把第一批次 ID 复制到全部来源边。
- 明确定义兼容键，至少包括企业、法定类别、收款机构、政策版本、缴费所属期/税期和币种；含义不唯一时返回 `needs_information`。
- 一笔缴款可核销多个兼容批次和多次部分发薪产生的代扣开放项；每个来源均有独立规范边。
- 任一来源类别、机构、政策、期间或企业不兼容时，整笔原子拒绝且不产生部分核销。
- 冲正时完整复制并反转多批次来源集合；查询逐边返回批次、工资支付、开放项、员工/险种或法定类别。

最低测试：两批同机构兼容、不同机构/政策/期间/类别不兼容、部分核销、多员工、多次发薪、混合企业、冲正与幂等重放。

### R5-008：真实 STDIO PostgreSQL 测试必须逐步证明工资全生命周期

现有 STDIO 用例的银行重记账使用额外 `expense_cash`，没有证明“冲正工资付款本身后，用同一工资银行流水重新发薪”。若干关键写入也只在流程末尾集中检查，来源边只断言 `link_kind` 集合。

必须新增或重写一个独立测试，满足：

- 通过真实 STDIO 客户端调用 MCP，不直接调用服务来代替协议边界。
- 每次工具调用完成后，使用新的独立数据库连接立即核对持久状态；不得只复用服务 Session。
- 覆盖证据登记、银行导入、员工、profile、policy、试算、确认、部分发薪、法定缴款、冲正和查询。
- 对每个来源边核对事件、批次、来源支付、来源开放项、类别和企业，不只比较 `link_kind` 集合。
- 正常工资付款绑定银行流水 A；冲正该工资付款；再次调用工资付款并复用 A；断言匹配历史两条、旧边失效、新边唯一 active、current 指向新工资付款。
- 同一流程验证凭证平衡、开放项守恒、证据不可变、版本 ID、审计轨迹和无明文敏感异常。

## 5. 必须保持的第四轮通过项

## 6. 工作包与交接顺序

### 工作包 A：数据库闭包与迁移

范围：R5-001、R5-002、R5-003、R5-005 的数据库部分。独占 `0006` 和相关 ORM 模型；先画出“最终事实依赖闭包”，再实现所有反向触发器和升级预检。

### 集成工作包

范围：R5-008 和全量回归。必须在 A、B、C 合并后实施，且使用新的独立 PostgreSQL 17 实例；不要把开发数据库已有状态当成测试前提。

推荐顺序：A 定义数据库契约并合并 `0006`；B/C 基于契约分别实现；最后集成。共享文件由调度 Agent 显式交接，禁止多个 Agent 同时覆盖 `service.py` 或迁移。
