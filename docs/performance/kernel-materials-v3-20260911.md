# 公司 v3 资料归期容量验证

2026-09-11，Windows 本地受控 Python 3.12.13、SQLite 3.53.1；冻结构建 `local-kernel-2:fd7f5319e51bbe0329f9d3de4fd57ec2b7c2b8695e35b7020e19b338ee766913`。公司 v3 结构指纹 `69684e2f0294cbf8dfa93a20dc51ae61b67ad41c74e40b38d490b282d6fcbdcf`，640 个结构对象。

全部在临时合成公司库执行，没有修改真实公司账务。此次与全量 pytest 同时运行，时间是该负载下的测量，不代表独占机器的极限性能。RSS 是阶段结束值，并非峰值。

## 精确上限原件

CSV 原字节精确 20 MiB，100,000 条金额明细交替归属两个月，产生无法按连续区间合并的 100,000 条类型化归期明细。使用真实 `Materials.receive`，证据在计时前另行登记。

| 测量 | 结果 |
|---|---:|
| 接收全部用时 | 18.089 秒 |
| SQLite 持写锁时间 | 13.345 秒 |
| SQLite trace 次数，含触发器 | 200,066 |
| 接收结束 RSS | 102.70 MiB |
| 公司数据库文件 | 34.00 MiB |
| 单月完整性检查 | 24.138 秒 |
| 单月检查读取 SQL | 28 条 |
| 检查结束 RSS | 377.68 MiB |
| 公开检查结果 JSON | 36,378 字节 |

数据库中实际保存 100,000 条归期明细，外键检查零错误，来源与归期同版本且仅有两个当前事实。提交故障注入后，来源、归期和状态版本全部回滚。单月保留 50,000 个待处置业务项，正确返回 `needs_information`，没有因为分页而声称完整。

## 已知性能边界

容量与原子性通过；接近上限的完整月检尚未达到亚秒交互目标，13 秒持锁也不能描述为短交互事务。此结果不能外推为普通看板、工资或记账延迟，不能据此扩大现有文件与行数上限。后续优化应减少完整性检查的重复解析和对象构造，并缩短批量归期写事务；继续保留逐项检查及同库原子性。

验证脚本和完整原始测量保存在开发机忽略目录 `.tmp/audit-materials-review.py`、`.tmp/materials-review-final-receive.json`。业务 v2 备份独立恢复至 v3 后，141 张既有表逐内容摘要保持一致，两个公司的证据及事实摘要验证通过；此项恢复检查不代表真实历史账务已全部重建。
