# 会计 AI 读取与工作稿优化

本轮基于 `ad15cf9` 减少重复返回和重复查询。资料仍由负责人陆续提供，AI 按当前事项先查已有来源，再问剩余核算缺项。正式登记、预览、批准、核算发布、关账和清单推进规则继续由现有内核执行。

## 开始与接续

1. 首次读取接口概要。按当前事项获取 `selected` 合同，并核对返回视图与选择；同一会话、同一 `build_id` 复用已读合同。旧MCP连接没传选择参数时，使用通用 `schema` 命令。
2. 绑定公司，按现有清单确定月份和事项。范围未知时列工作稿供选择，不推定最新稿或资料所属期。
3. 调用 `work_context(include_work_draft=true)`，一次取得该范围的工作稿、版本、当前资料及正式状态。工作稿文件和数据库快照分别核验，不属于同一事务。
4. 后续查资料和翻页省略该参数，不重复传整份工作稿。需要原文细节时读取对应解析页，再按精确位置追溯。
5. 复用候选、已回答问题和来源；关键节点按当前版本保存。正式写入前保留完整原请求，结果不明时查原编号，不自动换键重做。

`work_context` 返回版本2，`include_work_draft` 默认 `false`；`true` 不能与续页 `cursor` 一起传。工作稿不存在时明确返回，损坏、身份不符或格式不支持时保留并报错。默认资料查询仍可独立执行。四个独立工作稿入口继续用于列举、单独查看、保存和删除。

## 接口与内部读取

概要和显式完整合同保留完整操作协议。`selected` 只传所选合同、必要引用定义、程序及合同版本、操作协议版本和简短错误说明。通用登记模型仍按所选事实收窄，运行校验器仍使用完整注册模型。

合并恢复只绑定一次公司，直接读取工作稿，不在内部串调两个公共入口。同次数据库快照中的事实正文和摘要复用一次，来源封签、对象引用、正式采用和待重算状态仍分别核对；不新增跨请求业务缓存。

保存输入通过检查后直接保留原始工作稿，不再复制完整正文后丢弃。字段省略、整数、布尔值、显式空值及原请求载荷保持原样，不补正式字段。多个旧待判明请求需要移除时，共用一个只读快照逐项核对回执；任何未知、损坏或身份不符都保留旧稿。回执同时拒绝重复JSON字段、数值与布尔值混淆和空结果。

8MiB上限、私有权限、文件锁、唯一版本、原子替换和保存结果确认规则保持现有要求。解析缓存仍只供阅读，正式资料检查继续解析和核验。

## 清单问题引用

`workflow` 返回版本2，顶层 `issues` 集中保存完整问题正文，编号从0开始且只在本次响应有效：

| 位置 | 引用字段 |
|---|---|
| 六类事项的资料、核算；关账；清偿；个税文件映射 | `issue_refs` |
| 六类事项的关账问题 | `close_issue_refs` |
| 外部办理的采用依据 | `basis_issue_refs` |
| 文件任务的合同问题 | `contract_issue_refs` |
| 单个文件结果问题 | `result_issue_ref`，可为 `null` |
| 清单顶层核算问题 | `fact_issue_refs` |

只有完整JSON内容完全相同才复用正文，省略和显式 `null` 不合并。每个位置的原顺序、重复次数和业务范围保留，按引用展开能还原原响应。共用正文不表示不同公司、期间或事项可以合并追问。

转换只处理明确列出的问题位置，发现新位置会报错。返回前检查引用范围和对应问题类型，服务边界继续检查完整合同；转换处不再重复校验整份响应。生成的JSON Schema和前端校验器检查静态形状、非负整数等约束，动态目录长度及目标问题类型由后端检查。期间准备、关账等其他入口保留自身原合同，共享模型没有改为引用格式。

## 验证与复现

验证只使用临时合成公司。覆盖合并与分开读取一致、隔离与分页、重启恢复、损坏稿保留、事实正文单次读取及封签／对象引用／采用异常、多请求回执、清单所有位置的完整展开和空公司／开放月／已关账月／跨月状态。

前后脚本测量通过实际 `MCP → ServiceClient → HTTP → LocalService`，基线为 `ad15cf9`：

```powershell
git archive --format=zip --output=<基线.zip> ad15cf9
.\.tmp-kernel-venv\Scripts\python.exe -X utf8 scripts/benchmark_work_drafts.py compare --output <新目录> --baseline-archive <基线.zip> --baseline-reference ad15cf9 --current-source src --phase both --repeats 3
```

工作量插桩与纯计时分开运行。SQL计数表示执行语句数，连接计数包含完整服务链的目录与公司连接；不表示扫描行数。文件计数是工作稿JSON／临时文件的打开次数，写入包括临时写入及替换后的同步打开，不是逻辑保存次数或字节数。模型令牌未由该链路提供，不估算为实测。

独立AI对话使用同一继承模型和推理设置，分别核对资料、保存剩余问题、接收负责人回答、保存后停下，再由无前文的新智能体恢复。原始返回和笔记保存在忽略目录 `.tmp/reading-draft-optimization-20261009`。脚本测量与AI对话分别报告，不能混为对话提速倍数。

本轮不改变数据库结构、看板界面、依赖、缓存体系或AGENTS.md；不写真实业务，不自动提交、推送或重启现有服务。

## 实际 AI 对话与最终验证

两个版本使用同一继承模型和推理设置，不覆盖模型参数。新智能体没有前文，只能读取明确范围和自己新请求的MCP返回。两组都先问原资料真正缺少的第2笔债权人类别，收到“也是供应商”后保存，再经合成服务重启恢复2笔候选及1条原答复；剩余问题和重复追问均为0，两笔重新核对均为 `clear`，没有正式登记或发布。

| 实际对话阶段 | 基线调用 | 新版调用 | 基线返回字节 | 新版返回字节 | 基线SQL | 新版SQL |
|---|---:|---:|---:|---:|---:|---:|
| 查资料、询问、收到回答并保存 | 16 | 16 | 182,349 | 117,737 | 1,047 | 1,092 |
| 新智能体恢复并核对、保存 | 14 | 12 | 155,090 | 129,290 | 1,148 | 948 |
| 合计 | 30 | 28 | 337,439 | 247,027 | 2,195 | 2,040 |

合计数据库连接81→75，工作稿读打开均4次、写打开均6次。解析次数4→5：新版首次对话额外选择了登记准备核对，完整工作清单与登记准备继续执行正式解析。所有尝试均计数，包括两组各一次来源引用不完整的保存拒绝，以及新版一次不合法视图请求；这些技术问题按接口纠正，没有变成负责人追问。新版另一次 `needs_information` 正是第2笔确实缺少的事实，不能算技术错误。

这是一组合成事项，不证明每个AI会话都减少相同数量的调用。两组原稿都尚未保存正式提交请求编号，因此原键恢复由脚本中的已提交合成请求单独验证。已恢复的负责人答复仍需在未来正式登记前保全为不可变证据，工作稿没有代替正式依据。

最终集中回归 **545项通过、2项平台跳过，389.29秒**；前端 **356项通过**。合同生成／一致性检查、前端合同样本、类型检查及构建、所有改动Python文件Ruff、差异格式检查和独立代码审查通过。平台跳过分别为通用合成链接夹具不可用及Windows不适用的POSIX模式检查；实际工作稿与缓存链接保护仍有独立测试。

最终源码、测量和实际新版对话使用同一构建身份，原始试跑另存且未混入结果。合成测试服务均已停止，现有服务没有重启；新实现尚未载入现有记账服务。此前工作区已有的公司管理边界及相关文档修改保留，本轮没有改写它们。
