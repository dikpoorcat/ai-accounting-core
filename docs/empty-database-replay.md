# 既有 SQLite 重录与恢复历史记录

本文保存公司库 v13、目录库 v3 时期的资料保全方法和合成验证范围，供追溯原件、负责人确认及过去实现。当前系统使用 `ai-accounting-kernel/2`，目录库与公司库处于 `draft / 0` 开发合同；旧库、旧备份和旧接口不能作为新系统的升级或恢复来源。本轮不进行真实资料重录、旧业务转换、正式换库或旧资源清理。当前新库的隔离验证见[新公司库隔离验证与恢复检查单](formal-empty-db-startup-checklist-template.md)。

## 已保全原件的私有索引

原件与负责人补充确认保存在忽略的 `data/reconstruction-sources`，具体公司身份、金额和凭据不进入源码。每家公司原有私有来源索引记录原始相对路径、原文件名、字节数、SHA-256、来源、允许的日期精度、稳定业务引用、依赖引用、明确确认的核算事实和未决事项。身份证件、工资、账号、真实说明及完整响应仍只留在私有资料目录。

原索引中的 `expense:2026-01:office:001` 一类键用于历史资料对应，不是数据库 UUID。历史重录设计曾要求为目标保存稳定引用到新 `subject_id` 的映射，员工、往来方、资金账户和资产也逐项映射；事实版本、计算、凭证、代发和报表依据及预览摘要均以当时目标库返回为准。旧 ID 或旧摘要不能直接跨库套用。

原件按真实字节和原文件名保存；相同内容的其他路径或别名记录在私有索引，不能为改名修改字节。文件说明不能替代核算事实。原件只明确月份时保留月份，实际收付款日需要真实日期；规则税额、实际扣税、实际申报和实际付款分别有自己的来源。旧凭证、余额和计算结果可解释历史差异，不能替代原始事实。

这些保全原则仍有效，但本页不提供在当前库执行真实重录的步骤。任何未来正式资料处理都须先按当时明确的用户授权和运行时 Schema 确定范围；不能因为原索引存在就推定已获真实写入或清理授权。

## 当时记录的任务边界

历史流程区分三件事：完整公司包恢复保留包内公司库身份与全部记录；按原件空库重记会生成新的身份、事实与计算版本；派生汇总维修只重算已保存正式内容对应的投影，不能补回缺失原件或业务事实。它们互不替代。

当时的执行顺序曾包括隔离资料根、负责人登录、原件登记、类型化事实、预览确认、经营说明、逐月关账、看板核对和便携备份。该顺序记录过去的核对范围，不构成现在的命令清单。当前实际工作以 `workflow` 的六类业务资料与核算状态、关账、真实办理和文件交付为准；响应丢失用原请求键或 `request_result` 查询，`unknown` 不能解释为失败。

特别保留原时点已知事实和说明、后来核实的录入修订、后来实际发生的新业务、关账后补充的管理资料这四类时间关系。最新才取得的姓名、用途或经营解读不能伪装为旧关账前已知内容。当前系统从首版保存完整必要历史采用依据，不用当前计算覆盖冻结历史。

旧 `finance-replay`、`finance-backup`、`ai_accounting.replay_cli`、`finance_record_event`、组合协议回放执行器、PostgreSQL 和 Alembic 均已退出运行层。原公司 v13、目录 v3、旧便携包也不是当前格式 2 的导入来源。源码历史由 Git 保存，原数据库及保全原件继续保留。

## 历史合成验证的范围

`tests/kernel/test_dashboard_empty_replay.py` 当时使用合成临时 SQLite 公司，经 `LocalService.dispatch` 验证原件、出资、费用、付款、展示档案、公司说明、经营结论、汇总维修和便携恢复的连续过程。案例包含重复提交、确认响应丢失、不同空目标的新 ID 映射、旧经营结论摘要拒绝，以及恢复后的金额、往来名称、资金账户名、原件名和经营说明一致。

当时另以隔离 `Display`／`Periods` 案例核对无业务月份的原时点说明、合成关账与后补说明顺序；`test_display.py`、`test_display_migrations.py` 补充关账管理封存、失效上下文和迁移路径。那些测试没有覆盖真实公司全业务重录或原生密码窗口，也不证明真实资料完整，更不是当前开发基线的验收记录。
