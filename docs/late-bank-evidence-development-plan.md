# 迟到银行外部证据开发基线（DEC-013 B）

> 状态：DEC-013、DEC-014、DEC-015 A、DEC-020 至 DEC-024 已决定，确定性实现进行中；DEC-023 A 只建本地单负责人账户，DEC-024 A 不设业务角色；负责人会话授权 AI/内核执行时仍不允许推测缺失事实或绕过预览—哈希—确认提交点
> 记录日期：2026-08-11
> 上位决策：[会计期间与月结产品决策记录](./accounting-period-close-decisions.md#dec-013月结后能否补导入属于已关闭月份的银行流水)
> 上位基线：[会计期间生成与月结第一期开发基线](./accounting-period-close-development-plan.md)
> 定位：单企业私有试用内核的外部证据补入与审计链；不构成银行对账单完整性证明、法定账簿、纳税申报或审计意见。

## 1. DEC-013 B 已冻结的产品边界

允许把 `booking_date` 落在已关闭自然月的银行流水导入为**迟到外部证据**。它不是回写原月的会计业务，也不是反结账：旧 `AccountingPeriodClose`、关闭来源全集、计数、规范 JSON、SHA-256 和前期哈希均不可更新或重算。

迟到事实必须可查询、可审计，并只在一个后续**已生成且开放**的自然月中处理。该处理月不是银行流水的发生日；它只承载“该外部证据在月结后到达，以及已如何处理”的后续轨迹。系统不得把迟到导入自动解释为漏记、重复记账、已对账或已完成会计更正。

本工作包不新增 Agent 可自由指定借贷行、科目、金额或旧月凭证修改的接口。所有金额仍为整数分；任何需要新增会计凭证的路径只能复用既有确定性专用业务工作流和期间写入保护。

## 2. 三个必须分离的日期

| 字段 | 含义 | 不可替代关系 |
| --- | --- | --- |
| `booking_date` | 银行流水发生/记账日期，由原始文件给出 | 决定它是否属于关闭月；永不因迟到导入改为处理月。 |
| `imported_at` | 系统成功接受该流水及其文件摘要的时间 | 用于判断是否在对应会计月关闭之后才到达；不得由调用方指定。 |
| `handling_period_month` | 处理迟到证据时选择的后续已生成开放会计期间首日 | 导入时可以为空；只在后续遗漏入账处理或仅追加证据关联时冻结，不能属于原关闭月、已关闭月或未来期间。 |

“迟到”定义为：流水的 `booking_date` 命中一个已关闭期间，且该流水在该期间的 `closed_at` 后首次成功持久化。正常导入但在关闭前已存在的流水不是迟到流水；导入日落在未来不构成会计日期，也不放宽现有未来正式入账限制。

## 3. 导入、月结和后续处理的锁序

正式实现必须在 PostgreSQL 与服务层使用同一锁序，且导入不改变现有月结锁的含义：

1. 预览只读一次文件字节，并据此完成 SHA-256、解析、规范行、身份歧义和关闭月投影；不写银行流水或审计动作。
2. 正式导入先取得企业税期锁，再按 `(org_id, booking_month)` 稳定排序取得文件涉及的全部会计月份锁和期间行，锁后重新解析同一组字节事实并校验预览哈希。
3. 若 `booking_date` 所属期间已经关闭，系统直接把流水持久化为 `late_external_evidence_pending`，冻结原期间、原关闭记录与关闭哈希；导入不要求当时已经存在后续开放处理月，也不修改旧关闭快照。
4. 后续处理动作再按“税期企业锁 → 原月锁/期间行 → `handling_period_month` 锁/期间行 → 银行行/动作”取锁，并验证处理月仍已生成、开放且不在未来。任何并发 close、post、重复导入或重复处理都必须线性化为一个成功结果或稳定领域错误，不能在外层提交泄漏裸数据库错误。

锁顺序固定为：**税期企业锁 → 原 `booking_date` 月锁/期间行 → 后续处理月锁/期间行（仅处理动作）→ 银行行与审计动作**。不得锁闭月的凭证、来源事件或关闭快照；不得在取得后续月锁后反向取得原月锁。没有可用后续开放月时仍允许先保存 pending 外部证据，但任何处理动作返回 `needs_information`，不能猜测处理月。

## 4. 迟到分类与后续开放月处理

持久化分类至少为以下互斥状态，所有状态转换追加历史而非覆盖原始事实：

| 分类 | 已冻结行为 |
| --- | --- |
| `late_external_evidence_pending` | 已成功导入，原月已关闭；保留原始流水和关闭引用，不修改旧快照，等待后续开放月明确处理。 |
| `late_external_evidence_omitted_entry` | 经调用方提供的确定性业务事实确认原月存在遗漏入账；只允许在 `handling_period_month` 通过相应专用工作流生成后续更正/关联冲正链。原月不补记。 |
| `late_external_evidence_evidence_only` | 按 DEC-020 A，在后续开放月创建不可变的仅证据关联动作；不生成凭证、不修改旧事件或旧关闭快照，冻结操作者、说明、证据、原关闭哈希及关联历史。 |

“重复流水”不是迟到处理状态。有稳定流水号时由导入身份规则证明；无稳定流水号时由独立的人工身份解析动作表达“新增”或“合并既有”，并冻结说明和证据。确认前既不自动合并，也不自动新增。

对于 `omitted_entry`，必须明确引用迟到流水、原关闭期间、后续处理期间、所复用的业务专用工作流、生成的事件/凭证（如有）、操作者、说明、证据和计算/动作哈希。不能根据金额、摘要或对方自动推断会计处理；缺少影响借贷处理的业务事实必须返回 `needs_information`。若后续处理月后来关闭，任何未完成的迟到证据仍应作为该月人工复核计数/警告可见，但不重写原关闭月。

## 5. 查询投影与审计可见性

新增只读投影必须同时给出“关闭时点”和“当前已知”的视角，避免把两者混为一谈：

- 原关闭月：关闭快照中的 `unmatched_bank_transactions` 原值、关闭哈希、`closed_at`，以及关闭后到达的迟到流水数量/ID 列表；明确标示后者**未包含在关闭快照**。
- 后续开放月：按分类显示待处理迟到证据、处理期间、处理状态、关联动作/事件/凭证和稳定错误码；不得把 pending 自动显示为已对账。
- 每笔迟到流水：`booking_date`、`imported_at`、原关闭期间与关闭哈希、`handling_period_month`、分类及不可变状态历史。原始敏感字段的查询范围遵循既有证据与银行流水读取边界。
- 导入动作：成功动作保存文件 SHA-256、请求哈希、列映射摘要、计数、迟到计数、幂等键、认证操作者、时间和结果。正式确认失败或部分失败只保存文件/请求哈希、稳定错误码、行号、字段路径和计数，不保存原始失败值、完整文件或本地路径。

## 6. 0013/0014 身份归因前置、0015 银行模型与稳定错误码

正式银行动作不能伪造操作者，因此迁移顺序固定为：`0013` 先实现由
DEC-015/023/024 决定的单一负责人登录，并由 `0014_execution_attribution` 实现 AI/系统执行归因与授权提交点；其后 `0015_late_bank_evidence`
再引用真实身份主键。不得用 `confirmed_by` 或任意 actor 文本替代，也不能修改已发布的
`0012`。银行模型与迁移至少需覆盖：

1. `BankTransaction` 的不可变迟到来源字段：原关闭期间 ID、原关闭快照 ID/哈希、首次 `imported_at`、迟到标志；其复合外键必须限制在同一企业。
2. 追加式 `LateBankEvidenceAction`（名称可在实现前调整）：动作类型、幂等键、请求哈希、结果状态、稳定错误码、处理期间、分类、操作者、说明、证据和创建时间；成功记录不可更新、删除或跨企业重绑。
3. `late_bank_evidence_action_evidence` 复合关联；成功分类或遗漏处理必须有非空证据。实际新增事件/凭证只保存引用，不复制或修改其原始会计事实。
4. 迟到流水与处理动作的一对多历史、每一动作的同企业和状态转换约束，以及适合关闭月/处理月投影的索引。
5. 独立导入动作及最小失败审计模型；预览阶段不留失败动作，正式提交阶段也不得保存失败字段值、原始行、完整文件、本地路径、SQL 或异常正文。

迁移首个 DDL 前必须检查：已有关闭月的银行流水不会被猜测标为迟到、跨企业引用不存在、处理期间不存在、动作链不完整或不可验证。发现污染时以稳定迁移预检失败中止，保持 revision 与存量不变。downgrade 只允许在不存在迟到动作/关联/标记数据时执行；否则明确拒绝，不能删除审计事实。数据库触发器必须独立执行关闭快照不可变、同企业、期间状态、锁序与动作不可变检查。

拟冻结错误码命名空间（具体码在实现设计评审后固定，不以本草案替代待决产品决定）：

- `LATE_BANK_EVIDENCE_HANDLING_PERIOD_REQUIRED`
- `LATE_BANK_EVIDENCE_HANDLING_PERIOD_NOT_OPEN`
- `LATE_BANK_EVIDENCE_HANDLING_PERIOD_FUTURE_NOT_ALLOWED`
- `LATE_BANK_EVIDENCE_ORIGINAL_PERIOD_NOT_CLOSED`
- `LATE_BANK_EVIDENCE_SNAPSHOT_IMMUTABLE`
- `LATE_BANK_EVIDENCE_IDEMPOTENCY_PAYLOAD_MISMATCH`
- `LATE_BANK_EVIDENCE_ACTION_IMMUTABLE`
- `LATE_BANK_EVIDENCE_CROSS_ORGANIZATION_REFERENCE`
- `LATE_BANK_EVIDENCE_MIGRATION_PRECHECK_FAILED`

这些错误只能返回稳定码和必要字段路径；不得回显 SQL、文件路径、完整原始行、关闭快照正文或凭据。

## 7. 已决定的导入、身份歧义和失败审计契约

`DEC-020 A`、`DEC-021` 的自定义选择和 `DEC-022` 的“预检优先 + 最小失败审计”现冻结为：

1. 银行导入改为 `preview → 规范 SHA-256 → confirm`。预览不落流水、不落失败审计；确认必须锁后重读并复算同一哈希。
2. 有稳定 `external_id` 时按企业、银行账户和稳定流水号识别；同 ID 但规范金额、日期或币种冲突时拒绝，不能静默覆盖。
3. 缺少稳定流水号时，每个规范源行都返回稳定 `row_identity_sha256` 和 `needs_information`。AI 必须向用户展示候选、追问“确认为新流水或确认为既有流水”，并要求同企业证据；确认前既不新增也不合并。文件路径、原始失败值和自由文本不得进入身份哈希。
4. 预检存在行错误时，默认不执行正式写入。只有用户仍明确提交并接受已知错误，确认才可按有效行部分成功；成功动作冻结完整规范结果，失败行只保存文件/请求哈希、稳定错误码、行号、字段路径和计数，不保存原始字段值、完整文件或本地路径。
5. `evidence_only` 采用专用预览/确认动作和不可变关联边，只连接已在原关闭月正确入账的事件及其关闭来源快照；数据库独立验证银行方向和金额，不生成新凭证。遗漏入账仍只走既有类型化业务工作流，不能新增自由分录接口。
6. 所有成功确认、部分成功和仅证据关联必须使用服务端认证上下文，公共请求不得接受 `actor_id` 或用 `confirmed_by` 文本替代。负责人会话按 DEC-023 A 建立，不引入 DEC-024 A 排除的角色、邀请或多用户模型。按 DEC-015 A，负责人在会话中提供凭据与业务事实后，可授权 AI/内核执行确定性流程；审计必须同时冻结负责人授权会话和 AI/系统执行者，不得把 AI 伪装成负责人。

## 9. 正式试用前停止线

本工作包和正式试用控制完成后，**在正式试用前必须停止**，向用户报告实现范围、当时仍未决定的身份/平台/发布治理事项、全量验收、部署、备份恢复及专业复核证据。未经用户新的正式试用授权，不导入真实试用数据、不部署生产环境、不宣称可作为正式会计或银行对账系统使用。
