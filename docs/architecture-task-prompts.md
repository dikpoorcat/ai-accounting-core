# 架构改进任务会话启动说明

## 如何使用

1. **T1—T6 及用户随后授权的正式更新均已完成架构审核。** 正式环境采用公司库 v11、目录库 v3 和前端 `production-frontend-r3`；结果见[正式前端更新](t6-production-update-r3.md)及[正式迁移](t6-production-update-result.md)。原 T6 为 `01a095d6-05dd-7c63-82eb-d29543bf6c48`，无需继续执行或重新创建任务。以下输入仅保留为分工记录，其中版本与范围按各任务规划时点理解；当前结论以总体计划为准。
2. 在 `D:\GitHub\ai-accounting-core` 项目中使用本地目录新建任务，选择 **GPT-6 Astra / Ultra**，手动开启**计划模式**，粘贴对应任务的完整输入。
3. 任务会话先制定详细计划，并主动把计划返回架构会话。架构会话负责审核和明确放行，用户无需重复审核技术计划。
4. 计划阶段结束后可切回默认模式，便于后续直接协作；仍须等架构会话明确批准后才开始执行。
5. 完成结果也由任务会话主动回传架构会话，经过审核后再推进下一任务。

架构会话：`审查看板与内核架构`

架构会话 ID：`01a09416-a4e3-76b2-bf46-6387d8d47cfc`，主机：`local`。

总体计划：[architecture-roadmap.md](architecture-roadmap.md)。本说明负责分发任务，详细实现与验收计划由任务会话制定。

## 全部任务共同遵守的协作约定

- 用户授权架构会话负责方案取舍、计划审核、执行放行和结果审核。收到本任务输入只表示允许规划，不表示允许实施。
- 先读总体计划、本说明及 `AGENTS.md`；涉及前端时遵守 `FRONTEND.md`。以当前主仓库为基础，保留已有未提交改动。执行时只有本任务写入对应范围。
- 计划应明确关键决策、范围、前置依赖及必要验证。已有审查证据直接复用，只为影响方案选择的未知点做必要检查，不重做整轮审查。
- 将详细计划一次性发送到上述架构会话，附本任务 ID、任务编号和计划版本，然后等待反馈。使用 `mcp__codex_app__send_message_to_thread`，目标 `threadId` 为上述架构会话 ID；工具需发现时先搜索。不要把计划发送给其他任务。
- 若计划模式禁止发送工具调用，先在本任务最终回复完整计划；切回默认模式后只执行回传。回传失败时明确告知用户转贴，不另建架构会话或自行视为已批准。
- 架构会话可以要求修改计划。明确批准后按批准范围执行；实质性范围或契约变更先回传架构会话确认。
- 阶段只做当次改动不得不做的检查，复用仍然有效的结果。T1—T5 的统一回归已在 T5 完成；T6 在自身收口时集中验证受影响页面，不例行全量测试，不堆叠重复验证。具体检查由任务会话按风险提出。
- 结果回传包含完成范围、关键决策、必要验证结果及未决事项，保持简短，避免原始长日志。架构会话审核后可能继续派发修订。
- 不修改真实业务数据库、原件或已冻结的历史记录，不自行部署；源码结构变更遵守冻结合同和前向迁移要求。不提交无关改动，不自行创建后续任务。
