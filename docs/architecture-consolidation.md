# 架构收口

以架构优雅为原则，从整体架构审视本轮改动：职责是否放对，模块边界是否清楚，数据和判断是否有明确归属，是否增加了重复判断、特殊分支或不必要的依赖；同时检查原设计中哪些接口、字段、流程和抽象已经失去用途。

动手前先反向质疑：问题能否通过调整职责或统一数据来源解决？方案是否只是局部补丁？现有差异是否确有必要？保留合理差异，不为形式统一硬造框架，也不无关扩大重构。

确定方案后，贯通清理相关实现、调用方、测试和设计文档。技术问题自行解决；涉及业务规则、功能或体验取舍时，说明具体影响交给用户决定。

完成后重新通读受影响的设计和代码，确认旧路径已清理、整体更简单，再做必要验证。简明报告架构问题、调整理由、验证结果及剩余问题，文档只保留最终事实。
