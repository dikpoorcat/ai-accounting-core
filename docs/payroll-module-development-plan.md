# 工资、社保、公积金与个税模块开发基线

> 状态：工资模块第一阶段核心实现已通过第七轮独立验收
> 更新日期：2026-08-10
> 适用仓库：`ai-accounting-core`
> 阶段属性：单企业私有模拟试用，不是法定工资系统、个税申报系统或税务意见
> 当前门禁：[工资模块第七轮验收整改任务书](./payroll-module-acceptance-remediation-round-7.md) 已全部销项；后续扩展必须继续保持其中的数据库、迁移、MCP、STDIO 和全量回归门禁

## 1. 文档目的

本文档是下一阶段多 Agent 协作开发的统一依据。实现 Agent 负责各自工作包的代码和单元测试；总设计与验收 Agent 负责接口裁决、全量测试、会计与数据库不变量审计以及最终验收。

出现下列情况时，实现 Agent 必须暂停并向总设计 Agent 报告，不得自行扩大范围：

- 文档中的业务事实不足以唯一决定计算或会计处理。
- 需要新增任意借贷分录接口、自由科目代码或 Agent 自选科目能力。
- 官方规则与本文档存在冲突，或者目标日期没有有效规则。
- 需要修改已入账凭证、覆盖历史规则或绕过期间关闭。
- 需要存储身份证号、银行卡号等本文档明确排除的敏感信息。

## 3. 不可破坏的设计原则

- Agent 只能提交工资业务事实，不能提交借贷方向、借贷金额或任意会计科目。
- 所有业务金额和入账金额均为整数“分”；比例、税率和中间税额使用 `Decimal`，禁止二进制浮点数。
- 缺少会改变结果的事实必须返回 `needs_information`，不得推断员工类别、缴费基数、扣除金额或奖金计税方式。
- 工资草稿可以被新版本替代；正式工资批次、凭证和已使用规则版本不可修改。
- 更正必须创建关联冲正。存在下游支付或后续累计个税依赖时，先冲正下游和后续批次。
- 所有政策有效期化，并保存官方主要依据 URL；政策到期且没有后继版本时拒绝计算。
- 社保公积金只支持单企业参数化规则，不在代码中硬编码某个城市。
- 本阶段不进行税务申报，也不声称结果可以直接替代专业人员复核。

## 4. 首版业务范围

### 4.1 支持范围

- 中国居民个人的正常工资、薪金所得。
- 从月度薪资项目开始计算，不计算出勤天数、加班或请假工资。
- 月度薪资项目包括基本工资、绩效工资、应税补贴、免税收入和考勤扣款。
- 员工确认的专项附加扣除及其他依法确定扣除金额；内核不判断员工是否具备扣除资格。
- 养老、医疗/生育、失业、工伤等参数化社保险种和住房公积金。
- 全年一次性奖金的单独计税与并入综合所得场景。
- 工资计提、工资发放、社保缴纳、公积金缴纳、个税缴纳、部分支付、核销和冲正。

### 4.2 明确排除

- 非居民个人、劳务报酬、稿酬、特许权使用费和离职补偿。
- 考勤、排班、加班、请假和工作日历计算。
- 专项附加扣除资格判断或家庭成员资料管理。
- 股权激励、跨境薪酬、外籍人员优惠和年度汇算清缴。
- 个税申报文件、社保申报文件或税局、社保机构外部连接。
- 身份证号、银行卡号和用于外部申报的完整个人身份信息。

## 5. 官方规则基线

规则实现必须引用并测试以下主要依据：

- 居民工资薪金累计预扣：[国家税务总局公告2018年第61号](https://www.chinatax.gov.cn/chinatax/n810341/n810765/n3359382/201812/c4182700/content.html)。
- 个人所得税法及综合所得税率：[中华人民共和国个人所得税法](https://www.chinatax.gov.cn/chinatax/n810219/n810744/n3752930/n3752974/c3970366/content.html)。
- 专项附加扣除现行标准：[国发〔2023〕13号](https://app.www.gov.cn/govdata/gov/202308/31/506746/article.html)。
- 全年一次性奖金政策：[财政部、税务总局公告2023年第30号](https://m.mof.gov.cn/czxw/202308/t20230828_3904328.htm)，当前文件规定执行至 2027-12-31。

社保和公积金版本由企业按参保地官方文件配置。每个版本至少包含地区、险种、单位与个人比例、基数上下限、舍入规则、生效日期、失效日期和官方依据 URL。

## 6. 数据模型设计

### 6.1 数据库迁移前置修复

新增工资模型前，必须先把初始迁移中的 `Base.metadata.create_all/drop_all` 改成固定的初始结构操作。否则新模型被导入元数据后，全新数据库会在 `0001` 提前创建工资表，随后与工资迁移冲突。

要求：

- 初始迁移修改后的最终结构必须与当前已运行的 `0001` 数据库等价。
- 新增独立 `0002_payroll` 迁移。
- 同时测试现有 `0001` 数据库升级和空数据库从零迁移。
- 不删除或重建当前企业数据。

### 6.2 新实体

建议将工资领域代码放入独立 `ai_accounting.payroll` 包，避免继续扩大现有 `service.py`。

必须建立：

- `Employee`：组织、唯一员工编码、姓名、入职和离职日期、状态。
- `EmployeePayrollProfileVersion`：有效期、费用角色、社保基数、公积金基数和居民员工标志。
- `PayrollPolicyVersion`：地区、有效期、官方依据及社保公积金参数。
- `PayrollBatch`：组织、批次类型、期间、版本、状态、计算哈希、规则版本、确认信息及冲正关系。
- `PayrollLine`：员工、工资组成、个人和单位缴费、个税、应发和实发金额以及逐步计算轨迹。
- `PayrollOpeningState`：员工在某纳税年度、截至某月的累计收入、扣除和已预扣税额。
- `AnnualBonusUsage` 或等价唯一约束：保证每名员工每年最多使用一次单独计税方式。

可以复用现有 `BusinessEvent`、`Voucher`、`VoucherLine`、`OpenItem`、`Settlement`、`Evidence` 和 `AuditLog`，但开放项内部生成逻辑必须支持一个事件产生多个应付款。不得为绕过该限制而直接改写科目余额。

### 6.3 状态与唯一性

工资批次状态：

```text
calculated → posted → reversed
     │
     └────→ superseded
```

- `calculated`：已保存的试算版本，可以被新版本替代但不可原地修改。
- `posted`：用户确认后原子入账，不可修改或删除。
- `reversed`：已由关联冲正批次撤销。
- `superseded`：未入账草稿被新版本替代，仅保留审计记录。
- 同一组织、月份只能有一个有效的普通工资正式批次；更正必须先冲正再重新计算。
- 幂等键、计算哈希、员工编码、批次版本和单独计税年度使用数据库唯一约束保护。

## 7. 计算契约

### 7.1 普通工资输入

每名员工使用明确、非负的整数分字段：

- `base_salary_fen`
- `performance_pay_fen`
- `taxable_allowance_fen`
- `tax_exempt_income_fen`
- `attendance_deduction_fen`
- `special_additional_deduction_fen`
- `other_legal_deduction_fen`

不接受含义不明的正负调整金额。应发工资必须大于零，任何扣减不得造成负数应发或负数实发。

### 7.2 社保公积金

- 缴费基数来自工资档案版本；缺失时返回 `needs_information`。
- 每个险种分别按有效政策进行基数上下限处理、比例计算和舍入。
- 单位与个人承担金额分别保存，不允许只保存合计。
- 禁用险种必须由政策明确配置为不适用或零比例，不能通过字段缺失推断。

### 7.3 累计预扣个税

普通工资按有效规则计算：

```text
累计应纳税所得额
= 累计收入
- 累计免税收入
- 累计减除费用
- 累计个人社保公积金
- 累计专项附加扣除
- 累计其他依法确定扣除

本期预扣税额
= max(0, 累计应预扣税额 - 累计减免税额 - 累计已预扣税额)
```

中途启用系统且员工在本单位已有当年历史工资时，必须先登记 `PayrollOpeningState`；不得把缺失的历史累计值当作零。

### 7.4 全年一次性奖金

- 奖金使用独立 `annual_bonus` 批次。
- 第一次试算可以同时返回 `separate` 和 `combined` 两个场景，但未选择时不可确认。
- 用户选择后必须重新生成含明确 `tax_method` 的可确认草稿和计算哈希。
- `separate` 按有效奖金政策计算并执行每人每年一次限制。
- `combined` 纳入对应月份累计工资薪金计算。
- 内核不得自动选择“最优”方式；未来收入未知时，场景比较必须标注为基于当前已知累计值。

## 8. 会计处理契约

新增默认系统角色，具体科目代码可由会计政策映射，但 Agent 只能选择允许的费用角色：

- `payroll_management_expense`
- `payroll_sales_expense`
- `payroll_service_cost`
- `employee_salary_payable`
- `employer_social_payable`
- `employer_housing_fund_payable`
- `withheld_employee_social_payable`
- `withheld_employee_housing_fund_payable`
- `individual_income_tax_payable`

### 8.1 确认工资批次

- 借：员工对应的工资费用或服务成本，应发工资。
- 借：员工对应的费用或成本，单位承担社保和公积金。
- 贷：应付职工薪酬—工资，应发工资。
- 贷：应付职工薪酬—社保，单位承担社保。
- 贷：应付职工薪酬—公积金，单位承担公积金。
- 按员工建立工资开放应付款；按机构及险种建立单位缴费开放应付款。

### 8.2 工资发放

- 借：应付职工薪酬—工资，应发工资。
- 贷：银行存款，实发工资。
- 贷：个人社保代扣应付款。
- 贷：个人公积金代扣应付款。
- 贷：应交个人所得税。
- 工资开放项按员工核销；个人扣缴部分形成对应机构开放应付款。

### 8.3 缴纳社保、公积金和个税

- 分别借记对应单位承担及个人代扣负债，贷记银行存款。
- 支付事件必须引用开放项和银行流水；允许部分缴纳，禁止超额缴纳。
- 一笔银行流水可以对应多个同类开放项，但总额必须严格相等。

### 8.4 冲正规则

- 工资批次没有支付或后续累计依赖时，可以直接生成关联反向凭证。
- 已发工资或已缴法定款项时，必须先冲正相应支付事件。
- 要冲正较早月份工资时，必须从最新月份向前冲正所有依赖其累计个税的工资批次。
- 冲正恢复开放项和累计状态，原始工资批次、凭证和计算轨迹保持不变。

## 9. MCP 公共接口

新增以下工具：

- `finance_register_employee`
- `finance_register_employee_profile_version`
- `finance_register_payroll_policy_version`
- `finance_register_payroll_opening_state`
- `finance_preview_payroll`
- `finance_confirm_payroll`
- `finance_get_payroll_batch`

### 9.1 工资试算

`finance_preview_payroll` 至少接收：

```text
org_id
idempotency_key
batch_kind                 # regular | annual_bonus
payroll_period             # YYYY-MM
posting_date
payment_date
employee_items
evidence_references
description
```

返回：

- `calculated`：试算完成，返回 `batch_id`、`calculation_hash`、员工明细、汇总、规则版本和轨迹。
- `needs_information`：列出缺少的员工档案、政策、累计状态、扣除或奖金计税方式。
- `rejected`：日期、金额、状态、重复、政策有效期或数据库约束冲突。

### 9.2 确认入账

`finance_confirm_payroll` 至少接收：

```text
org_id
batch_id
calculation_hash
idempotency_key
confirmed_by
confirmation_note
```

确认时必须重新读取全部版本并验证哈希。任何员工事实、政策版本或累计状态变化都应返回 `STALE_PAYROLL_CALCULATION`，要求重新试算。

### 9.3 支付事件

在现有 `finance_record_event` 中新增受支持事件：

- `salary_payment`
- `social_insurance_payment`
- `housing_fund_payment`
- `individual_income_tax_payment`

这些事件只能接收业务金额、开放项分配、银行流水和证据引用，不得接收借贷分录。内部工资计提事件只能由 `finance_confirm_payroll` 产生，不得列为 Agent 可提交事件。

## 10. 工作包与多 Agent 边界

### 工作包 A：数据库、迁移与内部开放项能力

- 冻结初始迁移结构并新增工资迁移。
- 实现工资实体、约束、索引和系统科目角色。
- 将内部入账计划扩展为一个事件生成多个开放项。
- 单元测试迁移、唯一约束、多开放项守恒和 PostgreSQL 约束。

### 工作包 B：纯工资计算规则

- 实现不依赖 MCP 的工资、社保公积金、累计个税和年终奖计算器。
- 所有输入输出使用明确类型；计算器不得访问任意会计科目或生成借贷分录。
- 为税率级距、累计月份、基数上下限、舍入和奖金场景建立单元与性质测试。

### 工作包 C：工资服务、MCP 与凭证闭环

- 实现草稿版本、哈希确认、工资批次查询及审计轨迹。
- 把计算结果转换为固定的内部记账模板和开放项。
- 实现四类支付事件、银行流水匹配、核销与冲正。
- 完成 MCP 单元测试和 STDIO 工具契约测试。

### 协作限制

- 工作包开始前由总设计 Agent 分配共享文件的唯一负责人。
- `models.py`、`schemas.py`、`mcp_server.py`、现有 `service.py` 和 Alembic 迁移同一时间只能由一个 Agent 修改。
- 工作包 B 优先使用新的工资子包，避免与 A、C 修改同一文件。
- 每个实现 Agent 必须随代码提交对应单元测试，不得把测试留给验收阶段补写。
- 任何公共字段、状态码、事件类型或会计模板变更必须先更新本文档或形成经总设计 Agent确认的设计记录。

## 11. 测试门禁

### 11.1 实现 Agent 单元测试

每个新增事件必须具备：

- 借贷平衡测试。
- 幂等重试测试。
- 冲正测试。
- 规则解释轨迹测试。

工资规则还必须覆盖：

- 累计预扣各税率级距边界、零税额及跨月累计。
- 当期计算差额为负时不生成负数退税。
- 员工年中入职、系统年中启用和缺少累计期初状态。
- 各险种基数低于下限、高于上限、恰好在边界及逐项舍入。
- 应发、个人扣款、个税和实发金额勾稽关系。
- 年终奖单独计税与并入综合所得、每年一次约束和规则到期。
- 草稿幂等、草稿替代、过期哈希、重复确认和并发确认。
- 部分工资支付、合并支付、超额支付及重复银行流水。
- 已关闭期间、下游支付存在和后续累计依赖下的冲正顺序。

### 11.2 总设计 Agent 全局测试与审计

- 运行完整 `pytest`、Ruff 和覆盖率检查；仓库已纳入的回归用例和关键不变量覆盖不得减少。
- 使用 PostgreSQL 验证现有数据库升级及空数据库完整迁移。
- 使用 Hypothesis 随机生成多员工、多月份事件序列，验证总账、开放项和累计个税守恒。
- 通过真实 STDIO MCP 完成员工登记、政策登记、试算、确认、发薪、缴费、缴税、查询和冲正流程。
- 审计所有 MCP 工具，确认不存在任意借贷分录或自由科目入口。
- 审计数据库约束，确认不存在修改已入账凭证、超额核销或重复单独计税的路径。
- 检查每个计算结果能追踪到业务事实、政策版本、官方来源、计算步骤、确认哈希、凭证和支付证据。

## 12. 最终验收标准

全部满足后才能把 `payroll` 从停用模块中移除：

1. 普通工资和全年一次性奖金均能先试算、后确认，并生成平衡凭证。
2. 工资、社保、公积金和个税的应付款均可部分核销但不可超额核销。
3. 累计个税可跨月重算验证，历史正式批次不可原地修改。
4. 任何缺少政策、基数、累计状态或计税选择的请求都返回具体的 `needs_information`。
5. 所有新增事件通过平衡、幂等、期间关闭、冲正和解释轨迹测试。
6. 全新数据库与现有数据库升级路径均通过 PostgreSQL 集成测试。
7. 全量测试、静态检查和真实 MCP 端到端测试全部通过。
8. 不存在 Agent 通过公共接口制造任意分录、负数工资应付款或无依据税额的路径。

## 13. 后续路线

工资模块验收后的路线进展如下：

1. 固定资产购置、启用、月折旧和处置：第一期已于 2026-08-10 完成并独立验收通过。
2. 无形资产与借款利息。
3. 会计期间生成、结账前检查和月结闭环。
4. 期初余额、银行对账增强、备份恢复和 CI。
5. 仅在实际业务需要时开发库存及成本结转。

开始真实数据试用前，必须先补齐会计期间、期初余额、权限、加密、备份恢复和专业会计复核，不能因为工资模块验收而跳过这些条件。

## 14. Git 与交付纪律

- 实现前检查当前分支、上游、工作区以及待推送和待拉取提交。
- 只有在远端和同名上游已经建立、完成 fetch 并核对 ahead/behind 后，才执行推送或部署。
- 各工作包只提交本包相关文件和测试，不混入其他 Agent 或用户改动。
- 提交信息使用中文标题、空行和编号正文，例如：

```text
实现工资累计预扣计算

1、增加居民工资薪金累计预扣规则
2、补充税率边界与跨月累计测试
```

- 禁止强制推送、改写已发布历史或删除远端分支。
