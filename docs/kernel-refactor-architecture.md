# 内核重构整体架构

本文定义按“全新开发、全新库”重整后的目标架构，作为各阶段设计的共同依据。基础修订已建立新库通用机制；业务领域的剩余改造和验收状态以路线图为准，不把整份目标视为已经实现。

问题来源为[内核架构审查](kernel-architecture-review.md)。阶段顺序、条目归属、待决选择和执行状态统一放在[阶段安排](kernel-refactor-roadmap.md)。具体字段、命令参数、迁移脚本和文件拆分，在相应阶段开始时细化。

## 一、设计基础与已定范围

本次重构建立在原审查 §1.1 的信任链上：

```text
原始资料 → 输入事实 → 凭证、报表和余额 → 老板核对 → 密码批准 → 关账冻结
```

重构不得破坏其中任何一环。核算结果必须能追到实际采用的事实和依据，老板必须能核对自己批准的业务内容。验证随具体改动进行，不增加逐项解释或证明信任保护的流程。

系统继续采用 Python 模块化单体、SQLite 和现有 Vue 五页看板。一位本地负责人管理多家公司，每家公司独立业务库；产品仍不承担法定账簿、纳税申报或报税系统的职责。

本次以目标职责决定设计，可复用现有实现，但不受旧数据库、旧接口和旧数据格式约束。不做现库升级、旧备份导入、旧业务转换或真实资料重录。新系统投入使用后的升级、备份恢复、历史读取和业务纠错必须支持。

本文的“历史”指新系统自身保存的业务历史。期初、累计工资、跨月清偿、事实修订和闭期更正都是正常业务能力，不能作为旧系统兼容删除。没有必要为了复用代码保留旧结构，也不能根据生产样本零使用删除业务能力。

已确定的产品取舍：

- 关账采用整月统一批准，不要求逐笔勾选。正式使用按公司逐月关账，批量能力只为测试准备、回放和验证服务。
- 备用金只记录管理费支出和实际退款，不管理余额、最大金额、可退额度或内部消费。
- AI 会计流程属于本次重构范围，包括查证、老板交互、执行反馈和中断接续。
- 先整理架构、减少重复读取和推导，再评估缓存。
- 继续使用现有本机运行方式。同账户直接改文件的风险如实保留，本次不追加操作系统隔离工程。
- 定期备份和跨公司配对本轮延后；新系统保留备份、恢复及各独立公司的实际业务能力，现有真实备份继续保全。

已有类型化入口、整数分、凭证平衡、原子提交、幂等、证据留存、闭期冻结及开放期关联更正继续成立。缺少影响核算的事实仍返回 `needs_information`；管理资料不能代替核算事实。具体约束以[仓库规则](../AGENTS.md)和[前端规则](../FRONTEND.md)为准。

## 二、职责与调用关系

业务模块、纯计算、事务引擎和适配层分别承担明确职责。现有实现符合这些职责时直接复用，需要调整时可直接修改。共同定义、读取规则和响应合同只在确有共同消费者的位置集中，不新增通用业务框架。

| 职责 | 接收与产出 | 归属与边界 |
| --- | --- | --- |
| 原始资料与确认 | 原件、明确的老板回答 → 不可变证据、来源位置和类型化事实 | 资料登记与业务模块；保留原文和实际精度，不根据接口需要补造资料。 |
| 身份与业务定义 | 已有身份、明确资料 → 可查找的对象身份、共同业务定义 | 身份登记与各业务模块；现实对象身份和单笔业务编号分开。 |
| 计算 | 明确版本的事实、规则、依赖 → 确定性结果 | 业务计算器；继续通过 `Context` 取得输入，不直接读取数据库、文件或当前时间。 |
| 发布与更正 | 已预览结果及对应版本 → 正式计算、凭证、依赖、审计和投影 | 统一事务引擎；专用业务入口也走相同的提交和幂等机制。 |
| 查询 | 公司、期间和读取口径 → 一致快照下的业务结果及来源 | 共享读取规则与页面投影；前端不重新计算税额或会计结果。 |
| 关账 | 期间准备结果、核对内容及批准 → 冻结结果和精确采用依据 | 期间模块与现有负责人批准通道；展示、批准和冻结绑定同一版。 |
| 文件交付 | 冻结的生成计划 → 持久任务和已验证文件 | 现有导出、备份及任务机制；生成文件不等于已经付款或申报。 |
| 会计流程 | 已有事实、缺项、执行回执及任务状态 → 待办和实际进度 | 内核提供业务状态，AI 查证和执行，老板决定确实需要其判断的事项。 |

一笔业务的正常路径是：登记依据和事实，读取明确输入并预览，在写事务内复核版本后正式发布。保存新事实不直接改写已发布凭证。来源变化后的复核、更正和撤去都回到这条路径，不增加独立的写账旁路。

## 三、数据由谁说了算

| 数据 | 权威来源 | 变化与恢复方式 |
| --- | --- | --- |
| 原始证据 | 实际登记的原件内容、摘要和来源位置 | 内容保留；新资料独立登记，不覆盖旧原件。 |
| 业务事实和确认依据 | 类型化事实修订及其证据 | 追加新版本，保留旧版本；闭期后可更新已知事实，但不得改写原冻结账务。 |
| 正式结果与凭证 | 已发布计算、凭证版本、发布关系及冲正关系 | 开放期按规则保号替代；闭期通过开放期更正，原冻结结果不变。 |
| 历史读取与采用依据 | 当时实际读取的版本、作用域以及明确采用关系 | 保留当时的记录，不能用今天的代码重新生成后覆盖。 |
| 关账记录 | 当时冻结的结果、直接采用记录和核对内容 | 保持不可变；后补事实及实际办理状态分别展示。 |
| 精确引用目录 | 不可变关账、任务和审计源中的原始引用 | 可以受控重建；目录不自行宣称业务已采用、已完成或已冻结。 |
| 金额投影与期间汇总 | 有效发布记录、凭证、余额影响和独立期初 | 可重建，并与权威来源交叉核验；不能简单累加全部历史行。 |
| 展示资料 | 有明确对象关系的名称、档案、说明及其版本 | 可追加、复用已有来源；后补资料不能冒充当时已知内容。 |
| 工作进度 | 事实、准备检查、正式发布、外部完成依据及持久任务 | 查询时组织成待办，不用聊天记忆或另存的完成标记覆盖实际状态。 |

“从其他数据生成”不等于“可以随时重算历史”。引用目录可以按冻结源恢复，历史依赖却记录了当时实际采用什么，两者保持不同职责。

## 四、共同业务定义与身份

### 4.1 定义集中，核算仍由计算器决定

同一业务含义只维护一份定义，优先消除资金业务科目映射在发布和查询之间的重复。科目名称、报表归属、资金业务对应科目、税种和义务来源由对应模块声明，其他消费者引用。

费率、政策生效区间和实际适用依据作为事实保存。统一登记、修订及使用时的来源语义，保留官方来源、证据与生效版本。新系统从登记起满足来源要求，不接入旧系统缺少来源的政策格式；以后规则变化也不得补造或改写已保存的历史依据。

共同定义不向 AI 开放任意科目和借贷配置。精确匹配是否包含子科目按业务含义决定，不统一改成前缀匹配。登记侧已有从模型生成事实合同的机制继续使用。

事实字段统一声明核算或管理语义、允许精度和可复用来源。按月成立的依据不补成实际日，管理日期不代替核算日期；缺项和冲突由结构化字段说明，不将接口字段逐个转成老板的问题。

### 4.2 身份能够查找、复用和纠错

人员、机构、公司资金账户、资产、项目和基金产品统一登记，对象编号由内核生成；单笔业务另有业务编号。姓名、外部编号和已有档案用于查找，不能单独证明两个对象相同。一个自然人可同时承担员工、报销人和交易方角色。payee 指向人员或机构，户名和账号属于付款指令，不是公司的资金账户。

事实模型声明哪些字段引用哪类身份。登记时核对引用，并建立对象与事实的查询关系。先查找已有身份，再明确复用或新建；姓名、金额或拼写相似只能提供线索，不能自动合并。实际资金账户来自明确的业务身份，不能根据会计科目反推。

身份纠错使用专用预览和提交，按精确事实范围覆盖新旧作用域、累计、清偿及资产批次。事实版本、纠错依据、计算、发布、投影及名单状态在同一事务完成；开放段保留原入账月，闭期差额明确开放月。未冻结期初追加事实并重算原包；冻结期初用精确采用绑定调整归属，原包及经济内容保留。冲突期初明确保留／取代依据，只有整组差额平衡才发布，不自动补权益。再次纠错可恢复被误指的归属或误取代的业务，不建立永久全局别名。普通保存和修改不能变更既有对象引用的编号；新增、撤下业务明细仍按各领域规则处理。

新系统使用后，同一个人同月出现两份冲突工资时，必须先解决事实冲突，不能自动相加、取最新或隐藏其中一份。纠错前的身份和历史关系保留，修改展示名称不等于完成了核算纠错。本轮不设计现库身份回填或历史数据接入。

### 4.3 业务查重与身份查找分开

业务唯一性、工资及一般债务的防重复核销、请求幂等继续保护正式处理。现实业务的疑似重复结合原件位置、期间、对象、日期和金额形成候选；同一原件可以支持多笔业务，候选本身不等于重复。备用金不因此恢复退款额度或容量控制。

各类型声明业务角色、对象、金额及完整核算比较字段，不用模糊评分。同角色同对象同金额且同已核验原件位置、完整内容及非支持性依据相同、或实际资金完整组合相同，形成强候选；已核验不同明细可以区分。同名、同额、同文件等弱线索只供查找和详情，不主动打断。

强候选先核对，AI 先查资料，仍不明白才问负责人。复用或另建结论绑定拟登记内容、候选事实、资料及规则版本；另建需要明确区分依据。登记、发布、关账重新检查，批量登记一项未解决则整体回滚，领域硬限制仍有效，不增加每笔密码批准。后补资料或纠错发现的疑点由适用开放期承接。

事实发现按类型、对象、角色、期间和状态筛选，区分原记录身份与当前确认归属，返回原始事实及匹配依据。当前与历史使用各自索引，先取 limit+1，再按类型批量装载本页。游标绑定公司、数据库、全部筛选、业务和读取修复版本；无期间不造假条件，单边只用单边谓词。引用索引只作派生查询，普通页核验命中，完整核验及备份发现缺行，显式修复不改权威资料。

## 五、读取、发布与版本

### 5.1 共用读取语义

沿用 `Read` 和 `Context`，让数据库选择、同批次输入覆盖、依赖排序及后续失效使用一致的来源、类型、作用域和期间规则。精确版本、跨类型、按月、通配和空命中读取保留各自含义。

事实变化同时考虑旧、新作用域。读取实际用到的版本及空范围进入依赖记录，相关版本参与提交检查。测试辅助函数不再另写一套生产匹配规则；业务结果验证仍使用独立的期望结果。

读取范围按用途组织：列出对象、选择会计结果和展开依据各自只做所需工作。返回行数有限不等于后台扫描有限，关键路径还要检查实际读取、解码和依赖展开量。

### 5.2 版本分别负责不同问题

| 版本或标识 | 负责什么 |
| --- | --- |
| 数据体系标识、数据库类别与结构版本 | 区分新旧系统、目录库与公司库，并决定是否允许打开或执行已知升级。 |
| 事实与结果格式版本 | 说明保存内容如何解读和核验；今后格式变化不抹去已保存历史。 |
| 接口合同版本 | 识别调用方与服务的合同是否一致，不代替数据快照或数据库结构版本。 |
| 事实、计算和凭证的精确版本 | 指明实际处理、引用和核对的是哪一份记录。 |
| 核算、资料、管理的提交版本 | 判断预览后相关输入是否变化；由实际读取和修改范围决定检查哪些版本。 |
| 内容摘要与核算比较 | 内容摘要核对具体内容；核算比较判断会计影响，两者不能互相代替。 |
| 读取修复版本 | 让页面、分页及复用结果识别投影或目录修复造成的变化，不必推动所有业务版本。 |
| 计算器构建身份 | 识别运行代码变化；继续由构建内容派生，不能单凭它断定新旧核算等价。 |

页面快照包含公司、数据库实例、期间和相关版本。分页、准备结果和核对内容不得拼接不同快照。恢复、修复或切换公司后，消费者重新取得相符的数据。

### 5.3 发布、删除和维护

普通发布与专用业务操作都复用统一事务，保留幂等、提交前授权检查和失败回滚。删除预览与最终事务核对同一事实版本和相关依赖，旧预览不能撤去后来修订的事实。

内容核验覆盖正式计算、完整凭证行、凭证版本、有效采用、投影和关账内容。发布核对本次影响范围，关账核对本期及实际采用依据，备份、恢复和显式完整性检查覆盖全库。历史核验使用当时保存的结果，不要求历史账务等于今天重新算出的结果。

新系统从首个正式版本保存完整的必要采用依据。缺少必需记录属于错误，不沿用旧系统“历史未记录，因此只能有限核验”的兼容分支。未知格式明确拒绝，不能用补默认值或重新计算掩盖内容缺失。

引用目录修复从不可变源取得完整预期内容，在受控维护事务中恢复目录并验证后提交。修复机制只处理可恢复的目录，不改变源记录和历史依赖，不提供通用绕过约束的模式；普通连接不自动扫描和修复。

文件权限统一覆盖资料目录、目录库、公司库、边车文件和备份的创建、打开与恢复。现有密码重认证、节流、会话撤销和事务内批准消费继续保留。原生窗口不是操作系统隔离；同账户有文件写权限时仍可能绕过 API。内容一致性检查也不能证明被一致改写的全部内容真实，本次不宣称解决这一环境边界。

## 六、期间、历史与关账

### 6.1 三种时间口径

| 读取口径 | 回答的问题 | 选择依据 |
| --- | --- | --- |
| 当前有效结果 | 现在账上是什么状态？ | 当前有效发布与明确的后续关系。 |
| 按现有结果还原历史 | 截至目标月实际入账多少、该月发生多少？ | 正式发布链按实际入账月归集，后来更正在实际更正月体现。 |
| 当时冻结 | 当时关账到底采用了什么？ | 该次关账的精确结果和不可变采用依据。 |

资金页和报表共用实际入账口径。1 月冻结 100 元、3 月更正为 120 元，1 月账面仍是 100 元，3 月增加 20 元；业务详情另列当前业务值 120 元及冻结采用。未发布事实不能替代账上结果，五页不新增口径切换按钮。报表 `source=open|closed` 分别表示当前账面还原和当月精确冻结；不存在当月关账时明确请求冻结返回 `frozen_snapshot_unavailable`。

余额贡献投影按正式发布、实际入账期、类别和对象归集，期初单独标记，不计本月发生。当前余额保留并与期间贡献合计核对。清偿贡献投影独立保存明确来源、义务键、期间、金额和未知状态，只服务读取，不决定付款或核销资格。简报 KPI 汇总完整范围，明细先分页再装载。看板与报表共用冻结基线、后续发生额、独立期初的汇总算法。

已决定开放月份按业务所属月入账，不允许任意选择另一个开放月。所属月已关账的迟到业务及冻结结果更正须明确提供 `posting_period`。开放更正继续替换原开放段，不因操作日期变晚而移期。自动重算的开放期依赖保留各自原月，不随闭期更正移月；显式选择结果与指定月份冲突时拒绝。原业务允许的所属月纠错仍有效；改到新的开放所属月时，该开放段的冲正和替换一同移到新月份。工资等业务的身份限制不变。保留空月覆盖规则，覆盖不等于独立批准。

`calculation_publication` 是唯一正式发布链，节点不可改删，按主体无分叉接续。节点记录实际顺序、前次发布、计算、动作、入账月、固定比较基准和凭证。撤去产生明确节点，资产成员不独立发布金额。首次增加贡献，开放替换撤旧段再加新段，闭期更正增加新旧差额，无影响复核沿用金额与凭证并记录新依据。固定基准保证连续更正不会重复计额。

两类投影与正式发布同事务更新；维修只重建派生数据，实际变化推进读取修复版本。按期间和类别保存内容封签，期间封签同时绑定类别和发布集合，空结果也保留范围核对。普通读取核对命中投影及来源摘要；关账、完整性检查、备份和维修独立重建语义。核验成功只在同一只读快照、相同来源和范围内复用，失败不缓存，不增加跨请求缓存。缺少上年可比资料只影响比较列，不豁免本期完整性。

### 6.2 直接记录实际采用的结果

`period_close` 的不可变内容和摘要是唯一冻结权威。新合同直接保存本期采用的发布与计算、精确凭证版本、凭证拥有者与采用依据、冲正关系、无凭证结果、独立期初、资产批次及逐卡采用，连同资料清单、准备依据、管理快照、负责人确认和试算平衡。发布顺序边界、批准快照版本、前次关账身份和摘要共同确定该次冻结范围。复核可沿用旧凭证，但新依据不是旧凭证的产生依据；依赖中出现也不等于本期直接采用。

完整依据沿已有不可变依赖追溯，避免每期反复保存累计闭包、查询时再从闭包倒推实际采用结果。原始引用目录只索引冻结源实际记录的引用，不把推导出的采用结论变成新的权威来源。

本轮不保留旧系统关账格式的双重读取，不做新旧关账表示之间的接续。新系统自己的冻结记录仍不可改写。累计链与独立业务分别测量，不承诺所有存储增长都变成固定复杂度。

第 3 阶段用当前可复用业务和合成结果验证共同历史机制。后续身份、备用金、工资阶段明确自身结果、余额变化和精确采用引用，并在当期接入读取、核验和页面；历史层不靠猜测补齐业务含义。

### 6.3 同一版内容用于核对、批准和冻结

内核从生成关账预览的同一快照产生可读核对内容，包括主要金额、业务清单、关键变化、资料覆盖、实际采用依据和剩余事项。AI 撰写的摘要不能替代这份核对内容。

看板与批准窗口显示同一版。原件、来源位置、工资方案、政策版本及官方来源可以按需展开；内部编号和哈希放入技术详情。保留现有密码重认证、批准与版本绑定、单次消费和失败回滚。

数据变化后旧预览失效。关账冻结对应内容及其依据，后补事实和实际办理进度另行展示。核算依据的业务化展示不扩展为看板上的逐层计算依赖图，`trace` 继续作为 CLI/MCP 读取能力。

## 七、需要收敛的业务模型

### 7.1 工资确认贯通发布

本期已确认工资方案或仍有效的明确沿用依据，成为工资正式计算和发布的依赖。普通工资、bounded 工资、已有工资的准备、直接发布和重算遵守同一要求，不能通过跳过准备命令绕开。

采用依据明确公司、月份、人员和确认范围。方案或相关来源变化使受影响计算失效，真实付款不被重算改写。沿用现有业务确认方式，不新增工资密码窗口；确认原文与来源保留，不能把 AI 自写“已确认”说成独立的人类认证。

不为旧系统闭期工资缺少确认依据保留例外，也不补造负责人当时已经确认。新系统保存实际采用的确认版本；后续修改不改变已冻结内容。个人扣款无法映射个税文件的问题提前在准备环节呈现，正式文件仍明确拒绝错误映射。

### 7.2 闭期补录有人承接

归属已关月份的补录资料仍保留原归属。新出现的未处理行、重复占用或金额冲突进入开放期待办，由关账和完整代发共用的检查器承接，直至问题被有效处置。

合法未来资料只影响自身期间，不以全局文件状态阻断所有月份。资料清单中的计数自洽不能代替逐行覆盖；残留字段随资料模型整理，不将未使用字段包装成已有控制。

### 7.3 备用金直接表达支出和退款

实际转入备用金计管理费，实际退回公司冲抵管理费。新业务直接说明支出或退款，不以范围、成本目录、FIFO、容量或跨期接续作为前置条件。

工资付款中的净薪与备用金部分继续按明确依据拆分，保持银行全额、实际资金方向和工资防重复核销。备用金内部怎样消费不进入本模型。

范围、成本资格、容量、FIFO、分配和接续模型随本阶段退出，不设计旧业务迁移、兼容读取或专用转换。新系统登记的支出与退款仍支持有依据的误记撤去、开放期更正和闭期冲正。

债务结清或退款权利不等于钱已退回。支出和退款必须依据实际资金事实，不自动造日期、账户或一对一分配关系，也不把备用金内部消费作为必填资料。

## 八、共享接口、看板与 AI 会计流程

### 8.1 共享响应合同从前期建立

以 Python 类型化读取模型作为响应合同来源，共享字段含义、版本规则和校验要求。复用已实现的 TypedDict、TypeAdapter、HTTP JSON Schema、TypeScript 和 Ajv 预编译校验器生成链，以及事实登记合同生成机制，不另造通用 Schema 框架。

MCP 金额保持整数分，HTTP 金额使用十进制整数分字符串，浏览器用 `BigInt`。合同明确字段省略与 null、未知与零、已建立与未建立、分页范围、快照和任务状态；空目录、没有月份、尚未检查都属于正常情况。整数分拒绝浮点、布尔、越界及非规范编码。静态类型不代替运行时校验。

允许直接修改命令、字段和响应，不承担旧接口兼容。每次变化同时更新服务边界、Schema、生成产物、CLI、MCP、页面及操作说明，并删除被替代的字段别名和旧校验路径。第 7 阶段完成剩余看板合同接入，不负责补救此前留下的接口断裂。

生成产物入库，生成检查在临时目录比较，不暗中修改文件。后端返回不符合合同属于程序错误，只报告必要路径，不泄露值或转成老板追问。已知需要更换专用入口的错误返回结构化指引，真正的核算缺项继续用 `fact_issues`。

### 8.2 五页继续使用共同上下文

经营简报、资金、员工、资产和财务报表继续使用同一公司与月份上下文。汇总按完整集合计算，明细按需分页；应收应付等主数字不能用已加载页凑数，也不能整体推迟到详情展开。

实际收支、业务确认金额、凭证合计和账户互转保持区别。清偿事件显示后端真实状态及问题，未知金额不计入已确认结果；员工历史明细继续按需读取并保留跨月视角。

普通未关账、正常往来和非必需管理资料缺项不当作异常。具体中文文案和展示层级沿用前端规则，有实质使用取舍再由老板决定。

### 8.3 会计工作按真实状态推进

内核统一组织资料与核算、关账、实际办理、文件交付四类工作状态。银行、工资、一般业务、资产、税务和融资缺项进入对应业务位置；关账可以汇总问题，不能成为它们第一次出现的位置。

例如：“8 月账已关，个税还没申报，备份正在生成。”三个状态可以同时成立。文件生成、付款完成和申报完成分别有自己的依据，不能用一个“完成”覆盖。

运行协议承接会计流程要求，Skill 和默认提示与其保持一致：泛化开始时说明公司、月份和进度；明确事项直接处理；先查已有资料再问；老板回答落实到刚才展示的范围；真正推进后更新进度；失败或中断后从事实、版本和任务回执接续。同一步未推进不反复刷整张清单。

第 8 阶段验证完整对话流程，前面各阶段涉及的操作说明当期更新。正式批量关账入口在单月核对流程接入时退出，不能继续通过旧提示或生产包里的测试入口使用。

## 九、新库起点、未来升级与交付

### 9.1 独立的新版本体系

当前新系统标识为 `ai-accounting-kernel/2`，类别为 `catalog` / `company`，SQLite 辅助标识为 `0x41414332`。目录库和公司库均使用 `draft / 0`，备份格式为 2；不再承接原目录 v1–v3、公司 v1–v13 或旧备份。不可修改的 `schema_meta` 保存系统/类别/状态，`user_version` 保存结构版本，`schema_history` 保存实际安装指纹；稳定业务身份不包含版本。

创建、打开、读取、绑定、核验、升级、备份和恢复使用一致的身份与结构识别。新系统拒绝旧体系或缺少新标识的库和备份，不补标识、不隐式转换。已经存在的文件即使没有业务行，也不能当成可覆盖的新建目标。

开发期使用明确的开发基线，包内合同、库内记录和 SQLite 实际保存的 SQL 原文必须相符；未发布不意味着跳过结构校验。同一开发结构可以登记、发布、关账、备份和恢复测试。结构改变后由测试显式创建另一个临时资料根，不承诺阶段间测试库升级，不自动删除或重建已有文件。

第 9 阶段交付时冻结目录库和公司库各自的首个正式版本。正式版不承诺接收开发库；本轮不包含把开发资料或真实公司资料转入正式库。

### 9.2 从首个正式版本开始前向升级

每类数据库以一份完整根合同起步，后续合同保存父版本及指纹、明确的对象变化和完整目标指纹。加载时还原并核对完整目标，结构差异能够直接审阅；已发布的新体系合同不可回写。

迁移步骤由包内可信代码登记，绑定同体系的源和目标版本及指纹，明确变更动作和数据保留检查。保留加列、重命名、索引或触发器替换，以及必要时的单表复制替换。整次升级原子执行，锁内复核结构，失败回滚；外键恢复并回读成功后连接才能继续使用。不得接收外部 SQL 或自动猜测未知结构。

基础修订阶段就用隔离测试合同验证未来升级，不等正式 v1 发布后才验证。独立新建目标库与升级结果应有相同完整结构，原数据、主键、引用和历史保留；版本记录只记实际经过的步骤。

未来升级分别处理数据库结构与保存内容的版本，保留新系统自身历史的明确读取和必要适配。不得以当前计算器重算来覆盖冻结结果，也不得补确认、补付款或把技术变化误认为会计金额变化。

### 9.4 性能与交付范围

性能先从对象枚举、结果选择、依据展开、批量读取及期间汇总减少实际工作。缓存放在结构调整后评估，必须有明确的有效版本、容量和清理条件；不能仅因内容不可变就无限复用，也不能通过省略必要核验凑出耗时。

验收保留看板刷新低于 500 毫秒的目标。测量包含点击刷新到主数字及首屏明细完成显示的整条路径，审计涉及的四个主端点分别记录服务端耗时。准备度和详情按需读取时明确显示尚未检查，不提前显示通过。固定代表性样本，报告重复测量分布而非最小值，冷启动另列。

使用新建合成公司和独立的业务预期，覆盖多期累计、频繁修订、跨月清偿、身份纠错、独立期初、资产批次、关账冻结、证据体积和公司切换。各阶段完成自身回归，最后统一验证性能、整轮会计工作、运行包及备份恢复。旧测试按新合同调整，不能通过删除断言掩盖缺陷，也不能用旧审查或旧阶段的测试数字冒充当前结果。

本次不操作原始资料、负责人确认、现有公司数据库或既有备份。真实公司的重录、替换和切换不在本轮范围，也不以旧公司余额一致作为正确性证明。独立年报格式、所得税按税率推算和新增权益业务等能力扩展，不夹带进本次缺陷重构。
