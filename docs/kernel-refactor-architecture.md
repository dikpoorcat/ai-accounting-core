# 内核重构整体架构

本文定义独立新体系的目标架构，作为各阶段设计的共同依据；当前优先接续已有的本体系公司库，空库重放仅由用户明确指定。阶段进度见[路线图](kernel-refactor-roadmap.md)，实际修改和验收见各阶段文档。本轮第9阶段保持目录库与公司库draft／0，现有5173、资料根和负责人身份原样；正式合同冻结、正式包交付和运行入口切换延期。局部读取优化保留完整金额、来源、冻结采用、未知和失败原子性，不能改变固定历史版本的核验规则；当前开发库不承诺自动接入未来正式版本。

问题来源为[内核架构审查](kernel-architecture-review.md)。阶段顺序、条目归属、待决选择和执行状态统一放在[阶段安排](kernel-refactor-roadmap.md)。具体字段、命令参数、迁移脚本和文件拆分，在相应阶段开始时细化。

## 一、设计基础与已定范围

普通记账保留原审查 §1.1 的信任链：

```text
原始资料 → 输入事实 → 凭证、报表和余额 → 老板核对 → 密码批准 → 关账冻结
```

核算结果必须能追到实际采用的事实和依据，老板必须能核对自己批准的业务内容。重放专用流程以已登记负责人确认和本机显式范围限制执行批量关账，仍逐月核对并冻结精确采用依据；其范围审计不冒充密码批准。入口已实现并通过合成验证，实际重建仍暂停，第9阶段本轮开发范围完成；需本机显式重新启动才启用范围。验证随具体改动进行，不增加逐项解释或证明信任保护的流程。

系统继续采用 Python 模块化单体、SQLite 和现有 Vue 五页看板。一位本地负责人管理多家公司，每家公司独立业务库；产品仍不承担法定账簿、纳税申报或报税系统的职责。

本次重构开发以目标职责决定设计，可复用现有实现，不受旧体系数据库、接口和数据格式约束；旧备份导入和新旧体系业务转换不在范围内。当前本体系现库优先，所需开发结构变化通过有明确来源的前向调整接续，不自行换库、重放或重新设置负责人。真实业务执行单独记录公司范围、资料及回执，不混入合成开发验收。升级、备份恢复、历史读取和业务纠错必须保留新系统自身已有的数据与身份。

本文的“历史”指新系统自身保存的业务历史。期初、累计工资、跨月清偿、事实修订和闭期更正都是正常业务能力，不能作为旧系统兼容删除。没有必要为了复用代码保留旧结构，也不能根据生产样本零使用删除业务能力。

已确定的产品取舍：

- 普通记账关账采用整月统一批准，不要求逐笔勾选，保留逐月本机密码批准。按重放文档执行时默认采用[重放专用批量关账](replay-batch-close.md)，由本机显式范围服务及有效负责人登录限制公司、数据库、月份和已登记范围确认摘要，不逐月请求密码；正常常驻服务拒绝批量命令。新入口已实现并通过合成验证，不恢复阶段7退役的通用批量批准体系。
- 备用金只记录管理费支出和实际退款，不管理余额、最大金额、可退额度或内部消费。
- AI 会计流程属于本次重构范围，包括查证、老板交互、执行反馈和中断接续。
- 先整理架构、减少重复读取和推导，再评估缓存。
- 继续使用现有本机运行方式。同账户直接改文件的风险如实保留，本次不追加操作系统隔离工程。
- 定期备份和跨公司配对本轮延后；新系统保留备份、恢复及各独立公司的实际业务能力，现有真实备份继续保全。

已有类型化入口、整数分、凭证平衡、原子提交、幂等、证据留存、闭期冻结及开放期关联更正继续成立。缺少影响核算的事实仍返回 `needs_information`；管理资料不能代替核算事实。具体约束以[仓库规则](../AGENTS.md)和[前端规则](../FRONTEND.md)为准。

## 二、职责与调用关系

业务模块、纯计算、事务引擎和适配层分别承担明确职责。现有实现符合这些职责时直接复用，需要调整时可直接修改。共同定义、读取规则和响应合同只在确有共同消费者的位置集中，不新增通用业务框架。

| 职责 | 接收与产出 | 归属与边界 |
| --- | --- | --- |
| 原始资料与确认 | 原件、明确的老板回答 → 不可变证据、来源位置和类型化事实 | 资料登记与业务模块；保留原文和实际精度，不根据接口需要补造资料。 |
| 身份与业务定义 | 已有身份、明确资料 → 可查找的对象身份、共同业务定义 | 身份登记与各业务模块；现实对象身份和单笔业务编号分开。 |
| 计算 | 明确版本的事实、规则、依赖 → 确定性结果 | 业务计算器；继续通过 `Context` 取得输入，不直接读取数据库、文件或当前时间。 |
| 发布与更正 | 已预览结果及对应版本 → 正式计算、凭证、依赖、审计和投影 | 统一事务引擎；专用业务入口也走相同的提交和幂等机制。 |
| 查询 | 公司、期间和读取口径 → 一致快照下的业务结果及来源 | 共享读取规则与页面投影；前端不重新计算税额或会计结果。 |
| 关账 | 期间准备结果、核对内容及操作范围 → 冻结结果和精确采用依据 | 普通记账保留负责人密码批准通道；重放专用入口绑定明确范围、当前版本和有效登录，逐月完整检查及冻结，范围审计不是密码批准。 |
| 文件交付 | 冻结的生成计划 → 持久任务和已验证文件 | 现有导出、备份及任务机制；生成文件不等于已经付款或申报。 |
| 会计流程 | 已有事实、缺项、执行回执及任务状态 → 待办和实际进度 | 内核提供业务状态，AI 查证和执行，老板决定确实需要其判断的事项。 |

一笔业务的正常路径是：登记依据和事实，读取明确输入并预览，在写事务内复核版本后正式发布。保存新事实不直接改写已发布凭证。来源变化后的复核、更正和撤去都回到这条路径，不增加独立的写账旁路。

## 三、数据由谁说了算

| 数据 | 权威来源 | 变化与恢复方式 |
| --- | --- | --- |
| 原始证据 | 实际登记的原件内容、摘要和来源位置 | 内容保留；新资料独立登记，不覆盖旧原件。 |
| 业务事实和确认依据 | 类型化事实修订及其证据 | 追加新版本，保留旧版本；闭期后可更新已知事实，但不得改写原冻结账务。 |
| 正式结果与凭证 | 已发布计算、凭证版本、发布关系及冲正关系 | 开放期按规则保号替代；闭期通过开放期更正，原冻结结果不变。 |
| 历史读取与采用依据 | 当时实际读取的版本、作用域以及明确采用关系 | 保留当时的记录，不能用今天的代码重新生成后覆盖。 |
| 关账记录 | 当时冻结的结果、直接采用记录和核对内容 | 保持不可变；后补事实及实际办理状态分别展示。 |
| 精确引用目录 | 不可变关账、任务和审计源中的原始引用 | 可以受控重建；目录不自行宣称业务已采用、已完成或已冻结。 |
| 金额投影与期间汇总 | 有效发布记录、凭证、余额影响和独立期初 | 可重建，并与权威来源交叉核验；不能简单累加全部历史行。 |
| 展示资料 | 有明确对象关系的名称、档案、说明及其版本 | 可追加、复用已有来源；后补资料不能冒充当时已知内容。 |
| 工作进度 | 事实、准备检查、正式发布、外部完成依据及持久任务 | 查询时组织成待办，不用聊天记忆或另存的完成标记覆盖实际状态。 |

“从其他数据生成”不等于“可以随时重算历史”。引用目录可以按冻结源恢复，历史依赖却记录了当时实际采用什么，两者保持不同职责。

## 四、共同业务定义与身份

### 4.1 定义集中，核算仍由计算器决定

同一业务含义只维护一份定义，优先消除资金业务科目映射在发布和查询之间的重复。科目名称、报表归属、资金业务对应科目、税种和义务来源由对应模块声明，其他消费者引用。

费率、政策生效区间和实际适用依据作为事实保存。工资、奖金、劳务、税务与申报日历共用底层来源校验，仅接受合法 HTTPS `gov.cn` 及其子域，拒绝凭据、伪装主机与非法字符。来源原文、证据和生效版本保留，计算不联网，也不自动选政策或改变税率。新系统从登记起满足来源要求，不接入旧系统缺少来源的政策格式；以后规则变化也不得补造或改写已保存的历史依据。

共同定义不向 AI 开放任意科目和借贷配置。精确匹配是否包含子科目按业务含义决定，不统一改成前缀匹配。登记侧已有从模型生成事实合同的机制继续使用。

事实字段统一声明核算或管理语义、允许精度和可复用来源。按月成立的依据不补成实际日，管理日期不代替核算日期；缺项和冲突由结构化字段说明，不将接口字段逐个转成老板的问题。

### 4.2 身份能够查找、复用和纠错

人员、机构、公司资金账户、资产、项目和基金产品统一登记，对象编号由内核生成；单笔业务另有业务编号。姓名、外部编号和已有档案用于查找，不能单独证明两个对象相同。一个自然人可同时承担员工、报销人和交易方角色。payee 指向人员或机构，户名和账号属于付款指令，不是公司的资金账户。

事实模型声明哪些字段引用哪类身份。登记时核对引用，并建立对象与事实的查询关系。先查找已有身份，再明确复用或新建；姓名、金额或拼写相似只能提供线索，不能自动合并。实际资金账户来自明确的业务身份，不能根据会计科目反推。

身份纠错使用专用预览和提交，按精确事实范围覆盖新旧作用域、累计、清偿及资产批次。事实版本、纠错依据、计算、发布、投影及名单状态在同一事务完成；开放段保留原入账月，闭期差额明确开放月。未冻结期初追加事实并重算原包；冻结期初用精确采用绑定调整归属，原包及经济内容保留。冲突期初明确保留／取代依据，只有整组差额平衡才发布，不自动补权益。再次纠错可恢复被误指的归属或误取代的业务，不建立永久全局别名。普通保存和修改不能变更既有对象引用的编号；新增、撤下业务明细仍按各领域规则处理。

新系统使用后，同一个人同月出现两份冲突工资时，必须先解决事实冲突，不能自动相加、取最新或隐藏其中一份。纠错前的身份和历史关系保留，修改展示名称不等于完成了核算纠错。本轮不设计现库身份回填或历史数据接入。

### 4.3 业务查重与身份查找分开

业务唯一性、工资及一般债务的防重复核销、请求幂等继续保护正式处理。现实业务的疑似重复结合原件位置、期间、对象、日期和金额形成候选；同一原件可以支持多笔业务，候选本身不等于重复。备用金不因此恢复退款额度或容量控制。

各类型声明业务角色、对象、金额及完整核算比较字段，不用模糊评分。同角色同对象同金额且同已核验原件位置、完整内容及非支持性依据相同、或实际资金完整组合相同，形成强候选；已核验不同明细可以区分。同名、同额、同文件等弱线索只供查找和详情，不主动打断。

强候选先核对，AI 先查资料，仍不明白才问负责人。复用或另建结论绑定拟登记内容、候选事实、资料及规则版本；另建需要明确区分依据。登记、发布、关账重新检查，批量登记一项未解决则整体回滚，领域硬限制仍有效，不增加每笔密码批准。后补资料或纠错发现的疑点由适用开放期承接。

事实发现按类型、对象、角色、期间和状态筛选，区分原记录身份与当前确认归属，返回原始事实及匹配依据。当前与历史使用各自索引，先取 limit+1，再按类型批量装载本页。游标绑定公司、数据库、全部筛选、业务和读取修复版本；无期间不造假条件，单边只用单边谓词。引用索引只作派生查询，普通页核验命中，完整核验及备份发现缺行，显式修复不改权威资料。

## 五、读取、发布与版本

### 5.1 共用读取语义

沿用 `Read` 和 `Context`，让数据库选择、同批次输入覆盖、依赖排序及后续失效使用一致的来源、类型、作用域和期间规则。精确版本、跨类型、按月、通配和空命中读取保留各自含义。

事实变化同时考虑旧、新作用域。读取实际用到的版本及空范围进入依赖记录，相关版本参与提交检查。测试辅助函数不再另写一套生产匹配规则；业务结果验证仍使用独立的期望结果。

读取范围按用途组织：列出对象、选择会计结果和展开依据各自只做所需工作。返回行数有限不等于后台扫描有限，关键路径还要检查实际读取、解码和依赖展开量。

### 5.2 版本分别负责不同问题

| 版本或标识 | 负责什么 |
| --- | --- |
| 数据体系标识、数据库类别与结构版本 | 区分新旧系统、目录库与公司库，并决定是否允许打开或执行已知升级。 |
| 事实与结果格式版本 | 说明保存内容如何解读和核验；今后格式变化不抹去已保存历史。 |
| 接口合同版本 | 识别调用方与服务的合同是否一致，不代替数据快照或数据库结构版本。 |
| 事实、计算和凭证的精确版本 | 指明实际处理、引用和核对的是哪一份记录。 |
| 核算、资料、管理的提交版本 | 判断预览后相关输入是否变化；由实际读取和修改范围决定检查哪些版本。 |
| 内容摘要与核算比较 | 内容摘要核对具体内容；核算比较判断会计影响，两者不能互相代替。 |
| 读取修复版本 | 让页面、分页及复用结果识别投影或目录修复造成的变化，不必推动所有业务版本。 |
| 计算器构建身份 | 识别运行代码变化；继续由构建内容派生，不能单凭它断定新旧核算等价。 |

页面快照包含公司、数据库实例、期间和相关版本。分页、准备结果和核对内容不得拼接不同快照。恢复、修复或切换公司后，消费者重新取得相符的数据。

### 5.3 发布、删除和维护

普通发布与专用业务操作都复用统一事务，保留幂等、提交前授权检查和失败回滚。删除预览与最终事务核对同一事实版本和相关依赖，旧预览不能撤去后来修订的事实。

内容核验覆盖正式计算、完整凭证行、凭证版本、有效采用、投影和关账内容。发布核对本次影响范围，关账核对本期及实际采用依据，备份、恢复和显式完整性检查覆盖全库。历史核验使用当时保存的结果，不要求历史账务等于今天重新算出的结果。

新系统从首个正式版本保存完整的必要采用依据。缺少必需记录属于错误，不沿用旧系统“历史未记录，因此只能有限核验”的兼容分支。未知格式明确拒绝，不能用补默认值或重新计算掩盖内容缺失。

引用目录修复从不可变源取得完整预期内容，在受控维护事务中恢复目录并验证后提交。修复机制只处理可恢复的目录，不改变源记录和历史依赖，不提供通用绕过约束的模式；普通连接不自动扫描和修复。

文件权限统一覆盖资料目录、目录库、公司库、边车文件和备份的创建、打开与恢复。普通关账保留密码重认证、节流、会话撤销和事务内批准消费。重放专用服务以 `daemon --replay-scope <private.json>` 显式启用，仍验证负责人登录及限定范围；会话改变使原批量失效，服务自动重启不隐式继承范围。原生窗口不是操作系统隔离；同账户有文件写权限时仍可能绕过 API。内容一致性检查也不能证明被一致改写的全部内容真实，本次不宣称解决这一环境边界。

范围文件严格采用 `format="ai-accounting-kernel/2/replay-close-scope/1"`、`catalog_instance_id`、`targets`；目标只含 `company_id`、`database_id`、`first_period`、`last_period`、`owner_confirmation`。启动校验目录身份、1至120个连续月及公司不重复；执行入口另核对目标公司和数据库身份、开发draft合同及已登记确认原件，released正式公司库拒绝。文件在显式启动时读取并固定，自动启动默认普通服务，更新范围需显式重新启动。

## 六、期间、历史与关账

### 6.1 三种时间口径

| 读取口径 | 回答的问题 | 选择依据 |
| --- | --- | --- |
| 当前有效结果 | 现在账上是什么状态？ | 当前有效发布与明确的后续关系。 |
| 按现有结果还原历史 | 截至目标月实际入账多少、该月发生多少？ | 正式发布链按实际入账月归集，后来更正在实际更正月体现。 |
| 当时冻结 | 当时关账到底采用了什么？ | 该次关账的精确结果和不可变采用依据。 |

资金页和报表共用实际入账口径。1 月冻结 100 元、3 月更正为 120 元，1 月账面仍是 100 元，3 月增加 20 元；老板业务详情按明确期间展示金额和业务影响，精确采用依据由 AI 会计通过 CLI/MCP 读取。未发布事实不能替代账上结果，五页不新增口径切换按钮。报表 `source=open|closed` 分别表示当前账面还原和当月精确冻结；不存在当月关账时明确请求冻结返回 `frozen_snapshot_unavailable`。

余额贡献投影按正式发布、实际入账期、类别和对象归集，期初单独标记，不计本月发生。当前余额保留并与期间贡献合计核对。清偿贡献投影独立保存明确来源、义务键、期间、金额和未知状态，只服务读取，不决定付款或核销资格。简报 KPI 汇总完整范围，明细先分页再装载。看板与报表共用冻结基线、后续发生额、独立期初的汇总算法。

已决定开放月份按业务所属月入账，不允许任意选择另一个开放月。所属月已关账的迟到业务及冻结结果更正须明确提供 `posting_period`。开放更正继续替换原开放段，不因操作日期变晚而移期。自动重算的开放期依赖保留各自原月，不随闭期更正移月；显式选择结果与指定月份冲突时拒绝。原业务允许的所属月纠错仍有效；改到新的开放所属月时，该开放段的冲正和替换一同移到新月份。工资等业务的身份限制不变。保留空月覆盖规则，覆盖不等于独立批准。

`calculation_publication` 是唯一正式发布链，节点不可改删，按主体无分叉接续。节点记录实际顺序、前次发布、计算、动作、入账月、固定比较基准和凭证。撤去产生明确节点，资产成员不独立发布金额。首次增加贡献，开放替换撤旧段再加新段，闭期更正增加新旧差额，无影响复核沿用金额与凭证并记录新依据。固定基准保证连续更正不会重复计额。

两类投影与正式发布同事务更新；维修只重建派生数据，实际变化推进读取修复版本。按期间和类别保存内容封签，期间封签同时绑定类别和发布集合，空结果也保留范围核对。普通读取核对命中投影及来源摘要；关账、完整性检查、备份和维修独立重建语义。核验成功只在同一只读快照、相同来源和范围内复用，失败不缓存，不增加跨请求缓存。缺少上年可比资料只影响比较列，不豁免本期完整性。

### 6.2 直接记录实际采用的结果

`period_close` 的不可变内容和摘要是唯一冻结权威。新合同直接保存本期采用的发布与计算、精确凭证版本、凭证拥有者与采用依据、冲正关系、无凭证结果、独立期初、资产批次及逐卡采用，连同资料清单、准备依据、管理快照、负责人确认和试算平衡。发布顺序边界、批准快照版本、前次关账身份和摘要共同确定该次冻结范围。复核可沿用旧凭证，但新依据不是旧凭证的产生依据；依赖中出现也不等于本期直接采用。

完整依据沿已有不可变依赖追溯，避免每期反复保存累计闭包、查询时再从闭包倒推实际采用结果。原始引用目录只索引冻结源实际记录的引用，不把推导出的采用结论变成新的权威来源。

本轮不保留旧系统关账格式的双重读取，不做新旧关账表示之间的接续。新系统自己的冻结记录仍不可改写。累计链与独立业务分别测量，不承诺所有存储增长都变成固定复杂度。

第 3 阶段用当前可复用业务和合成结果验证共同历史机制。后续身份、备用金、工资阶段明确自身结果、余额变化和精确采用引用，并在当期接入读取、核验和页面；历史层不靠猜测补齐业务含义。

### 6.3 同一版内容用于核对、批准和冻结

内核从生成关账预览的同一快照产生核对内容，保存关账所需的正式核算事实、业务结论及完整历史依据。老板看板保留业务对象、金额、时间、影响、风险和明确本人待办，并按用户要求保留会计凭证的公开编号、摘要、科目、往来对象及借贷金额，以及税务局模板格式。凭证可展开、分页或查看全部；试算过程、来源引用或采用证明、原始 JSON、内部编号和技术排查不进入看板。来源追踪和核算诊断由 AI 会计通过服务端及 CLI/MCP 完成。

关账核对存储合同保持版本 4，`OwnerReview` 保持版本 1。AI／MCP读取同版核对合同，原生密码批准窗口显示绑定 `preview_digest` 的同版业务摘要；预览失效后停止使用旧内容，不静默切换到新版本。老板看板保留业务结果及明确本人待办，独立月度核对模块与专用请求／缓存已退出。普通关账的本机密码重认证、批准与版本绑定、单次消费和失败回滚保持；展示精简不改变冻结合同、历史依据或批准边界。

重放通过 `preview_replay_close_range` 核对限定范围，再以同一 `company_id`、`first_period`、`last_period`、`owner_confirmation`、`preview_digest`、`epochs` 和稳定 `request_id` 调用 `confirm_replay_close_range`。每月在前月实际关闭后独立准备完整核对、事务冻结并创建备份任务，冻结 `approval=null`，另存范围、负责人及请求身份审计。中间阻断保留已关前缀并停止；稳定键原样重试核对实际冻结链后接续。事实、资料、管理、读取修复或会话改变后重新预览剩余范围，范围确认不能替代任何业务事实或检查。

核对内容作为关账合同中的 `owner_review` 冻结，纳入已有预览摘要。明细复用精确采用目录及版本化展示规则，按固定分块摘要核验；分页只读取命中块，完整核验独立检查全部内容。同公司同月只存在一个活动预览，AI／MCP核对、密码批准窗口与正式提交固定同一摘要，新预览不能被静默替换进正在核对或批准的同版内容。

数据变化后旧预览失效。关账冻结对应内容及其依据，后补事实和实际办理进度另行展示。老板看板展示业务摘要，核算依据和计算依赖由 AI 会计通过 `trace` 等 CLI/MCP 能力读取。

## 七、需要收敛的业务模型

### 7.1 工资确认贯通发布

本期已确认工资方案或仍有效的明确沿用依据，成为工资正式计算和发布的依赖。普通工资、bounded 工资、已有工资的准备、直接发布和重算遵守同一要求，不能通过跳过准备命令绕开。

采用依据明确公司、月份、人员和确认范围。方案或相关来源变化使受影响计算失效，真实付款不被重算改写。沿用现有业务确认方式，不新增工资密码窗口；确认原文与来源保留，不能把 AI 自写“已确认”说成独立的人类认证。

方案绑定完整工资输入、实际采用的档案和政策修订，以及全部有效变更通知；失效方案不能回退到无变化复用。无变化保存完整员工范围与逐人精确来源，由上月输入严格派生本月输入，不能更改金额后仍声称无变化。确认不绑定计算 ID 或程序版本；累计和实际扣款变化仍须重算，但不凭计算版本变化要求重复输入确认。个税尚未开始时，不要求未采用的个税政策。

不为旧系统闭期工资缺少确认依据保留例外，也不补造负责人当时已经确认。新系统保存实际采用的确认版本；后续修改不改变已冻结内容。AI 会计的核算详情分别提供当前结果与当时冻结结果的确认来源；老板详情只保留对应工资金额、时间、状态和业务影响。工资准备可登记同身份的事实修订，发布仍走统一入口；身份纠错必须连同方案和复用依据一起验证。

个人扣款无法映射个税文件的问题在准备和期间当前待办中呈现，仅影响该文件。缺失或错误映射、模板表达能力不足、已发布内容损坏分别处理。正式文件重新检查映射、人员和扣除明细；工资、付款、关账和真实外部完成不因文件能力受到新增限制。

### 7.2 闭期补录有人承接

归属已关月份的补录资料仍保留原归属。新出现的未处理行、重复占用或金额冲突由所有后续开放期持续承接，直至问题被有效处置。关账和完整代发共用同一快照批量检查，不另建可消音或任意移转责任月的待办事实。

合法未来资料只影响自身期间，不以全局文件状态阻断所有月份；未知归属必须明确。检查从权威当前来源、逐行归属和闭期清单取候选，不能凭旧完成标记过滤，需重新核对后来失效的处置和关联业务。每个原件每快照解析一次，逐项覆盖和精确版本仍完整进入冻结摘要。

资料清单中的计数自洽不能代替逐行覆盖。保留 expected、received 及缺件检查，移除无实际作用的 processed 字段。关账保留完整覆盖和精确来源；页面通过关账根认证的依赖目录与关账后的精确变化，定位需要重新检查的来源和竞争组。变化记录与业务同事务追加，不能改写或通过维修补造；它只负责定位，不代替命中来源核验，不是聊天或调用记录。完整核验独立核对所有来源、变化历史和可修目录，成本随资料增长，不用目录版本冒充内容证明。第 9 阶段接入该读取机制，验收进度见阶段文档。

### 7.3 备用金直接表达支出和退款

实际转入备用金计管理费，实际退回公司冲抵管理费。`managed_reserve_expense`、`managed_reserve_refund` 直接表达两种真实业务，支持银行、现金和公司平台账户；三个账户字段恰好一个非空，不重复保存可由它确定的账户类型。资金科目来自共同定义，平台原行继续精确核验并唯一采用。备用金自身不建账户，不维护范围、成本目录、FIFO、容量、退款额度或跨期接续。

工资付款中的净薪与 `reserve_expense_fen` 按明确依据拆分，保持银行全额、实际资金方向和工资防重复核销。实际退入备用金的确认、同月及已有日期依据保留，差额守恒不代替实际退入证明；这里的退入备用金与退回公司分别表达。备用金内部消费不进入本模型，原件沿现有有依据的不入账处置保留。

范围、成本资格、容量、FIFO、分配、接续和原债结清模型退出，不设计旧业务迁移、兼容读取或专用转换。普通费用回收、公司资金收付和公司内部划转保留；内部划转不再被备用金范围改变会计处理。新支出与退款接入真实资金查重、身份纠错、期间贡献和冻结采用。实际资金事实不能直接撤去或由身份纠错终止；录入错误通过明确纠错追加版本，开放期替换、闭期在开放月冲正，历史保留。

债务结清或退款权利不等于钱已退回。退款不读取历史支出、不要求原支出编号，不产生债权或清偿贡献；无历史支出或超过已记支出都不构成拒绝理由。支出和退款必须依据实际资金事实，不自动造日期、账户或一对一分配关系；已知交易方用于查找和展示，未知时不虚构，也不为查重增加管理必填门槛。

## 八、共享接口、看板与 AI 会计流程

### 8.1 共享响应合同从前期建立

以 Python 类型化读取模型作为响应合同来源，共享字段含义、版本规则和校验要求。复用已实现的 TypedDict、TypeAdapter、HTTP JSON Schema、TypeScript 和 Ajv 预编译校验器生成链，以及事实登记合同生成机制，不另造通用 Schema 框架。

MCP 金额保持整数分，HTTP 金额使用十进制整数分字符串，浏览器用 `BigInt`。合同明确字段省略与 null、未知与零、已建立与未建立、分页范围、快照和任务状态；空目录、没有月份、尚未检查都属于正常情况。整数分拒绝浮点、布尔、越界及非规范编码。静态类型不代替运行时校验。

允许直接修改命令、字段和响应，不承担旧接口兼容。每次变化同时更新服务边界、Schema、生成产物、CLI、MCP、页面及操作说明，并删除被替代的字段别名和旧校验路径。共享合同覆盖五页、共同上下文、业务详情、期间准备、关账核对，以及浏览器任务列表、安全公开状态和报表生成回执；不扩为全部业务写命令的响应改造。各分页集合只保存一份 `items/page`，完整范围的汇总独立保存。

生成产物入库，生成检查在临时目录比较，不暗中修改文件。后端返回不符合合同属于程序错误，只报告必要路径，不泄露值或转成老板追问。已知需要更换专用入口的错误返回结构化指引，真正的核算缺项继续用 `fact_issues`。

### 8.2 五页老板看板使用共同上下文

经营简报、资金、员工、资产和财务报表继续使用同一公司与月份上下文。本轮只对齐这五页，不增加趋势页、其他页面或业务写入功能。看板帮助老板判断经营资金状况、重要变化及影响、风险，以及本人是否需要行动。

页面呈现经营资金业务对象、金额、时间、影响、风险和明确待办，并保留老板要求查看的会计凭证及税务局模板报表。简报凭证清单提供公开凭证号、摘要、科目、往来对象和借贷金额，可展开、分页或查看全部。试算过程、来源证明、原始 JSON、内部编号及技术排查不进入页面或折叠区。实际收支、业务确认和账户互转分别表达，不以凭证借贷合计替代经营金额，也不将互转计为对外收支。AI 会计核对中不等于老板待办；普通未付款、未申报和未关账状态不自动要求老板付款或办理。

默认每个明细集合 20 条，同时给出完整范围汇总和全量数量。筛选在后端完整集合上应用后再分页；精确业务直跳不受默认前 20 条限制。摘要和待办不能从当前页凑数。员工页只展开本月薪酬，退出各月份工资与付款、专用历史读取和人员历史页缓存；截至月末未付仍保留必要历史汇总及核验，核心历史查询和冻结读取不变。HTTP 金额为十进制整数分字符串；请求与响应合同、精确请求关联、失效处理和快照一致性检查继续留在 wire 层，不展示为技术信息。

看板响应版本为 `context` 3、`brief` 11、`funds`／`assets`／`employees` 9、`business-status` 6、`quarterly-report` 5；关账核对存储为 4，`OwnerReview` 为 1。老板看板默认不运行完整 readiness。AI workflow、完整 `period_readiness` 和 corebusiness trace 仍提供完整业务工作流及核算追踪能力。以上是目标定位，不表示整阶段验收已经完成。

### 8.3 会计工作按真实状态推进

内核统一组织资料与核算、关账、实际办理、文件交付四类工作状态。银行、工资、一般业务、资产、税务和融资缺项进入对应业务位置；关账可以汇总问题，不能成为它们第一次出现的位置。

例如：“8 月账已关，个税还没申报，备份正在生成。”三个状态可以同时成立。文件生成、付款完成和申报完成分别有自己的依据，不能用一个“完成”覆盖。

运行协议承接会计流程要求，Skill 和默认提示与其保持一致：泛化开始时说明公司、月份和进度；明确事项直接处理；先查已有资料再问；老板回答落实到刚才展示的范围；真正推进后更新进度；失败或中断后从事实、版本和任务回执接续。同一步未推进不反复刷整张清单。

`workflow(as_of, period?)` 和 `period_readiness(period, as_of?)` 共用期间读取。自动选月只来自已有事实、资料、正式入账和已建事项；未来月不自动成为当前工作月。闭期资料的真实问题由开放月承接，无开放任务时用最近处理月作背景，空公司返回空状态。完整计数与问题保留，详细依据按需读取；不逐月运行完整关账检查。

`external_completion` 记录真实办理、原采用事实或计算及凭据，`external_basis_review` 记录与正式账务精确版本的核对，产生无分录结果。实际完成和核对状态分别返回；后续账务变化使核对过期，不抹掉真实办理。真实补报接续原办理，核对不伪装成再次申报。季度税务与季度财报分别管理，财报要求相应期间核算及关闭。

版本化运行协议是操作规则来源，Skill 负责模式入口、资料阅读和调用。`request_result` 从已有请求及审计读取原回执，未知状态不推定失败；任务保存公开错误码和本地诊断，自动尝试有上限。恢复和切公司重新绑定真实上下文，不保存聊天状态或增加调用日志。第 8 阶段通过隔离 MCP 与独立智能体验证完整对话；正式批量入口不再进入操作指引。

## 九、新库起点、未来升级与交付

### 9.1 独立的新版本体系

当前新系统标识为 `ai-accounting-kernel/2`，类别为 `catalog` / `company`，SQLite 辅助标识为 `0x41414332`。目录库和公司库均使用 `draft / 0`，备份格式为 2；不再承接原目录 v1–v3、公司 v1–v13 或旧备份。不可修改的 `schema_meta` 保存系统/类别/状态，`user_version` 保存结构版本，`schema_history` 保存实际安装指纹；稳定业务身份不包含版本。

创建、打开、读取、绑定、核验、升级、备份和恢复使用一致的身份与结构识别。新系统拒绝旧体系或缺少新标识的库和备份，不补标识、不隐式转换。已经存在的文件即使没有业务行，也不能当成可覆盖的新建目标。

开发期使用明确的开发基线，包内合同、库内记录和 SQLite 实际保存的 SQL 原文必须相符；未发布不意味着跳过结构校验。同一开发结构可以登记、发布、关账、备份和恢复测试。当前本体系库需要结构变化时，先停止服务并完成已验证备份，再显式执行 `upgrade-development`，只接受包内声明的精确来源和目标。入口逐公司原子调整并校验所有原表数据及冻结历史保留，追加不可改写的 `schema_draft_history`，原 `schema_history` 的版本 0 记录保持不变；目录和负责人身份不变。公司失败时该事务回滚，已完成公司前缀保留，不宣称全资料根共同原子。普通启动不隐式迁移，不补指纹，不删除或重建。入口已通过合成验证，真实执行与核验分别记入私有回执；步骤见[开发库前向升级](development-database-upgrades.md)。测试可以显式新建临时合成库，不能据此替换现库；空库重放须由用户明确指定。

按用户当前决定，第 9 阶段本轮继续开发库draft／0，不冻结目录／公司／内容的正式合同，不交付正式包、不切运行入口；现有5173、资料及身份原样。正式版目标延期，已完成的released／1隔离合同和升级测试仅证明其记录范围。正式版不承诺自动接收开发库；当前显式开发结构调整不等于将资料转入正式库，也不允许回写已发布的 `released` 合同。

### 9.2 从首个正式版本开始前向升级

每类数据库以一份完整根合同起步，后续合同保存父版本及指纹、明确的对象变化和完整目标指纹。加载时还原并核对完整目标，结构差异能够直接审阅；已发布的新体系合同不可回写。

迁移步骤由包内可信代码登记，绑定同体系的源和目标版本及指纹，明确变更动作和数据保留检查。保留加列、重命名、索引或触发器替换，以及必要时的单表复制替换。每个数据库的全部步骤在一个事务内完成，锁内复核结构，失败完整回滚；外键恢复并回读成功后连接才能继续使用。资料根先逐公司升级，最后升级目录库；跨库不作整体原子提交，失败保留已经完成的公司，重试核验后跳过，混合版本不能启动。不得接收外部 SQL 或自动猜测未知结构。

基础修订阶段就用隔离测试合同验证未来升级，不等正式 v1 发布后才验证。独立新建目标库与升级结果应有相同完整结构，原数据、主键、引用和历史保留；版本记录只记实际经过的步骤。

未来升级分别处理数据库结构与保存内容的版本，保留新系统自身历史的明确读取和必要适配。不得以当前计算器重算来覆盖冻结结果，也不得补确认、补付款或把技术变化误认为会计金额变化。

### 9.4 性能与交付范围

性能先从对象枚举、结果选择、依据展开、批量读取及期间汇总减少实际工作。缓存放在结构调整后评估，必须有明确的有效版本、容量和清理条件；不能仅因内容不可变就无限复用，也不能通过省略必要核验凑出耗时。

验收要求保留看板刷新低于 500 毫秒的目标。当前五页默认明细20条，测量包含点击刷新到上下文、主数字、首屏明细和全部可见附属内容完成显示的整条路径，每页30次成功样本全部低于目标。老板看板保留全量业务汇总、本人待办和必要业务结果，退出独立月度核对模块、专用请求／缓存、完整readiness与技术证明展示；AI／MCP同版核对合同、原生批准窗口摘要、完整准备、关账及冻结信任链仍执行对应检查。服务端工作量与耗时单独记录，不能代替浏览器纯计时。详情和文件任务按需单列，未检查不显示通过；固定代表性样本，报告重复分布而非最小值，冷启动、首次进入和公司切换另列。
