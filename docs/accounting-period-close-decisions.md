## 单一小企业负责人模式、本地部署与发布治理

## DEC-023：单一小企业负责人如何登录

**问题与决定原因：** 产品目标不是建立财务部门，而是让一位不懂财务的小企业负责人提供原始凭据和业务事实，由 AI 与确定性内核完成会计处理。现在只需要决定这位负责人怎样安全登录，以及 MCP 怎样取得不可伪造的登录上下文。

**主要影响：** 本地账户最简单、最符合单人试用，但系统要负责密码哈希、会话和恢复；外部身份平台更成熟，却增加配置与外部依赖；完全依赖本机进程身份仍无法证明是谁操作。

- **A：单一企业负责人使用本地账户和密码。** 使用强密码哈希、服务端会话和一次性恢复码；一期不做邀请、成员目录、SSO 或多用户生命周期。
- **B：使用邮件一次性登录链接。** 不保存密码，但需要配置可靠的邮件服务和找回流程。
- **C：使用外部 OIDC 登录。** 不保存本地密码，但增加身份提供方配置和依赖。

**推荐方案：A。** 最贴合“一位小老板亲自使用”的目标，账户模型最小，同时仍能给每次 AI/系统执行留下真实的负责人会话来源。

**用户决定：A**

## DEC-028：备份期间如何保证数据库和证据处于同一时点

**问题与决定原因：** 数据库可以用 `pg_dump` 生成一致快照，但证据文件保存在普通文件系统中。若备份时仍允许新业务写入，恢复后可能出现数据库记录与证据文件不对应。

**主要影响：** 停服备份最容易证明一致，但每天会短暂不可用；在线写入栅栏体验更好，却需要改造全部写入入口和并发约束；不做一致性控制则无法信任恢复结果。

- **A：每日和升级前采用停服快照。** 备份前退出正式服务并确认无活跃业务连接，数据库和已登记证据完成交叉校验后再启动。
- **B：建设数据库维护栅栏。** 所有正式写入参与共享锁，备份取得独占锁并等待在途写入完成。
- **C：允许在线 `pg_dump`，不保证它与证据文件处于同一时点。**

**推荐方案：A。** 单人本地私有试用可以接受每日几分钟停服，它最容易验证，也不会为了备份引入全局并发协议。

**用户决定：A**

## DEC-029：备份命令和每日计划任务使用哪个数据库身份

**问题与决定原因：** 运行账户与迁移账户已分离，但完整逻辑备份需要读取全部财务数据，停服检查还需要读取连接状态。日常任务复用高权限凭据会扩大泄露影响，新增账户则会多一项本地配置。

**主要影响：** 独立备份账户能分开长期自动任务、迁移和应用权限，但需要保存第三份凭据；复用既有账户更省事，却会把日常备份与其他高权限操作绑在一起。

- **A：新增单独的本地 `finance_backup` 数据库登录账户。** 只授予完整逻辑备份和停服检查所需的读取/监控权限；凭据由 Windows Credential Manager 或计划任务保护，不进入仓库、环境示例、命令行或备份清单。
- **B：每日备份复用迁移账户。**
- **C：每日备份复用应用运行账户。**

**推荐方案：A。** 每日自动任务是长期存在的敏感执行面，独立账户更容易审计、撤销和限制影响。

**用户决定：A**

## DEC-030：依赖漏洞扫描器报告哪些结果时阻断 CI

**问题与决定原因：** DEC-026 A 已要求 High/Critical 或 CVSS 不低于 7.0 无豁免阻断。当前选用的 `pip-audit` 命令没有稳定的“只按 CVSS 等级失败”参数；直接以其退出码作门禁，会把所有已知依赖漏洞都阻断，比 DEC-026 A 更严。

**主要影响：** 全部漏洞一律阻断最简单、最保守，但中低危问题也可能长期卡住发布；只阻断高危更精确，但需要换用或自建能稳定获取严重程度的检查器；只报告不阻断会违反 DEC-026 A。

- **A：`pip-audit` 报告任何已知依赖漏洞都阻断，不设豁免。**
- **B：改用能稳定提供严重程度的官方数据/工具，只阻断 High/Critical 或 CVSS≥7.0，中低危保留报告。**
- **C：所有扫描结果只报告，不阻断。**

**推荐方案：A。** 当前锁定环境为零已知漏洞，依赖规模也较小；一律阻断无需自建严重程度解析和豁免机制，最符合单人本地试用的保守边界。

**用户决定：A**

## DEC-031：本地登录后，MCP 进程如何取得会话凭据

**问题与决定原因：** 密码不能经过 AI 对话或 MCP 工具参数。当前项目只有 STDIO MCP，没有桌面登录界面；负责人在本地登录后，需要一条不进入模型上下文、命令行或日志的通道，把不透明 session token 交给 MCP 进程。

**主要影响：** 完整本地伴生应用体验最好，但开发量大；Windows Credential Manager 不需要新界面，但同一 Windows 账户下的进程可以读取所授予的凭据；把 token 放进环境变量或命令行最简单，但容易进入进程检查、错误报告或配置文件。

- **A：新建本地伴生应用。** 负责人在界面中登录，伴生应用在同一受控进程边界内保管会话并托管 MCP。
- **B：使用 Windows Credential Manager 保管不透明 session token。** `finance-login` 通过无回显本地控制台认证并写入当前 Windows 账户的凭据库；MCP 启动时读取，服务端每次仍校验哈希、过期和撤销。
- **C：通过命令行、环境变量或 MCP 参数传递密码/session token。**

**推荐方案：B。** 它不会为只有一位本地负责人的试用阶段引入整套桌面应用，同时避免把密码或 token 放进 AI、MCP schema、命令行或明文配置。

**用户决定：B**

## DEC-032：多个实际银行账户怎样分别导入和对账

**问题与决定原因：** 当前导入和对账只用总账科目代码识别银行账户，但同一企业可能有多张银行卡或多个实际银行账户。0015 现在必须确定流水号去重、期初期末余额和对账快照按什么粒度隔离，否则不同账户的流水和余额可能混在一起。

**主要影响：** 每个实际账户使用独立科目最省开发量，但科目会更多；建立银行账户名册更贴近现实，却会增加资料维护和迁移；合并对账最简单，但不能证明每个账户的余额。

- **A：一期要求每个实际银行账户对应一个独立的银行存款科目代码。** 导入、流水号唯一性和月度对账都按企业加科目代码隔离。
- **B：新增独立银行账户名册。** 保存脱敏账户标识，再把多个实际账户映射到总账科目。
- **C：同一银行存款科目下的实际账户合并导入和对账。**

**推荐方案：A。** 它复用现有确定性科目模型，能保持逐账户核对，又不为当前单人试用增加一套账户名册。

**用户决定：A**

## DEC-033：未选择处理月的迟到流水在哪些月提醒

**问题与决定原因：** DEC-013 允许先保存迟到流水，不能替负责人猜一个处理月。但月结和对账需要知道：负责人尚未选择处理月时，这笔待办应在哪些后续月份出现。

**主要影响：** 每月持续提醒最不容易漏，但可能重复出现；只在选定月份提醒界面更简洁，却会让未选月份的事项离开月结视野；一律阻断最安全，但少量迟到证据可能卡住所有后续关账。

- **A：从原关闭月后的每个待关闭月份持续作为警告显示，直到处理完成。** 不自动填写处理月，也不单独因此阻断月结。
- **B：只有负责人明确选择处理月后，才在该月月结中提示。** 未选择时只显示在独立待办查询中。
- **C：存在任何未处理迟到流水时，阻断所有后续月份关账。**

**推荐方案：A。** 它不猜处理月，也不会让待办消失；同时延续“资料可解释时警告、确定性错误才阻断”的月结边界。

**用户决定：A**

## DEC-034：正式银行对账确认失败保留多少审计

**问题与决定原因：** DEC-022 已决定银行文件导入失败只保存最小摘要，但尚未覆盖“正式提交月度对账后失败”的情况。0015 现在要建立对账动作表，必须确定失败行是否长期保存，以及是否保留余额和说明原文。

**主要影响：** 最小失败审计便于追踪重复失败且减少敏感数据留存；只留成功最简洁，但无法复核正式提交失败；保存完整输入最便于排错，却扩大余额、说明和证据引用的长期留存。

- **A：预览失败不留记录；正式确认失败只保存请求哈希、稳定错误码、字段路径和计数。** 不保存余额、说明原文、证据内容或异常正文。
- **B：只保存成功的对账快照，所有失败都不落审计。**
- **C：正式确认失败保存完整请求、余额、说明和证据引用。**

**推荐方案：A。** 它与 DEC-022 的最小失败审计一致，既能证明正式提交失败，又不额外长期保存敏感银行信息。

**用户决定：A**

## DEC-035：应用数据库账号本身是否也属于不可信边界

**问题与决定原因：** 当前本地登录能阻止 AI、MCP 请求和普通调用方伪造负责人身份；但如果有人已经拿到应用数据库写账号，就能直接读取有效会话的数据库记录，并伪造一条新的“负责人授权 + AI 执行”归因。要连这种直接数据库滥用也阻止，必须增加安全函数、收紧表权限，并改造身份与业务写入路径。现在 0014 正在冻结执行归因边界，因此需要明确威胁范围。

**主要影响：** 信任本机应用数据库账号最简单，符合单负责人本地试用，但该账号泄露就等同本机系统被攻破；用数据库安全函数隔离更强，却显著增加权限部署、排错和维护；再增加独立身份数据库账号最强，但会新增凭据和运维面。

- **A：一期信任本机应用数据库账号。** 正式保证 AI、MCP 和公共请求不能伪造负责人或执行者；明确说明拥有应用数据库账号或本机 Windows 账户控制权的人不在一期防护边界内。
- **B：应用数据库账号也不可信。** 撤销它对身份与执行归因表的直接权限，只允许通过验证原始 session token 的 PostgreSQL `SECURITY DEFINER` 安全函数认证、创建归因和执行业务写入。
- **C：新增独立身份数据库账号。** 身份 CLI 和会话验证使用单独低权限凭据，业务运行账号只能消费受控授权结果；迁移账号继续独立。

**推荐方案：A。** 当前是负责人本人控制的本地单机私有试用；若本机 Windows 账户或应用数据库凭据已经失守，Credential Manager 中的本地会话也很难继续视为安全。先把外部请求和 AI 边界做实，更符合项目定位，也避免为不存在的多人或远程攻击面建立复杂权限系统。

**用户决定：A**

## DEC-036：月结怎样确定哪些银行科目必须逐月对账

**问题与决定原因：** DEC-032 A 已规定每个实际银行账户使用独立的银行存款科目，但当前科目表没有可靠标记能说明“这是一个实际银行账户、从哪月开始使用、何时停用”。月结必须现在确定应对账账户集合，否则本月没有流水的在用账户可能被漏掉，也不能从科目名称、代码前缀或当月活动自行推断。

**主要影响：** 直接在科目上记录银行账户生命周期最简单，但会增加几个受控字段；另建有效期清单审计更强，却增加表和维护流程；按流水或固定角色推断开发最少，但零流水账户和多个账户无法可靠覆盖。

- **A：在总账科目上显式记录银行账户属性和对账有效期。** 每个实际账户对应一个科目；保存“需要银行对账”、启用月份和可选停用月份，月结按期间末日确定完整集合，历史关闭快照不随之后停用而改变。
- **B：建立独立的银行对账范围有效期清单。** 清单引用总账科目并保存每次启用、停用历史，月结按有效记录确定集合。
- **C：根据固定银行角色、科目代码或当月是否有流水自动推断。** 不要求用户维护范围，但零流水账户或多个实际账户可能被漏掉。

**推荐方案：A。** 它延续 DEC-032 的“实际账户就是独立科目”，能覆盖零流水月份，又不引入另一套银行账户名册；启用和停用月份足以让逐月对账可重现。

**用户决定：A**

## DEC-037：迟到流水的处理目标后来被冲正后怎么办

**问题与决定原因：** 一笔迟到流水可以通过 `evidence_only` 关联原关闭月已正确入账的事件，也可以通过 `omitted_entry` 关联后续开放月补记的类型化事件。若这个目标或结果事件以后被合法冲正，旧处理动作必须保留，但系统还要决定这笔迟到流水当前是否重新成为待办、能否关联替代事件，以及后续月是否继续提醒。

**主要影响：** 自动恢复待办最不容易漏掉替代关联，但会让已处理事项再次出现；保持完成最稳定，却可能让当前有效账务链没有银行证据；按动作类型区别更贴合部分场景，但状态机、解释和测试更复杂。

- **A：目标或结果事件冲正后，当前状态重新变为 pending。** 原处理动作永久保留为历史；允许在新的开放处理月以新幂等键关联有效的替代事件，DEC-033 警告持续到新处理完成。
- **B：仍视为已处理，只显示“关联事件已冲正”警告。** 不允许再次处理，旧动作继续代表最终分类。
- **C：按动作类型区分。** `omitted_entry` 的结果事件冲正后恢复 pending；`evidence_only` 的旧关联仍视为完成，只增加冲正警告。

**推荐方案：A。** 当前有效账务链应当能找到有效的银行证据关联；保留旧动作历史同时恢复待办，既不改旧关闭快照，也不会让已失效的事件永久掩盖未完成事项。

**用户决定：自定义。** 冲正只撤销它直接造成的效果，恢复到这次被冲处理动作发生前的状态；不自动追踪后续替代、也不跨多层联动。

## DEC-038：首次月结前怎样确认企业实际有哪些银行账户

**问题与决定原因：** DEC-036 A 要求按显式银行科目和启用月份确定逐月对账范围，但默认科目中存在“银行存款”角色并不能证明企业真的开了该账户，也不能证明它从哪个月启用。反过来，若所有科目默认不要求对账，系统又无法区分“负责人已确认没有银行账户”和“范围尚未配置”，可能静默漏过月结。

**主要影响：** 首次月结前显式确认最可靠，但会增加一次设置和证据；自动把默认科目当真实账户最省操作，却会推测业务事实；等首次流水出现再纳入范围较轻量，但零流水月份和从未导入的真实账户仍会漏掉。

- **A：首次月结前必须完成一次银行账户范围确认。** 负责人明确列出每个实际账户对应的科目和启用月份，或明确确认当时没有银行账户；保存负责人会话、说明、证据与不可变动作。范围未确认时阻断月结，之后新增或停用账户继续走受控变更动作。
- **B：自动把默认 `system_role='bank'` 科目视为真实银行账户。** 启用月份取企业第一个已生成期间，不再单独询问。
- **C：首次出现银行流水或银行科目分录时自动纳入范围。** 此前没有活动的月份不要求对账。

**推荐方案：A。** 它符合“老板提供原始事实、AI 与内核执行和把关”的定位，不从科目模板或缺少流水推断企业事实，也能可靠表达确实没有银行账户的月份。

**用户决定：A**

## DEC-039：银行流水尚未导入时，银行收付款记到哪个实际账户

**问题与决定原因：** 现有类型化业务可以在银行流水尚未到达时先生成固定凭证，模板一直使用唯一的 `bank` 角色。DEC-032 A 改为每个实际账户独立科目后，系统不能再猜默认账户；若后来引用银行流水，还必须证明凭证银行行与流水账户一致。

**主要影响：** 每笔银行业务显式选择账户最清楚，但会多一个必填事实；先导入流水再记账最容易派生账户，却会拖慢凭证处理并依赖银行文件到达；只有一个在用账户时自动选择最省操作，但以后新增账户会改变相同请求的含义。

- **A：每个银行收付款业务必须显式提供一个 `bank_account_code`。** 系统只生成该账户的固定银行分录；引用的全部银行流水必须属于同一账户且金额方向一致。确实由多个账户分担时拆成各自的类型化业务动作，不接受自由分录。
- **B：银行业务必须先有银行流水引用。** 账户完全由已验证流水派生；没有流水时返回 `needs_information`，不能先记账。
- **C：若当期只有一个启用银行账户则自动选择；有多个时才追问。**

**推荐方案：A。** 账户归属本来就是负责人能够说明的原始业务事实；显式冻结后既可在流水迟到前记账，也不会因企业以后新增账户而改变历史请求含义。

**用户决定：A**

## DEC-040：一期怎样安全支持 Excel 银行对账单金额

**问题与决定原因：** 普通 XLSX 的数值金额经常由解析库转换成 binary float，但本项目要求金额必须精确到整数分，禁止用浮点数推导会计金额。当前接口若继续宣称普遍支持 XLSX，却只在金额单元格是文本时可用，会造成正式导入体验与公开契约不一致；实现精确的 XLSX 原始值解析又会增加安全解析和兼容工作。

**主要影响：** 一期只支持 CSV 最简单、最容易验证，但用户需要从网银导出或另存 CSV；允许 XLSX 文本金额兼容一部分文件，却容易让用户不理解为什么普通数字单元格失败；实现受限的精确 XLSX 解析体验最好，但要直接校验压缩包、工作表 XML、共享字符串、日期样式和公式边界，开发与长期维护明显增加。

- **A：一期正式银行导入只支持 CSV。** XLSX 不出现在正式 MCP Schema；提示用户从网银导出或另存为 CSV，后续单独建设精确 XLSX 支持。
- **B：一期保留 XLSX，但金额列必须是文本单元格。** 数值单元格稳定返回 `needs_information`，不做浮点转换。
- **C：本期实现受限但精确的 XLSX 原始值解析。** 直接读取并验证 OOXML 中的十进制原文与日期/字符串映射，拒绝公式、宏、外部链接和不支持样式；不得经过 binary float。

**推荐方案：A。** CSV 能完整保存日期、标识和十进制金额原文，攻击面和兼容矩阵最小，最符合私有试用先守住确定性再扩格式的顺序。

**用户决定：A。** 像这种 AI 能很简单处理、但系统正式支持成本较高的格式转换，交给 AI 在正式导入前完成；一期正式接口只接受 CSV。

## DEC-041：企业自己的两个银行账户之间转账怎样记

**问题与决定原因：** 普通银行收付款只涉及一个实际账户，但内部转账同时有转出和转入账户，不能只填一个 `bank_account_code`。现在需要固定事件形状，否则系统可能把一笔内部资金移动误拆成两笔不相干业务。

**主要影响：** 单一转账事件最直观、余额能一次闭合；拆成转出和转入两件事需要新增清算科目和链接；一期不支持最省开发量，但老板遇到真实账户互转时无法处理。

- **A：保留一个类型化内部转账事件。** 显式填写转出和转入两个 `bank_account_code`，固定借记目标账户、贷记来源账户；两边银行流水分别验证并关联同一事件。
- **B：拆成有链接的转出和转入事件。** 两个事件通过固定清算科目衔接，必须成对完成后才视为闭合。
- **C：一期不支持内部转账。** 遇到时返回专用 `needs_information`，等待后续模块。

**推荐方案：A。** 它最贴合“一笔资金在自己的两个账户间移动”的事实，不引入临时清算余额，也能直接核对两边流水。

**用户决定：A**

## DEC-042：老板有第二个银行账户时，系统怎样建立对应科目

**问题与决定原因：** DEC-032 和 DEC-038 要求每个实际银行账户对应一个独立科目，但系统目前只预置一个银行存款科目，也没有让不懂财务的老板自己创建科目的正式流程。现在需要决定第二个账户怎样得到确定、可复现的科目。

**主要影响：** 系统按规则创建最省用户心智，但需要维护稳定编码规则；要求用户先给科目代码会把会计知识重新推给老板；限制一个账户会直接削弱已决定的多账户能力。

- **A：范围确认时由系统按固定规则创建银行子科目。** 老板只提供账户标签、启用月和证据；系统生成不可冲突的代码并冻结映射，不接受自由会计分录。
- **B：确认范围前必须先显式创建科目。** 老板或 AI 提供科目代码与名称，系统校验后再绑定实际账户。
- **C：一期只允许一个实际银行账户。** 仅使用预置银行存款科目，第二个账户留到后续。

**推荐方案：A。** 它最符合“不懂财务的老板只说清事实，AI 与内核处理会计结构”的产品定位，同时保留逐账户对账能力。

**用户决定：B。** 像这种 AI 能轻易处理、但确定性系统实现成本较高的结构整理，交给 AI 完成。老板负责提供原始数据，AI 负责处理并形成明确输入，系统负责严格校验和执行；不要在系统内重复增加属于 AI 的智能推断，系统应尽量精简。

## DEC-043：后来发现银行账户在已关闭月份就已启用怎么办

**问题与决定原因：** 老板可能在关账后才补充某个实际账户更早已经启用。系统不能把真实启用月伪写成当前月，也不能改写已经确认的旧关账快照，因此需要决定怎样保存这项追溯事实。

**主要影响：** 保留追溯事实和待办最真实，但需要持续提示并补证据；禁止追溯实现简单，却会保存错误启用月；重写旧关账会破坏已决定的不可变边界。

- **A：允许记录追溯范围事实，但不改旧关账。** 保存真实启用月、负责人会话、说明和证据；旧快照保持不变，从后续月份持续提示“历史对账范围缺失”，直到完成受控补证据处理。
- **B：禁止追溯启用。** 账户只能从当前或未来开放月份纳入范围，历史事实不进入系统。
- **C：重写受影响的旧关账快照。** 重新计算旧月的账户范围和对账结果。

**推荐方案：A。** 它同时保留真实业务事实和旧关账不可变性，不会为了省实现而伪造启用时间。

**用户决定：自定义，事实优先。** 账户什么时候实际开户，就必须写什么时候启用，即使该日期位于已关闭月份；不得为了迁就旧规则改写事实日期或拒绝事实。原关闭记录保留为当时的审计快照，系统另追加更正事实并明确标记受影响期间的历史对账范围缺失；当前查询和后续处理以更正后的真实事实为准。以后规则与已确认事实冲突时，同样不得伪造事实来满足规则。

## DEC-044：银行账户范围要在第一笔银行业务前确认吗

**问题与决定原因：** DEC-038 只明确要求首次月结前确认完整银行账户范围，但银行收付款在月结前就可能发生。现在需要决定未完成范围确认时，系统能否先使用一个已明确给出代码的银行科目入账。

**主要影响：** 先确认再入账最安全但多一个前置步骤；允许先入账更适合补历史业务，但期间关闭前仍必须补齐完整范围；自动把出现过的账户加入范围最省操作，却会用活动推断负责人尚未确认的事实。

- **A：先确认范围，后记录任何银行收付款。** 未完成首次范围确认时，所有银行结算业务返回 `needs_information`。
- **B：允许先记录显式账户的银行业务。** 账户必须是已存在且形状合法的资产借方科目，业务冻结明确 `bank_account_code`；但不自动纳入对账范围，首次月结前仍必须完成完整范围确认和证据。
- **C：第一笔银行业务自动把该账户加入范围。** 不再单独要求负责人确认该账户。

**推荐方案：A。** 它让银行账户身份、启用月份和证据先成为已确认事实，之后每笔业务与逐账户对账都使用同一稳定范围，最容易避免历史补录时漏账户。

**用户决定：A**

## DEC-045：现金存入银行或从银行取现怎样记

**问题与决定原因：** 旧 `internal_transfer` 同时允许银行和现金科目，但 DEC-041 只冻结了两个银行账户之间的互转。现金存取只涉及一侧银行流水，不能伪装成两个银行账户，也不能在这次改造中静默删除。

**主要影响：** 独立类型化事件最清楚但多一个事件；继续复用内部转账字段较少，却会让银行双侧和现金单侧验证变复杂；一期不支持最省开发量，但有现金业务的老板无法记录存取款。

- **A：新增类型化的现金—银行转移事件。** 显式提供方向、`bank_account_code`、金额和一侧银行流水；现金侧只使用固定现金科目，存现借银行贷现金，取现借现金贷银行。
- **B：继续复用 `internal_transfer`。** 来源或目标可选择固定现金科目，只有银行一侧要求流水；同一 Schema 同时表达银行互转和现金存取。
- **C：一期不支持现金存取。** 遇到时返回专用 `needs_information`，等待后续现金模块。

**推荐方案：A。** 它把一侧银行流水和固定现金科目的规则说清楚，不会削弱 DEC-041 的双银行账户精确验证，也不开放自由科目。

**用户决定：A**

## DEC-024：是否需要业务角色和权限分工

**问题与决定原因：** 当前产品面向一位企业负责人亲自提供资料、让 AI 和系统完成会计工作。若仍引入操作员、复核人等角色，会把并不存在的财务部门流程强加给小企业。

**主要影响：** 单一负责人模型最简单，但不能表达未来多人协作；增加只读观察者方便外部查看，却要维护授权；完整多角色会显著增加界面、迁移和测试成本。

- **A：一期不设业务角色。** 每个部署只有一个企业负责人账户，可访问本企业全部业务、证据、确认和月结；AI 与系统是执行者而不是另一名用户，迁移/部署凭据也不是业务用户。
- **B：负责人之外增加一个只读观察者。** 观察者只能查看和导出，不能确认事实、记账或关账。
- **C：建立操作员、复核人和管理员等多角色权限。**

**推荐方案：A。** 与小企业单人使用场景一致，避免为不存在的分工增加复杂度；未来真的出现多人协作时再单独立项。

**用户决定：A**

## DEC-025：本地单机部署的加密与备份责任边界

**问题与决定原因：** 本阶段已确定只在企业负责人自己的本地计算机上单机部署，不引入云平台。DEC-016 和 DEC-017 已决定静态加密、每日加密备份和恢复演练；现在要把本地责任边界写清，避免以后把开发机的默认配置误当成正式试用部署。

**主要影响：** 本地单机最符合当前范围，但设备丢失或磁盘损坏时不能只依赖同一块磁盘；备份介质越独立，恢复能力越强，但需要负责人定期连接、断开并保管。

- **A：本地 Windows 单机 + 系统卷静态加密 + 独立加密移动备份介质。** 备份完成后断开介质，由企业负责人保管恢复码、备份介质和恢复演练记录。
- **B：本地 Windows 单机 + 系统卷静态加密 + 局域网 NAS 加密备份。** 恢复更方便，但引入 NAS 账号、网络暴露和另一套运维配置。
- **C：只在本地保留开发数据，暂不建立加密备份与恢复边界。**

**推荐方案：A。** 不引入云或局域网服务，又避免备份与运行数据共用同一块磁盘，与 DEC-016 A 和 DEC-017 A 一致。

**用户决定：A。本阶段只在本地单机部署，不开展云部署。**

## DEC-026：高危漏洞是否允许临时豁免

**问题与决定原因：** DEC-019 要求阻断高危结果，但单一小企业负责人模式没有安全委员会或多级审批人，需要决定是始终等修复，还是允许负责人临时接受风险。

**主要影响：** 阈值过低可能长期阻塞维护；阈值过高会放过实质风险；没有批准人与到期日会让“临时豁免”变成不可审计的永久例外。

- **A：CVSS 不低于 7.0 或扫描器标记 High/Critical 一律阻断，不提供豁免。** 修复或升级后才能继续发布。
- **B：同样阻断 High/Critical，但允许企业负责人根据系统生成的风险说明临时豁免。** 最长 30 天，必须记录漏洞、影响、补偿措施和到期日。
- **C：扫描只告警，不阻断发布。**

**推荐方案：A。** 单人模式下没有合适的独立审批人；不设豁免比让不懂安全的使用者独自承担高危漏洞判断更简单、更安全。

**用户决定：A**

## DEC-027：CI 依赖和第三方 Action 如何锁定

**问题与决定原因：** 当前项目只声明依赖版本范围，GitHub Actions 也使用主版本标签；同一提交在不同日期运行时可能解析到不同依赖或 Action 内容。正式发布前需要决定怎样保证供应链和测试可复现。

**主要影响：** 锁得越严格，复现和审计越可靠，但升级需要专门工具与定期维护；继续只用范围最省事，却可能出现代码没变、门禁结果变化。

- **A：使用 `uv.lock` 冻结全部 Python 依赖，并把第三方 Action 固定到提交哈希。**
- **B：生成带哈希的 pip 约束文件，并把第三方 Action 固定到提交哈希。**
- **C：继续使用 `pyproject.toml` 版本范围和 Action 主版本标签，由 Dependabot 跟踪更新。**

**推荐方案：B。** 不更换现有 pip 工作流即可获得可复现安装和可审计的 Action 来源，改造与长期维护成本较低。

**用户决定：A**

## DEC-014：正式试用的银行对账要做到什么程度

**问题与决定原因：** 现有系统能导入流水、逐笔匹配和显示未匹配数量，但月结的“已对账”仍是人工声明，不能证明对账单是否完整，也不能解释余额差异。正式试用前需要确定最小对账证据。

**主要影响：** 对账越严格，月结可信度越高，但录入和实现成本也越高；继续只靠勾选最轻量，却无法复核覆盖范围。

- **A：每月必须录入对账单期初/期末余额，所有差异自动阻断月结。**
- **B：保存对账单覆盖范围、期初/期末余额、差异和解释证据；缺资料阻断，已解释差异作为月结警告。**
- **C：继续只保留人工“已对账”勾选。**

**推荐方案：B。** 与 DEC-004 的分层处理一致，先保证对账事实可审计，不把合理在途差异误判为系统错误。

**用户决定：B**

## DEC-015：老板、AI 和确定性内核分别负责什么

**问题与决定原因：** 产品目标是让不懂财务的小企业负责人只提供原始凭据并说清发生了什么，由 AI 与确定性内核完成分类、计算、记账、检查和提示。现在需要明确哪些动作可由系统在登录会话内自动完成，审计中怎样区分“老板提供事实”和“AI/系统执行”。

**主要影响：** 自动化越高，老板越省心，但必须让缺失事实停下来询问，且不能把 AI 操作伪装成老板亲手完成；每个关键动作都要求单独点击会更传统，却削弱产品价值。

- **A：负责人登录后提供凭据和业务事实，即授权 AI 与内核执行确定性流程。** 信息不足必须追问；审计同时记录负责人会话、AI/系统执行者、输入证据、规则与结果。凭证和月结仍只能走现有预览/哈希/确认提交点，但不要求设置另一位人类复核人。
- **B：每次生成凭证、税期确认和月结前，都要求负责人另行点击确认。** AI 只准备草稿和解释。
- **C：允许 AI 根据推测补齐业务事实并自动入账。**

**推荐方案：A。** 它保留“老板只需说清发生了什么”的核心价值，同时用 `needs_information`、固定模板、哈希确认和双重审计防止 AI 猜测或冒充用户。

**用户决定：A**

## DEC-016：试用数据的部署、加密和文件访问边界

**问题与决定原因：** 当前数据库凭据是开发默认值，证据文件明文落地，导入接口可读取运行账户能访问的路径。真实凭证和工资证据进入前必须确定数据由谁保管、在哪里保存、如何加密及如何限制文件访问。

**主要影响：** 更强的隔离和密钥管理提高保护能力，但会增加部署和运维成本；继续开发默认配置会把本地测试便利误当成正式安全方案。

- **A：单企业隔离部署，数据库与证据卷使用平台级静态加密，运行/迁移账户分离，导入目录白名单。**
- **B：在 A 的基础上，对证据文件再做应用层信封加密和密钥轮换。**
- **C：继续使用开发默认凭据和明文本地目录。**

**推荐方案：A。** 先建立可运维、可验证的最小安全边界；应用层加密可在试用稳定后按风险增加。

**用户决定：A**

## DEC-017：备份恢复与试用结束后的数据处置

**问题与决定原因：** 当前没有备份、恢复、保留期或退出流程。财务事实和证据一旦真实导入，故障恢复和试用结束后的交付或删除不能临时决定。

**主要影响：** 更短恢复目标和更长保留期成本更高；没有恢复演练可能造成不可逆数据丢失。保留年限还可能涉及外部合规判断，内核不能自行声称答案。

- **A：每日加密备份、30 天保留、每次升级前备份；正式试用前和每季度恢复演练；试用结束先交付可验证导出，再按用户书面确认处置。**
- **B：托管数据库持续归档/PITR、90 天保留、异地副本并固定 RPO/RTO。**
- **C：仅在人工操作前导出数据库和证据目录。**

**推荐方案：A。** 对单企业私有试用提供可验证的最低恢复能力，同时不擅自宣称法定保留期限。

**用户决定：A**

## DEC-018：单人 AI 会计模式是否还需要外部专业复核

**问题与决定原因：** 产品希望由 AI 与确定性内核承担实际会计工作，不设置内部会计或复核角色；但当前内核仍明确不是法定账簿或税务意见，需要决定正式试用前是否保留一次外部专业校准。

**主要影响：** 一次外部校准能降低企业配置、税务政策和首月结果错误，但会增加启动成本；完全不做复核最符合“老板 + AI”愿景，却把规则配置风险全部留给试用者。

- **A：只做一次外部专业校准。** 专业人士离线复核企业配置、税务/工资政策、历史补录边界及首个关闭月；企业负责人上传书面结论，不给专业人士创建系统账户，也不让其承担日常工作。
- **B：只复核试用启动时的企业配置和政策，不复核首个关闭月。**
- **C：不安排外部专业复核，完全依赖 AI、内核检查和企业负责人提供的事实。**

**推荐方案：A。** 它不把传统会计岗位引入日常流程，只在正式试用入口做一次规则和首月校准，适合当前仍处于私有试用阶段的风险水平。

**用户决定：A**

## DEC-019：CI 与依赖安全门禁采用什么最低标准

**问题与决定原因：** 现在全部门禁依赖本地手工执行；没有自动依赖漏洞、密钥或变更告警。正式试用前需要决定后续提交如何持续保持已验收的不变量。

**主要影响：** 自动门禁会增加构建时间和维护工作，但能更早发现回归和高风险依赖；仅本地检查难以证明每个推送都经过相同验证。

- **A：GitHub Actions 执行非 PG/PG 测试、Ruff、迁移检查和 `pip check`；启用 Dependabot、依赖漏洞扫描、secret scan 和 SBOM，并阻断高危未豁免结果。**
- **B：只建立 CI 测试与静态检查，依赖告警仍人工定期处理。**
- **C：继续只在本地运行门禁。**

**推荐方案：A。** 私有仓库也需要可重复的提交证据；当前依赖规模较小，适合先建立轻量自动化基线。

**用户决定：A**

## DEC-020：迟到流水若已在关闭月正确入账，如何追加关联

**问题与决定原因：** 迟到银行流水可能对应一笔已经在关闭月正确入账、只是当时没有银行流水证据的业务。系统需要决定能否在后续开放月只追加证据关联，而不重复生成凭证。

**主要影响：** 允许追加证据边能完成真实对账且不改旧账，但需要新的不可变关联动作；保持待处理实现较小，却会长期留下无法匹配的真实流水；重复入账会破坏账务正确性。

- **A：允许在后续开放月创建不可变的“仅追加证据”关联。** 不生成凭证、不修改旧事件和旧关闭快照，记录操作者、说明、原关闭哈希及关联历史。
- **B：一期保持未匹配。** 等 DEC-014 的完整银行对账模块完成后再处理。
- **C：在后续开放月重新创建一笔会计事件和凭证。**

**推荐方案：A。** 银行流水是外部证据，追加可审计证据边比重复确认同一经济业务更符合不可变原则。

**用户决定：A**

## DEC-021：银行流水缺少稳定流水号时如何识别重复

**问题与决定原因：** 当前在没有银行流水号时，用日期、金额、对方和摘要计算指纹。同一账户同一天两笔内容完全相同的真实流水会被误当成一笔，正式审计链不能静默丢失证据。

**主要影响：** 强制稳定流水号最安全，但部分银行导出可能没有该字段；使用文件行号兼容性更好，但重叠区间重复导出可能重复入库；继续启发式指纹体验最省，却有漏记风险。

- **A：正式导入必须提供银行稳定流水号。** 缺失时返回 `needs_information`，不导入该行。
- **B：缺少流水号时使用文件内容哈希加原始行号。** 同一文件可重放，但不同重叠导出需要人工识别重复。
- **C：继续使用日期、金额、对方和摘要的启发式指纹。**

**推荐方案：A。** 宁可明确要求补充可验证身份，也不能把两笔真实流水静默合并。

**用户决定：自定义。** 由 AI 向用户追问并要求明确确认及证据。确认前不得自动合并或自动新增。

## DEC-022：失败或部分失败的银行导入审计保留多少内容

**问题与决定原因：** 新增导入动作审计后，需要决定解析失败和行校验失败是否长期保存原始内容。该选择直接影响排错能力、隐私和存储量。

**主要影响：** 保存完整文件和失败行最便于排错，但会扩大敏感数据留存；完全不保存最简洁，却无法审计重复失败；只留最小摘要能兼顾追踪与隐私。

- **A：保存完整原始文件、映射和全部失败行内容。**
- **B：只保存成功导入动作；失败和部分失败详情只返回调用方。**
- **C：保存文件哈希、请求哈希、稳定错误码、行号、字段路径和计数，不保存失败字段值或完整文件。**

**推荐方案：C。** 与 DEC-007 的最小失败审计原则一致，可以追踪问题，又不长期保存无效或敏感输入。

**用户决定：自定义，采用“预检优先 + 最小失败审计”。** 如果 AI 预检发现问题，应在正式导入前先与用户解决。只有用户仍提交正式动作，或写入过程中出现部分行失败时，才保留最小失败审计。

## DEC-001：关闭月份是否允许反结账

**问题与决定原因：** 月份关闭后发现错误时，系统要决定是重新打开原月份，还是只允许在后续月份更正。这会直接影响已关闭数据的稳定性和审批要求。

**主要影响：** 允许反结账更符合部分传统软件习惯，但必须新增权限、审批和多版本关闭快照；禁止反结账更简单、更安全，但历史月份不能补录。

- **A：不允许反结账。** 原月份和关闭快照永不重开，只能在后续开放月做关联冲正和重记。
- **B：允许受控反结账。** 保留每次关闭/重开的不可变记录，并要求真实权限和审批后才能重开。
- **C：按企业配置。** 企业首次启用时选择 A 或 B，之后不得随意切换。

**推荐方案：A。** 当前没有真实身份、权限和审批体系，先保持关闭状态单向，最容易守住不可变边界。

**用户决定：A**

## DEC-002：期间控制何时自动启用

**问题与决定原因：** 当前企业默认可以在没有生成期间的日期入账。新增期控后，要决定是用户显式启用，还是系统自动启用。

**主要影响：** 自动启用更省操作，但会改变既有企业和测试的入账行为；显式启用更可控，但用户可能忘记开启。

- **A：所有企业显式启用。** 未启用时保持兼容；启用后未生成月份一律拒绝入账。
- **B：新企业默认启用，既有企业显式迁移。** 新用户更安全，但新旧企业行为不同。
- **C：升级后全部自动启用。** 行为最统一，但可能立即阻断既有业务和历史数据。

**推荐方案：A。** 私有试用阶段优先避免升级后突然改变既有企业的正式入账行为。

**用户决定：B。请记住：现在记账系统都还在开发，根本没有用户啊，当前尚无用户和既有企业。新建企业默认启用期间控制；未来如存在未启用的既有企业，须显式迁移后启用。**

## DEC-003：已有历史数据的企业如何接入期控

**问题与决定原因：** 既有凭证和旧期间没有生成动作、预览哈希和关闭快照。系统不能自动声称这些历史月份已经经过新月结流程。

**主要影响：** 直接包裹历史数据开发量小但审计事实不真实；严格拒绝最安全但限制试用；专门迁移流程最完整但工作量明显增加。

- **A：一期只允许从没有既有正式数据的新年度启用。** 有历史数据时拒绝，并提示另做迁移。
- **B：把可验证的历史凭证包入开放期间。** 用户再逐月预览和关闭，但不伪造旧关闭记录。
- **C：建设独立历史迁移项目。** 同时处理期初余额、历史期间、专业复核和迁移证据后再启用。

**推荐方案：A。** 先完成空账私有试用闭环；真实历史接入应与期初余额、专业复核一起单独立项。

**用户决定：先把“从零开始记账到关账”的流程做可靠；历史账迁移、期初余额等复杂问题以后单独做。但要能从以前的时间开始建账，比如我现在的公司是3月份注册和运营的，到现在有5个月的历史账目了，我要从3月份开始依次把这5个月的都录入进本系统。**

## DEC-004：哪些事项必须自动阻止月结

**问题与决定原因：** 固定资产、无形资产、借款、工资、税务、银行和往来都可能存在月末待办，但系统掌握的事实完整度不同。

**主要影响：** 阻断过多会因资料尚未录入而无法结账；阻断过少会把完整性责任全部留给人工。

- **A：分层处理。** 技术不完整和已存在明确合同/卡片所产生的到期义务自动阻断；银行、往来、未提交工资和税务只列警告，并要求人工明确确认。
- **B：严格阻断。** 银行未匹配、开放往来、工资和税期未完成也一律不能关闭。
- **C：最小阻断。** 只阻断草稿、失衡和缺失凭证，其他全部由人工确认。

**推荐方案：A。** 既能阻止内核已经确定的漏记，也不会从“没有录入资料”推断企业没有完成工作。

**用户决定：A**

## DEC-005：月结确认使用什么授权强度

**问题与决定原因：** 当前系统没有真实登录身份、角色或审批流，但月结确认需要记录“谁确认”。

**主要影响：** 自由文本只能作为审计声明，不能证明权限；真实权限和双人审批更安全，但会扩大到完整安全项目。

- **A：一期只记录确认人文本、说明和证据。** 文档明确它不代表真实授权。
- **B：先实现真实 RBAC，再允许关闭。** 至少区分经办与审核角色。
- **C：要求双人审批或外部身份系统签名。** 安全最强，但集成和运维成本最高。

**推荐方案：A。** 与当前私有试用定位一致，同时明确正式使用前 RBAC 仍是上线前置。

**用户决定：A**

## DEC-006：关闭快照保存多少明细

**问题与决定原因：** 月结哈希必须在以后可验证。可以保存每张凭证和分录的完整快照，也可以只保存引用和哈希。

**主要影响：** 完整快照审计和数据库自证能力更强，但重复数据更多；只存哈希占用小，但排查和独立验证更困难。

- **A：数据库保存完整凭证/分录快照和哈希。** 原凭证仍保留，快照用于关闭时点自证。
- **B：只保存凭证 ID 集合、汇总和哈希。** 查询时回读原凭证重建。
- **C：数据库保存摘要，完整快照归档到外部不可变存储。** 需要额外归档、恢复和可用性控制。

**推荐方案：A。** 当前数据规模是单企业私有试用，优先保证 PostgreSQL 能独立验证关闭事实。

**用户决定：A**

## DEC-007：失败的生成和关闭尝试保留多少内容

**问题与决定原因：** `needs_information` 和 `rejected` 请求是否长期保存完整输入，会影响审计能力、隐私和数据量。

**主要影响：** 全量保存便于追踪，但会长期保留无效或敏感输入；完全不保存则无法审计重复失败和并发结果。

- **A：完整保存所有成功和失败请求。** 包括输入事实、缺失项、错误和证据引用。
- **B：只保存成功动作。** 失败仅返回调用方，不入库。
- **C：失败只保存请求哈希、稳定错误码、字段路径、时间和调用标识；成功保存完整事实。**

**推荐方案：C。** 保留必要审计和幂等证据，同时减少无效输入和敏感内容的长期留存。

**用户决定：C**

## DEC-008：期间按年生成还是按月生成

**问题与决定原因：** 启用后，用户需要先生成开放期间。生成粒度会影响操作次数、未来月份误入账风险和维护复杂度。

**主要影响：** 全年生成最简单；逐月生成控制更细但操作频繁；自动滚动最省操作但引入后台任务和隐式状态变化。

- **A：显式按公历年度一次生成 12 个月。** 后续年度也由用户显式生成。
- **B：逐月显式生成。** 只能连续生成下一个月。
- **C：系统自动滚动生成。** 到期自动创建下一月或下一年。

**推荐方案：A。** 自然年度边界清楚、无需后台任务，也不会自动改变正式状态。

**用户决定：B**

## DEC-009：历史税期更正的调整凭证记在哪个月

**问题与决定原因：** 税期来源被更正后需要重新确认税期。若原会计月已经关闭，调整凭证不能再固定写回税期末日。

**主要影响：** 写入后续开放月能保持会计期间不可变，但税务归属期和会计入账日会不同；写回原月则必须支持反结账。

- **A：税务归属期保持历史期间，调整凭证显式记入后续已生成开放月。** 两个日期分别冻结和展示。
- **B：重开原会计月，把调整凭证写回税期末日。** 依赖 DEC-001 选择允许反结账。
- **C：关闭后不允许更正已确认税期来源。** 实现简单，但会形成无法修正的历史事实。

**推荐方案：A。** 保留税务事实所属期间，同时不破坏已关闭会计月；界面和 trace 必须清楚区分两个日期。

**用户决定：A**

## DEC-010：是否允许提前生成和记入未来月份

**问题与决定原因：** 选择逐月生成后，需要明确能否在当前日期之前提前建立下个月，并把未来日期的业务正式入账。

**主要影响：** 提前生成便于准备工作，但未来日期凭证可能造成误记；完全禁止最安全，但月初才能开始录入。

- **A：只允许生成当前月或过去月份，正式入账日也不得晚于当前日期。**
- **B：允许提前生成连续的未来月份，但未来日期到来前不能正式入账。**
- **C：允许提前生成并正式录入未来日期业务。**

**推荐方案：B。** 可以提前准备期间，又不会把尚未发生的日期当作正式入账日期。

**用户决定：A**

## DEC-011：没有任何凭证的月份能否关闭

**问题与决定原因：** 企业可能某个月没有业务。系统要决定空月份是正常关闭、禁止关闭，还是自动跳过。

**主要影响：** 允许关闭能保持月份连续，但需要明确人工确认“本月确实无业务”；禁止关闭会卡住后续月份；自动跳过会产生隐式正式状态变化。

- **A：允许显式关闭。** 系统确认凭证数为零，用户仍须完成全部人工复核并提供证据和说明。
- **B：禁止关闭。** 至少有一张正式凭证才能关闭。
- **C：系统自动跳过空月份。** 无需用户确认，直接生成关闭记录。

**推荐方案：A。** 保持期间连续和审计轨迹，同时不从“没有凭证”自动推断“没有业务”。

**用户决定：A**

## DEC-012：“当前日期”按哪个时区计算

**问题与决定原因：** DEC-010 选择了禁止生成未来月份和记入未来日期。应用服务和 PostgreSQL 可能部署在不同时区，每天零点附近会对“今天”产生不同判断，因此需要固定唯一时区。

**主要影响：** 固定中国时区最符合当前一期范围；按企业配置更灵活但需新增不可变配置和迁移；跟随数据库时区最简单，但更换部署环境可能改变结果。

- **A：固定使用 Asia/Shanghai 的日期。** 应用与数据库都以中国时间判断当前月和未来日期。
- **B：每个企业配置自己的会计时区。** 支持跨地区，但需新增配置、有效期和迁移规则。
- **C：跟随 PostgreSQL 会话或服务器默认时区。** 开发量最小，但相同数据在不同部署中可能得到不同结果。

**推荐方案：A。** 一期仅支持中国小企业、CNY 和中国税务规则，固定中国时区最简单且可重现。

**用户决定：A**

## DEC-013：月结后能否补导入属于已关闭月份的银行流水

**问题与决定原因：** 银行流水是外部原始证据，不是会计凭证。当前导入工具可在月结后继续插入 `booking_date` 属于已关闭月份的流水，这会使旧关闭快照中的“未匹配银行流水数”与之后查到的事实不同。

**主要影响：** 完全禁止最简单可验证，但会拒绝延迟到达的真实银行证据；允许补导入则需单独记录“月结后才到达”和后续月处理轨迹；改写旧关闭快照会破坏不可变性。

- **A：禁止补导入已关闭月份的银行流水。** 必须在月结前完成导入；关闭后返回稳定错误。
- **B：允许作为“迟到外部证据”补导入。** 不改旧关闭快照，新增迟到标记、导入审计和后续开放月处理链。
- **C：允许补导入并重写旧关闭快照。** 查询结果最接近当前证据全集，但已关闭月份不再不可变。

**推荐方案：B。** 外部流水确实可能迟到，但必须把迟到事实与原月结快照分开，并只在后续开放月完成匹配和会计更正。

**用户决定：B**
