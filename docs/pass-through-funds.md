# 代收代付的类型化处理

当前内核用 `pass_through` 事实记录有依据的代收债权和转付义务。登记必须明确付款方 `payer_id`、真实最终权利人 `beneficiary_id`、整数分金额 `amount_fen` 和权利义务确认。最终权利人必须引用已登记且具名的对象，名称可复用身份一致的对象档案、收款人或个税身份资料；缺少对象或真实姓名／名称时返回 `needs_information`，不能登记或核算。不得用付款方、猜测的人名或事后收款人代替最终权利人。未确认义务不得推断成收入、预收或可支付余额。登记前查已有对象、事实与证据，字段精度和所需来源以 `finance_local_schema` 为准。

用 `save_fact` 登记业务事实，`preview` 核对计算、期间和依赖后再 `confirm` 正式发布。实际收款、向受益人支付及其核销按各自发生日期和来源另行登记，资金方向、账户、银行原行、金额及未结义务逐项核对。看板本月发生按原采用类别拆分混合收付款；收入与代收分别列示，代收与代付各有分类，分项只展示本类别的对象、用途、金额及相关收付，原完整凭证仍可独立查看。资料接收与处置、事实登记、正式发布、真实资金收付和外部办理是不同状态，不能由其中一项推定其他项已完成。

实际付款仍须有真实收款人依据。`payment_method=individual` 要求非空 `counterparty_id`；没有单一交易方的银行汇总代付使用 `bank_batch` 并显式将顶层 `counterparty_id` 设为 `null`，每项分配仍引用真实 `recipient_id` 和精确来源义务。具名权利人的核销必须匹配其身份。此前已经采用的未具名责任仍按精确来源义务及明确的实际支付事实核验清偿，不以事后收款人改写原采用的来源。一个完整批次可以匹配同账户、同日、同方向且合计准确的多条原银行行，不据此猜测银行子行对应哪名收款人。

开放期事实错误通过类型化更正或符合依赖条件的删除入口处理；闭期不改原凭证，在开放月使用关联冲正和替代。新登记、批量登记、录入修订与重新核算遵守最终权利人必填要求。此前保存的未具名来源及冻结历史仍可读取、核验和备份，不因收紧录入要求而删改；财报分别核对每笔来源责任及其实际清偿，不跨未具名来源抵销。缺少受托性质、付款方、最终权利人、金额、期间、实际收款人或证据时返回 `needs_information`，不把未知余款默认归为预收或收入。完整命令和当前能力见[类型化业务事实](business-components.md)及运行时 Schema。

## 历史边界

旧 `finance_record_event` 的 `components`／`funds` 请求、`finance_get_event`、`finance_amend_event` 和任意 `metadata` 写入接口均已退出运行层。旧公司 v13、目录 v3 和组件式请求示例只保留在 Git 历史，不是新系统的导入或运行来源。当前使用 `ai-accounting-kernel/2` 开发合同，正式首版仍待第 9 阶段冻结。
