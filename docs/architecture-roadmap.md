# 内核与看板架构实施总计划

日期：2026-09-12

## 目标与方向

保留 Python 模块化单体、每公司独立 SQLite、类型化事实、确定性计算与统一事务发布。完善核算结果、来源追溯和只读查询之间的边界，使看板、报表及业务操作使用一致的业务含义。

现有写入核心继续作为基础。优先完善共享契约并复用同步汇总，通过现有模块中的必要调整降低重复解释和历史读取成本。具体实现方案由任务会话提出，架构会话审核后确定。

## 大任务与顺序

| 任务 | 目标与边界 | 前置 |
| --- | --- | --- |
| T1 核算结果与无影响复核 | 区分核算变化与依据、解释变化，完善无影响复核及旧结果兼容。核算意义覆盖分录、义务、余额和影响后续计算的状态。 | 无 |
| T2 历史来源与内容版本 | 明确冻结核算、后来补充资料、实际发生时间及资料知悉时间的查询含义；分开提交并发版本与内容有效性。 | T1 的边界确定 |
| T3 统一业务查询与状态 | 统一财务位置、清偿关系、期间准备和来源追溯；以稳定业务身份关联事实、发布结果、凭证和外部办理状态，供各入口共同使用。 | T1、T2 |
| T4 有界读取与看板接入 | 复用已有汇总和冻结结果，收敛历史装载、分页及报表读取成本；现有五页接入共同契约，修正必要的上下文与交互问题。视觉和布局重设计另行安排。 | T3 |
| T5 整体验证与交付收口 | 统一完成跨任务验证、遗留问题处置及现行架构文档更新，由架构会话作最终审核。 | T1—T4 |
| T6 看板交互与布局 | 在已验收的共同业务契约上，改善现有五页的信息层级、导航、筛选与分页、详情追溯及桌面／窄屏布局，使负责人更容易理解经营情况并定位待办。具体设计由任务会话规划，不扩大为内核重构。 | T1—T5 已验收 |

按上述顺序推进，同一时间只保留一个执行任务写入主仓库。必要的契约调整须先由架构会话确认，再进入后续任务。

## 协作与审核

- 本会话作为架构会话，负责整体取舍、任务边界、计划审核、执行放行及结果审核。
- 用户按[任务会话启动说明](architecture-task-prompts.md)手动创建 Astra Ultra 会话并开启计划模式。任务会话先形成详细计划并回传；未经架构会话明确放行，不开始实现。
- 计划阶段结束后可切回默认模式，后续由架构会话与任务会话直接协作；模式切换本身不代表执行授权。
- 任务完成后先交架构会话审核，处理反馈后才进入下一大任务。任务会话负责具体开发和验收方案，本总计划不展开这些细节。
- 各任务保留已有未提交改动，记录自身改动边界；开发授权不包含正式业务写入。用户后来明确授权的正式更新，由 T6 按获审范围完成结构迁移和前端发布，未重算或新增业务事实。

## 测试与资源原则

- 规划阶段以已有代码和审查证据为基础，仅对影响方案选择的未知点做必要验证。
- 各任务只执行与当次改动及风险直接相关的必要检查，复用已有测试和结论，不例行重复全量测试。
- T1—T5 的跨任务统一回归已集中在 T5 完成；T6 复用有效结果，只补交互、布局及实际受影响契约的必要验证，在本任务收口时集中检查页面协作，不重复内核全量矩阵。
- 架构审核以计划、差异和已有验证证据为主，避免重复任务会话已经完成且仍然有效的检查。
- 阶段交接只保留决策、变更范围、必要验证结果和未决事项，减少重复读取及长篇过程记录。

## 持续约束

公共入口只接受类型化业务事实；金额保持整数分；正式写入保持原子性和幂等性；已关账结果不可改写；缺失核算事实不得推断补齐。结构变更遵循现有冻结合同与前向迁移要求，原件和审计历史完整保留。
