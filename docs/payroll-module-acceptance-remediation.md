## 1. 文档用途与裁决

本文件是首轮实现后的整改任务书，不替代开发基线。开发基线继续定义目标业务能力、领域边界和长期不变量；本文记录本轮审计发现、明确修复要求和复验标准。二者冲突时按以下顺序处理：

1. 会计、税务、不可变性及数据隔离不变量优先。
2. 本整改任务书对本轮缺陷的明确裁决优先于开发基线中的概括性描述。
3. 仍无法唯一决定处理方式时，返回 `needs_information` 或向总设计 Agent 报告，不得自行引入会改变会计结果的默认值。

本轮结论为 **不通过**。已有计算器、迁移、MCP 工具和测试数量不能抵消下列阻断问题。在本文件全部销项前，不得将工资模块标记为“完成”“可试用”或合并进入下一阶段基线。

## 2. 整改通用要求

- 禁止新增 Agent 可提交任意借贷方向、金额或科目的接口。
- 所有业务和入账金额继续使用整数“分”；税率和中间税额使用 `Decimal`，禁止二进制浮点数。
- 已入账凭证、正式工资批次、工资行、已使用的政策快照均不可修改；更正只能通过显式版本或关联冲正完成。
- 所有查询和关系必须以 `org_id` 隔离；不能只依赖服务层过滤，关键关系必须有数据库复合外键、约束或延迟约束触发器保护。
- 缺少会改变计算、纳税期间或会计处理的事实时返回 `needs_information`，不得猜测。
- 每项修复必须新增能在修复前失败、修复后通过的回归测试，并在交付报告中给出“问题编号 → 测试名”映射。
- 不得通过放宽校验、删除测试、将异常吞掉或把失败改成跳过来完成整改。
- 不得修改、清理、暂存或提交不属于当前工作包的用户改动。是否创建提交由任务调度者另行决定。
- 本文出现的文件行号是 2026-08-09 审计快照，仅帮助定位；实现后应以符号名、表名和行为为准。

## 3. 阻断问题与修复要求

### PAY-001：银行流水引用可重复计数（P0）

审计定位：`src/ai_accounting/service.py` 的 `_match_bank_transactions` 附近。

已复现同一条 `-4,197.50` 元银行流水被请求重复引用两次后，系统成功入账 `8,395.00` 元工资付款，并把流水标记为已匹配。重复引用既可制造虚假付款，也会破坏核销守恒。

必须实现：

- 先把 ID、指纹等外部引用解析为数据库中的规范银行流水 ID，再去重和求和。
- 同一请求中任何两个引用解析到同一流水时必须 `rejected`，不得静默去重后继续入账。
- 同一引用同时给出 ID 和指纹时，两者必须指向同一记录，否则 `rejected`。
- 跨企业流水、已被不兼容事件占用的流水以及符号或金额不匹配必须拒绝。
- 错误结果使用稳定错误码，并明确指出重复或冲突引用；不得泄露 SQL。

最低测试：重复 ID、重复指纹、同一流水分别以 ID 和指纹引用、ID 与指纹互相冲突、正常多流水合计。

### PAY-002：并发部分发薪可能重复生成代扣负债（P0）

审计定位：工资支付校验在 `service.py` 约 646 行附近，开放项行锁在 `_apply_settlements` 中取得得过晚。

两个并发请求可能都在加锁前读到相同未支付状态，从而分别认定本次应生成完整社保、公积金或个税代扣负债。

必须实现：

- 在读取“此前已支付、已代扣、本次可分配金额”前，对相关工资开放项按稳定顺序取得数据库行锁。
- 锁、余额读取、代扣计算、凭证生成和核销必须在同一事务内完成。
- 为每条工资行建立可由数据库验证的代扣守恒：累计已生成代扣负债不得超过该工资行正式计提的对应金额。
- 若使用独立分配记录，应有唯一键和组织一致性约束；不得只依赖 Python 先查后写。
- 对锁冲突、唯一冲突进行受控重试或返回稳定冲突码，不得暴露数据库异常。

最低测试：两个独立数据库连接同时对同一工资行做部分发薪，最终现金、开放项、代扣负债和核销总额均守恒，最多一个请求获得冲突结果。

### PAY-003：累计个税状态未按纳税年度隔离（P0）

审计定位：`service.py` 的 `_prior_tax_state`，审计快照约 2228—2242 行。

已复现 2026 年 12 月工资入账后，2027 年 1 月预览返回 `INVALID_TAX_STATE`，老员工跨年无法算薪。

必须实现：

- 累计预扣状态查询必须限定当前纳税年度，不得读取上一年度最终状态作为本年期初。
- 连续任职员工进入新纳税年度时，从本年度空累计状态开始，同时保留依法由任职月份决定的累计减除费用。
- 纳税年度按实际支付/所得取得日期确定，不能仅按工资所属期确定，详见 PAY-006。
- 同年度存在多类工资所得记录时，必须通过明确依赖链选出唯一最终状态，不能依赖创建时间或 ID 的偶然排序。

最低测试：2026-12 → 2027-01 连续任职、同年连续月份、跨年但支付日在下一年，以及反向插入历史数据时的确定性。

### PAY-004：跳月时累计基本减除费用少算（P0）

审计定位：`src/ai_accounting/payroll/income_tax.py` 约 213—222 行。

已复现从 1 月直接计算 3 月时只累计两个月 `10,000.00` 元减除费用，而按任职月份应为三个月 `15,000.00` 元。

必须实现：

- 不得用“每调用一次固定增加一个月”代表累计任职月份。
- 计算器输入必须包含足以确定累计减除费用的任职起始月、当前所得月份或显式累计任职月数；服务层从不可变员工资料和支付日期构造该事实。
- 员工任职但某月工资为零或尚未生成批次时，该月不能因缺少一次函数调用而消失。
- 任职、离职、重新任职等事实不足时返回 `needs_information`，不得按相邻批次猜测。

最低测试：1 月 → 3 月跳月得到三个月累计减除、零工资月份、年中入职、新年度重置、期初累计状态导入。

### PAY-005：合并计税年终奖可漏税且状态次序不确定（P0）

审计定位：`service.py` 年终奖预览/确认流程约 1938—2008 行、`annual_bonus.py` 及 `_prior_tax_state`。

已复现未入账同月普通工资时，合并计税奖金批次只计提奖金自身个税 `300.00` 元，却把累计状态记录为已经扣缴 `450.00` 元，漏生成 `150.00` 元负债，并使以后月份少扣税。同月普通工资和奖金状态也没有确定优先级。

本轮采用以下唯一方案：

- 选择“并入综合所得计税”的年终奖，在生成可确认草稿前必须引用同一员工、同一纳税月、同一企业且已正式入账的普通工资批次 `regular_payroll_batch_id`。
- 普通工资税务事实必须从该不可变批次和工资行派生；不得在确认接口继续相信一份可独立填写的 `regular_tax_input`。
- 普通工资尚未入账时，可以提供明确标记为 `non_confirmable` 的情景试算，但必须在普通工资入账后重新试算并产生新哈希，旧结果不能确认。
- 普通工资状态是当月基础，合并奖金状态是该月最终状态；下月只能读取后者。依赖关系必须持久化并有唯一性约束。
- 冲正普通工资前必须先冲正依赖它的合并奖金及其下游累计批次。

最低测试：无普通工资批次不能确认、引用其他员工/月/企业被拒绝、正确补提合并税额、同月状态唯一、下月承接最终状态、依赖冲正顺序。

### PAY-006：个税和年终奖错误使用工资所属期选择政策（P0）

审计定位：`service.py` 约 1792—1805 行及 `annual_bonus.py` 约 171 行。

已复现 2027 年 12 月所属奖金在 2028-01-05 实际支付时，仍通过只有效至 2027-12-31 的政策，并把全年一次性奖金使用次数记入错误年度。

必须实现：

- 社保、公积金所属期政策可以按工资所属期月末选择。
- 工资薪金个税、全年一次性奖金政策、纳税年度和“一年一次”使用记录一律按实际 `payment_date`/所得取得日选择。
- `payroll_period` 与 `payment_date` 跨月或跨年是允许的业务事实，不得把二者悄悄归一。
- 目标支付日没有有效官方规则时返回规则缺失，不得回退到所属期规则。

最低测试：2027-12 所属工资/奖金在 2028-01 支付、政策生效首日和失效次日、跨年一次性奖金次数占用。

### PAY-007：工资支付轨迹错误引用增值税规则（P1）

审计定位：通用 `_post_event` 对所有事件调用小规模纳税人增值税规则。

必须实现：

- 规则轨迹按事件族选择，工资发放、代扣缴纳等事件不得依赖或声称执行增值税规则。
- 工资事件轨迹至少包含工资批次、工资政策/员工资料版本、开放项类别、代收机构、核销与来源事件。
- 增值税政策到期但工资相关有效规则齐全时，工资支付不得因此失败。

最低测试：VAT 规则失效后的工资支付、轨迹中不存在 VAT 规则、工资规则和证据链完整。

### PAY-008：MCP 实际工具契约仍为开放字典（P0）

审计发现 MCP 的工资工具仍以 `request: dict[str, Any]` 暴露，实际 `list_tools` 生成的 `inputSchema` 为 `additionalProperties: true`。现有测试只检查内部 Pydantic 模型，没有检查 Agent 真正看到的 MCP 契约。

必须实现：

- MCP 工具的真实 `inputSchema` 必须明确 required 字段、枚举、整数金额和嵌套结构，并拒绝额外字段。
- 优先直接使用 MCP 框架支持的类型化参数/Pydantic 模型；如框架限制无法做到，必须提供统一的 `finance_get_payroll_schema` 并在工具入口执行完全相同的严格校验，但真实工具仍不得表现为无说明的任意字典。
- 任何公开 schema 均不得包含借方、贷方、科目代码或自由分录字段。

最低测试：直接调用 MCP `list_tools()` 断言实际 schema，而非只调用 `model_json_schema()`；再以额外字段、浮点金额和缺字段请求验证拒绝。

### PAY-009：工资批次查询不能返回完整证据链（P1）

审计定位：`service.py` 的 `get_payroll_batch` 附近，当前主要返回批次摘要和工资行。

必须实现：

- `finance_get_payroll_batch` 返回稳定且有组织隔离的完整生命周期：原始试算输入摘要及哈希、员工/政策快照、官方来源、确认信息、证据、业务事件、凭证、开放项、支付与核销、冲正链、审计轨迹。
- 敏感字段继续最小化；不存在的数据使用明确空集合或状态，不用不稳定的隐式省略。
- 任何关联对象均再次校验 `org_id`，不得通过已知批次 ID 越权读取其他企业对象。

最低测试：从登记 → 试算 → 确认 → 部分支付 → 全部支付 → 缴纳 → 冲正的完整查询快照，以及跨企业访问拒绝。

### PAY-010：数据库异常会泄露 SQL 和参数（P0）

审计定位：`src/ai_accounting/mcp_server.py` 的 `_invalid` 附近。

必须实现：

- 对唯一冲突、并发冲突、约束失败和连接失败映射稳定的外部错误码。
- MCP 返回中禁止包含 SQL 文本、绑定参数、连接串、堆栈或原始 `SQLAlchemyError` 字符串。
- 完整异常只能进入内部日志；日志也必须遵循敏感数据最小化。

最低测试：主动触发幂等唯一冲突、并发冲突和外键错误，断言响应不含 `INSERT`、`SELECT`、参数值或连接信息。

### PAY-011：政策、员工资料和期初状态缺少可审计更正版本（P1）

当前注册接口可能接受重叠有效期或不完整参数，正式引用后又没有统一的关闭/更正路径；期初累计个税状态也缺少显式更正版本。

必须实现：

- 注册时验证完整政策合同，包括日期、有界比例、舍入模式、官方来源和模块所需参数。
- 同一企业和同一适用维度的有效期不得重叠；如允许后继版本，应显式保存 `supersedes_id` 或等价版本链。
- 员工资料、政策和期初状态都提供“新建更正版本”能力；已经被正式批次引用的版本不可原地修改或删除。
- 期初状态更正后，已经依赖旧状态的正式批次不能静默重算，必须按依赖链冲正后重建。

最低测试：重叠政策、无效参数、版本替代链、被引用版本不可变、期初状态更正及下游依赖保护。

### PAY-012：试算幂等键不校验载荷且版本号存在并发竞态（P0）

同一试算幂等键配不同载荷目前可能直接重放旧结果；`max(version)+1` 在并发请求中也可能竞争并泄露原始数据库错误。

必须实现：

- 对规范化后的完整请求计算载荷哈希，并与幂等键绑定；同键同载荷重放，同键异载荷明确拒绝。
- 工资期间版本分配必须由数据库锁、序列或原子 upsert 保证，不得依赖无锁的 `max+1`。
- 并发失败按 PAY-010 返回稳定错误，不泄露 SQL。

最低测试：同键同载荷、同键不同载荷、两个连接并发创建同企业同期间草稿，以及重试后版本连续且无重复。

### PAY-013：净工资为零的批次无法完成闭环（P1）

计算和数据库允许 `net_salary_fen == 0`，但现有支付接口要求正数金额和银行流水，因此无法把工资应付全部转成社保、公积金和个税代扣负债。

本轮采用以下唯一方案：

- 工资支付接口支持受严格约束的“零现金代扣结算”：`amount_fen == 0` 时不得提供银行流水，且工资分配总额必须完全等于本次生成的法定代扣负债总额。
- 该路径不生成银行存款分录，只生成工资应付转入相应代扣负债的平衡凭证和开放项核销。
- 非工资事件、存在现金净额或金额不守恒时仍禁止零金额入账。

最低测试：合法零净工资、错误附带银行流水、代扣不足/超额、幂等重试和冲正。

### PAY-014：正式工资批次和工资行可被数据库直写篡改（P0）

审计定位：`alembic/versions/0002_payroll.py` 约 439—481 行。

已复现：向 `posted` 批次新增工资行成功；把工资行从 `posted` 批次移动到草稿批次成功；批次改成 `reversed` 后可继续修改计算输入。

必须实现：

- `posted` 和 `reversed` 批次均为最终不可变状态。
- 工资行触发器覆盖 `INSERT`、`UPDATE`、`DELETE`；`UPDATE` 同时检查 `OLD.payroll_batch_id` 和 `NEW.payroll_batch_id`，禁止移入或移出最终批次。
- 正式批次仅允许一次受控的 `posted → reversed` 状态变化，且只能改变状态及必要的冲正关联字段；变化完成后继续不可变。
- 应用服务不能依赖绕过触发器的特殊写法。

最低 PostgreSQL 测试：最终批次新增行、改行、删行、移入、移出、篡改批次，以及合法关联冲正。

### PAY-015：工资关系缺少跨组织及实体一致性约束（P0）

批次、政策、业务事件、冲正批次，工资行、员工、资料版本，以及年终奖使用记录目前主要是各自独立外键。已复现企业 A 的批次引用企业 B 的政策；数据库也可插入无业务事件、无工资行的 `posted` 批次。

必须实现：

- 为关键父表建立包含 `org_id` 的复合唯一键，并以复合外键约束子关系；必要时在子表冗余 `org_id`。
- 员工资料必须属于同一员工和企业；政策、事件、凭证、冲正批次和奖金使用记录必须属于同一企业。
- 正式批次必须有来源业务事件、至少一条工资行及相应凭证；需要跨行判断时使用可延迟约束触发器，在事务提交前验证。
- `_payroll_accrual_template` 等服务函数即使面对污染数据也必须再次拒绝跨组织或错配资料。

最低 PostgreSQL 测试：逐项构造跨企业和错配关系、空正式批次、无事件正式批次，以及正常延迟提交。

### PAY-016：已入账凭证仍可追加平衡分录（P0）

审计定位：`alembic/versions/0001_initial.py` 的凭证行不可变触发器目前只覆盖 `UPDATE OR DELETE`。

已复现向现有 `posted` 凭证追加一借一贷两行成功。最终仍平衡不代表历史凭证未被篡改。

必须实现：

- 对凭证行 `INSERT` 同样检查父凭证状态；`posted` 或 `reversed` 凭证禁止新增、修改或删除任何行。
- 合法入账流程应先在非正式状态完整写入并校验，再一次性转为 `posted`。
- 冲正必须创建新凭证，不能开放原凭证写窗口。

最低 PostgreSQL 测试：向正式凭证追加单行、追加平衡双行、修改、删除均失败；草稿构建和正式冲正成功。

### PAY-017：开放项与核销缺少数据库守恒（P0）

当前数据库可构造开放项、往来单位、来源事件不同企业的关系，也可构造 `settled_amount_fen`、状态和有效核销合计互相矛盾的数据。

必须实现：

- 开放项与往来单位、来源事件，以及核销与开放项、支付事件均使用组织一致的复合外键。
- 事务提交时验证：未冲正核销合计等于开放项 `settled_amount_fen`，不超过原金额，余额与 `open/partial/settled` 状态一致。
- 冲正核销必须纳入守恒计算；不允许通过直接改累计字段绕过核销明细。
- 保留服务层稳定顺序行锁，但数据库约束必须能独立拦截污染写入。

最低 PostgreSQL 测试：跨组织、超额核销、累计字段不符、状态不符、冲正后守恒，以及并发核销。

### PAY-018：迁移升级不处理科目代码冲突且元数据漂移（P1）

审计发现 `0002_payroll` 只按 `system_role` 判断是否需要插入固定科目代码。若旧企业已占用相同代码但角色不同，升级会在唯一键处以不清晰错误中断。另有 `employees.org_id` 索引只存在于迁移，ORM 未声明，空库执行 `alembic check` 会建议删除该索引。

必须实现：

- 迁移前检查目标科目代码。若现有科目的类别、余额方向及空 `system_role` 与目标兼容，可确定性地绑定角色；若不兼容，升级前以清晰诊断终止，不得半升级或覆盖用户科目。
- 为兼容与冲突两条路径各建立带旧数据的 `0001 → head` 测试。
- 修正 ORM 与迁移索引定义漂移，使空 PostgreSQL 和测试所用数据库执行 `alembic check` 均无待生成操作。
- 保持 `head → base → head` 和 `0002 → 0001 → 0002` 的可验证迁移路径；降级不得遗留工资对象。

### PAY-019：模块能力元数据仍把工资标记为未启用（P1）

工资已有专用工具，但通用事件目录中的旧 `PAYROLL` 哨兵仍可能报告 `MODULE_NOT_ENABLED`，造成 Agent 对能力状态理解冲突。

必须实现：

- 工资计提继续只能通过专用工资工具，不能加入可由 `finance_record_event` 任意调用的通用事件。
- 能力查询应明确报告“工资模块已启用，入口为专用工具”；旧哨兵应移到内部枚举或从公开事件目录移除。
- 契约测试确保工资能力可发现，同时普通事件接口仍拒绝工资自由入账。

### PAY-020：关键流程测试缺失（P0）

首轮已有测试未覆盖真实 MCP 契约、完整年终奖服务流、跨年、跳月、并发确认/付款、重复银行流水、期间关闭和完整 STDIO 闭环。

必须新增：

- PostgreSQL 集成测试，而非只在 SQLite 或 mock 上验证数据库不变量。
- 真实 MCP `list_tools` 契约测试和至少一条本地 STDIO 端到端流程。
- 多员工、多月份、各种舍入模式、政策生效边界的性质测试。
- 工资确认、四类支付、零现金代扣结算和冲正的期间关闭测试。
- 每个本文问题编号至少对应一个明确回归测试；P0 通常需要多个正反例。

### PAY-021：个税和年终奖规则缺少各自官方一手依据（P1）

个税与年终奖政策不能用通用社保政策 URL 代替来源。

必须实现：

- 累计预扣、全年一次性奖金、社保和公积金规则分别保存与其内容相符的官方一手来源 URL、政策版本及有效期。
- 注册时拒绝空 URL、非绝对 URL 或缺少对应规则来源的政策；不能在代码中散落无版本硬编码。
- 测试应验证规则轨迹返回实际使用的政策版本和对应来源。
