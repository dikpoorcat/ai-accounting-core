# 重放推进中的来源引用与组合银行对账修复

## 问题与范围

已启用重放批量服务并恢复真实重建。继续处理时，付款模型拒绝内核自己生成的含冒号工资主体编号；另有一条原始银行流水对应普通费用付款与备用金支出两个已确认的业务来源，现有对账只允许该原行引用一个来源。这两处是运行能力阻断，真实业务在原进度暂停，使用新建合成库完成修复与验证后再恢复。

## 业务来源身份

通过 `@subject_id` 读取的引用沿用内核主体身份合同：非空字符串，最多200个字符。实体、账户和普通业务字段继续采用各自类型；不把来源改为旧别名、事实修订ID或其他身份。逐一检查付款、清偿、工资备用金付款、银行匹配及其他实际来源引用，覆盖内核生成身份和最大允许长度。

## 组合银行对账

复用现有 `matches` 的扁平 `reference`、`source_kind`、`source_id` 字段；同一真实原行可以列出多个不同的已发布资金来源。这些来源必须全部只对应这一原行，同账户、同实际日、同方向，其完整金额合计精确等于原行金额。现有一个来源对应多条原行的核对方式继续成立。

每条原行和每个已发布资金来源必须完整覆盖，重复引用边拒绝。组合来源再跨其他原行形成不明确的多对多关系时拒绝；不引入缺乏依据的逐项金额分配。原银行行保持原编号、日期和总额，对账不产生凭证或改变实际付款。

资金看板每条原行只出现一次，完整金额及分页汇总不因多个来源倍增；按对账实际采用的计算绑定全部来源，复用既有响应合同显示组合付款与对象。精确计算引用通过CLI/MCP的 `trace` 和冻结采用依据查询，冻结读取使用当时采用版本。

## 验证与恢复

合成验证包括内核工资准备与正式发布、按原工资主体清偿并完成银行对账；组合普通付款与备用金支出、原行保全、分页与金额汇总、金额／方向／日期／账户差异、未发布来源、遗漏与重复、模糊组合及原子失败。确认SQL结构合同保持不变，保留当前真实公司库和已关账历史。

修复已完成，最终两组相关验证共269项通过：银行、工资、来源边界和资金看板131项，现金、投资、期初、税额抵减、销售税点、报销资产与资产批次138项。新增39项合成用例包含实际生成的200字符工资主体完整付款对账路径。Ruff检查及格式检查、差异空白检查和SQL结构合同核验均通过，数据库结构未变。
