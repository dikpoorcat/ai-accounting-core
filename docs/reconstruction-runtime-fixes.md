# 重建资料的业务来源与当前库运行修复

## 当前边界

重建资料中的完整原始事实通过当前类型化入口登记，默认先使用当前本体系库试用并补齐缺口。运行阻断先集中记录；开发历史查证可追溯保全原件、负责人确认、Git历史及旧业务输入，但空库执行只采用最终清单明确索引的已保全原件和确认。旧凭证、计算、余额、冻结状态不能代替新事实。真实写入与实现修复分别执行；开发结构变化不触发自行新建空目标、重放业务或重新设置负责人。空库重放只有用户明确指定时执行。本轮开发范围的状态见路线图；正式合同冻结、正式交付和运行切换仍延期。

当前库需要结构调整时，使用已实现的显式 `upgrade-development` 入口：停机后先完成并验证各公司备份，核对包内精确源合同、目标合同和完整指纹，逐公司原子调整并保留目录、公司、数据库及负责人身份、业务数据、原件、审计和冻结采用依据。原版本0安装记录保持不变，调整依据追加到不可改写的开发结构历史。已发布的 `released` 合同不可回写，旧体系库和备份不能作为新体系导入来源。未知结构保留现库并补齐升级实现，不改为自行空库重放。具体步骤见[开发库前向升级](development-database-upgrades.md)。

## 来源身份与完整银行原行

业务来源沿用内核主体身份合同：非空字符串，最多200字符。实体、账户采用各自合同；含冒号的内核工资主体是合法业务来源，不能替换为修订ID或旧别名。

一条银行原行可引用多个不同的完整已发布资金来源，要求全部来源只对应该原行、同账户、实际日及方向，完整金额之和精确一致。单一来源可覆盖同日同方向的多条完整原行。原行编号、日期及金额保留，不推断逐人逐行分摊，不允许模糊多对多匹配。资金页每条原行仅计数一次。

`payment_method="bank_batch"` 的付款没有单一交易方时，必须显式提交 `counterparty_id=null`；每项 allocation 仍提供真实 `recipient_id`，与采用义务核验身份及金额。单人付款必须具名。完整整批付款与完整银行原行匹配，不虚构汇总机构或把第一人当整批交易方；实际少付保留未清偿责任。本月发生按原采用类别展示混合付款分项，单类多人批次保留精确原批次主行，首次展开即显示逐人用途和个人金额，不按姓名或相同成员集合跨原批次合并。完整原凭证与银行原行继续保持原金额和内容；活动分项的增加不重复计数凭证或资金原行。

## 未具名的代收转付责任

`pass_through.beneficiary_id` 必须提交，最终权利人未知时显式为 `null`。实际付款人、受托性质、转付责任及金额仍须有明确来源，`rights_and_obligation_confirmed=true` 才能核算。具名最终权利人继续采用实际实体。

未具名责任按精确 `pass_through:<subject>:remittance` 来源义务单独列示，原责任与其实际清偿采用同一稳定键，不按空姓名合并，不跨来源抵销。后来实际收款人不会追认为原最终权利人。原来源和闭期采用保持不变。

## 未来回放的支付平台与现金边界

未来回放依据每家公司负责人明确确认的长期边界，不将支付平台及现金账户纳入本内核资金或投资管理，不追问范围外的资金来源、余额、内部支出或内部对账细节。已确认属于备用金的公司银行实际转入通过 `managed_reserve_expense` 计管理费用，实际退回公司银行通过 `managed_reserve_refund` 冲减管理费用，采用真实银行账户、日期、整数分金额及完整银行原行；不把现金收付推定为备用金费用。平台内部消费、申赎、收益和退款只保全资料，不再确认公司费用、退款、投资或余额。

范围外的平台及现金原件作为支持资料保留完整内容、实际位置及明确支持用途；内部业务明细依该公司负责人确认的边界作有依据的不入账处置，不同时分配核算金额。未来回放不登记范围外的平台或现金账户、期初、内部收付款与划转，也不登记平台产品的货币基金持仓。公司银行实际收付仍完整处理，与平台对应行不重复核算。明确有独立来源的股东投资到账直接按实际公司银行 `funding` 登记；验证款、押金及其退回保留实际业务性质，同日同额的不同业务仍按原行独立匹配。具体公司身份及边界确认保存在私有最终事实清单和所索引的负责人确认中，说明重建按[当前内核空库重建](empty-database-replay.md)执行。

当前通用平台接口继续存在。`managed_reserve_internal_movement` 是现有的精确原行留证能力，要求平台账户、当前正式原行、同月同账户、唯一采用及明确边界确认；其结果没有公司凭证、余额、现金流、费用或税额。这个接口不作为上述未来回放的输入，原有合成验证记录保留其实际范围，不证明新回放口径已经执行。文档和最终事实清单的修订不改动现库、身份或运行服务。

## 重复复核与资料刷新

已保存的“分别登记”复核按双方业务修订、内容、信号及完整原件分配语义核验。业务和原行处置未变时，资料处置重新绑定生成的事实或计算编号不会单独撤销复核；真实金额、期间、类别、位置、成员或分配改变仍使其失效。持久 `business-duplicate/2` 摘要算法及冻结v1规则不重写。详见[资料处置与重复复核](duplicate-review-material-semantics.md)。

## 验证与恢复

跨月原件的完整处置版本可以包含未来月份链接。关闭本月时，资料变化目录仍保留所有链接的反向追踪键，但只核验核算所属月不晚于关闭月的历史采用；未来链接由其实际月份核对，不能因前月留证提前冻结，也不能借此跳过未来月份失效链接。检查规则修复不重写已保存的目录根、冻结内容或v1历史验证器。

显式开发升级后的首次滚动备份会遇到先前来源结构的当前ZIP。滚动入口仅对包内明确声明的来源与目标使用精确来源合同，完整核验旧ZIP的证据、内容和同一公司身份，再原样保留为previous并发布当前结构ZIP；普通恢复和验证入口的结构边界不扩大。跨结构的相同请求键不能把旧ZIP误认成已生成当前包，中断接续继续核对档案原字节。

便携备份任务的完成证明来自完整格式2清单及内容验证结果，不能套用报表导出任务的顶层文件SHA字段。工作状态核对公司与数据库身份、结构、期末、证据数量、完整覆盖结果及非负计数；当前文件是否仍存在另记为尚未检查，不能将过去成功证明冒充当前文件检查。

上述实际试用缺口完成后，跨月资料、升级后滚动备份、任务展示与批量关账联合57项通过；已有资料冻结相关50项通过，备份与升级相关90项通过，任务与响应合同相关108项通过。这些合集存在重叠，不相加为总数。跨月验证覆盖未来单行与联合组、实际失效阻断和重绑后关账，备份验证覆盖发布中断、身份与内容拒绝、恢复以及跨结构相同请求键。

验证使用隔离合成公司，覆盖类型化登记、原子失败、完整银行原行、真实收款人、匿名来源清偿与财报、独立往来责任、平台唯一采用、不入账结果、资料复核、冻结、批量关闭、结构合同、便携备份与页面响应合同。新增12项开发库升级测试通过，覆盖全部原表行值、已关账历史、两家公司独立备份、四处事务故障回滚和中断重试；最终结构历史、升级、重放关账及备份相关合集119项通过。重复复核38项、领域相关合集113项通过，前端134项通过且构建成功。SQL草案和浏览器生成合同同步生成。新建合成库不构成替换当前库或重放真实业务的授权；真实库执行和逐月交付另记私有回执。

修复及所需前向调整完成后，核对当前库的原身份、保留数据、冻结链、服务版本和实际MCP，在用户已有授权范围内沿当前进度继续。负责人复用既有身份，通过本机安全渠道核对登录，不因开发修复安排新负责人设置，也不传递令牌或密码。需要新的预览时以当前实际版本核对，不能沿用过期摘要。只有用户另行明确指定空库重放时，才按[空库重建流程](empty-database-replay.md)准备其指定目标与范围；既有重建范围确认不代替这次指定。真实结构调整、关账与已验证ZIP的完成状态只写入私有记录。
