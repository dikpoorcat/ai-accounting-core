## 2. P0 阻断整改

### R2-001：禁止反向插入破坏累计个税依赖

对应前轮：PAY-003。

已复现先确认三月工资、再确认一月工资后，四月仍继承旧三月状态，累计收入遗漏后来入账的一月工资。

本轮裁决：

- 对每个员工，以实际 `payment_date` 对应的税年和税月建立持久化税务状态顺序。
- 预览较早月份时，如存在同一员工、同一税年且税月更晚的 `posted` 状态，返回 `rejected`，错误码固定为 `LATER_PAYROLL_TAX_STATE_EXISTS`，列出需要先冲正的批次 ID。
- 确认时必须在事务内再次检查，并锁定该员工本税年的状态槽；不能只依赖预览时检查。
- 一个批次中任一员工存在后续状态时，整个批次原子拒绝，不得部分确认。
- 冲正必须从最新税月向前执行；后续依赖尚未冲正时继续返回 `REVERSE_DEPENDENT_PAYROLL_BATCHES_FIRST`。
- 本阶段不实现自动重算和自动重发凭证。

最低测试：三月后补一月、十二月后补十一月、跨税年补录、多人批次中一人冲突、两个连接并发确认前后月份，以及正确的从后向前冲正重建。

### R2-002：把普通工资与合并奖金依赖变成数据库事实

对应前轮：PAY-005。

`regular_payroll_batch_id` 当前只存在于请求 JSON，两个合并奖金可并发通过“先查后写”，为同一员工和税月生成两个最终状态。

本轮采用以下结构：

- 在 `PayrollLine` 或独立规范关系表中保存 `regular_payroll_batch_id`，使用包含 `org_id` 的复合外键指向普通工资批次。
- 新建等价于 `payroll_tax_state_slots` 的状态槽，唯一键为 `(org_id, employee_id, tax_year, tax_month)`；至少保存 `regular_batch_id` 和 `final_batch_id`。
- 普通工资确认时原子创建状态槽，初始 `final_batch_id` 为普通工资批次。
- 合并奖金确认时 `FOR UPDATE` 锁定状态槽；仅当当前最终批次仍是所引用普通工资批次时，才能把 `final_batch_id` 更新为奖金批次。第二个并发确认必须稳定拒绝。
- 合并奖金行必须绑定同企业、同员工、同实际支付税月、已入账的普通工资行。
- 冲正合并奖金后恢复普通工资为最终状态；冲正普通工资前必须先冲正奖金和后续税月。
- 不得再通过扫描 JSON 判断唯一依赖或冲正顺序；JSON 只可作为审计快照。

最低 PostgreSQL 测试：两个连接并发确认合并奖金、跨员工/月/企业引用、第二个最终状态直接写入、奖金冲正恢复状态槽、普通工资依赖保护。

### R2-003：按具体险种保证代扣守恒

对应前轮：PAY-002。

当前只校验社保、公积金和个税总额。已复现工资行确认 `pension=80,000`、`medical=20,000`，付款时提交 `pension=100,000` 并成功入账。

本轮采用规范化分项：

- 新建工资行代扣权利明细，唯一键至少为 `(org_id, payroll_line_id, contribution_group, insurance_kind)`，保存正式计提的分项金额。
- 新建支付代扣分配明细，逐项引用工资行权利明细和付款事件；唯一键防止同一付款重复写入同一险种。
- PostgreSQL 延迟约束在提交时验证每个险种的未冲正支付累计不超过工资行对应权利金额。
- 服务层逐险种比较，缺少、增加、改名或跨组挪用均拒绝；最终工资支付必须逐险种完全结清。
- 现有 JSON 分项可以保留为不可变快照，但不能作为唯一的守恒依据。
- 冲正工资支付时相应分项分配标记冲正，并重新满足逐项守恒。

最低测试：养老与医疗互相挪用、社保与公积金跨组挪用、未知险种、分次代扣、并发代扣、最终结清、付款冲正后再次支付。

### R2-004：所有工资相关写操作绑定幂等载荷

对应前轮：PAY-012。

试算已有请求哈希，但工资发放、社保、公积金、个税支付和冲正仍会把“同键异载荷”静默当成成功重放。

本轮裁决：

- 为 `BusinessEvent` 保存规范化请求 SHA-256；哈希必须覆盖完整业务请求，不包含服务端派生字段。
- `finance_record_event`、`finance_reverse_event` 及内部工资确认均执行：同键同哈希重放，同键异哈希返回 `IDEMPOTENCY_PAYLOAD_MISMATCH`。
- 工资发放哈希覆盖金额、开放项分配、逐险种代扣、银行流水、证据和日期。
- 冲正哈希覆盖原事件、原因、记账日和企业。
- 并发唯一冲突后必须重新读取并比较哈希，不能一律返回旧事件。
- 对无法可靠还原请求哈希的历史事件，返回 `IDEMPOTENCY_PAYLOAD_UNVERIFIABLE`，不得假装同载荷重放。

最低测试：上述五类工资写操作分别覆盖同键同载荷、同键异金额、异银行流水、异分配、异日期和两个连接并发。

### R2-005：正式凭证和工资事件必须在数据库层完整且不可变

对应前轮：PAY-015、PAY-016。

已复现零分录 `posted` 凭证提交成功，并可支撑表面完整的正式工资批次；正式工资 `BusinessEvent` 也可事后改成 `rejected`。

必须实现：

- 延迟约束在事务提交时验证所有 `posted/reversed` 凭证至少两条分录、借贷相等且总额大于零。
- 凭证只能在 `draft` 状态构建完整分录，再一次性转为 `posted`；最终状态之后禁止新增、修改或删除分录。
- `BusinessEvent` 的 `posted/reversed` 状态、业务事实、日期、规则轨迹和规则版本不可任意修改。
- 只允许一次受控的 `posted → reversed`，同时设置同企业有效 `reversed_by_event_id`；完成后继续不可变。
- 正式工资批次的事件必须是同企业 `payroll_accrual` 且为 `posted/reversed`，凭证必须满足上述完整性，不能只检查“存在一张凭证”。

最低 PostgreSQL 测试：零分录正式凭证、单分录、零金额平衡双分录、正常平衡凭证、事件改为 rejected、篡改事实/日期/轨迹、合法冲正状态转换。

### R2-006：凭证分录必须与凭证属于同一企业

对应前轮：PAY-015。

`VoucherLine` 当前没有 `org_id`，已复现企业 A 的凭证引用企业 B 的科目并成功提交。

必须实现：

- `VoucherLine` 增加并回填 `org_id`。
- 以复合外键分别绑定 `(org_id, voucher_id)`、`(org_id, account_id)` 和可空的 `(org_id, counterparty_id)`。
- `Voucher`、`Account`、`Counterparty` 建立相应复合唯一键。
- 迁移前扫描现有凭证行；发现跨企业污染时以清晰错误终止，不得自动改成任一企业。
- `create_voucher` 显式写入事件企业 ID，不能由外部输入。

最低 PostgreSQL 测试：跨企业科目、跨企业往来单位、跨企业凭证、正常同企业分录和带空往来单位分录。

### R2-007：所有工资入口暴露严格、可发现的 MCP 契约

对应前轮：PAY-008。

专用工资工具的外层契约已变严格，但工资发放和法定款项使用的 `finance_record_event` 仍显示 `request.additionalProperties: true`；政策 `parameters` 仍是开放字典，且 `12.0` 会被转换为整数 `12`。

必须实现：

- `finance_record_event` 和 `finance_reverse_event` 直接使用严格类型化请求，真实 `list_tools()` 不得出现开放 `request` 字典。
- 为政策参数建立嵌套 Pydantic 模型：缴费规则、个税规则、奖金规则和支付目标都有 required、enum、范围及 `extra="forbid"`。
- 所有金额字段使用严格整数校验，拒绝 `bool`、`12.0`、`12.5` 和数字字符串；日期字符串仍按 MCP JSON 契约正常解析。
- 工资相关所有实际入口的 schema 文本不得出现 `debit_fen`、`credit_fen`、`account_code` 或任意分录字段。
- `finance_get_event_schema` 返回的 schema 与真实 `list_tools()` 保持一致，不维护第二份漂移契约。

最低测试：直接读取真实 `mcp.list_tools()`，覆盖试算、确认、通用工资支付、四类缴款和冲正；分别提交额外字段、整数值浮点数、非整数浮点数、字符串金额和缺失字段。

### R2-008：补齐真实 STDIO 全生命周期验收

对应前轮：PAY-020。

当前 STDIO 测试只覆盖登记、试算、确认和查询，不能作为完整闭环证据。

必须使用隔离 PostgreSQL 17 和真实 STDIO 子进程完成：

```text
登记证据、员工、资料、政策
    → 工资试算与确认
    → 第一笔部分发薪
    → 第二笔剩余发薪或零现金结算
    → 社保缴纳
    → 公积金缴纳
    → 个税缴纳
    → 按依赖顺序冲正法定缴款、工资付款和工资计提
```

每一步必须从 MCP 返回和数据库分别核对：规则来源、计算哈希、凭证借贷平衡、开放项余额、逐险种代扣、银行流水匹配、证据链、审计轨迹和冲正关联。不得以直接调用 `FinanceService` 代替 STDIO 工具。

## 3. P1 必须整改

### R2-009：单独计税奖金不得依赖普通工资批次

对应前轮：PAY-005。

Schema 只对 `combined` 要求普通工资批次，但服务层对所有年终奖无条件要求，导致合法的 `separate` 试算返回 `needs_information`。

本轮裁决：

- `separate` 只需要奖金金额、实际支付日、该税年单独计税使用状态和有效奖金规则。
- `separate` 不要求 `regular_payroll_batch_id`，也不创建综合所得最终状态槽。
- 如产品需要同时展示 `combined` 对比方案，但普通工资尚未入账，则该对比标记为 `unavailable/non_confirmable`；不能阻止用户明确选择的单独计税方案。
- `combined` 继续严格执行 R2-002 的依赖要求。

最低测试：无普通工资的单独计税确认、重复使用拒绝、同日普通工资存在与不存在、对比方案不可用标记，以及 combined 缺依赖拒绝。

### R2-010：真正实现资料、政策和期初状态更正版本链

对应前轮：PAY-011。

三个 `supersedes_*` 当前只进入审计日志，模型和迁移没有列，同期间更正均无法成功。

必须实现：

- 三类实体分别增加自引用 `supersedes_id` 复合外键，要求同企业、同员工或同政策适用维度，并对 predecessor 建立唯一 successor。
- 允许新版本与它明确替代的祖先有效期重叠；与非祖先版本仍禁止重叠。
- 生效查询只选择当前版本链叶节点；历史正式批次继续引用旧版本和旧快照，不受后来更正影响。
- 同期间期初状态允许通过新物理记录更正，唯一键不得继续阻止合法新版本。
- 若已有正式下游工资，允许登记更正事实但禁止静默重算；重新使用新版本前必须按依赖顺序冲正和重建。
- 查询和审计结果返回完整 predecessor/successor 链，不能只在 `AuditLog.details` 中保存文本 ID。

最低测试：三类同期间更正成功、跨企业/员工替代拒绝、分叉替代拒绝、历史批次保持旧引用、叶节点选择和下游冲正保护。

### R2-011：个税与年终奖规则必须有独立有效期

对应前轮：PAY-006、PAY-021。

当前个税和奖金规则继承同一个外层政策有效期，且登记普通工资政策时强制要求奖金参数，无法表达普通工资个税继续有效但单独计税奖金已经到期。

本轮裁决：

- 外层政策有效期作为社保、公积金所属期政策有效期。
- `income_tax` 和 `annual_bonus` 参数分别增加自己的 `effective_from`、`effective_to`、`version` 和官方一手来源。
- 普通工资只要求支付日有有效 `income_tax` 规则，不要求存在奖金规则。
- 合并奖金使用支付日有效的 `income_tax` 规则；单独计税奖金还要求支付日有有效 `annual_bonus` 规则。
- 奖金规则可以缺省或已经到期，不得为登记普通工资政策而虚构延长期限。
- 回归测试和项目示例必须使用财政部、国家税务总局等真实官方链接；`example.gov.cn` 只能用于明确的 URL 格式负例，不得作为通过证据。

最低测试：2028 普通工资政策无奖金规则、2027 奖金规则到期后 separate 拒绝但 regular/combined 正常、各规则生效首日/失效次日、轨迹返回各自版本和来源。

### R2-012：法定款项支付必须回溯工资来源

对应前轮：PAY-007。

个人社保、公积金和个税开放项来源于工资付款事件，当前轨迹只把直接来源事件当作工资计提查询，导致批次、政策和员工资料 ID 为空。

本轮采用规范关系：

- 新建等价于 `payroll_event_links` 的关系表，使用复合外键把工资发放、社保、公积金、个税支付及其冲正事件关联到来源工资批次和必要的来源支付事件。
- 工资发放时写入批次关系；法定缴款从被核销开放项沿关系继承批次，并验证一笔缴款的全部来源兼容。
- 轨迹返回工资批次、政策版本、员工资料版本、来源事件、开放项类别、机构和险种。
- 不得只从 `facts.derived` JSON 临时回溯；JSON 可以作为解释快照，但规范关系用于约束和查询。

最低测试：工资确认 → 发放 → 三类缴款，逐步检查轨迹；混合不兼容批次、跨企业来源和冲正后的关系查询。

### R2-013：草稿阶段也必须形成证据链

对应前轮：PAY-009。

未确认工资草稿没有业务事件，当前批次查询只从事件关联收集证据，导致已经引用的证据只返回数量而没有 ID、哈希和元数据。

必须实现：

- 新建工资批次与证据的组织一致关联表；预览保存草稿时即原子写入。
- 证据不存在、重复或属于其他企业时，预览拒绝。
- 确认时业务事件关联相同证据，不复制证据内容；批次与事件均可追溯到同一 SHA-256 对象。
- 草稿、正式、已取代和已冲正批次查询均返回稳定的证据数组。

最低测试：草稿查询、确认后查询、跨企业证据、重复引用、草稿 superseded 后查询和冲正链查询。

### R2-014：迁移必须处理存量污染并可恢复科目变更

对应前轮：PAY-017、PAY-018。

已复现 `0001` 中核销合计与开放项累计不一致的数据可以带病升级；降级后还遗留新增工资科目或绑定的工资系统角色。

必须实现：

- 安装守恒触发器前扫描全部旧开放项和核销；发现不一致时以 `OPEN_ITEM_SETTLEMENT_INVARIANT_VIOLATION` 终止，revision 保持 `0001`，不得半升级。
- 升级时记录每个工资科目动作：新建科目或为兼容旧科目绑定角色，以及原始角色值。
- 空工资数据降级时删除由迁移新建且未被引用的科目，并恢复兼容旧科目的原始角色。
- 已有工资事件、凭证或其他引用导致无法安全删除时，降级必须以明确诊断拒绝；不得删除历史账务，也不得悄悄遗留半降级状态。
- `alembic check` 在空 PostgreSQL 和带旧数据升级后均无漂移。

最低 PostgreSQL 测试：矛盾存量核销升级失败、正常存量升级、新建科目降级清理、兼容科目角色恢复、有正式工资数据时安全拒绝降级、`base → head` 和允许场景的 `head → 0001 → head`。

## 4. 建议工作包与顺序

### 工作包 A：税务状态与奖金

范围：R2-001、R2-002、R2-009、R2-011。

主要文件：工资计算器、税务状态关系模型、相关 schema；工作期间独占 `service.py` 的工资试算、确认、年终奖和冲正依赖段落。

### 工作包 B：数据库与迁移

范围：R2-003、R2-005、R2-006、R2-010、R2-014。

主要文件：`models.py`、`ledger.py`、`alembic/versions/` 和 PostgreSQL 不变量测试。模型和迁移必须由同一工作包统一维护，避免元数据漂移。

### 工作包 C：支付、MCP 与证据链

范围：R2-004、R2-007、R2-012、R2-013。

主要文件：`mcp_server.py`、严格 schema、支付和查询服务。必须在工作包 A、B 合并后取得 `service.py` 独占权。

### 集成工作包

范围：R2-008 和全部交叉回归。集成者负责真实 STDIO PostgreSQL 闭环，不能通过绕过工具直接调用服务层完成。

推荐执行顺序：A 与 B 在不共享文件的前提下并行准备；B 先落地关系和迁移，A 接入状态槽；随后 C 接入支付关系和 MCP；最后执行集成工作包。
