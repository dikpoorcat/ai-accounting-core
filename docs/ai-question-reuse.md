# 会计 AI 信息复用与追问机制

本轮解决跨步骤和恢复对话后的重复追问，并以业务能否接续作为验收。已有依据能明确回答的事项直接复用；预览过期、回执未知和待重算通过现有入口处理；真正变化的事实只核对变化部分。会计操作不修改实现，也不因技术限制再次索取已确认业务事实。

## 实现

- 操作协议版本17把提问前定位、上下文复用、分页及精确来源读取、领域核验和技术恢复串成明确流程。公司、实际业务期间、对象和字段分别核对，工作月份不代替业务期间。
- 工作稿问题支持可选 `pending / answered / resolved / withdrawn / deferred` 状态、明确业务范围的 `target` 及 `disposition_reason`。旧稿保持原样可读，不根据自然语言回答或省略状态推断事实。状态和来源引用不代替正式事实、批准或完成依据。
- 登记准备、直接登记和命令验证使用同一叶字段元数据，完整保留缺项、核算／管理语义、允许精度、可复用来源与约束。单次错误组按实际字段复用元数据，不跨请求或 union 分支共享；路径索引及对象来源仍逐项构造。显式字段元数据优先于标量类型的精度说明，不把管理日期变成核算必填事实。
- 个税文件诊断在 `cause` 保留原问题，结合文件的 `blocking_scope` 解释影响范围；工资准备与个税文件共用原异常的问题投影，逐项 `resolution / blocking_scope` 优先且不修改原异常。下一步入口仍是单一类型化目标，命令名单由一个类型定义提供，不能从中文错误文本推断业务答案。
- 已有 `save_display_profile` 入口可以在工作稿中保存候选及完整未判明请求。只有当前公司对应的成功回执及结果引用才能移除原请求，不增加新的业务写入能力。
- 生成的浏览器合同同步保留诊断字段、候选唯一性与数量约束。Ajv 字符串长度辅助函数采用其原始 Unicode 实现内联，避免 ESM 模块含 CommonJS `require`，不关闭长度校验。
- 四个合成评测入口显式选择种子、计数器和中继参数，共用子进程参数构造；模块导入不会改写其他入口，CLI及基线比较脚本的公共接口保持可用。

详细工作稿字段和恢复用法见[事项工作稿恢复](work-draft-recovery.md)；业务办理顺序与独立能力缺口的处理见[本地内核操作](local-kernel.md)。

## 初次实现验证（2026-10-13）

集中相关 Python 回归376项通过；随后增加的毛额变化、六类事项恢复及管理请求回执场景通过，最后一组工作稿／回执回归24项通过。合计379个不同相关测试场景通过。前端测试、类型检查与构建、数据库及响应合同一致性、Ruff和差异空白检查通过。

合成测试使用 `tests/kernel/question_reuse_agent_harness.py`，复用生产 `MCP → ServiceClient → HTTP → LocalService`，HTTP端口由系统分配。合成库和负责人身份保留后重启；三个独立智能体均使用 GPT-6.1-sol、medium 推理，不继承前次对话，只读取公开元数据及自己请求的工具响应。文件访问遵守评测任务约束，没有为智能体另设操作系统级文件沙箱。

| 实际 AI 对话 | 结果 | 重复追问 | 必要新增追问 |
|---|---|---:|---:|
| 第2步工资及税额已确认，第3步社保登记回执待恢复，第4步接续 | 恢复原回执、读取分页来源，复用方案和税额，正式发布净额8,874元的工资 | 0 | 0 |
| 服务重启后接续办公服务，债权人答复提前保存在工作稿 | 保全原答复为证据，补齐类型化事实，正式发布555元费用并关联原行 | 0 | 0 |
| 已确认工资毛额从10,000元更正为11,000元，新方案有效但旧税额仅覆盖旧毛额 | 预览阻止沿用旧税，只询问当前毛额对应税额，保存待答及接续位置 | 0 | 1 |

这三段对话验证了已解决范围的复用、技术恢复和实际变化后的必要提问，不宣称所有未来对话都不会误问。合成对话没有执行银行付款或外部申报。不同运行阶段的构建身份和原始工具结果保存在忽略目录 `.tmp/question-reuse-20261013`，汇总记录为 `validation-results.json`。

额外的字段来源清单检查未通过，返回18条既有说明缺口：3条已退出人员档案字段的语义补充，以及15条备份、投影、回放、保留边界等表的来源归属。这些对应本轮前已有的字段／结构改动，不由本轮问题状态或诊断合同产生；未删除旧说明或替其他工作补写来源。诊断保存在同一忽略目录的 `field-inventory-diagnostics.json`，不计入通过项。

## 代码收口验证（2026-10-13）

收口统一了异常上下文投影和 resolution 命令定义，消除了评测模块导入时的全局覆写，并将服务端已有的候选唯一性约束同步到浏览器合同。工作稿状态、业务采用范围、金额精度和正式写入门槛保持原规则。

单次组装100行资料的202个缺项，只对4个实际叶字段生成元数据；两对象批次的404个缺项仍为4次，下一请求重新读取4次。验证同时检查不同对象的来源、同名 union 分支、更新后的字段声明及原异常不被修改，不将元数据复用变成跨请求业务缓存。

成组相关回归367项通过；前端全套测试、合同同步检查、类型检查与构建、Ruff和限定改动的差异空白检查通过。有界分页检查明确断言首个资料页只有1条，再沿游标查齐确认来源并正式发布。隔离MCP启动、工作稿读取、保留身份重启与schema检查通过，合成进程正常退出且监听关闭。本次没有重新运行真实AI对话基线，初次对话结果仍仅属于上一节记录的样本和构建。

本轮没有改变公司或目录数据库结构，没有处理真实业务或重启现有服务；Git提交按用户另行指令执行。源码优化尚需现有记账进程重新加载后才会生效；独立的劳务代发能力和页脚解析不属于本轮实现范围。
