# 记账引擎选型调研报告：开源改造 vs 自研

> **决策文档 · v1.0 · 2026-08-09**
> 目标：回答「有没有可适用或改造的开源记账引擎（用于中国小规模纳税人），还是自己从头打造更合适」
> 历史快照：本文中的事件数、测试数和未启用模块均为 2026-08-09 立项时状态；当前能力以文档索引中的最新开发基线和最终验收记录为准。

---

## 一、TL;DR（结论先行）

**结论：继续自研（你的 `ai-accounting-core` 方向完全正确，且已远超"从零"阶段），不要引入任何现成记账引擎作为核心依赖。**

理由一句话：你要做的不是"记账引擎"，而是 **「业务事实 → 分录」的决策内核 + 中国小规模纳税人税务规则引擎**。开源世界的"记账引擎"分成三类——纯文本簿记（Beancount/hledger）、通用账本基础设施（Formance/Midaz）、重型 ERP 会计模块（ERPNext/Odoo）——**没有任何一类覆盖"中国小企业会计准则科目体系 + 增值税价税分离/起征点/减免 + 凭证生命周期 + Agent 函数接口"这条完整链路**。你的项目恰好已经把这些最难的部分（事件目录、开放项核销、税务规则版本化、借贷平衡约束、不可变凭证、MCP 接口）做出来了。

**唯一值得做的是"思想借鉴"而非"代码依赖"**：Beancount 的数据完整性哲学、Formance 的可编程交易 DSL 思想，可以在架构文档里吸收，但不必成为运行依赖。

## 二、问题本质：你需要的不是一个"记账引擎"

「应收账款负数」这类问题的根因，你在消息里已经诊断得很准：

> 系统没有把「业务事实 → 收入确认/预收/应收结算 → 税务处理」这条链路建模，导致用户能在不存在应收余额时直接贷记应收账款。

这说明需求本质是**三层能力的组合**：

| 层 | 能力 | 开源引擎现状 |
|---|---|---|
| L1 决策层 | 业务事实 → 分录模板（事件驱动，非自由分录） | ❌ 几乎所有开源方案都缺 |
| L2 内核层 | 复式记账 + 借贷平衡 + 科目体系 + 凭证生命周期 | ✅ 有现成，但均为"通用"或"西方税务"语义 |
| L3 规则层 | 中国小规模纳税人税务（价税分离/起征点/减免/附加税） | ❌ 全部缺失，必须自研 |

复式记账本身是**五百年前的成熟算法**，实现难度低、不是护城河；真正的护城河在 L1 的事件目录（什么业务事实→什么分录）和 L3 的税务规则引擎（政策时效、地区差异、减免条件）。这两层开源世界**没有任何东西可以直接搬**。

## 三、开源候选盘点（按定位分三类）

### A 类：纯文本复式记账（Plain Text Accounting）

| 项目 | 语言 | 定位 | 中国适配 |
|---|---|---|---|
| **Beancount** | Python | 单用户、纯文本、强校验复式记账 | 无科目体系、无税务、无凭证生命周期 |
| **hledger** | Haskell | Beancount 同类，CLI 优先 | 同上，功能更轻 |
| **Ledger** | C++ | 同类鼻祖 | 同上 |

**关键评估**：

- ✅ **优点**：数据完整性做得极致——借贷必平衡、账户必存在、余额断言（balance assertion）、交易不可变。它是"账目严谨性"的最佳教科书。
- ❌ **硬伤**：
  1. **纯文本文件存储**，面向单用户个人记账，不是为并发 SaaS/多组织设计的；你要的"数据库 + 事务 + 触发器级约束"它没有。
  2. **无业务建模**：它记录"分录"，不回答"这笔收入要不要预提增值税"。
  3. **无中国税务**：价税分离、起征点、减免全是空白，甚至金额是小数而非"分"。
  4. 要改造成企业记账引擎，相当于**重写 80% + 保留格式解析**，得不偿失。

**可借鉴点**：`balance assertion` 的"账户余额不可为负（除非明确允许）"思路，与你开放项核销机制是同一哲学——已在你的内核中实现得更业务化。

---

### B 类：通用账本基础设施（Ledger Infrastructure）

| 项目 | 语言 | 定位 | 中国适配 |
|---|---|---|---|
| **Formance Ledger** | Go | fintech 核心账本，Numscript 可编程交易 DSL，PostgreSQL 存储，REST API | 无凭证/科目/税务语义 |
| **Midaz** | Go | 较新的开源多租户账本 | 同上 |
| **Medici** (Node.js) | JS | MongoDB 复式记账引擎 | 无税务，MongoDB 事务弱 |

**关键评估**：

- ✅ **优点**：Formance 做了扎实的**原子多分录交易 + 账户建模 + 可编程 DSL**，PostgreSQL 存储，社区活跃（1.3k stars），很适合"钱包/支付/余额转移"类 fintech 场景。
- ❌ **硬伤**：
  1. **建模对象是"账户余额和资金流转"，不是"会计凭证"**。没有借贷科目语义、没有凭证编号/期间/冲正/结转这些中国企业记账的基本构件。
  2. **无中国税务**：它甚至没有"税"的概念，遑论增值税简易计税。
  3. 引入它 = 在 Go 服务外围再包一层你的 Python 决策内核，中间还要做语义映射（balance ↔ 科目），**两头不讨好**。

**可借鉴点**：Numscript 的"交易模板可编程化"思想——如果你未来要把分录模板参数化/可配置化，可以借鉴这种 DSL 设计，但那是远期优化。

---

### C 类：完整开源会计系统（重 ERP）

| 项目 | 语言/框架 | 定位 | 中国适配 |
|---|---|---|---|
| **ERPNext** (Frappe) | Python/Frappe | 开源 ERP + 会计模块 | 有 erpnext_china、CAS4ERPNext 等社区本地化，但偏"企业会计准则"且质量参差 |
| **Odoo Community** | Python/Odoo | 开源 ERP + 会计 | 有 l10n_cn 中国准则模块（企业准则，非小企业准则）；Community 版会计功能受限 |
| **华夏ERP (jsh_erp)** | Java/Spring | 中国本土开源进销存+财务 | 有总账/凭证，但架构老、财务模块浅，社区弱 |
| **GnuCash** | C++ | 桌面单机复式记账 | 无中国税务 |

**关键评估**：

- ✅ **优点**：这是开源世界里最接近"中国会计"的选项，尤其是 ERPNext + erpnext_china 组合，有科目表、凭证、报表。
- ❌ **硬伤**：
  1. **面向"人类用户在 Web UI 里点鼠标"设计**，与你「只有一个聊天界面 + 财务 AGENT 调用函数接口」的愿景**完全相反**。你要的是 API-first 的"内核"，它们是 UI-first 的"应用"。
  2. **框架极其沉重**：Frappe/Odoo 的 MVC、权限、ORM、迁移体系是一整套"操作系统"，Agent-first 改造要么绕开它（等于没用到它的记账能力），要么被它绑架。
  3. **中国适配是"社区补丁"级别的**：小企业会计准则（区别于企业会计准则）支持薄弱，小规模纳税人税务（3%/1%、月10万/季30万起征点、六税两费减半）几乎空白，仍需你自己建模。
  4. 记账能力与进销存/CRM 深度耦合，解耦成本高。

**可借鉴点**：ERPNext 的科目表结构、凭证/冲销/期间结账的**产品语义**可以参考对照，但不必用它的代码。

## 五、决策分析：改造 vs 自研

### 方案 1：改造 Beancount/hledger
- 工作量：需重写存储层（文本→DB）、加科目体系、加税务引擎、加凭证生命周期、加多组织 —— 相当于**重写 80%**。
- 风险：被纯文本单用户的底层模型长期拖累。
- **判定：不推荐。**

### 方案 2：改造 Formance/Midaz
- 工作量：需在其上重建会计语义（科目/凭证/期间/冲正/税务）——**语义鸿沟太大**，且跨语言（Go vs Python）维护成本高。
- 风险：绑定一个 fintech 方向的社区，中国会计支持遥遥无期。
- **判定：不推荐。**

### 方案 3：改造 ERPNext/Odoo 的会计模块
- 工作量：先解耦记账与 ERP，再重写税务层，再为 Agent 写全套 API —— **比自研更慢**。
- 风险：被重型框架和社区补丁的坑反噬。
- **判定：不推荐。**

### 方案 4：在现有 `ai-accounting-core` 上继续自研（推荐）
- **现状盘点**（我已通读代码）：
  - 19 类业务事件（服务现销/赊销/履约、客户回款/预收/退款、费用、供应商付款、报销、股东往来、银行手续费、内部转账、税款支付/减免、工资/社保/公积金/个税、工资计提）；
  - 事件目录驱动分录模板（`_derive_entries`），**Agent 不能自由造分录**；
  - 开放项严格核销，**从机制上杜绝"应收账款负数"**；
  - 税务规则版本化（2026–2027 小规模试点：3%/1%、月10万/季30万、六税两费减半、城建税显式配置），带官方来源 URL；
  - 借贷平衡（应用层校验 + **PostgreSQL 延迟约束**）+ 已入账凭证**不可改删触发器**；
  - 幂等（idempotency_key + payload hash）、期间关闭、关联冲正、审计日志、证据库（SHA-256）；
  - 103 个测试（含 Hypothesis 属性测试、PG 集成不变量测试）、ruff 全绿。
- 工作量（历史判断）：当时核心记账和税务链路已完成，存货、固定资产、无形资产、借款利息仍返回 `MODULE_NOT_ENABLED`，展示层也暂缓；固定资产、无形资产和借款闭环后来已按各自最终验收记录完成。
- 风险：单点维护，但记账内核本身小而稳定，风险可控；税务政策变化已被"版本化规则"机制兜住。
- **判定：唯一推荐。**

## 六、对现有项目的三条强化建议

1. **把 Beancount 的哲学写成文档，而不是引代码**。在 `docs/` 里固化一条架构原则："任何账户余额的异常方向（如应收为负、应付为负）都必须是**事件目录显式建模**的结果（如预收冲应收），绝不可能是用户/Agent 自由录入的结果。"——你的开放项机制已经做到，把它写成不可侵犯的 invariants 文档，防止未来演化走偏。

2. **事件目录是最大资产，持续扩充它**。未来新增业务（存货、固定资产）时，沿用"证据齐备 + 规则唯一 + 平衡分录 + 冲正闭环"四件套，拒绝为图省事开放任意分录接口（AGENTS.md 已守住这条线，继续保持）。

3. **远期可选：可编程分录模板**。若事件类型膨胀到难以枚举，可借鉴 Formance Numscript 的思路，做一个**受限的、可审计的分录模板 DSL**（模板仍由你发布，Agent 只能选模板不能改分录），但这是"优雅后路"而非"当前刚需"。
