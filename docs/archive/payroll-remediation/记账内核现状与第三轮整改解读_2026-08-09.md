## 1. 先说人话：这套系统是什么、不是什​​么

这不是一个“让 AI 随意写借贷分录”的记账工具，而是一个**受约束的确定性会计内核**。

Agent（例如 Codex）理论上只能说：

> “8 月 8 日已完成咨询服务，收到客户 10,100 元，普通发票，税率 1%。”

内核再根据事先确定的规则，生成唯一的凭证，例如：

```text
借：银行存款                    10,100.00
  贷：主营业务收入                10,000.00
  贷：应交增值税                     100.00
```

它刻意禁止 Agent 直接提交“借什么、贷什么、金额多少”的自由分录。这正是在解决你提到的根源问题：**业务事实 → 收入/预收/应收/结算 → 税务处理**必须由规则链路决定，不能让聊天模型在不存在应收余额时直接贷记应收账款。

但要注意：当前仓库是**后端记账内核 + MCP 函数接口**，不是面向普通人的聊天产品，也不是可直接用于报税、申报或法定账簿的产品。

以下能力已从 README、MCP 工具、数据模型、服务代码和测试中交叉确认。

### 3.2 你最关心的“负数应收账款”防线

当前设计已经包含正确方向的三道防线：

1. **业务类型拆分**：服务赊销、客户回款、客户预收、履约、退款不是同一个“收款/收入”按钮。
2. **开放项（Open Item）模型**：应收/应付不是科目余额上的随意加减，而是逐笔业务产生的待核销项目。
3. **严格核销**：付款要指定核销哪一笔开放项；单笔和累计均不能超过可核销余额。

因此，若聊天 Agent 不知道客户这笔钱是“还旧应收”还是“新预收”，系统应返回 `needs_information`，而不是自行贷记应收账款。这正是你希望的产品机制。

## 5. 第三轮 todo 翻译：12 项究竟缺什么

### P0：不修绝不能试用的 4 项

| 编号 | 原始技术问题 | 人话解释 | 真实风险 |
|---|---|---|---|
| R3-001 | 个税累计状态未在“员工 + 税年”层面做并发顺序锁 | 两个操作员/Agent 同时确认同一员工不同月份工资时，都可能按看不到对方的旧累计数算税 | 个税累计错误，后续月税额错误 |
| R3-002 | 税务状态槽和奖金依赖仅靠服务层判断 | 有数据库权限或缺陷路径时，可以让 A 员工奖金引用 B 员工工资，或让二月状态指向五月工资 | 员工、月份、奖金与个税关系错配 |
| R3-003 | 工资确认后的逐险种代扣额度仍可改 | 工资已确认后，攻击者可事后把“养老代扣 0”改为“养老代扣 100”，再据此付款 | 可伪造代扣负债与付款依据 |
| R3-004 | 业务事件的“已冲正”与“已退款”混用 | 全额退款后系统把原业务事件当成已冲正；再冲正退款时尝试把旧事件改回已入账，数据库拒绝 | 服务层先说成功、提交时却失败；退款链断裂 |

### P1：不一定立即错账，但必须在工资模块验收前修完的 8 项

| 编号 | 缺口 | 人话解释 |
|---|---|---|
| R3-005 | 版本更正链没有真正接通 | 员工工资档案、社保政策、期初累计税状态只能“拒绝重叠”，不能保留新旧版本并明确替代关系 |
| R3-006 | 工资付款来源链只有一对一 | 一次法定缴款如果对应两次分批发薪，来源字段被置空，系统丢掉了“钱从哪两次工资来”的证据 |
| R3-007 | 已保存工资批次的证据可被数据库直改 | 工资草稿或正式批次的附件可以被事后删、换、加，审计链不稳定 |
| R3-008 | 并发冲正的幂等回放不稳定 | 两个 Agent 同时提交同一个冲正，有一个可能错误地收到“不可冲正”而不是同一笔冲正结果 |
| R3-009 | 银行流水冲正后无法用同一流水重记账 | 原付款冲正后，原银行流水仍被占用；正确的新记账无法匹配这条真实流水 |
| R3-010 | 计算快照显示的政策版本与实际计算用的版本可能不同 | 例如跨年发薪，系统显示“按 2026 政策算”，实际却按 2027 个税规则算；审计哈希自相矛盾 |
| R3-011 | 迁移前只检查核销金额，不检查开放项状态 | 旧数据可出现“金额已结清但状态仍为 open”并升级成功，之后报表和可核销余额会混乱 |
| R3-012 | MCP 参数校验错误会回显用户原始输入 | 输入身份证、银行卡、连接串等非法字段时，错误消息可能原样回显，存在隐私泄露风险 |

### 6.2 复核发现的迁移阻断问题

本次在本地 Docker PostgreSQL 上发现实际升级失败：

```text
0001_initial → 0002_payroll → 0003_payroll_round2_integrity
失败于：0003 给 voucher_lines 回填 org_id
错误：lines of a final voucher are immutable; create a reversal
```

原因是：

1. `0002` 先安装了“正式凭证行不可修改”的数据库触发器；
2. `0003` 随后要对历史 `voucher_lines` 执行 `UPDATE ... SET org_id = ...`；
3. 如果数据库中已有正式凭证，该 UPDATE 被前一步触发器禁止。

本地库在升级尝试后仍停留在 `0001_initial`，并且有 2 张正式凭证。PostgreSQL 的事务性 DDL 使这次失败没有留下半升级状态；本次审阅未修改业务数据。

这项问题不在第三轮任务书的 12 项中，但它直接影响“有历史账的用户能否升级”。建议把它提升为：

```text
R3-000：历史正式凭证存在时，0001 → head 迁移必须可成功完成
优先级：P0（上线/试用阻断）
```

可行修复方向不是“临时关闭所有保护”，而是让迁移以受控方式完成数据回填，例如：

- 在触发器中识别仅供一次性迁移使用的受限会话变量；
- 或调整迁移顺序：先回填 `org_id` 并加组织一致性约束，再启用最终凭证行不可变触发器；
- 必须在隔离 PostgreSQL 中覆盖“已有 posted/reversed 凭证”的 `0001 → head` 升级用例；
- 不得在用户真实数据库上做破坏性降级测试。

### 6.3 为什么“15 个 PostgreSQL 测试通过”仍不矛盾

测试容器通常从空库或特制的测试数据开始；本地失败的路径是“已有历史正式凭证、迁移还需要回填新字段”。

所以：

```text
PostgreSQL 测试通过 ≠ 所有真实历史数据库升级都通过
103 测试通过 ≠ 第三轮 P0/P1 已解决
```

这也是第三轮验收文件强调“主动反例、双连接并发、直接 SQL 攻击、迁移污染数据”的原因。

## 7. 现在还缺哪些产品级能力

即使第三轮工资整改全部完成，距离“非专业人士可放心聊天记账”的第一版产品还缺至少四层。

### A. 聊天编排层：尚未实现

目前没有模型调用、对话上下文、追问策略或用户确认体验。需要新增：

- 从自然语言抽取候选业务事实；
- 先查应收、预收、银行流水和最近事件；
- 对“收到 1 万元”之类歧义强制追问：是还款、预收、当期服务收入还是股东款？
- 把内核返回的 `needs_information` 翻译成普通人能回答的问题；
- 先展示“将产生什么会计影响”，获得用户确认后再调用写入函数；
- 解释最终凭证为什么这样做，而不是只显示借贷术语。

### B. 企业初始化与真实数据接入：尚未产品化

目前缺少一套面向非财务用户的引导：

- 公司基本信息、纳税人身份、按月/按季申报；
- 起始期间、期初银行余额、期初应收应付、已有预收；
- 所在地社保公积金政策配置与专业人士复核；
- 银行账户、银行流水持续导入、票据归档；
- 当前会计期间和结账权限。

### C. 生产安全：尚未完成

当前定位仍是“单企业私有模拟试用”。真实试用前至少需要：

- 用户/角色/组织隔离与授权；
- 数据加密、证据文件访问控制、日志脱敏；
- 数据库备份、恢复演练、审计留存；
- 迁移发布策略与 CI；
- 支持/诊断机制；
- 会计师复核流程。

### D. 会计范围：当前明确未覆盖或未完成

- 固定资产及折旧；
- 无形资产；
- 借款利息；
- 存货及成本结转；
- 完整会计期间创建、结账前检查、月结闭环；
- 期初余额和真实银行对账增强；
- 报表、导出、纳税申报和法定账簿。

## 9. 建议的实施顺序

不要现在就把精力放到聊天 UI 或报表。正确顺序是：

```text
第 0 步：保护当前成果
  └─ 将现有未提交改动做一次独立、可审查的 Git 提交，并建立远端备份

第 1 步：先补 R3-000 历史迁移阻断
  └─ 有旧正式凭证的 0001 → head 必须可迁移、可回滚、无半升级

第 2 步：完成第三轮 P0
  ├─ 累计个税并发顺序域
  ├─ 税务状态与奖金依赖数据库约束
  ├─ 代扣权益冻结
  └─ 退款与冲正状态机统一

第 3 步：完成第三轮 P1
  └─ 版本链、来源链、证据链、幂等、银行重记账、快照、迁移预检、脱敏

第 4 步：独立验收
  └─ 真实 STDIO + PostgreSQL 双连接并发 + 直接 SQL 攻击 + 迁移污染数据

第 5 步：只做一个极简聊天编排层
  └─ 描述业务 → 追问缺失事实 → 预览会计影响 → 用户确认 → 入账 → 可读解释

第 6 步：选择 20–30 个真实但脱敏的业务案例做封闭试用
  └─ 先覆盖服务型小规模纳税人的收入、预收、应收、费用、股东款、退款、银行流水
```

### MVP 第一版的关键产品原则

不要让用户看到“请选择借方科目、贷方科目”。应让用户回答业务问题，例如：

> 这笔 10,000 元客户收款，对应哪种情况？
>
> - 已完成的服务收入
> - 结清此前某笔应收
> - 尚未履约的预收款
> - 不确定，帮我根据合同/流水/历史记录判断

内核最终仍必须保留“不确定就不入账”的权利。**降低门槛不等于让系统猜账。**

## 最终结论

你并不是“做了一个没有功能的东西”。相反，当前已经有一套相当认真、且方向正确的**确定性记账内核原型**，尤其“不得自由分录、应收应付按开放项核销、信息不足返回追问、已入账凭证不可改”的设计，正对准了传统财务软件对非专业用户最危险的缺陷。

但也不能因为 103 个测试绿了就把它当作可以开始给真实工资、真实银行流水自动入账的软件。第三轮 todo 说明：工资模块正在从“能跑”走向“在并发、篡改、冲正、历史迁移下仍不会错账”的阶段。这个阶段最值得投入，因为它决定未来聊天 Agent 是真正降低门槛，还是只是把复杂错误更快地自动化。
