# 当前开发库的显式结构升级

当前本体系库优先用于试用和补齐缺口。结构变化通过已声明的前向升级保留实际进度，空库重放只有用户明确指定时执行。此入口用于 `ai-accounting-kernel/2`、公司 `draft / 0` 的精确已知来源；不升级旧体系，不把开发库改称正式版，不接收外部SQL或猜测未知结构。

## 运行入口

先正常停止当前根目录的常驻服务，并等待进程退出。服务仍持有 `.resident.lock` 时，升级拒绝执行。

```powershell
finance-local --root <当前资料根> stop
finance-local --root <当前资料根> upgrade-development
```

普通 `serve`、`daemon`、MCP连接和数据库打开只做当前合同核验，不自动执行升级。没有明确升级路径时保留当前库并补齐实现。原公司、数据库、目录和负责人身份保持不变，不要求建立新负责人。

升级入口先核验目录身份、全部公司源结构、保存内容及后台任务。每家公司使用相匹配的来源或当前合同完成完整核验，任何未完成的创建、恢复或后台任务先处理。源合同原文随包保全，目标与来源由可信代码固定声明；新增或移除其他SQL对象、超出声明的列或约束变化均拒绝。

## 备份与原子性

任何DDL执行前，先在当前根下独立 `.development-upgrades/<操作编号>` 保存目录SQLite快照，并为每家公司生成和核验独立格式2便携ZIP。目录快照核对负责人、会话、公司登记及设置历史。全部公司备份完成后才开始结构调整；已有备份目录和正常关账备份不覆盖。

每家公司独立事务升级，锁内重新核验来源。改变可空约束时，完整复制原表行到临时表，以目标精确SQL原名创建，再完整复制回去并恢复全部索引和触发器。保留所有原列、原行值、身份、引用和SQLite保存的SQL；不重新计算业务，不新增凭证。SQL、全部原表行值摘要、保留历史摘要、外键与完整内容核验全部通过后提交。失败回滚并恢复外键；外键恢复失败的连接关闭。

多公司操作按公司提交。后续公司失败时，回执明确已完成前缀、失败公司和备份目录，失败公司回滚；不声称所有公司共同回滚。重试重新核验实际状态，已达到目标的公司跳过，不重复修改。

## 结构历史

原始 `schema_history` 的版本0记录及指纹保持原文，不改成目标指纹。每次已声明调整向不可变 `schema_draft_history` 追加来源指纹、目标指纹、保留历史摘要和实际安装时间。

普通连接同时核验当前完整SQL和追加链：从原安装指纹起，序号连续，每个端点均有包内精确合同，每条边均有明确声明，最后达到当前合同。普通连接只读小结构链，不扫描业务历史。新公司原安装记录就是当前合同，追加链为空。正式合同不能借开发链接收开发库，已发布合同和正式版本升级规则保持独立。

## 恢复实际操作

成功后核对返回的各公司验证结果，继续使用同一资料根和原有登录身份。业务资料及范围未改变时，原重放范围身份可继续使用，但服务需显式以原范围重新启动；同版预览重新取得。原关闭月份和冻结采用保持不变，新增业务仍通过类型化MCP入口登记。

升级备份采用其源结构的精确合同；它不冒充当前结构备份。恢复验证必须在独立目标完成来源合同和内容核验，不能用普通当前结构恢复入口静默跳过指纹差异。后续当前结构关账备份仍在每家公司配置目录独立生成，并以后台任务成功及ZIP核验为准。

首次滚动时，既有ZIP可以仍属于包内已声明的升级来源。滚动入口使用该精确来源合同核验全部内容、证据与原公司身份，保留原字节为previous，再发布当前结构ZIP；不会把旧包改标为当前包。普通验证和恢复仍使用其原有精确结构边界。请求键相同但结构不同不能返回旧包作为当前备份；发布中断恢复也按同一来源与身份核验。
