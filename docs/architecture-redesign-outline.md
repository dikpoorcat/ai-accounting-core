# 项目架构重新设计纲要

本纲要安排新架构设计和后续实施。先弄清现状、目标与信任分工，按目标独立设计完整的新架构及数据、接口和技术方案，再对照现有实现复用和查漏，形成可直接交付开发的文档，最后按依赖并行或分阶段实现与验证。完整细化结果见 [新体系需求与开发设计](redesign/README.md)，本文件保留讨论主线。

讨论背景见 [AI 与内核分工及信任模型讨论记录](ai-kernel-collaboration-discussion-2026-10-14.md)。

## 一、现状与目标

### 1.1 项目为谁服务，完成什么工作

本项目让不懂财务会计知识的老板，也能依靠会计 AI 和内核，更轻松地独立完成日常会计工作。

会计 AI 是老板的“外挂”：既理解业务、使用内核办理，也主动说明该做什么、需要哪些资料、怎样取得和按什么顺序办理。老板可以先交资料，不必先学会会计分类。

沿用一位本地负责人管理多家公司的场景，各家公司分别保存资料和账务。看板供老板核对现实业务，也方便专业顾问只读查看凭证、明细、报表和依据，协助发现问题。工作包括资料整理、核算、收付款核对、文件准备、外部办理跟进和反馈更正。

### 1.2 当前系统如何运转

当前由聊天中的 AI 与老板沟通、理解资料和安排操作，本地后台服务负责登记、核算、保存、查询及文件任务，每家公司使用独立数据库。

普通业务通常经过原件和对象登记、事实保存、计算预览、正式入账及资料关联。事实保存不等于正式入账。表格已有业务行、隐藏内容、金额和覆盖检查，图片等更多依靠 AI 阅读。已有批量入口、八步工作清单、持久工作稿和请求回执，支持资料复用与中断接续；不少内部步骤仍需 AI 协调。

看板有经营简报、资金、员工、资产和财务报表五页，已使用完整汇总、分页、按需详情及专用读取数据提高速度。网页可以查看凭证和报表，深入追查主要通过 AI 查询工具完成。

当前开放期可更新结果，闭期保留冻结记录并关联更正；普通关账仍有老板核对、独立密码批准和同版提交过程。已有文档执行能力用于指定范围的重放，通用日常标准文档交接尚需设计。

### 1.3 当前架构的主要问题

记账、存储和看板仍了解彼此较多的内部细节：写入直接衔接看板更新，业务追查使用看板内部规则，看板读取又依赖核算和存储结构。更新范围跟随底层表和查询，共同程序版本变化还可能使已准备好的读取数据失效。

因此，即使页面需求没有变化，调整记账也可能影响读取速度，需要重新检查已完成的优化。AI 同时承担业务判断和内部编号、调用顺序、资料关联的协调，增加了办理与恢复成本。

### 1.4 重新设计的范围与边界

按业务目标和已选信任模型重新设计整体架构，完整说明工作流程、模块职责与依赖、整体数据关系、公开接口及运行方式。现状用于理解需求与问题，旧代码、旧表和旧调用顺序不作为新结构的起点。

现有看板主要部分的显示内容、UI 样式和读取优化是明确保留的边界，接入安排见 4.4。整体方案形成后，再按第 5 章对照现有实现复用和查漏；本次交付范围的模块详细设计达到 6.1 的文档标准后，再进入实现。

### 1.5 重构后应达到什么效果

通过有代表性的业务和修改场景，检查：

- 老板能按 AI 引导准备资料、理解问题并继续办事。
- 老板能核对现实，专业顾问能找到凭证及依据、指出具体问题。
- 记账、报表和看板中含义相同的结果一致，更正得到正确处理。
- 补交资料、失败和中断后能够接续，减少重复询问及返工。
- 模块内部修改的影响可控，其他模块按原约定工作，已有读取效率得到保持。
- 有相应基础的开发者能按开发文档分别实现模块，具备条件的模块可以并行开发，并按约定完成集成。

## 二、信任模型与责任分工

### 2.1 系统怎样看待会计 AI

采用**协作信任**：接受 AI 在职责内的专业判断，资料理解、业务判断和办理中的问题交给会计 AI 解决；程序专注按明确规则核算、可靠保存和提供有效结果。

老板需要了解处理原因时，直接向会计 AI 询问。架构不为此积累操作日记或纠错档案，新设计不设置授权、审批或逐次批准流程。

### 2.2 老板、AI、专业会计人员和程序分别负责什么

| 参与方 | 责任 |
| --- | --- |
| 老板 | 提供现实信息和资料，作经营决定，核对现实差异，负责付款、申报等全部外部实际办理。 |
| 会计 AI | 主动引导资料和步骤，先查已有依据，作专业判断，整理业务事实和关系，使用业务入口办理，解释结果并接续反馈。 |
| 专业顾问 | 只读查阅账务和依据，协助发现会计处理或系统问题，提出建议；不能直接修改或批准。 |
| 程序 | 按明确规则核算，承接内部关联和执行步骤，可靠保存、查询、生成文件并返回实际处理结果。 |

老板回答现实问题，AI 承担专业工作。专业判断有疑问时，AI 继续核查，必要时借助顾问。程序问题通过相应入口或交维护处理，不用老板确认代替修正。

### 2.3 哪些检查值得保留

检查按实际作用和办理成本取舍：

- 金额精度、凭证平衡、公司与业务范围对应、一次提交完整保存，以及重复请求不重复记账，由程序保证。
- 内部关联、读取更新和任务接续，由程序承接，减少 AI 搬运编号和维护技术关系。
- 银行余额、明细与原有合计等独立核对，按发现问题的价值保留或简化。
- 反复证明已明确判断的手续予以简化或退出，审批手续退出。

清单内部相符不能证明原件没有遗漏，例如 AI 漏交两笔，程序把收到的其余业务算对，也无法知道遗漏。减少检查应明确会减少哪类发现能力，无需再补一套同等复杂的证明。

### 2.4 如何发现遗漏和处理错误

AI 主动查漏，老板核对现实，程序提示缺项和矛盾，顾问协助审查。问题按“定位、查证、处理、核对、接续”办理。

AI 先查当前记录、来源、已有答复和实际处理状态，确属遗漏再补入；事实或判断错误就修正。顾问意见是核查线索，程序缺陷交维护处理。正式结果正确而读取异常时，只修复读取内容。

处理后核对正式结果和相关展示，更新未解事项及下一步。已有资料和仍适用的答复继续使用，不因一次问题重新索取整月资料。更正规则集中在 4.1 中说明。

### 2.5 如何确定检查与效率的平衡

按问题的实际影响决定等待范围：缺少必要核算事实或存在明确矛盾时，相应结果等待查清；已有资料和准备工作可以保留。未知金额不填零，按月成立的信息不补造日期，普通管理备注缺失按实际影响处理。

无关且具备条件的当前工作继续；共同依据确有影响时，说明涉及的业务和结果。一次正式提交中需要共同成立的内容一起成功或失败，整月工作可以分步完成，局部成功不代表整月完整。

资料、核算、展示、文件和外部实际办理分别说明进度。文件失败不自动推翻正确账务，展示未更新也不能把旧内容说成当前结果。

AI 保持合理办理顺序，说明当前能做什么、哪项等待、需要什么资料及之后从哪里接续。已有资料、答复和决定仍适用时继续复用，变化时重点核对受影响部分。

## 三、新系统整体架构与模块设计

### 3.1 整体工作链路和模块边界如何确定

整体链路包括老板提供现实资料和答复、AI 引导并整理业务、内核核算与正式保存、读取接口组织结果和看板查阅。核对与顾问反馈由 AI 接续，程序承接内部关系和执行步骤。

每个模块负责明确的工作，通过公开约定交换输入、结果和状态。其他模块使用这些约定，不依赖它的私有函数、内部表结构或缓存安排。

交接含义不变时，内部代码、保存方式和读取方法应能分别调整。例如，修改记账内部实现，看板仍能正确读取并保持既定性能；优化看板也不应影响正常记账。确需改变交接含义时，明确受影响的模块并一起验证。金额单位、期间和完成状态的含义都属于交接约定。

独立模块仍有明确的依赖，共同核算口径、真实业务关系和完整提交继续保留。文件夹或程序数量不能证明独立，验证范围应按实际影响确定。

### 3.2 项目主体如何分别承接

六个主体各有承接模块，后台业务能力另按 3.3 划分。

| 项目主体 | 承接模块及职责 |
| --- | --- |
| 老板交互 | 接收资料、现实说明、答复和反馈，呈现 AI 的引导与结果解释。 |
| 会计 AI | 查找进度、引导老板、理解资料、作专业判断，提交完整业务并接续问题。 |
| 内核 AI 接口 | 提供业务办理和查询入口，把请求交给相应能力，返回实际结果及未完成事项。 |
| 数据库 | 数据存储模块执行约定的可靠读写和完整提交，业务含义由所属业务模块决定。 |
| 内核看板接口 | 看板读取模块按共同业务口径取得正式结果，组织完整汇总、分页和详情，负责读取效率与更新状态。 |
| 看板 | 沿用现有展示模块提供只读查阅和问题定位，方便老板核对、专业顾问审查。 |

沟通和看板查阅应能接回同一事项，问题由 AI 接续。记账与看板通过约定的结果及变化信息协作，记账不直接调用看板内部步骤。运行方式见 4.5。

### 3.3 核算与其他基础能力归谁负责

| 后台能力 | 主责 |
| --- | --- |
| 业务规则与计算 | 各业务模块定义事实含义、所需条件、适用规则和计算方法，说明真实依赖。 |
| 核算提交 | 承接计算结果，维护正式结果、凭证和依据，落实金额精度、凭证平衡、完整提交和请求防重；也承接无需生成凭证的结果。 |
| 资料与来源 | 保全原件、来源位置和交接范围，维护业务与来源的对应。 |
| 对象身份 | 维护公司、人员、机构、账户等共同身份；业务中的角色由所属业务负责。 |
| 报表与取数 | 维护报表项目、跨业务汇总和取数范围，供 AI、文件和看板共同使用；各业务字段的含义仍由所属业务维护。 |
| 办理与接续 | 按业务依赖安排内部处理，提供当前结果与未完成事项，供 AI 接续。 |
| 期间与关账 | 汇集相关业务结果和问题，维护月份状态、关账条件及冻结结果。 |
| 文件与任务 | 根据明确范围和正式结果生成文件，维护任务状态及失败接续。 |
| 备份恢复 | 明确备份范围，完成备份与核验，恢复其中的公司、负责人身份及业务资料。 |

AI 提交类型明确的业务事实，业务模块负责计算，核算提交模块落实正式结果，数据存储执行保存。内部协调由程序完成，不向 AI 开放任意借贷分录，也不把所有业务规则堆进公共模块。

### 3.4 各类业务如何进一步划分

按业务含义和共同规则划分，各模块通过公开约定使用其他业务的结果，现有实现的取舍见 5.2。

| 业务模块 | 承接范围 |
| --- | --- |
| 日常经营与往来 | 收入费用、项目成本、报销垫款、预收预付、应收应付、代收代付和押金等。 |
| 用工与薪酬 | 用工关系、工资、奖金、劳务、社保公积金及相应应付。 |
| 税费 | 适用规则、已有计税能力、有依据的实际税额、申报取数及缴款关系。 |
| 资产 | 固定资产和无形资产的购置、启用、折旧摊销及处置。 |
| 借款与股东资金 | 直接借入借出、本金利息与归还，以及股东对本公司的出资。 |
| 投资与理财 | 金融产品、对外股权及合作项目投资，按类型承接购买或出资、持有、收益、损失和退出。保留现有货币基金能力，其余按实际需要增加。 |
| 资金收付与对账 | 实际收付款、内部划转、跨月与部分清偿、流水匹配和余额核对。 |
| 期初接续 | 汇集各类期初余额和必要累计数据，复用所属业务规则，与本期发生额分开。 |

投资类型先预设货币基金、银行理财、其他基金、债券、对外股权和合作项目投资，分别讨论适用规则。“公司出资、张某经营项目，双方按约定分享收益、承担风险”是投资理财模块近期需要支持的一种记账方式，区分出资本金、收益分配、损失和本金收回。它不单独设模块或详情页，具体处理根据实际合作约定确定。

业务发生与实际收付款分别承接：工资形成应付后，付款只办理清偿；投资模块维护投资关系和结算结果，资金模块记录实际收付。税费使用各业务提供的明确结果，同一含义的金额只按一套规则计算。

AI 说明真实业务关系，程序衔接内部记录和处理顺序。各模块不直接修改其他模块的内部数据，也不因新增一种收付款就复制整套业务规则。

### 3.5 模块之间交换什么内容

模块按用途交换内容，不把内部处理步骤交给使用方安排。

| 交接内容 | 说明什么 |
| --- | --- |
| 业务事实 | 明确的事项、对象、金额、日期或期间、来源及真实业务关系，供相应业务模块处理。 |
| 处理结果 | 实际完成的内容和有效结果，以及尚未处理、缺项或失败的事项与原因。 |
| 变化信息 | 哪些业务结果和范围发生变化，供相关模块取得有效结果并更新自己的内容。 |
| 展示数据 | 按共同口径组织的完整汇总、分页明细、凭证及按需依据，供看板直接呈现。 |

交接应能定位公司、业务或对象，并说明适用期间和金额含义。AI 说明哪次付款对应哪笔业务，程序维护内部编号、关联和执行顺序。负责结果的模块维护数据版本，读取方据此区分当前结果和更新状态，避免汇总与明细混用；版本标识不意味着保存开放期的旧内容。

收到请求不等于完成，变化通知也不代替正式结果。失败或响应丢失时，程序先查实际处理状态，再返回原结果或接续未完成部分，避免重复入账。业务缺项由 AI 先查已有依据，确实缺少现实信息时再引导老板补充。

交接只围绕有效事实、实际结果和当前待办，不积累交接过程档案。具体交接格式在第 4 章细化。

## 四、数据、接口与技术方案

### 4.1 整体数据模型与资料规则如何设计

整体阶段先明确各模块及跨业务的共同概念和数据关系：公司、对象、业务事实、收付款、正式结果、凭证、期间和来源怎样对应，各由谁维护。金额、日期或期间、共同身份等含义统一，业务待办、正式完成和看板就绪等状态分别说明。

三类资料都围绕最终正确账务保存，排除重复草稿、历次改错和无用技术过程：

- **原件**保留支持最终事实的原始资料，由 AI 在指定公司目录中按月整理，资料模块维护来源。文件月份不代替业务期间，跨月使用通过引用接续。
- **标准业务文档**在日常变更时就改写为最终有效事实。改错、因纠错产生的红冲重记和补正直接归并，已经撤去的误记移出有效清单；真实付款、退款等仍分别保留，未解决事项单列。
- **数据库**保存当前有效事实和账务结果。开放月份直接修改或按条件撤去误记，已有凭证保留原编号，不保存被替换的错误内容和纠错过程。已关月份保留冻结结果，以关联冲正处理错误，冲正记录本身说明变化。补充依据而核算结果不变时，更新依据并沿用原结果。

文档更新与业务入口的实际处理保持对应。

新系统对三类资料安排备份，重建所需的最终事实及来源应能独立于数据库取得。备份恢复保存时的账务状态；文档重建按最终事实建立简化新账，不回放旧纠错过程。

### 4.2 标准业务文档和办理接口如何设计

AI 按所属业务模块定义的模板整理标准文档，说明公司、业务范围、对象、金额、日期或期间、来源、真实业务关系及未解决事项。文档能由程序直接读取，正常事项一次交接后，由程序完成内部处理。

本次提交明确要新增、更正或撤去哪项业务，同一业务保持稳定对应。换文档或调整行序不应重复登记，从文档删除一行也不自动表示撤去账务。程序依据明确资料查找或登记对象，衔接内部关联、计算和保存；存在歧义时返回具体问题，由 AI 核查。

文档中的独立事项可以分批办理，需要共同成立的一次处理一起成功或失败。必要事实未明确的事项保留待办，缺失内容不靠猜测补齐。程序返回实际完成内容、有效结果和未完成原因，AI 据此核对并接续。

响应丢失或办理中断时，先查实际处理结果，已成功的事项不重复登记。办理后文档归并为最终有效事实和当前待办，撤去成功的误记移出有效清单，提交动作不累积为过程记录。日常维护好的文档直接服务简化重建。

### 4.3 数据库结构和读写边界如何设计

总体阶段明确各模块的数据范围、主要表的用途与关系、公开读写入口及跨模块完整提交的边界。详细设计将本次交付模块的字段类型、必填项、关联与唯一性等约束，以及查询与索引写入开发文档，达到 6.1 的标准后交付开发。

同一公司共用数据库，不代表各模块共用全部表。所属模块负责数据含义和结构，存储模块执行可靠读写，其他模块通过公开入口使用，AI 和看板不直接修改业务表。

公司资料、数据库及备份位置由配置明确；每家公司使用独立 SQLite 业务库，目录库记录公司索引、负责人身份与本地配置。原件和标准业务文档在公司目录分区、按月整理，AI 整理内容，程序维护与正式记录的对应；数据库不可用时仍能读取资料。各次读写绑定公司，文件位置不作为业务身份或核算期间。

跨模块正式提交需明确共同成功的范围及协调方；资料文件、标准文档与数据库分别成功或失败时，说明实际状态，并按当前未完成事项接续。保存内容按 4.1 的原则执行。

看板读取数据由看板读取模块维护，业务查询索引由所属业务模块维护，都能根据已保存的有效记录重新生成。重新生成只整理已有内容，不重新办理业务、补造事实或改写已关账结果；内部表和缓存安排由负责模块维护。

### 4.4 记账与看板如何保持一致

现有看板主要部分先只接入新后台，保持显示内容、UI 样式和既有用法，保住已经完成的读取优化。看板读取模块适配现有展示需要，不因后台重构而重做原有页面。

个别点击后展开的内容若暂时取不到数据，可以先不读取。开发时说明具体位置、缺少什么及对老板核对、顾问查阅的影响，由老板决定是否补齐。现有看板不支持且确有需要的内容，新增独立页面或板块，保持原有模块及读取性能。

正式账务、当前结果标识和受影响范围一起生效。提交成功后及时安排更新，看板读取模块通过公开入口取得结果，自行管理缓存和分页。按实际依赖更新受影响内容，复用仍适用的结果，普通查看不反复扫描全部历史或重新核算。

记账完成与看板就绪分别返回实际状态。未提供的数据不能当作没有业务或金额为零，旧结果不能冒充最新结果。更新失败后按当前有效记录接续，不重新记账；只维护当前待更新范围，确认读取结果已对应当前账务后清除相应状态。

实际提供的汇总、分页明细、凭证和依据对应同一公司、期间、筛选范围及结果标识。汇总覆盖完整业务范围，明细和依据按需读取；切换选择后，迟到响应不能覆盖新内容。已关期采用冻结结果，后续关联冲正按实际入账期间体现。验证金额与状态一致、更新耗时和读取速度，具体性能目标结合数据规模确定。

### 4.5 模块如何组织和运行

优先采用**模块化单体**：业务和基础能力按职责划分为独立模块，共用一个本地后台，通过约定入口协作。采用 Python、SQLite 和 Vue 作为当前技术方向，统一启动和部署，内部可以分别修改和验证。具体实现按 5.2 评估复用。

| 运行方式 | 适用条件与代价 |
| --- | --- |
| 同一后台内划分模块 | 适合当前本地、单负责人场景，启动维护较简单，同公司一次正式提交容易完整保存；各模块仍共用运行资源。 |
| 多个独立程序或服务 | 便于分开运行、重启和隔离资源；需要处理更多通信、失败接续和跨程序一致性，维护成本较高。 |

会计 AI 可以继续在现有聊天环境中工作，看板在浏览器中运行，分别通过业务入口和读取入口连接后台。每家公司继续使用独立业务库，模块划分不要求各建一套数据库。

导出、备份和读取数据准备按新职责设计后台任务，现有机制是否复用按 5.2 评估。验证时检查记账、读取和任务同时运行的表现；同一后台的资源争用仍可能影响速度。出现明确瓶颈或独立运行需求时，再拆出相应执行部分，保持原有交接和完整保存要求。

### 4.6 如何限制修改的影响范围

各模块明确允许的依赖方向。公开接口、标准文档和返回格式由负责模块维护，说明字段含义、金额单位、期间范围及完成状态。其他模块依照约定调用，不把私有函数、表结构或缓存细节当作接口。

内部实现变化不自动等于交接变化。只调整代码组织、保存或读取方法时，保留仍适用的结果；确实改变业务规则、结果或公开格式时，按真实依赖确定更新范围。代码版本、交接规则版本和业务结果版本分别处理，不因整个程序的版本变化就让所有看板读取数据失效。

交接确需变化时，明确新版本及受影响的输入、输出和使用方，一起更新相关入口、调用、文档模板、测试和说明，统一采用新约定，不长期维护两套接口。看板的接入和新增展示仍按 4.4 执行。

通过自动检查发现并阻止跨模块调用私有代码、依赖私有表结构等问题，再用代表性业务检查交接格式、字段含义和实际结果。修改先验证本模块及受影响的交接，涉及共同核算或读取路径时，再覆盖相关业务的一致性和性能；验证范围按实际依赖与风险确定。

## 五、现有实现对照与复用

### 5.1 如何用现有实现检验新设计是否遗漏

整体架构及数据、接口方案清楚后，再对照现有代码、表结构、说明、测试和已经解决的业务问题，检查新设计是否遗漏必要能力。按新模块职责建立对应：新设计需要什么、旧实现怎样处理、是否适合复用、还有哪些缺口。

旧实现即使不能复用，也要弄清它解决过哪些问题，把仍有价值的规则和场景补入目标设计。重点核对：

- 日常收支、往来、工资劳务、社保公积金、税费、资产、基金、借款、期初和报表等业务。
- 跨月收付款、部分结清、退款、后补资料、对象纠错及闭期更正。期初余额不能算成本期收入，发生与付款期间各自保留。
- 无需生成凭证的正式结果、补充依据而不改变核算结果的处理，以及批量办理和工作接续。
- 现有看板主要部分的显示内容、UI 样式、完整汇总、按需明细、分页一致性和读取优化，接入范围按 4.4 执行；文件任务、失败恢复、备份核验与恢复经验。

现有能力、尚存缺口和新增需求分别标明，按业务能力归纳，不逐个函数建档。发现遗漏时先补正新设计，再决定怎样承接，验收以明确业务预期为准。

### 5.2 哪些实现复用、改造或退出

依据新架构的职责、数据关系和公开交接，逐项决定现有实现的去向：

- **直接复用**：符合新设计且边界清楚的计算、解析、文件生成等成熟实现，以及适用的测试和读取优化。
- **改造后使用**：保留有效规则，调整不合适的数据结构、内部耦合、重复处理及仍需 AI 手工协调的程序步骤。
- **退出实现**：不再需要的代码、旧入口和已决定取消的手续；其中仍有价值的问题处理经验按 5.1 补入新设计。

不为复用旧代码而迁就旧边界，也不因重新设计而全部重写。新实现承接并验证后，清理退出使用的部分；资料与数据库另按 5.3 安排。

### 5.3 原有资料和数据库如何安排

现有原件如仍在，按公司和月份整理到指定资料目录；已有重放文档按 4.1、4.2 整理成标准业务文档，归并为最终有效事实，保留来源及当前未解决事项。

现有数据库保持内容不变，另找位置单独存放，与新库隔离，由老板以后自行删除；新系统不加载这些旧库。新数据库以空库作为测试起点，不迁移旧账，也不预先导入标准业务文档。现有备份清理，不作为新系统恢复或接续的来源。

新系统的备份恢复、按标准业务文档重建简化账本和读取数据重新生成，仍作为独立能力建设，分别使用测试数据验证。

## 六、开发文档、并行实施与验收

### 6.1 需求与开发文档需要细化到什么程度

完成第 3、4 章的整体方案，并按第 5 章查漏补正后，先将本次交付范围的需求和各模块开发说明写到可直接交付的程度，再启动编码。有相应基础的开发者应能按文档独立实现、测试并交付，无须从历史对话或其他模块的私有实现中猜测设计。文档至少明确：

- **职责与规则**：业务范围、交付内容、计算与处理规则、缺项及异常处理。
- **接口与协作**：输入输出字段、格式与含义、允许依赖、共同提交范围及协调方。
- **数据与保存**：数据归属、表字段、约束、查询与索引，以及修改、撤去和失败接续规则。
- **开发与交付**：运行环境、代码位置、可复用组件、允许修改的范围及测试运行方式。
- **验收依据**：开发前给出正常及异常样例、测试数据、预期结果和性能要求，模块测试与集成验收使用共同约定。

公共约定集中维护，各模块引用。开发者可以选择不影响约定的局部代码写法，不自行补定业务规则、数据库结构或跨模块接口。发现设计有误、缺项或冲突时，先补正文档和受影响的验收样例，再继续相关实现；无关工作可以继续。

### 6.2 如何安排并行开发和分阶段集成

按模块职责拆分开发任务，明确共享基础、接口和数据的负责方，列出依赖与集成节点。当前交付范围的文档先按 6.1 完备，分批或并行只安排实现顺序；以后新增需求先完成相应设计再开发。

1. **准备共同基础与交接。** 提供一致的公共类型、接口说明、测试样例和必要的开发环境，由明确的负责方维护。
2. **按依赖并行实现。** 具备条件的模块交给不同开发者独立开发。依赖尚未实现时，可使用符合共同约定的模拟接口；真实实现就绪后及时联调，不等所有模块完成才集成。
3. **尽早贯通完整业务。** 用空库和合成数据，将一项简单收支从 AI 整理标准文档、业务办理和正式保存接到现有看板，核对实际结果与读取表现；同时推进其他已具备条件的模块。合作项目投资纳入首批新增。
4. **真实集成与集中验收。** 按 6.3、6.4 核对跨业务关系、结果、模块边界和性能，再清理退出的旧实现。模拟接口测试通过不能代替真实模块集成。

文件、备份恢复和标准文档重建同样纳入开发任务与验收。看板始终遵守 4.4，原件和文档整理按 5.3 安排，不作为空库测试的前置条件。

### 6.3 如何验证业务能力没有丢失

按目标业务范围及 5.1 查漏得到的必要场景，从空库建立合成测试公司与业务数据，明确各场景应有的金额、期间、凭证及办理状态。已有测试筛选复用，验收以明确业务预期为准。

覆盖正常业务、缺项补交、公司隔离、期初接续、开放期修改撤去、跨月及部分清偿、无凭证结果、补充依据而核算不变、闭期冻结与关联冲正。检查正式提交失败不留下半笔结果，重复请求不重复记账，中断后能按实际状态接续；文件失败不损坏正确账务，文件与备份能力随相关业务验证。

同公司、同期间、同含义的结果，在记账、报表和看板中应一致。检查 AI 能否引导老板办事、顾问能否只读审查；看板查阅范围按 4.4 执行，模块边界和性能影响按 6.4 验证。

备份恢复核对保存时的账务状态。日常标准业务文档应归并为最终有效事实，并能据此重建简化新账，真实业务完整、金额和期间正确，不要求复制原凭证编号、旧错误及纠错过程。恢复与重建分别设定预期。

### 6.4 如何验证模块化与按文档开发真正有效

由不同开发者或独立开发任务，依据共同文档分别实现有协作关系的模块，再验证真实集成。开发者不应靠猜测其他模块的内部实现才能完成工作。频繁需要口头补充规则或临时修改接口才能接合，说明设计和文档尚未达到交付要求。区分设计问题与实现缺陷，分别补正文档或修复实现，再验证相关部分。

选择不改变业务含义和公开交接的内部修改，例如调整记账算法、结构或保存方式。通过依赖检查确认没有越界调用，再检查公开查询和看板结果是否正确，是否引起无关范围的全量更新、额外读取或性能退化。

反向优化看板读取时，检查业务计算、正式写入和保存结果未被改变。交接确需变化时，列明受影响方并同步更新，确认无关模块仍按原约定工作。现有看板主要部分的显示、样式及用法按 4.4 保持，展开缺口和新增展示也按该节处理。

在明确的数据规模和相同条件下比较修改前后的读取、更新耗时，并检查记账、看板与文件任务同时运行的表现。新增页面或板块也应检查对原有读取的影响。同一后台仍可能争用资源，验证范围按实际依赖与风险确定。
