# 未关账联动更正：协议与逐规则审查

适用版本：业务库 `0001_business_baseline_v4` 及前向迁移至 `0005_payroll_provenance`；组件协议仍为
`business-components-v3`，运行契约为 `accounting_execution_assistant_v42`。

## 工作流程

1. 读取原业务及其 `facts_hash`。来源资料发生变化时保留其新版本事实和前版引用，不先删除工资或冲正。
2. 调用 `finance_preview_correction`。提交 `org_id`、`source_changes`、
   `event_replacements`；至少一个非空。`reason` 是可选管理说明。
3. 预览返回原凭证、前后金额及完整依赖。核对资金与扣缴差额后，用相同请求、
   `calculation_hash` 和新 `idempotency_key` 调用 `finance_confirm_correction`。
4. 用 `finance_get_correction` 读取更正批次、来源版本和审计。
   `finance_get_event.amendments[].correction_id` 关联到同一批次。

`source_changes` 仅接受社保实际数登记和首次工资扣除处理的既有类型化事实。
`event_replacements` 的每项为 `event_id`、`expected_facts_hash`、既有类型化 `replacement`。
后续业务默认复用原记录，只有明确改变的事实才提交替换；不提供自由分录。

预览不产生正式记录；确认重新锁定公司、来源和依赖并重新计算。
同一幂等键重试返回原结果，输入或确认哈希不一致则拒绝。
单笔修改和联动更正共用事件准备、撤去派生记录、重算和审计完成过程及唯一正式提交器。

## 逐规则审查

| 原限制或风险 | 决定及实际依据 | 请求／服务／数据库与验证 |
| --- | --- | --- |
| 社保实际数被工资引用后一律先冲正 | 删除；来源版本与开放期间工资整体更正 | 登记返回更正入口；联动更新使用关系；PostgreSQL 校验新来源不得留下旧工资消费者 |
| 首次工资扣除处理后一律先冲正 | 删除；标准扣除属于计税事实，需要重算实际消费者 | 与社保共用来源影响检查；计税计算仍复用原计算器 |
| 首扣原始依据和派生使用关系共用绝对不可变触发器 | 原始依据及证据仍不可变；使用关系允许由受控更正撤去后重建 | `0003_payroll_correction_uses` 仅放行使用表的 DELETE，复用当前事务、归因、审计快照及精确主键授权；UPDATE 和无授权 DELETE 仍拒绝 |
| 仅处理社保仍强求计税工资与个税扣除零额 | 取消；必填仅适用于实际进入工资个税计算的人员 | `uses_wage_tax` 同时约束必填检查；省略无关分项，不在请求中补造零额；居民身份等必要计税事实保留 |
| 只检查已有来源使用表 | 补充人员、所属期、险种／税年有效范围 | 首次补登实际数也识别政策计算工资；测试覆盖无旧来源记录 |
| 合并计税奖金重复要求直接登记首次扣除依据 | 复用明确的原工资来源 | 计算与数据库均验证工资的有效依据；同凭证工资、奖金及后月累计计税联动回归 |
| 单笔后续依赖一律阻止修改 | 已支持消费者进入显式联动范围 | 依声明的所有权和实际引用展开；循环、未知所有权仍拒绝 |
| 原因在 API 选填、数据库必填 | 删除数据库非空要求 | 修改、删除、银行导入撤回均测试省略原因 |
| 申报日期在管理协议允许、数据库白名单遗漏 | 同步白名单与日期格式校验 | 管理日期允许省略、填写与后补，不决定入账日期 |
| 同公司任意后月工资都阻止修改 | 限定真实累计计税消费者 | 识别人员、税年与计税方式；单笔和联动及数据库同步检查 |
| 修改失败自动改冲正 | 服务与数据库拒绝 | 全部影响期间开放时返回 `OPEN_PERIOD_REQUIRES_AMENDMENT`；技术失败不构成例外 |
| 闭期源或消费者被原位改写 | 保留禁止 | 列明关闭期间与事件；既有闭期更正路径不变，本轮不提供闭期自动联动 |
| 后续付款随新工资自动变化 | 禁止 | 默认复用每笔原资金日期、金额、账户、扣缴及明确税额结果；流水唯一匹配 |
| 更正后债务小于已付款或扣缴不能核对 | 保留必要差额事实要求 | 返回 `CORRECTION_PAYMENT_DISPOSITION_REQUIRED` 和 `fact_issues`；不猜退款、补款或员工应收 |
| 修改、删除丢失原业务键 | 保留稳定身份 | 原事件、凭证号、组件键及同义往来标识复用，原入账幂等键保持稳定 |
| 工资重算删除同凭证的无关劳务批次 | 保留未变化的独立计算 | 混合工资、劳务更正后，劳务批次、行和金额不变 |
| 试算临时对象在长会话留下余额缓存 | 试算回滚后刷新对象 | 失败后正式行和再次查询的余额都恢复；不只检查凭证数量 |
| 所有 SQL 失败都叫数据库冲突 | 区分技术故障、并发冲突和业务门禁 | 仅输出 SQLSTATE、约束／保护标识等安全诊断，不暴露参数，不根据错误码猜缺项 |
| 新代码直接读取尚未升级的真实业务库 | 公司读写前验证当前进程所需的 Alembic head；启动只读检查目录库与各业务库 | `DATABASE_SCHEMA_UPGRADE_REQUIRED` 明确报告当前／所需版本；空库、退役链、未知或多 head 不冒充可升级库；不省略更正历史来兼容旧结构 |
| 管理字段混入确认哈希 | 排除 | 核算投影绑定来源版本、原事实、实际计算规则与结果；管理说明、申报日期不参与 |
| 临时更正授权可以修改其他记录 | 禁止 | 当前事务、真实执行身份、明确成员及声明所有权共同校验；整批完成后授权失效 |
| 来源版本变化被误报为需要补填旧来源 | 确认时统一要求重新预览 | 来源被其他更正替代、事实哈希改变或新增付款依赖时返回 `CORRECTION_PLAN_STALE`；整组回滚 |
| 未完成更正或预览批次被直接提交 | 禁止 | PostgreSQL 延迟约束要求全部成员审计完成且来自确认入口；SQL 绕过服务的来源写入也不得留下旧工资消费者 |
| 无后续依赖误记仍需冲正 | 改用原删除入口 | 删除恢复余额与匹配并保存历史，不级联删除真实付款 |

必要保护不放宽：公司隔离、证据、整数分金额、确定性税额、借贷平衡、资金守恒、
来源有效期间、余额上限、并发及闭期保护。无法重算的机制明确拒绝，不以删除校验代替实现。

## 回放与历史

现有 `preview_confirm` 回放操作可直接使用
`finance_preview_correction`／`finance_confirm_correction`：`preview_request` 保存类型化更正事实，
`confirm_request` 只补该操作的稳定幂等键，执行器取得当前预览哈希后确认。
来源、人员和事件通过回放引用解析为目标库编号，不能沿用旧库 UUID。
确认已提交但回放检查点尚未写入时，先从更正批次取得原确认哈希并幂等恢复，
不重新生成另一份预览覆盖原确认。此流程已在隔离 PostgreSQL 数据库验证。

便携备份保存新表、来源版本和原有审计；空库业务重录根据有效业务事实建立终态，
不强求重现历史凭证数量。只读导出必须同时保留原始更正审计快照以供核查，不能将历史审计当成待重演的付款。
导出包的 `correction-history.json` 保存更正批次及逐事件审计，标明仅用于审计；
业务操作仍只来自 `operations.jsonl`。`0002_atomic_corrections` 仅提供前向升级，
不通过降级删除已形成的更正历史。

本次开发不修改真实库，不撤销已经发生的三笔凭证，不续录公司业务，不改变现有回放状态或已完成前缀。
交付分别说明代码验证、资料整理与隔离回放结果；“隔离验证通过”不表示“真实业务已重录”。

## 读取故障补修（2026-09-09）

只读核对确认：两家公司业务库仍为 `0001_business_baseline_v4`，缺少
`business_corrections` 和 `business_event_amendments.correction_id`。新代码读取工资时也读取
更正审计，即使历史为空仍会选择缺失列，PostgreSQL 返回 `42703`。原外层将其压成
`DATABASE_OPERATION_FAILED`；不是工资业务事实缺失，也不是原凭证损坏。

修复使用共同的部署版本检查，不增加旧表结构查询分支。MCP 业务读写与看板公司路由在使用
新模型前核对版本；缓存连接也重新检查。无法使用的数据库不会因检查而被初始化、stamp、迁移
或重建。底层缺表／缺列另返回 `DATABASE_SCHEMA_MISMATCH` 和不含 SQL 参数的诊断编号。
运行契约明确不根据该类失败追问核算事实或改走冲正。

`finance-company check-schema` 和 Windows 启动脚本提供不触发登录窗口的只读检查。
部署步骤见[本机数据库版本检查](windows-local-operations.md#代码更新后的数据库版本检查)。
PostgreSQL 17 回归在有原工资的 v4 库复现原错误，经现有前向迁移后通过公开 MCP 读取
原事件、事实哈希、原凭证和审计，核对迁移前后的业务行完全一致；同时覆盖迁移前读写阻断
和连接缓存下的版本变化。

验证结果：版本检查、Windows 启动、MCP、身份校验、多公司路由、工资联动更正及基线迁移
共 79 项回归通过，Ruff 与 `git diff --check` 通过。补充看板错误传递和执行归因无写入核对后，
再执行该 PostgreSQL 17 迁移用例通过。此次只读诊断真实库，未部署真实库迁移、未修改工资或凭证，
