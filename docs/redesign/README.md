# 新体系需求与开发设计

本设计面向一位本地老板管理多家公司。老板借助会计 AI 准备资料、理解事项和办理日常会计工作；内核负责明确规则下的计算、可靠保存及内部协调；看板供老板核对，也供专业顾问只读审查。

设计交付的标准是：具备相关 Python、SQLite 或 Vue 基础、没有参加前期讨论的开发者，能够按模块说明独立实现、运行测试并提交成果；不同模块能按事先约定完成真实集成。业务规则、接口含义、数据库结构及验收预期不留给实现者临场决定。

本目录定义完整需求与开发设计，包含可检查的字段合同、数据库结构和预先定义的验收样例。实现放在独立的 `src/ai_accounting_modular/`，按 [开发与验收](07-delivery-acceptance.md) 接通真实模块并验证；设计文件存在不代表相应功能已经实现。开发使用合成公司和隔离资料，不自行改变现有公司库或服务。

讨论设计时先读 [产品需求](01-product-requirements.md)、[整体架构](02-architecture.md) 和 [AI 工作要求](08-ai-work-and-materials.md)。交付开发时，以本目录全部合同、规则、结构及任务包为一套依据；机器合同不需要老板逐字段阅读。

## 设计范围

先独立设计目标架构，再核对旧实现是否存在可复用能力或遗漏的业务情形。新体系采用模块化单体、每家公司独立业务库，保持现有看板主要显示内容、UI 样式、既有用法及读取优化。

第一轮交付覆盖原有有效业务能力。投资理财先承接现有货币基金及近期需要的合作项目投资；合作只是其中一种记账方式，与其他投资类型共用办理、保存和查询，不另建项目经营子系统或独立详情页。预设类别不等于已实现全部金融产品，不支持的类型明确说明范围。

## 实现与模块边界

实现位于 `src/ai_accounting_modular/`，各模块仅通过公开入口协作。运行 Schema 和模板随包交付，不依赖工作区文档目录。

| 模块 | 提供的能力 | 详细规则 |
| --- | --- | --- |
| contracts / storage | 严格字段、整数金额与日期；单公司事务、回滚试算、结构核验及一致数据库副本。 | [公开合同](03-contracts.md)、[数据结构](04-data-model.md) |
| identity / 六类业务 / ledger | 稳定对象、类型明确的业务核算、原子采用、统一凭证与余额、开放期替换及闭期更正。 | [业务规则](05-business-rules.md)、[统一财务取数](05b-financial-reporting.md) |
| application / agent | 完整业务协调、事实查找、只读月结检查、现实说明、当前未解事项和AI调用。生成文档或页面失败后由程序接续，不重复记账。 | [公开命令](03-contracts.md)、[AI工作](08-ai-work-and-materials.md) |
| records | 原件身份、归档、只读检查和当前标准业务文档；标准文档只表达最终事实。XLS可读缓存值，不能提取公式表达式时明确说明。 | [数据结构](04-data-model.md)、[资料处理](08-ai-work-and-materials.md) |
| files / 离线交付 | 已验证ZIP备份、准确恢复、最终事实重建、任务接续和受控下载；新目标不覆盖已有文件。 | [恢复与重建](02-architecture.md#备份恢复和简化重建)、[文件合同](03-contracts.md) |
| reading / dashboard | 同一快照的五页、完整分页、精确业务与凭证、只读月度核对及顾问来源；各owner声明实际读取依赖。 | [看板合同](06-dashboard-adapter.md) |
| 报表 / host | 固定三表XLSX及验证下载；独立本机服务、CLI、MCP、原生身份窗口和后台接续。 | [财务取数](05b-financial-reporting.md)、[看板报表](06-dashboard-adapter.md#8-报表生成状态和下载)、下节运行入口 |

备份恢复保留原账务和必要冻结依据，简化重建重新核算最终事实；两者交付独立公司目标，随后明确登记。读取投影是可重建的加速数据，不是正式账本。技术边界、失败含义和支持范围以链接中的唯一合同为准。

## 新体系运行入口

安装、前端构建、独立服务、完整公司接入 JSON、CLI `call` 和实际 MCP 调用统一见[安装、运行与会计 AI 接入](09-runtime-and-ai.md)。操作说明和所选业务规则随包按需读取，运行时不依赖工作区设计文档。

这些命令不会自动搬移真实资料、接替现有入口或导入旧体系数据库。运行入口、功能正确性和性能分别验收；交付结论及可复核证据统一见[开发与验收](07-delivery-acceptance.md)。

## 开发前如何核对

在仓库根目录运行：

```powershell
& '.tmp-kernel-venv/Scripts/python.exe' docs/redesign/verify_design.py
```

[检查脚本](verify_design.py) 只读取设计文件，核对 Schema 引用、合成输入输出、来源摘要、冻结看板合同、文档链接，并在内存 SQLite 验证结构和保护约束。它不会打开任何现有公司库。

设计检查使用仓库虚拟环境与项目锁定的依赖，不使用系统默认 Python；实际环境版本随验收记录交付。

这些检查只证明合同一致，不能代替真实业务、模块集成、浏览器和性能验收；程序按规定场景逐项核对，性能数字是必须实测的交付要求。

## 设计原则与资料边界

- 采用协作信任。会计 AI 承担职责内的专业判断，也主动引导不熟悉财务的老板准备资料和继续工作。
- 老板提供现实信息、作经营决定并负责全部外部付款、申报等实际办理。专业顾问只读审查，不修改账务或批准处理。
- 公共业务入口只接受类型明确的事实，不向 AI 开放任意借贷分录。
- 金额使用整数分，核算金额不经过二进制浮点数；月份与实际日期分开，不补造日期或未知金额。
- 开放月份直接更正或按条件撤去误记，保留原凭证编号，排除旧错误正文和纠错过程档案。闭期保留必要冻结结果，并通过关联冲正更正。
- 原件、标准业务文档和数据库保存最终正确账务所需内容。标准业务文档在日常工作中归并为最终有效事实，真实收付、退款和损失不因归并消失。
- 文档重建建立简化新账；备份恢复保存时状态；读取重建只重建派生数据，三种行为分别定义和验收。
- 现有数据库保持内容不变，另行隔离存放，由老板决定删除；原件如存在则整理，原重放文档整理成标准业务文档，旧备份按指定安排清理。新体系使用独立空库测试及自身备份恢复格式。
- 上述真实资料搬移、换库、重放、旧备份清理和服务切换在明确安排后执行；开发中的合成建库与验证不操作这些真实资料。负责人按通过复核的节点统一安排 Git 提交。

方向依据为 [架构重新设计纲要](../architecture-redesign-outline.md)。旧架构和旧约定仅作为实现参考，不能覆盖本设计明确的业务和资料边界。
