# 业务事实、核算规则与正式结果

本文规定首轮业务计算和跨业务约束。字段名称、类型、必填和严格变体的唯一机器合同是 [business-facts.schema.json](contracts/business-facts.schema.json)；本文补充 Schema 不能单独判断的业务条件、公式、科目、依赖和边界。金额在线路和文档中是规范整数分字符串，在 Python/SQLite 中是严格整数；比率用 `Rate`，例如 1% 写作 `"0.01"`，不是 `"1"`。

业务模块接收事实并产生内部 `PostingPlan`。AI 不能提交分录、科目、借贷方向、任意余额调整或自己计算的税额来填程序缺口。输入一个业务类型已经说明 AI 对业务性质的判断，不再要求老板逐次提交 `confirmed=true` 或批准。

货币基金和合作项目投资均由[投资与理财](#投资与理财)承接；合作项目本次只增加所需记账规则。

## 公共事实与计算条件

每个正式事实包含 `business_id、kind、period、evidence_ids、data`；确知实际日时使用 `effective_on`。公司由打开的公司工作单元和提交合同绑定，不能从文件目录或对象名称猜测。`evidence_ids` 引用 `Source.source_id`，来源位置使用公共 `SourceLocator`。已有原件、业务表或老板有效说明可以复用，不另索取同义确认，也不一律要求发票或另一份凭据；只核查会改变当前业务处理的真实缺项或冲突。

- `period` 是核算所属月。实际资金、放款、真实个人付款、资产处置及银行利息/奖励必须有实际日且属于该月；有据的资产接受、收入履约和投资确认可以只知道月份。不得用个人采购日代替公司取得日，也不得把月末补成未知实际日。
- `BusinessRef={business_id,slot}` 指向领域公开的义务或成本，跟随开放期更正；`slot` 必须能唯一解析。内部完整结果使用 `result_slot`，不能把工资的多个义务拆成多份不平衡结果。
- 必要事实缺失返回具体 `fact_issues`，含字段路径、原因、允许精度和可复用来源。矛盾、超额或不支持的会计模型不能靠默认值通过。普通管理说明缺少不阻止无关核算。
- 输入的同一真实关系、同一成本或实际资金只使用一次。不同真实业务即使同金额同日仍可分别存在；不得按金额相等自动合并。
- 一个原子业务单元的所有事实、正式结果、关系和读取目标共同提交。事实引用可指向同单新增事实；程序拓扑计算。既有有效结果直到新单完整成功才被替换。

关系声明区分事实、结果、集合观察以及资源使用/余额读取，具体合同见03。结果依赖和余额所需使用者参加计算拓扑；税点可以读同单真实收款事实，申报分摊可以识别同单工资事实，不要求先把它们发布一次。程序先核对事实及原件，再算收入/税，随后完整核对实款清偿；任一最终交叉核验不成立，整单回滚。

`PartialFact` 仅用于当前未解事项：已给字段仍验证类型、枚举、金额及额外字段，缺少字段可以保留；不接受 `null` 代替未知。它不能交给正式 `apply`。

## 经营与往来

常规服务默认在业务所属月确认收入和应收，计划次月收款；实际到账按真实日期核销原应收，不重复确认收入。该安排不制造已收款、具体到账日或合同付款日，已明确的其他结算安排优先。收入月、实际收款月和增值税税期分别承接，增值税仍按下文税点规则确定。

| kind | 必要事实和特殊条件 | 正式计算及公开资源 |
| --- | --- | --- |
| `operations.service_sale` | 客户、含税毛额、VAT 适用及有来源税点。实际履约日可未知。税点早于收入确认时，必须承接已有预收税务来源。 | 按适用含税拆分得收入和 VAT；形成客户 `primary` 应收。已到税点部分列应交，未到部分列待转；不因日后收款再认收入。 |
| `operations.expense` | 债权人及供应商/员工/个人角色、金额、费用性质。公司承担的员工报销可直接以员工为债权人，不为取得票据另造供应商债务。银行费、税滞纳金、社保滞纳金分别分类。 | 同时确认费用和 `primary` 应付。实际收付款另记。report_details可省；省略时对应财报细目未知，但费用/付款照办。提供时是完整分类，逐项合计必须等于费用，未分部分用明确other承接，不能自动补；代码不得重复且属于对应费用类别。 |

| `operations.advance_refund` | 原预收和本次真实退款责任毛额。 | 将未履约预收转为 `refund` 应付；按已采用税务来源处理对应税额；实际退款另记。它不是删除原销售的技术动作。 |

| `operations.expense_recovery` | 已确认普通或平台费用、同一交易方、本次可追收金额及来源。 | 冲原费用类别，形成 `primary` 应收；累计不超过当前原成本。闭期后的真实退费是本期新事实，实际到账另记。 |
| `operations.pass_through` | 公司确实承担代收代付责任时，明确付款方、公司应转付的具名权利人和金额。 | 同时形成 `collection` 应收、`remittance` 应付，不认收入费用。不能只凭“回扣、报销、代付”等字样选择此模型；公司应付员工已明确后，不追问员工收款后的个人去向。 |
| `operations.pass_through_return` | 原代收业务、本次实际成立的退款责任。 | 将尚未转付部分转为对原付款人的 `refund` 应付。金额不超过实际已收、未转付和未退回部分。 |
| `operations.deposit` | 可退押金对象及金额；个人垫付另需垫付人。 | 保留对押金收取方的 `deposit` 应收，直付形成 `primary` 应付，垫付形成 `reimbursement` 应付；报销不消灭押金债权。 |
| `operations.reimbursement` | 真实个人付款：垫付人、employee/owner 角色、实际日、原债分配。公司接受已付款债务：明确接受月份和来源分配，未知个人付款日可以省略。两者是同一经济转债的不同依据，不重复叠加。 | 消耗原公司债务，转为对垫付人的 `reimbursement` 应付；不再认费用，不生成公司资金。原债实际收款人须对应原债权人；合计不超未清原债。 |
| `operations.overpayment` | 原应付的实际多付，或原应收的实际多收；交易方沿用原责任，另填时必须一致。 | 多付形成 `recovery` 应收，多收形成同槽退款应付。分次处理只占用各自截止前尚未归属的真实超额区间，累计不得超过实际超额；已经实际退款不释放该区间。不能改小真实收付款来凑新应付或应收。 |

### 收入与预收的累计拆分

含税毛额为 G、适用计税基础率为 b 时，净额按 `round_half_up(G/(1+b))` 到分，VAT 为毛额减净额，或按对应减征政策规定的应纳率计算；具体基础率与应纳率由有效政策明确，不能混用。

同一预收分次履约按原毛额范围接续，采用累计拆分并保全真实红字税额；全部消耗时，净额及税额必须耗尽原总额。混合履约保留已采用部分的真实税期，只为未计税部分确定新税点，不重复计税。完整税点先核对身份、范围和继承关系，再计量本次负责的部分。税点前已经全部真实退回、没有剩余税源时，不再索取无用途的税率；尚存量或真实先后会改变结果时，仍需相应依据。

供应商预付只能抵同一交易方的相应债务；资产用途预付只能对应已明确同类的直接取得、资本化项目或劳务成本义务，不能抵普通费用，也不在抵销时再确认一次成本。项目成本先进入项目可消费成本，完工转资产或退出转费用时消费同一份成本，不能两处同时留着。

有权保留、无返还义务且没有销售对价的账户验证入款，按[小企业会计准则](https://kjs.mof.gov.cn/zhengcefabu/201111/P020111118325852319878.pdf)第68条的非日常净流入原则归入营业外收入。这是对已明确事实的规则应用，不是准则认定所有验证款均可保留。

合作经营的服务和费用如何提供公司份额及分配基数，统一见[合作项目投资](#合作项目投资)。

## 用工与薪酬

### 输入与来源

下表的 wage/bonus/labor 是 `people.remuneration.data.type`，不是另一个序列化 kind。

| kind / 变体 | 必需事实 | 条件与边界 |
| --- | --- | --- |
| `people.relationship` | 人员、按已确认先后排列的当前正确关系段；每段含状态及生效月份或实际日。 | 状态为在职 regular、停薪 unpaid_leave、离职 departed、劳务 labor、劳务结束 labor_ended。不补造实际日，不强迫补齐首段以前的履历；未知关系不从工资或缴费推断。本事实不产生记账结果。 |
| `people.employment` | 员工、缴费适用起月、是否参保/公积金、差额承担方式；终月可省。 | 这是缴费参数，不代替在职、离职等关系。参与并采用政策计算时，相应基数必需。未参与或未启用项目不需要假基数；不能把工资直接当缴费基数。 |
| `people.contribution_policy` | 官方来源、生效区间、地区和缴费项目。每项含代码、类别、个人/公司比率、基数上下限、舍入和是否启用。 | 同类别及代码唯一、下限不大于上限、政策覆盖核算月。采用实际缴费额的项目不强求估算基数。 |
| `people.contribution_actual` | 同员工同月逐项 declared/not_declared 及个人/公司金额。 | not_declared 两边必须为零；参与类别须有完整实缴项目或明确未申报；采用政策时还须对应其项目，不能漏项后把缺项当零。 |
| `people.remuneration.wage` | 一人一月毛工资、费用归属、用工档案；当时已有明确扣税组成时提供tax_basis，参与缴费时明确采用方式及所需来源。 | 同员工同工资月只有一个工资业务。计提不等待后来扣税或付款；双方均不参与时四类缴费为零，不造禁用政策或虚假实缴；有完整实缴不强求政策，只有采用政策计算的部分必须引用有效政策。 |
| `people.remuneration.bonus` | 人员、奖金毛额、费用归属；当时已有明确扣税组成时提供有据最终税额。 | 计提不等待后来扣税或付款；不在内核恢复未选的累计个税或奖金优惠试算。 |
| `people.remuneration.labor` | 人员、已发生劳务毛额、费用或项目去向、未扣未报或扣税已明确的状态。 | 未扣未报可先记全部毛额应付；明确扣税后将同一债务拆分，不再确认一笔成本。首轮劳务项目去向承接已满足外购无形资产资本化条件的成本；其他劳务资本化模型不默许套用。 |
| `people.remuneration_tax` | 原报酬、税期、采用依据、该范围完整的有据扣税组成。 | 一个报酬一个税期一个当前目标；内核比较初始组成，只转移尚未分出的员工应付，不增加成本或公司现金流。 |

一人一份关系时间线，直接改为当前正确内容，`period`只表示这份资料的归档月；实际生效取各段的 effective_from。数组次序表达已确认先后，须与月份及已知实际日不矛盾。同月劳务转员工可以分别出现，不把整月同时算成两份工资。有来源确认本段确实开始雇佣或劳务关系时，可填 relationship_start=true；省略不推断，复工不当作入职，入职即停薪也能明确记录。读取返回月末状态、月内确定及可能状态、员工与劳务成员的 true/false/未知；首段以前及月精度不能确定的月内持续情况保留未知，不要求补日才能记账。关系资料更正不改冻结金额，也不要求冲正；明确的工资、缴费和劳务金额仍按各自事实核算。没有关系资料时显示未知，不自动当作在职或离职。

工资按劳动所属月确认费用和应付，依据[小企业会计准则](https://kjs.mof.gov.cn/zhengcefabu/201111/P020111118325852319878.pdf)第50条。内核的通用办理安排为当月计提、次月计划发放，老板明确的其他安排优先；这不生成实际付款、不限定真实付款月，也不推导税期或税额。[工资支付规定](https://www.mohrss.gov.cn/SYrlzyhshbzb/ztzl/rslyyhyshj/zcwd/202411/t20241111_529582.html)要求按约定日期支付，不是全国统一必须次月发薪。

工资、奖金没有 `tax_basis` 时仍可按已经明确的劳动成本和缴费承担计提，不要求老板另行证明“未扣未报”。结果的零扣税额及 `tax_state=not_withheld_not_filed` 只表示本账尚未记录扣缴和申报，不能证明外部没有扣税、尚未申报、零税或免税，也不保证该净额已适合直接支付。劳务输入仍按合同区分未扣未报与扣税已明确；零税也须有据，不能推断免税。有扣税事实却缺其必要金额依据时继续查证。计划次月发放不产生任何扣税或付款事实。

税额依据包含独立 `tax_period`、整数分税额、final_statement/actual_withholding、原件或有效说明位置。零税额也是明确事实，不能按低工资自行推断。actual_withholding 的实际扣税日未知可省；final_statement 不能附一个虚构实际扣税日。核算月、税期、申报日和付款月各有含义。

工资的 `tax_basis` 是初次已经采用的薪酬组成；工资原来确实记错才更正工资。后来才发生的扣税使用独立 `people.remuneration_tax`，不通过补税额去重做已关账工资。按[个税扣缴办法](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5194838/content.html)第6条区分支付时的预扣与劳动所属月；当前内核只采用有来源的明确税额，不代替尚未实现的累计计税。

`people.remuneration_tax` 引用原报酬、明确税期及采用依据；period是此次扣税组成成立的核算月，确知实际日才提供effective_on。其components始终表示**该报酬、该税期完整且不重叠的有据扣税组成**：整张最终表是一项，只有分项来源时列出完整分项。每项引用直接金额及来源，或实际申报行的本报酬分配；内核读取分配并求和，AI不手算税额或新增差额。已有初始100元、后来分项20元时复用100元的原依据，合计由程序算为120元，不能用部分20元覆盖整期。重复明确来源或分配拒绝；原件中合计与明细是否重叠仍由会计AI理解，不另加证明流程。

同一报酬、同一税期只有一个当前目标。内核把完整目标与原报酬同税期初始已采用税额比较，只把尚未分出的部分从员工应付转成个税应付；初始100元、后来总额100元不再扣款，总额120元只转20元。即使原100元已缴清也不能再扣100元，因此比较的是已采用组成，不能用当前未付税款余额代替。另一个税期有独立目标，支持分月发放。无差额不造凭证、现金或第二份税义务，后来的同额申报也不必强建扣税事实。

后续扣税不重算工资成本、缴费承担或真实付款。目标低于工资初始已采用额时，先查清是原组成错误还是确有退抵、补发或追偿；本事实不自动假造退款权利。独立目标本身确需更正时沿用其身份及开闭期规则，转回只在真实可用余额内办理，已付款不删除。申报、扣取和向税局付款各自保存，不能把申报自动当成又扣一次税。

一条实际申报行覆盖多笔报酬时，`taxes.actual_declaration.payroll.rows[].allocations` 明确各笔采用金额，合计等于该行税额；同一报酬只采用其中自己的份额。`pooled_source` 指向该申报和行，人员、税期和金额必须对应。不存在旧任意 64 条读取上限的业务规则。

### 缴费与工资公式

1. 对启用且参与的每个缴费项目，将有据基数限制在规定上下限内；个人额和公司额分别为基数乘各自比率，按项目的 half_up/down/up 到整数分。逐项舍入后，分别加总社保/公积金。
2. 有完整实际申报额的项目使用实际额；没有实际额时，只在 `policy_until_actual` 范围内按有效政策估算。参与缴费时必须明确采用方式，`actual_required` 缺实际额返回缺项；双方明确不参与可省缴费方式及两个来源引用。
3. 个人缴费超过扣除有据个税后的可承担工资时，按明确的 reject 或 employer_borne 处理；个税本身超过毛额仍为矛盾。允许单位承担时，个人先承担社保、再承担公积金，同类别按项目代码升序分配；剩余转公司成本。政策及实际项目都按此顺序规范，输入排列不改变结果，机构应收总额保持不变。
4. 工资净应付 = 毛工资 − 个人承担社保 − 个人承担公积金 − 已采用个税；工资成本 = 毛工资 + 公司承担社保 + 公司承担公积金。后来正常扣税只拆分已经成立的应付，不能因此再运行不足承担规则改变成本。
5. 奖金/劳务净应付 = 毛额 − 已采用个税。净应付不是已经实发；实际支付前按当前已知扣税和缴费依据核对，真实实发只来自实际清偿。

工资一个 `main` 结果包含 `net_pay、employee_social、employee_housing、employer_social、employer_housing` 净薪和缴费义务，已明确的零额保留组成；有扣税依据时另含 `tax`，未扣未报不补造零税义务。奖金和劳务同样包含净额及已明确的税。税局/缴费机构未知时不造对象，人员、贸易债权人、垫付人必须明确。

工资、奖金和劳务共用 `disbursement_basis`。`declared_tax` 沿用实际申报行及明确税期，分配申报税额与原税额之差只形成代发暂留，不是扣税、缴税或付款。`current_payable` 则引用明确的本次付款安排来源，表示按内核当前可付余额发放、没有额外未明暂扣；不要求先提供税期，也不建立零税、免税、已申报或已付款结论。只有毛额、公司一般说明或一份已关联但未表达付款安排的原件，不能代替这项事实。已有来源明确本次安排时由AI直接采用，不重复向老板提问。

新发生的扣税直接采用独立税目标；people统一扣除尚未被该税期正式目标承接的剩余暂留，不能在原净薪、欠款和代发表里重复减税。`current_payable` 不锁定历史毛额或覆盖实际扣款，后续扣税、缴费、部分付款仍按当前正式结果计算。金额超出可用应付或真实资料冲突时整单失败，不造员工欠款。读取原报酬依据保持精确原值，当月发生、截止月完整组成、真实实发和未付余额分别表达。

实际办理或准备代发表时，AI用 `accounting_remuneration` 指定报酬身份和核对月，取得people统一提供的完整组成、正式剩余、当前可付额和 `payment_composition_state`。该状态从精确采用的付款依据、税依据及当前有效税目标派生，和 `tax_state` 分开；未扣未报不自动表示本次发放不明。当前可付额为正式剩余扣除仍有效暂留后不低于零的金额；已经付过的部分不再支付。原报酬 `accounting_get` 仍保留其精确含义，AI不能把原净额当作当前余额，也不自行减税、减暂留或从已缴税余额反算扣税。开放期可通过原业务补充付款依据并保号；原月已关账时沿已有无金额影响的更正采用新依据，不改原凭证或历史读取，不要求老板补实际付款日或税期。

### 合作项目投资

合作项目是投资模块内的一种投资方式。AI 根据真实合同选择核算配置、整理公司应入账的事实，程序计算并保存。只记录影响公司账务的出资、经营份额、实际收付和退出；不另建项目运营管理、专用接口或详情页。

本次配置 `direct_joint_operation_cash_labor_v1` 的含义一次规定如下：公司出初始现金，经营者出经营劳动；无独立财务主体，双方共同决定重大事项，日常经营由经营者办理。双方直接享有项目资产权利并承担相关债务，经营净收入和费用按同一固定比例分担。经营者劳动不估价入账；双方须补足自己应担的实际经营支出，先抵自己已代收的经营款。公司剩余资本优先返还，但不保本、不付固定息；内部比例不免除依法可能承担的对外责任。经营者属于有据的独立经营关系，公司的 VAT 在资金池外另行承接。

这是 AI 依据资料作出的专业分类。合同只填 `profile、project_id、operator_id、company_initial_commitment_fen、company_revenue_expense_share、contract_source` 六项，来源沿公共 `evidence_ids` 引用，不反复填写固定旗标、逐条证明或强制分类说明。未知的权利、比例或税务关系仍须核查，不能因字段减少而默认成立。只有净利润分红权、雇佣关系等不同安排不套本配置；已知资料保留为当前未解事项。首轮经营范围为服务及普通费用，复杂资产共同持有、非现金出资、真实比例变更和多层优先分配不临场发挥。

[小企业会计准则](https://kjs.mof.gov.cn/zhengcefabu/201111/P020111118325852319878.pdf)第三条及[企业会计准则第40号](https://kjs.mof.gov.cn/zhengcefabu/201402/t20140220_1045209.htm)支持按真实资产、负债、收入和费用权利分类；[民法典合伙合同规定](https://www.court.gov.cn/zixun/xiangqing/233181.html)提供风险分担和清偿顺序依据。下列公式是上述特定合同的设计应用，不是所有合作项目的通用政策。“投资方式”是模块分类，不能据此把公司经营份额改记成金融投资收益。

这些是通用 `apply` 下的受控事实变体，不是必须逐项办理的流程。只在真实发生时记录，所属月不得早于引用合同的生效首月；晚录合同不改变其真实生效月。实际公司资金自带一次 `funds`，同一转账不得再录普通收付款。用途是AI依据来源作出的专业判断，不是程序发放资金的许可；不同经济性质的真实借款等不能塞入本配置。

公司按份经营复用`operations.service_sale / expense`，给出`cooperation_id、project_total_fen`。销售基数是不含本方销项税的项目经营收入，费用基数为合同分担费用；公司净收入/费用等于基数×比例half_up到分。销售的净额与VAT分别形成公开义务，经营者只代收净额；税款实际收到时由同一笔真实资金另行分配，不虚构到账。经营模块公开CooperationTradeQuantity，投资模块使用其中项目量、公司净额及资源引用，不读取经营私表。

分次代收/代付没有其他混合清偿时，按同一来源累计计算：本次公司金额=H(区间起点＋本次后累计)−H(区间起点＋本次前累计)，H为合同份额half_up。已有公司直接收付、抵销或转债等使分配不唯一时，需明确实际`company_amount_fen`，不按剩余额猜测。代理可晚于经营确认月；真实日期决定必要先后，不用稳定ID充当现实先后。代理只清对应贸易义务，不产生公司银行款或第二份现金流；公司份额为零时不造零额清偿或证明。

退回沿原来源累计计算项目范围并公开负经营量，净额与VAT分别退回。更正只改变当前经营结果，真实已收付保持；多付或多收使用通用追收/退款关系，明确实际项目追偿基数，不从公司金额反除。追偿公开量供后续实际退款接续，不再次冲减经营利润。最终经营基数可以为零，仍保留真实清偿及必要的零额源身份。

程序按合同逐月派生必要位置`position:YYYY-MM`，以前月正式期末及本月变化接续，不让AI填写月末余额或无限生成未来任务。设F/D为公司经资金池投入/收回，X/Y为公司在池外承接的经营付款/收款，T/W为经营者补入/取走；R/E为确认收入/费用，r/e为实际收付，P为项目量，c为公司份额：

```text
F* = F + X，D* = D + Y
C = F* + rc - ec - D*
O = T + (rP - rc) - (eP - ec) - W
pool = C + O
operator_due = max(-O, 0)
company_due = max(-C, 0)
held = max(C, 0) - operator_due
company_capital = F* + Rc - Ec - D*
```

`held`是公司在经营者处的资金，双方应补不互相包含。公司资本=held+经营者应补−公司应补+公司净经营应收−公司经营应付；VAT在池外。池外直接清偿同时改变实际经营收付及X/Y，不虚增资金池。经营者直接补公司同时增加T/D。已知时点pool不得负；仅知月先用数量边界核验，确实影响真实资金先后才补日期。亏损可超本金，不把负资本截成零。闭期差错在发现期追收，不强迫把发现事实改填到原月；当前事实的早月反向往来由最终追偿接续，全单仍须容量一致。

明细按合同定位。位置只记相对期初的应补重分类，拨入/收回、经营和代理清偿已在原事实入账，不再记一遍；三类科目期末额须等于 held、operator_due、company_due。它们不是另一份可被普通资金任意清偿的义务。经营、代理结果和月末位置按结果槽依赖计算，同一单完整采用；合同条款槽不反向依赖其月末位置。

合同中的利润分配、清债和资本优先顺序用于AI指导办理，不作为拒绝登记已有真实款项的程序门禁。用途累计与经营确认的利润分别保存：早期收入更正或后来亏损时，保留真正发生的分回，只按正确经营事实确认利润和剩余权益；不自动改成资本返还、新借款或退款。简化重建采用同一规则，不依赖旧库证明款项曾被接受。全部资金、应补、资本和项目未收未付归零才结清；公司份额舍入为零不等于项目已清。无力补款不自动当坏账。

资金池不供公司随时支取，按[现金流量表准则](https://kjs.mof.gov.cn/zt/kjzzss/kuaijizhunzeshishi/200806/t20080618_46250.htm)的可用性和活动性质，本配置公司实付/实收分别采用 `other_operating_payments / other_operating_receipts`；池内收付不再进公司现金流。金融产品和股权另按其真实性质分类。

开放替换、闭期更正、资料发布及备份复用公共机制。标准业务文档只留合同及最终正确的真实事实，月末位置由程序重建。验收覆盖出资、利润分回、后续亏损和补足、资本退出，以及分次舍入、未收款、跨月代理、超本金损失和更正不重复入账；通用金额格式、原子性等不另建一套合作专用流程。

## 实际资金、备用金与核对

`money.movement` 必须有实际日、一个真实公司资金账户和金额；账户种类来自对象资料，不能填两个并让程序任选。平台真实收付必须消费 `money.platform_activity` 中匹配原行，日期、账户、方向和合计金额一致；同一原行不能重复消费。平台原行自身不入资金凭证。

| kind / 变体 | 必要条件和结果 |
| --- | --- |
| `money.movement.settlement` | 明确进/出、金额、付款方式、来源义务和分配。分配和等于实际额，方向及已知对象匹配；来源义务尚未明确收取对象时，实际付款可据来源单独明确该笔收款方，不反写义务或推定其他期对象。普通付款不能混两个不同已知权利人；批量付款仍逐分配给真实收款人。多个付款载体共用义务清偿容量，不能一个银行付款后又现金全额核销。 |
| `money.movement.managed_reserve` | 实际转入代管备用金或退回公司；性质和金额有来源，不按资金差额推定。转出列管理费，退回冲管理费。不建立一个与公司账户混同的虚构备用金余额。 |
| `money.movement.payroll_reserve` | 同一工资月的完整工资组；银行毛额=该组原毛工资合计=净薪分配+有依据实际返入备用金费用。每项完整清偿当前净薪、无已清偿或重复分配；返入月份与银行月相同，已知返款日不能早于银行日或跨月。 |
| `money.transfer.physical` | 两个不同的自有真实账户及金额、实际日；支持银行间、存取现、银行与平台。不认新损益；现金流表排除公司资金载体内部划转。 |
| `money.transfer.offset` | 两项等额反向义务、同一交易方、明确抵销用途；都允许抵销，且合计清偿不超额。资产预付款只能抵同类资产成本。不产生资金。 |
| `money.bank_statement` | 单账户单月，行包含稳定 row_id、来源位置、实际日、方向、正金额。原件有对方户名时填写 counterparty_text；memo 选用能说明本笔用途的原始摘要、用途或有意义备注，保留必要业务含义，不把独立的户名、流水号、账号、企业税号或空值占位等列重复拼成用途。原参考号放 reference，无资料则不补造，完整原文保留在来源原件。这些文字只作管理显示，不决定核算。同账户/月当前一份；行日属于该月，提供的原参考号在本单内唯一，期初+有符号发生额=期末。 |
| `money.platform_activity` | 单平台账户原行；稳定行身份、来源、日、方向和正金额；参考号、用途摘要和对方原文与银行行采用相同管理含义。它只提供来源，不自动把全部原行视为公司业务。 |
| `money.reserve_internal` | 明确仅为代管内部的边界来源和已有平台行。 |
| `money.reconciliation` | 原银行流水和组合匹配。每个组合可一行对多笔、也可多行对一个完整实际资金结果；组两边总额相等，账户、方向、实际日对应；组之间不重叠。全部原行及应核对资金都在范围内，不允许只匹配相互凑平的一部分。 |

工资毛额组合的银行资金只登记整笔一次；净薪组成和备用金费用各为对应分录，不再新增一笔假银行返款、个人返款矩阵或新债务。该组合不能用于未知返款月、部分工资、超付或已有其他清偿、转债的组；已经采用后续扣税转债的工资也走普通付款或银行批次，不套用这项无既有清偿的特殊组合。确有其他现实情况使用已定义的普通收付/待办，不能强行套组模型。

流水核对使用明确账面起点或已完成上月结果，不把流水期初直接认成账面期初。第一月、空行月份、跨年和中间缺月分别处理；中间缺月只影响相关对账。核对是无凭证正式结果，不再认银行资金。原行日期或方向冲突须查证，不用手续费/收入自动补差。

公司建账后新开的自有账户可在对象data中同时提供有据 `opened_period、zero_at_opening:true`，明确从该月零起点。不能直接传任意 starting_balance；已有余额使用期初或明确接续。缺开户管理资料不阻止其他可确定业务，仅在首次核对缺账面起点时返回缺项。

## 税费和期间口径

### 政策与含税拆分

政策以明确生效区间、官方 URL 和参数采用，不按计算机今天自动替换历史规则。比率均为 Decimal，金额到分，计算精度至少 80 位。普通 VAT、附加、旧资产出售 VAT、所得税、缴费规则分别有严格 payload。

2026 年边界不得沿用旧测试：[增值税法第二十三条](https://shanghai.chinatax.gov.cn/zcfw/zcfgk/zzs/202412/t474694.html) 区分未达到与达到起征点；[2026 年第 10 号公告](https://shanghai.chinatax.gov.cn/zzzb/zcwj/202602/t479283.html) 规定衔接期门槛及相应减征；[2026 年第 4 号征管公告](https://zhejiang.chinatax.gov.cn/art/2026/2/2/art_8409_84409.html) 的放弃免税/减税等规则需单独匹配。2023—2025 的 at_or_below 与 2026—2027 的 strictly_below 分别建政策样例，同额边界得到不同结果；不能只改起止日。

`nominal_rate` 用于规定征收率及申报减征展示；`tax_base_rate` 是含税金额拆分的分母率；`payable_rate` 是相应应纳税额率。三者由规则适用条件决定，不因“3%减按1%”的名称就自行选分母。普通/专用发票和免税适用资格仍须有据；`waive_exemption`、`waive_rate_reduction` 省略时采用内核默认 `false`，即不主动放弃，明确的其他选择仍按事实处理。实际采用依据固定保存这两个布尔值，原始输入不改写，不扫描或回填历史。默认不是免税资格、未开票或零税额；1%专票也不等于放弃1%减征，按[2026年第4号公告](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5247426/content.html)承接。旧资产出售另有基础率和实纳率，不套普通服务公式。

普通减按1%的含税销售以1.01拆分，政策参数为名义3%、税基1%、实纳1%；不能先按3%拆分再把2%差额当收益。税基公式见[总局说明](https://www.chinatax.gov.cn/chinatax/n810356/n3255681/c5183790/content.html)，与2026年减按1%政策结合采用。[财政部记账答复](https://www.mof.gov.cn/bd/mhwzzxly/hjs/202401/t20240123_3926932.htm)明确可预先确定的1%直接按1%记税，满足免税条件时再把已计税额转损益；销售业务不能提前把可能免税当成零税。明确放弃减税并按3%办理时，采用实际3%的拆分和税额。

### 税点及销售范围

`taxes.tax_point` 明确普通服务或分阶段预付服务、是否实际开始服务、合同收款权是否成立，以及有源事件（合同权利、开票、真实收款、开始服务、完成）的月份、可知实际日和含税金额范围。长期结算条款复用公司说明中的适用对象、业务范围、期间及不可变来源，每笔税点采用对应来源；计算器不解析说明正文，也不把收款习惯当作合同条款。按[增值税法实施条例第39条](https://fgk.chinatax.gov.cn/zcfgk/c100010/c5246349/content.html)，有书面合同付款日期时采用该依据；确无书面合同或未约定付款日期时采用交易完成时点，尚未核查不能当作无约定。提前开票或交易中收款可能形成更早税点，逾期到账不推迟已到的合同税点。收款事件必须有实际日、发生在交易前还是交易中/后的状态，并引用属于该业务的类型化实际收款分配，原件裸行不能自行证明钱属于哪笔业务。已开始时必须有开始事件，尚未开始不能填虚构开始日；该详细推导首轮支持2026年起规则，较早期间可以采用有据明确税月，不能自动套2026推导。条款变更保存新来源和当前正确说明，原业务及冻结结果保留实际采用依据。

程序按有效税点规则对金额范围作并集和先后判断：同一笔钱不能被原始位置、修订版本或相交范围使用两次；合同全额权利与分次收款不重复；只有已收的一段不能证明其他段更早没有税点。政策月中变化时需足够实际日；全月同规则且只需月精度时不追问假日。分阶段预付服务的开始时点及预收计税范围不能靠后来的收款日猜。

税点正式结果 TaxPointResolution 把原毛额分成互不重叠且完整覆盖的范围：已到税点的范围带税月、可知实际日、触发类型及事件身份，其余明确为尚未到税点。税点自身不确认税销售、收入或税额；经营结果采用这些范围，唯一产生相应 TaxSale 及待转税变化，避免重复。真实收款依据读取本单类型化事实，最终与正式资金结果一起核对，不形成彼此等待的循环。

### 增值税与附加

`taxes.assessment.vat` 采用完整自然月范围、VAT/附加政策及已明确的退抵来源；没有完整实际来源时，计算需要有效的VAT及附加政策。已有完整实际来源时，不因参考政策未提供就阻挡采用。期间不能跨年或与另一当前计提重复覆盖同月。销售、预收税、履约、待转税、处置及退回统一提供 `TaxSale`，报表/申报/看板不得另选收入范围。

1. 按适用率和应税类别汇总净销售及已计 VAT，先明确免税/不适用范围，再按相应政策阈值比较，不能只加已加载页面。
2. 符合免税的已计税额转入相关收益。应纳、减征及免税显示按采用表式求值；舍入差独立计算，不用余额猜补。
3. 城建、教育和地方教育附加按采用税基及各率、减征份额分别舍入后汇总；三者不能仅给一个合计再反分。
4. 真实销售退回的负向 TaxSale 使用退回所属月和退回业务身份，原税月、原销售及原分类留在必要依据；未计税预收退款不产生负向税销售。跨期本身不阻止扣减本期销售。净额为负或类别、税率无法按已支持规则正确处理时，只暂停受影响的税费计算，采用有源实际处理，不阻止真实退回记账，也不自动生成退税现金。

完整实际 `taxes.actual_declaration.vat` 优先采用其 VAT 及三项附加应纳。参考政策/算法缺少只降低参考可用性；实际源自己缺项或矛盾则不能用参考填补。预缴、应补退、表行及免税转回分别有字段；未知不填零、不从应纳反造已付款。`settlement_as_of` 只在确知时使用。

`taxes.tax_credit` 是税局实际已明确的退抵结果：原税期、原申报来源、真实退回、处置方式、VAT/附加抵退及原免税转回分别明确。它自身不自动退款或入现金。计提显式采用后，明确覆盖部分从普通本期扣减中排除，再产生受处置限制的 `vat_credit/surtax_credit` 资源，不能双算。部分或多税源覆盖须用 tax_ranges 明确原毛额范围，不能按退回 ID 盲目剔除整笔；全部覆盖且来源唯一时直接复用原范围。附加退抵只有合计时保留已知总数，不按比例猜城建、教育及地方教育金额；三项有源细分提供时必须齐全并对平，缺少时只将相应报表细目标为未知。晚确认时重算原税费完整目标，闭期在发现期补差，不能保留旧扣减后再无条件增加债权。

申报表按 `form_version` 明确采用，不把名义应纳展示额当实际会计应付。[2026 年第 6 号公告](https://liaoning.chinatax.gov.cn/art/2026/2/1/art_5869_7757.html) 及其[官方解读](https://liaoning.chinatax.gov.cn/art/2026/2/1/art_6365_164002.html)对应 2026 年业务、次月起申报；当前企业场景的未达起征点销售使用第10栏及其3%计算的第18栏，个体/自然人第11/19栏在本公司场景为零。减征率带来的第15/16栏与最终应纳第20栏分别计算，完整采用字段包含第1、9、10、11、15—22栏；实际申报原件对应字段缺失时保留未知状态，不能补造。其他未实现表式返回 `unsupported_form`，不阻断已有完整实际税额采用。

`filing_profile` 必须来自该企业实际税务适用资料，明确是否非试点；不能仅因地址是上海或日期已到2026年6月就自动换表。首交支持非试点既有表式，试点及其他表式明确不支持。第2/3栏分别取明确的专用/其他发票不含税销售，不能把开票总额代替核算税期销售。[现行表样填写说明](https://shanghai.chinatax.gov.cn/bsfw/xzzx/bgxz/sbzsl/202107/t459066.html)与2026年表样衔接核对；第21—25栏所需预缴/结算来源缺少时为 `partial`，不是自动零。实际来源缺少的表行也不能拿参考算法伪装为实际申报字段。

### 企业所得税

有据定额和 computed 季度暂计两条路线均保留：

- 定额采用明确累计应纳，支持确认暂计、实际申报及年度汇算。累计额不是本次应补额；实际来源包含累计应纳、预缴和应补退时，三者需相符。
- computed 只支持有据查账实际利润预缴、标准/小型微利适用及明确弥补亏损。需本年季度末、完整政策覆盖、资格和亏损来源；特殊调整/优惠未支持时明确缺口，不默认为无。
- 使用 `ledger` 同公司同季度共享税前利润，不接受 AI 提交替代利润。正计税利润=`max(0,累计税前利润)−有据可用亏损`；亏损扣除不超过正利润。小微超过适用上限需核对适用依据，不能静默切率。
- 累计暂计=`round_half_up(计税利润×适用计税份额×税率)`，先乘完再到分。当前变动=本次采用累计−之前已采用累计；正数计费用/应付，负数冲费用并形成可抵扣量，不能直接当成可收现金。零额保留正式结果。经济计提月按累计边界非递减，录入先后不受限制。
- 完整实际累计税额覆盖计算参考；参考失败不能改实际，实际缺少累计字段不能退回计算补值。已实际缴款不随税额下降消失，差额按真实权利义务接续。
- 每个累计节点的 main 确认税额变化，独立内部净额槽在真实资金就绪后，用公共资源窗口抵销应付和可抵扣量。同月季度/年度节点排除明确的晚序内部抵销，不排除真实资金，不改变更早月份以容纳后来的超付。
- 实际申报原应退额不是每次新增退款，也不随到账改写。只在来源明确时建立可收退款资源；以前确认但未收的权利接续转入，已经收回的前序退款不能再确认。本节点自己的到账通过正常清偿减少剩余，不反过来减少自己的原权利定义。

工资/奖金/劳务个税首轮只采用有来源明确金额，不宣称已恢复历史累计个税计算。税务表单准备和实际申报是不同状态，生成文件不表示老板已申报或付款。

## 期初与报表接续

`opening.package` 汇集 bank/cash、往来、资产、贷款、税、工资未清组成、权益、货币基金成本。成员稳定 `member_id`、来源及严格业务变体，不接收自由科目/借贷行。整个包一个建账起点，各成员同边界，资产=负债+权益；不得自动补差。新设立零起点可为空成员，不强制逐类制造零项证明。

bank期初涵盖明确的银行或自有支付平台对象，分别选1002/1012；cash对象选1001，不能为平台伪造银行账户。银行/现金不造旧现金流；往来保留真实对象、性质、原业务及未清金额；税和工资组成属于开账前期间。贷款本金尚存时从建账边界接续计息，不造放款日；本金已清只欠利息时，不要求无用途的计息起点。资产模块统一核验期初卡片的启用日、已摊月数、累计和舍入，并接续建账后的摊折；期初模块保存静态余额，不另算一套资产公式。货币基金保留具体产品和有据批次成本，后续赎回才消耗。

`reports.continuation` 属 `ledger` 报表基础，不是经营收入。它保存建账起点、期初引用及必要的年初余额和建账前当季/累计报表资料。固定当前小企业模板为资产负债 53 行、利润 32 行、现金流 22 行，行号各自连续唯一；明细名称及合计规则由报表合同维护。它不生成凭证，不能拿累计报表自动补历史业务。缺比较资料可以说明相应报表未就绪，无关本期业务继续。中途接账的本年累计已计所得税用有源 income_tax_carry 接续，明确税年、建账前累计截止及累计税额；不能从未付税余额或利润表所得税费用反推，也不能默认零。新设公司的明确零起点沿用期初依据。

旧 `report_classification` 不再接受凭证版本和任意行号作为 AI 办理动作。新的经营事实给出必要细类，领域产生报表贡献；税费、工资、摊折及投资由确定规则提供同口径取数。所得税零额由真实税费正式结果表明，不再要求另一份同义确认。

## 正式结果与必要采用依据

机器定义见 `ResultTarget、AdoptedBasis、PostingPlan`。每种 kind 的 `ResultTarget.values` 都是关闭额外字段的指标结构；例如工资必有毛额、总成本、实发、税、四类缴费、代发目标和暂留额；资产有原价、累计、账面及逐卡结果；税费有累计/差额、采用方式和确定的表式字段。政策及来源型事实可以没有凭证，不因此制造业务金额。

每份平衡 `PostingPlan` 明确 `business_id、result_slot、accounting_period、calculation_key、calculation_revision、rule_refs`，以及受控分录、义务、清偿、转债/重分类、可消费成本、成本消耗、实际资金、合作代理收付证明、税销售贡献和报表贡献。计算 key 为本文件对应点分 kind，首个版本 revision=1；自动摊折使用 `assets.consumption`。列表为空表示该种影响不存在。`ledger` 统一检查金额合法、借贷平衡、科目及资源名、来源方向/对象、总额和消费容量；不能只检查凭证平衡就认为业务正确。

领域先`declare_relations`统一声明直接事实关系，再在完整关系目录上`describe_change`返回ChangeDescription：责任、完整结果槽、依赖、发布范围及问题，不预先计算正式结果。应用以“business_id＋result_slot”为节点，按结果和资源余额依赖拓扑求值。合作合同main→经营main→代理收付main→合同position月槽不成环。对象/fact依赖只核对存在及含义，不进入结果拓扑。

逐槽结果齐备并交叉核验后，应用按owner组装 `ChangePlan` 交各owner持久化：领域、businesses、plans、dependencies、publications和issues。每个责任项明确业务身份、预期序号、动作、当前完整事实（撤去无正文）及完整 `complete_result_slots`；纯管理slots=[]，计划为空时仍能分清完整退出与没有负责。evaluate_slot不能临时扩大已声明的槽或依赖范围。内部recalculate使用未改变的当前事实，仅重算结果，不扩展AI的四种修改动作。

Dependency按consumer业务/结果槽、producer业务或对象及公开槽、fact/result读取模式、关系类型和必要期间范围完整声明，不能靠扫描JSON或basis猜图。对象只作identity事实依赖。应用层核对计划身份与目标/依据相符，替换负责业务的当前依赖和完整结果范围；未再成立的开放槽退出，仍被采用的闭期槽保留。不能漏旧槽留下孤立义务，也不能无条件删除闭期结果。

公开义务/成本 slot 在同业务中唯一。资产批次的逐卡成本使用 `cost:<asset_id>`，报销债权使用 `reimbursement:<person_id>`；工资沿用净薪、缴费和有据税额的固定槽名，基金用 `cost`，机构和股东借入用 `principal`，利息用 `interest`。调用方仅用公开业务引用；不能拿文件行号或内部 SQL 主键充当 slot。

单侧实际资金的公开资源名为 `funds`，内部划转为 `from_funds、to_funds`；每个受控 `FundMovement` 同时有稳定 movement_id 和 public_slot。税点的收款来源引用实际流入资源及其业务分配，不能用尚未收取的应收替代。数据库方向若使用in/out，入口和结果的inflow/outflow作明确一对一转换，不能混用符号。

实际资金的稳定身份与已采用金额分开：ledger保存每个采用结果的资金日、方向、金额、账户和现金流类别，当前或闭期查询由该结果取得；money只维护稳定身份、账户及原行核对。内部互转两边共用transfer_group_id；同一真实款被更正时身份不换，不把冲正凭证变成新的实际资金。原始流水文字只保存当前正确内容，冻结采用不保管理备注；历史行补充当前文字须核对同一清单、行身份、账户、日期、方向及金额，不能把新行或新资料位置套到旧采用上。

`AdoptedBasis` 保存计算实际采用的会计输入、必要数量、政策参数及来源定位。来源结果定位包含 `business_id、result_id、result_slot、result_generation、content_digest`；它不能代替已采用金额。闭期把实际消费的义务/成本/资产卡/工资组成/税销售/税前利润/余额按严格数量类型保存，不能指着将来会替换的开放结果头。政策只留采用的版本、有效范围、官方 URL 和必要参数，不保存整套个人资料或递归结果。

### 义务转移与多付重分类

同向债务承接与已付超额重分类共用内部 `ObligationReclassification`，字段为 relation_id、owner_business_id、source、target、amount_fen、mode。仅有 transfer 和 reclassify_excess 两个实际支持模式，均由严格业务事实生成；AI 不提交这类余额关系。

某项义务当前余额 = 当前确认金额 − 实际资金清偿 − 代理清偿 − 抵销清偿 − 同方向转出 + 反方向超额重分类。新目标义务的金额已经记录新形成权利，关系入边只证明它的来源，不能再加一次余额。

- 个人代垫转债采用 transfer，只能移未清正余额；源和目标均为应付，移后原债减少，新报销债务相应形成。多条来源转入同一新目标时，总和等于该目标金额。
- 已付1000元而工资改为800元，原净薪余额800−1000=-200；有据超付事实形成200元 recovery 应收，反向重分类200使原余额为零。分录为借1221贷原工资应付200；原1000元付款和分配保留，不新增200元薪酬或付款，也不能把出款分给应收。
- reclassify_excess 只恢复已经发生的负余额到零，不能使源产生新的正应付。后续真收回200元才清 recovery。普通真实退费是新的权利，不必向已清原债加恢复。

首轮没有一般坏账/债权核销入口；报表存在坏账行不代表已支持该业务。资产处置损失及货币基金零回款按成本规则办理，不因此引入通用核销或任意调余额接口。

开放期补充来源而核算实质不变，更新当前依据，保留原凭证；不新增无影响复核历史。科目、金额、期间或真实义务改变才按原子更正规则处理。已实际发生的后续收付不使早先闭期源重新变成未完成。闭期更正保留冻结结果及关联冲正/替代，原开放错误正文与操作轨迹不积累。

撤去有闭期基准的业务，使用内部 `system.withdrawal` 严格目标和依据：原业务 kind、结果槽、withdrawn 状态、冻结基准定位、撤去说明和必要来源。目标的分录及所有资源数组为空，ledger只据冻结基准生成必要正式冲正；不伪造退款。没有冻结引用的开放结果直接退出，不积累撤去过程。仍有真实收付、成本消耗或其他依赖时，必须同单完整处理关联，否则拒绝。

合作方真正代客户收款或代公司付款，用 `Settlement.method=agency` 清贸易义务。仅[合作项目投资](#合作项目投资)的类型化代理收付结果能产生 `agency_proofs`，证明指明原业务公开资源、实际原对象、经营者、方向、金额和期间。ledger核对采用头、对象、方向和总容量，不读取合作私有JSON。工资、税及普通无来源债务不能借此清零；它没有公司资金发生，也不增加公司现金流。

### 同一业务更正分类

首交允许 `operations.expense ↔ assets.acquisition` 受控转换，使用原business_id和replace，按03的旧owner退出、新owner接管协议一次完成。仅适用于同一笔真实采购：原件、交易方、总金额和已有真实收付连续；新资产取得须为direct，原费用须为supplier应付。新旧 `main` 和 `primary` 资源保持身份、方向、对象及金额兼容，已有付款直接继续清这项债务；转换不创造第二笔付款，开放凭证保留原号。资产对象必须存在且符合资产识别事实。

旧owner的内部责任op=handoff_out，fact禁止、complete_result_slots=[]，不产PostingPlan，只清所属旧正文；不改公共业务head、seq、当前来源或main。新owner的replace提供完整正确Fact及main唯一正式目标。应用严格匹配同ID一出一入，公共序号只加一次。handoff_out不是AI修改动作，不是撤去业务；两种首交类型都只有main，不引入通用迁移框架。资产启用是独立业务，需要退出时按同单withdraw及其依赖处理。

转为资产时新增卡片成本；转回费用时撤去该成本。已启用、已摊折、被其他成本消耗或存在不兼容冻结引用时，程序同单重算所需结果，不能完整办理就返回dependency_conflict，不静默丢卡或换业务ID。其他跨kind转换首交返回unsupported_change_kind。同kind内部误分类可以用同ID完整更正，但必须仍是同一现实事项；例如工资改为劳务时，已有实际付款保持身份、日期、金额和分配，相关借贷按正确分类原子重算。不能换个名称掩盖另一笔事项或绕过真实清偿与冻结关系。

财务三表、税前利润、分类、期间和闭期差额的唯一计算规范见 [财务取数](05b-financial-reporting.md)，不由看板或税务模块重新选择口径。
