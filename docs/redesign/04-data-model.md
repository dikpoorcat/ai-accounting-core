# 数据结构、归属与可靠保存

新库独立设计，不沿用现库表名或版本链。数据库结构的唯一字段真源是 [公司库 DDL](schema/company.sql) 和 [目录库 DDL](schema/catalog.sql)；本文件解释每组表的意义、生成方式和跨表约束。运行包的结构资源由该真源生成并检查一致性，不能分别修改两份字段。开发验证使用新建合成库，不对现有公司文件执行这些建表语句。

## 库与结构合同

目录库保存本地老板登录身份和公司位置，不保存公司业务。公司库只属于一家企业。路径为 `<公司资料根>/<统一社会信用代码>/runtime/company.sqlite3`，资料、标准文档、备份位置见 [标准文档](03-contracts.md#标准业务文档)。原数据库另行隔离，不注册进新目录库；具体搬移与清理在未来切换任务执行。

目录标识 `ai-accounting-modular-catalog/1`，公司库标识 `ai-accounting-modular/1`，标准文档标识 `ai-accounting-standard/1`。三者不能只比较尾部数字，也不能把当前旧体系的 v0/v13 改名成新格式。

`module_schema` 为每个 owner 记录当前结构合同摘要、父合同和 SQL 指纹。全库指纹按 owner/key 排序，对实际保存的表、索引、触发器 SQL 规范组合计算；校验合同、库内记录和 sqlite_schema 实际结构三者一致。字段合同、数据迁移合同和计算语义版本分别管理，不用一个应用构建号代替。

首版只新建空库，不承诺旧库自动迁移或旧备份导入。未来同体系结构修改必须先形成前向迁移、来源合同、保留核验和失败回滚，再升级已有库；本版不提供删除重建或只改指纹的“升级”。这项约束不要求现在建设尚无实际变更的万能迁移引擎。

## 表的分组与所有者

DDL 中每张表上方的 owner 是唯一写入者；数据库连接共用不改变归属。公共业务身份和对象身份可作为各模块外键，领域不跨读对方事实私表。表字段与 JSON 所用类型/必填条件分别由 DDL 和 Schema 定义。

## 当前事实及检索字段

`business_head` 不保存业务正文。family/kind 决定 owner 和 Schema，seq 为当前事实序号；current_digest 为规范事实摘要。`natural_key` 由所属模块在每份完整责任中声明，没有自然唯一性时为 null。应用按整单最终集合校验，允许同单交换身份；连带重算的业务也同步其派生键，不修改事实序号。普通两笔同金额付款没有这样的唯一键，不能按金额、姓名或原件哈希把它们合为一笔。

application_state 只保存已进入的工作末月。它从公司起账月开始，随明确业务月份或关账范围向后推进；撤去业务不让它倒退。标准清单保全这一当前值，使简化重建仍能生成相同范围的必要摊折，不保存“何时进入”的过程记录。

领域事实表的 data_json 保存完整严格 Fact，是该业务正文的唯一真源；identity_object.data_json 对应保存完整 CurrentObject。这样各 owner 可以独立导出自己的正确正文，不必反向拼接应用头或资料私表。业务头的 kind/period/archive_month/current_digest，以及身份表的 kind/name/seq/digest，均为同次保存的检索、并发或一致性投影，不能作为另一份可独立修改的正文。应用在事务末通过 owner 公开导出核对业务头；identity 自行核对对象投影。

effective_on 和 main_object_id 同样是领域维护的检索投影，调用方不能单独修改。main_object_id 选择如下：经营往来取主要交易方、薪酬取人员、资产取资产/项目、借款取合同交易方、投资取产品/项目、资金取账户、税费取适用公司对象（无则为空）、期初/报表接续为空。多对象业务仍通过当前关系和公开结果检索，不能仅凭主对象漏项。

工资按一人一个核算月建立业务根；奖金和劳务按真实事项分别保存，同月可以多笔。不把全公司工资放进一个巨型 JSON。银行和平台原行、期初成员有稳定独立身份，规范化到明细表；对应 JSON 是同一事实的输入/导出形状。保存后以所属明细表为唯一持久正文，根 JSON 中不再复制 rows/members，导出由仓储按固定顺序合成并重新校验完整 Schema。

上述拆分仅允许合同明示的三处：money.bank_statement.data.rows、money.platform_activity.data.rows、opening.package.data.members；schema_key 在存储中标为同类型的 storage_projection/1。父 JSON 省去数组，只增加有序完整明细的 collection_digest，不复制明细正文。完整导出先核对明细身份、顺序、所属及摘要，再恢复并严格校验 Fact；返回内容不含存储摘要，current_digest 仍取完整事实。三处共用拆分与恢复规则，批量导出按明细类型读取，不逐个父项查询。普通行分页只核验命中行，不冒充全清单完整性核验。

自有资金账户可以在公司建账以后新开。有据填写 opened_period 与 zero_at_opening=true，才允许从明确开户月零起点开始核对；已有余额须走期初或明确接续，不向对象资料开放任意 starting_balance。缺少这项不能阻止无关业务，只在确需该起点的核对中返回具体缺项。

SQLite 的 json_valid 只检查可解析性。各 owner 严格校验完整正文、金额范围和跨字段关系；schema_key 标明业务类型或上述明示的规范化投影，DDL 再保护类型、唯一性、外键、金额非负和索引。未知核算字段不能存为 0，也不能通过任意扩展 JSON 或自由 properties 绕过严格合同。

撤去后 business_head 只保业务身份、种类、当前序号、withdrawn 状态及最新撤去前提/摘要；当前事实、当前来源边和退出结果清理。已冻结正式结果不会级联删除。错误开放正文不留到“审计”“恢复请求”“调试”表中。

## 当前未解事项与资料来源

current_issue 保存当前已知的部分事实及还缺什么，仅使用 PartialFact 校验，不进入核算。其可选 business_id 可以是尚未正式建立的稳定业务 ID，不要求为待确认资料先造一条正式业务头。scope 头比较防止两个 AI 工作单互相覆盖待办。已解决事项在正式事实写入的同一事务退出待办；待办重写不保存之前问题和回答。assignee/action 区分由 AI 核查、老板提供现实资料或办理外部事务，程序错误不自动转为老板任务。

source 的内容身份固定，file 用字节摘要，owner_statement 用规范 UTF-8 正文摘要。改内容必须新 source_id，改归档月/位置由 records 管理，不改变内容身份。source_use 统一索引业务、对象、当前待办及当前说明的来源边。业务来源由唯一 Schema 的顶层 evidence_ids、嵌套 SourceLocator 以及明示 SourceId 的期初成员证据共同提取，不要求重复填写顶层证据；缺项指出实际 JSON Pointer。已有相同集合不重复删插，记录退出时同事务删除当前边。result_source 只保存正式采用真正需要的来源，不把所有旧答复列为必要。

文件读取/备份获得当前集合使用租约；清理检查当前事实、必要冻结结果、当前清单及租约。移月先保住新位置，再发布清单，最后清理旧位置。外部软件改坏原件会在摘要核对时明确报错，不能把被改内容沿用原 source_id。

company_note 只保当前说明及其依据 head。月份说明提交时比较 expected_basis_head；依据变化时原子清空旧正文及其 source_use 边、推进 seq，只保 scope/seq/needs_refresh，AI 更新正确说明；不展示/保存开放期被替代的旧正文。依据头排除说明自身及派生文件状态，避免自我失效。公司现实背景不随普通金额变化失效。NotesShard 只导出当前有效说明。闭期报表需要的实际采用说明可以包含在 period_close 必要附注，不额外保所有编辑版本。

## 完整结果槽与闭期更正

一个平衡计划对应一个 result_slot，包含若干稳定公开资源 slot。result_slot_current 指向当前完整目标；公开义务/成本身份是 business_id+public_slot，不能把 result_id 当成其稳定身份。

adopted_result 的 target_json 保存该领域完整已采用目标，basis_json 保存实际采用的最少核算字段、数量、政策和引用摘要。采用引用包含 result_id、generation、内容摘要；对于仍可能替换的开放源，冻结时嵌入本公式实际需要的数量，不能依赖那个 result_id 的当前正文永远不变，也不递归复制全部上游结果。

开放头重算时保持 result_id，generation 递增，完整替换其当前目标、分录和子结果；旧正文删除。冻结头不改，新更正头指定 baseline_result_id。若更正头仍开放，继续替换并始终对照同一冻结基线；若已冻结，下次以该更正头为新基线。

正式状态与凭证影响分别判断。完整内容及依据定位未变时复用原结果。开放来源代次或位置改变时，同步精确引用，结果版本可以更新，凭证身份、编号和分录不因定位更新而改变；闭期仅补来源位置或上游代次不新建更正采用。必要政策、接续数字或分类改变时更新正式头，即使没有借贷变化也保留正确状态。确有分录变化才产生关联冲正及替代；无凭证更正头沿基线解析有效目标凭证，撤去后不再继承退出凭证。必要实际日期进入 Basis；纯管理日期只在当前 Fact。

current_dependency 保存当前事实/结果依赖、collection 集合观察，以及资源 use/balance 声明。use/balance 按精确来源资源、类型、经济月份、必要实际日和显式排除结果槽安排计算，不保存金额或另一份余额。旧、新使用范围均通知余额观察者；事实关系查询只读取 fact/result。普通重复依赖合并覆盖范围，余额读取的实际日或排除名单不同则不能合并；不扫描业务 JSON 猜关系。

current_publication 按业务、结果槽和 tax_sales/pre_tax 集合保存当前发布月份范围，并按集合和范围建立索引。aggregate 结果依赖据此发现相关槽及消费者。发布范围只是可重建索引，不含金额和旧正文；与当前事实、依赖及正式采用同事务替换。退出或移月按旧、新范围通知，金额的唯一真源仍是账务正式结果。

每次计划声明该业务**完整结果槽集合**。未返回的旧槽、义务或成本必须处理退出；存在实际清偿、消耗或冻结必要引用时，不能静默删除。无凭证但有正式核算意义的结果同样采用，纯管理资料不伪造零额凭证。

关账先完成该月可确定的核算和必要检查，再在同一事务冻结结果、凭证、必要依据及三表，保存 period_close。无审批记录、预览采用表或密码批准表。closed 月份不接收新的原地采用；更正必须落到明确开放期。

## 义务、付款与成本不重复计算

obligation 由业务确认产生，settlement 只说明已发生的清偿，不能再确认一次收入/费用。净薪、个人扣款、单位缴费分别为明确 slot；未知机构可不具名，但贸易、净薪、报销和借款本金等需要明确的实际对象。允许 money/offset/agency 及非资金 transfer 的范围逐类声明，不能用“抵销”消掉不能抵销的实际欠款。

result_report_contribution 只保存受控报表细目。amount_fen 与 issue_json 恰有一项：前者为已知整数分（含零），后者为使该明细未知的必要问题。它们随完整结果替换或冻结，不保留旧错误版本；缺细分不阻断已经明确的总账和税前利润。

当前口径只选择每个结果槽的当前完整目标；某月末口径选择当时已采用、posting_period 不晚于该月的完整目标。正式月度发生额仍按该月有效凭证计算，不能只累加当前目标。冻结结果和更正头均保留时，不把原目标与替代目标重复累计。开放月份只能提供当前正确结果，不承诺查询过去某次错误录入时的状态。

同一来源的清偿合计不能超过其有效可用额，同一成本的消耗合计不能超过其有效账面成本；按 current 和所需历史截止分别核对。金额改变必须重新核对已有实际付款。例如工资 1000 改 1200，实付 1000 不动、剩余 200；改 800 时已付 1000 仍真实存在，需要明确多付 200 如何重新归类，缺事实时整单拒绝，不能擅自删付款或默认为借款。

非资金关系统一使用 obligation_reclassification，避免为每种代垫和多付各添一种余额补丁。transfer 只将未清的同方向义务移给明确新对象；reclassify_excess 只将已出现的超付/超收负余额转成反方向的真实权利义务，恢复原项余额至零，不能制造新的正应付。目标义务金额本身已是新权利义务，入边仅证明来源，不再加一次目标金额。

原项剩余额＝当前义务额−公司真实资金清偿−抵销−有据代理清偿−同向转出＋有据超额重分类。各 mode 的来源方向、目标方向、金额容量和会计分录由对应业务规则严格控制，AI 不能提交任意余额调整。例如薪酬降到 800、已付 1000，明确信息形成多付追收 200 时，计入借其他应收/贷应付薪酬 200，原付款及原清偿不删，原项剩余为 800−1000＋200＝0，追收应收 200。正常费用退款是新的真实业务，不为了套此关系回改原债务。首轮不凭现有报表上有坏账行就新增通用债权损失入口；已有资产及基金损失仍按各自成本规则处理。

合作投资所需的代管资金、双方应补及未收回权益，是投资模块内部派生的正式余额，只保存于既有 Target，不另建项目账本、余额表或专用查询接口，也不重复生成 ordinary Obligation。原客户/供应商的贸易义务仍由 ledger 维护，代理收付用通用 agency 关系清偿。AI 经普通业务结果读取所需余额；总账与报表按已采用分录取数。经营者代收代付不冒充公司银行资金，不重复现金流。

闭期付款需要改清偿用途时，保留原冻结采用，在开放期作明确重分类及当前目标更新；真实 occurrence_id 和实际付款日期不新增。读“真实对外收付”按唯一实际发生身份计，不将冲正/替代分录误算成再次付款。历史账面发生与当前已知实际发生的差异按看板既有 read_semantics 区分。现金流按正式已采用目标的有符号补差归入更正期，原期冻结不改；同一实际发生不新建，具体三表公式见 [报表取数](05b-financial-reporting.md)。

## 资金原行与对账

money_occurrence 只登记稳定实际发生身份与公开资源键，不另存一份可编辑金额。正式实际发生及分类存入 ledger 的 result_fund_movement，由当前/指定月末采用头选择；money 通过公开批量入口读取并补充账户及对账资料。单侧公开资源键为 funds，划转两端为 from_funds/to_funds，共享 transfer_group_id，对外收支排除这两端。方向入库为 in/out，业务 Schema 的 inflow/outflow 明确映射，不让其他消费者猜。

同样，TaxSale 与 ReportContribution 从完整计划进入各自正式表，随结果完整替换或冻结。item_no 只作为一份完整税务分类中的内部顺序，不对 AI 暴露成稳定业务身份；对外仍按原业务/税期/金额范围引用。result_report_contribution 仅为严格 profit 明细行分类，不提供任意 balance/cashflow 补丁；财报主项与补充分类的取数各有唯一规则，不把凭证金额和其分类重复相加。

一笔真实付款可能同时支付本金与利息，或净薪与代管款，仍只有一个 movement_id 和总额。obligation.cashflow_weights_json 保存按类别唯一的正式分类权重，必要来源在 Basis；result_fund_movement.cashflow_parts_json 保存本次真实款按类别归并的实际分量，合计等于该笔总额。分类欠缺为 NULL，不能假填空数组或零；已知单类在义务更正为零后仍保留权重1。现金流只消费正式资金及其更正补差，不重复加义务分类或报表贡献。内部划转以 none 分类并有真实两端组关系，对外收付排除。

银行/平台原行只证明发生，不自动再入一次账。同一账户/月的原行按实际日期、row_id 排序。原始 reference 可省；若存在只在本份清单内要求唯一，不假定所有银行所有月份流水号全局唯一。source_location 是原件定位，不能反过来决定核算期间。

对账按完整匹配组保存：一组银行/平台行对一组实际发生，账户、方向、有效日期关系和两边总额符合规则；可以一对多或多对一。成员在当前有效匹配中不得重复，不能把 300 元银行行与两笔 100/200 元付款虚构成三份新的付款，也不凭空分配每一行对每一笔的金额。未处理原行、金额差异及缺失资料明确返回，不能仅有一个旧“已核对”标记就关账。

## 文档与读取目标

document_shard_head、read_scope_head 只有当前 wanted/ready 或 published 头，编号来自公司提交序号。只在确有相关变化时推进。后台生成在一致读快照完成，发布前比较目标；旧任务不覆盖新目标、不清除新待办。

document_set 对应一套 current.json 清单。数据库与清单确认之间中断，启动时核对当前清单的集合及片摘要，匹配则补确认，不匹配则从当前事实接续。清单原子切换前的旧片只是安全发布所需临时保留，切换后清理，不作为第二套备份。

读取汇总保存在 read_component，分页项目保存在 read_item，完整计数与金额独立于分页列表。查询沿 scope/collection/sort_key/item_id 索引；对象、组、分类有各自索引。新增业务页不进入旧五页默认组件依赖。读模型损坏可清理重建，但不能因此删/重记正式业务。

## 文件任务与备份一致点

file_task 由独立 files 模块维护，仅有 backup/report_export 两类，每种 scope 只保当前计划。它通过 host 注入的生产者 Protocol 获取严格 FilePlan，不反向依赖业务应用。相同语义计划的 pending/running/succeeded 直接复用，即使 request_id 不同；最终失败的新显式请求才替换。同一开放报表被新结果替代则过期，旧文件清理；旧任务退出后可返回不存在，不保存所有过期任务身份。备份保留当前包和上一份有效包的滚动能力，与用户指定清理的旧体系备份分开。

BackupPlan 绑定捕获的数据库 head、完整 BackupManifest 和 CapturedFile 集合，文件只从公司根或本任务 capture 根按受控相对路径读取；capture 根为 runtime/tasks/<capture_id>，不是任意主机路径。语义 scope_head 根据 format、结构指纹、database_id/head、document_set_id、按包内路径/摘要/大小排序的必要文档及来源清单计算，不包含临时 capture_id/本地文件位置、派生缓存、file_task 状态或整个快照数据库字节摘要，避免循环或无意义失效；包内真实数据库文件摘要仍必须验证。ReportExportPlan 只接受 status=ready 的完整 FinancialSnapshot，同时捕获 organization 公司标题资料、显示变体和模板版本；其语义头覆盖财务内容/selection、范围、公司标题、变体、模板，排除无关全局 snapshot.head 和请求用 scope.expected_head。worker 使用计划中的公司标题，不临时读新名字拼进旧预览。两种计划存当前任务，不成为第二份可编辑账务。

备份使用 capture_backup_snapshot：先完成待归档，再取得公司提交/文档发布协调锁，核对各文档片 wanted_head=published_head，绑定此刻数据库 head 与清单 set_id，建立 SQLite 一致快照。current.json 和一起打包的 README 等可变文件须当场复制到本任务 capture 根；不能只租用原路径后放锁，因为下一次发布会替换路径里的字节。内容地址化分片及固定内容原件可从 company 根取得，并租用其精确文件集合。然后释放协调锁并打包。关账等不改变最终事实的提交不必改文档，不能错误要求文档序号数值永远等于数据库全局序号。新业务可继续；租约保证本次需要的不可变文件在复制中不被清理。包完成前核对每项摘要、结构、公司身份、关系和平衡，失败不替换现有有效包。

包内包含 format/company/database 标识、结构合同、数据库快照、完整标准文档清单及必要来源、相对路径/大小/摘要清单。禁止绝对路径、父目录跳转、符号链接越界或不明额外文件。restore/rebuild 不在源公司库建文件任务；离线 check/run 从明确包或标准清单验证到独立新目录，再显式注册，不覆盖已有路径。先校验包内原字节，再对新目标重定位根、清空 read_scope_head/read_component/read_item/file_task 并重建派生读取；不沿旧路径继续导出、备份或下载。备份恢复保留其正式采用及冲正；最终文档简化重建重新计算，不比对旧错误凭证数和编号。

备份 pending/running 的捕获文件引用也受当前计划保护。进程重启先从计划恢复引用租约、核对捕获集，再开放清理；捕获集无法恢复时标 failed，不能换抓新状态却沿用原 scope_head。离线命令中断留下的暂存仅在验证属于该明确目标后处理，不因此建设永久恢复日志。

## 事务末尾必须核对的内容

只核对本单及其影响范围，不每次扫描整个公司：事实 owner 与头一致、完整 Schema 合法、所有显式引用成立、结果槽和公开资源唯一、子结果完整替换、义务/成本容量成立、所有正式凭证已 sealed 且平衡、posting_period 未关闭、文档/读取目标同步推进。

DDL 以触发器阻止冻结结果及其子表改写，并在凭证 sealed 时校验平衡。SQLite 没有“任意事务提交时检查所有凭证”的通用触发器，因此提交入口还必须拒绝未 sealed 的凭证；不能把 SQL 中有一条平衡触发器就当作原子业务验证已经完成。

索引应在合成规模与真实查询计划中验证。出现新查询需求时，先检查公开批量结果及范围是否合适，再决定所属模块索引；不能为提速直接跨读其他模块私表，或让所有消费者各存一份正式金额。
