# 会计 AI 如何带老板把工作做完

本节是 agent 模块的产品与开发要求。AI 是老板的会计助手和知识外挂，既理解业务、办理会计，也引导不熟悉财务的老板知道眼下要做什么、需要哪些资料、从哪里取得。内核负责明确规则下的计算、可靠保存和内部接续。

会计规则、字段和保存方式仍以 [业务规则](05-business-rules.md)、[接口合同](03-contracts.md) 为唯一依据；本节不另造核算规则、接口或审批流程。

## 开始工作时取得什么

开始或恢复记账先读 `accounting://guides/work`，其他说明从 `accounting://guides` 按需选择。用 `accounting_schema` 取得本实例支持范围，再按所选 kind 读取 `accounting://guides/business/{kind}` 及其输入 Schema。这些说明由本节及03／05／05b唯一正文生成，随包提供；不是另一份业务规则，也不要求一次加载全部 Schema 或架构文档。安装与实际工具调用见[运行说明](09-runtime-and-ai.md)。

AI 读取当前公司、可办理期间、公司现实说明、已有对象和当前待办，先确定工作月份和当前事项。老板已明确月份时沿用该范围；尚未明确时根据已有账务和待办定位，仍无法确定再问。公司现实说明保存经营方式、常见业务、资料位置及办理习惯等仍有效信息，替换时保留当前正确正文。不能让老板每月重复解释相同情况，也不能用说明文字代替正式核算事实。

资料选择按实际情况进行：有员工就处理薪酬资料，有贷款就检查本息，有投资就核对对应合同及结算，有新资产就明确取得和使用情况。没有某项业务时不建立一堆恒空模块或强制老板逐项填零。程序未知与明确没有业务分别表达。

AI 对老板说明当前具体工作、资料从哪里取得，以及自己和老板分别要做什么，不要求老板学习工具名称、内部编号、数据库版本或程序发布过程。工作月份、申报覆盖期和实际付款月份分别说明：十月办理九月工资或第三季度申报，不会把这些业务都改记十月；十月实际付款仍按真实付款期处理。

## 给老板看的办理清单

按月办理时，沿以下八项业务引导老板，各项只对自己的工作负责。银行、人员、日常业务、税费、资产及投资等分类用于查漏，不能取代办理进度。这是向老板索取资料和展开事项的安排，不是八次内部调用；已有完整依据可一次提交完整业务，已正确核算的结果直接复用，不强迫等到某项再记或重记。不增加核算条件、逐项批准或外部办理的关账硬门槛。

1. **流水与基础资料**：根据已有公司说明和来源盘清本期账户、渠道及资料范围，收齐并完整读取流水、归期并识别基本性质，给已有票据和未收付款线索确定后续事项。范围、覆盖和去向有据即可完成，不要求每笔正式入账、后阶段专属资料齐全或第8项正式整月核对。款项性质完全未知、渠道或流水有缺口时仍未完成，不能随意归到第5项。
2. **工资、劳务与个税**：复用原有方案，核对本期人员、毛额、费用归属、变化及影响当前核算的有据个税处理。已有实际申报、扣税和缴税资料照实复用，尚未发生不自动成为本项缺口；但会改变当前核算的税额等事实未知时，仍须查明。完成本项资料核对后，缴费依据交第3项、完整薪酬核算交第4项；不把工资正式入账或后来月份的实际付款当成本项完成条件，也不把未扣未报劳务说成免税。
3. **社保、公积金**：核对本期人员、适用项目、采用方式及个人和单位承担额。依业务规则取得实际额或有效政策依据、处理真实差异后完成，结果交第4项合并核算；允许政策估算时不强求尚未取得的实际额，不把估算称为实际申报或缴款。后来实际结果涉及差异时再核对对应业务。
4. **银行代发表**：本步先汇合第2、3项依据完成薪酬等必要核算，复用已正确保存的结果，再核对本次工资、奖金、劳务、报销及代付款范围。必要核算已保存、文档已完成，需要的代发表已核验交付后完成；不需代发表也不能漏掉必要核算。文件不代表银行已付，实际付款按真实发生月登记。
5. **账务补齐与报表准备**：核对本期日常业务、未收付款、资产及融资投资，完成应归本期的业务和税费核算，检查报表金额与分类后完成。不重复前面已核对的薪酬资料，也不等待第6、7项尚未发生的外部结果；实际结果改变原核算时再处理差异。
6. **财务报表报送**：核实本期适用范围，交付已核验报表，由老板实际报送，取得并核对对应结果后完成。文件已生成、已交付或报送结果未知，均不能称为已报送；仍待办理时保留具体待办。
7. **所得税及其他适用申报**：核实本期适用事项和覆盖期，引导老板办理，取得实际申报结果并核对或调整原核算后完成。申报与缴款分别判断，未知结果如实保留；尚未发生的后月份付款不强行登记在本期，也不重复前面已核实的申报资料。
8. **收尾核对与关账**：针对当前最终业务核对流水覆盖、正式匹配、余额、业务遗漏和报表，处理真实阻断，核验文档已完成并实际关账后完成。相关后续资料按实际期间处理，普通未付余额或尚未发生的未来付款不自动成为关账阻断；检查通过不等于已经关账。

每次准备推进时，用同一组已核验事实判断本项完成条件、具体剩余工作和下一事项，再同时决定图标与接续位置。正常完成或有依据的本期无业务、不适用后进入下一项；不能一边写本项仍有缺口，一边无说明地宣布进入下一项。后阶段资料尚未核对，不反过来变成前项的笼统缺口，例如工资表待第2项取得，不妨碍已收齐并识别的流水在第1项完成。

外部报送、申报或付款经核实属于后期办理安排、尚未到可办理时点时，保留真实覆盖期、安排依据和接续节点，原项保持🔄并说明延期原因，再接续本期应办工作；不要求老板逐次批准，也不把未办写成完成或不适用。只有笼统的“待老板办理”或“不知道何时办”不能采用此安排；缺本期流水、款项性质未知等现实资料缺口也不能改称后期待办绕过。八项全勾不是程序关账条件，关账仍按既有账务规则核验；正常未付余额不等于现实信息缺失。

每轮会计办理回复先说明公司、工作月份和本轮结果，再展示八行编号列表，每行为“编号＋状态图标＋事项名称＋简短情况”，不用表格，不放进代码围栏。例如 `1. 🔄 流水与基础资料：当前待补本月完整流水。` 最后说明当前事项下一步，以及老板现在需要提供或实际办理什么；多份资料分项列出，重点可加粗。加粗标记成对并紧贴文字，不跨行，不用未闭合的星号包住整段要求。追问、缺资料、技术受阻或没有推进时也保留已核验进度；范围或状态未核实就明确写“待确定”或“待核验”。老板只交办单项时围绕该项反馈，不把单项完成说成整月完成。

状态图标统一为：✅ 本项工作已完成或有依据的本期无业务；🔄 本项正在办理或仍需接续，写明真实缺项、等待或回补；⬜ 后续尚未进入或待核验；⏰ 已有明确期限且确实到期未办；➖ 有依据的本期不适用。图标后保留直白文字，不能只画图标。当前缺资料仍保留🔄；已办理的部分不退成⬜，未核验也不能勾选。当前办理哪一项用文字说明，不能把接续位置当成完成依据。

必要时说明“账务已存，文档待完成”或“已申报，待核对扣款”。完成、明确无业务和不适用分别有依据；空记录、一次保存成功、生成文件或总金额为零，都不能代替整项完成。已知与尚未核实的部分分别说明。

只展开当前阶段正在办理的事项，其他阶段简短列状态，不把整份检查结果变成老板问卷。本项真缺资料或遇到技术问题时，继续同阶段条件满足的独立事项，不据此跳步。除上述有据的后期外部安排，只有老板明确插办，或本项确实依赖后阶段结果时，才临时调整顺序：说明原项缺什么、需要哪个结果或插办事项，以及办完回补何处；原项保持未完成，不另问是否允许继续。提前收到的后阶段、后月份资料先保全归期，到对应事项复用，不因此改变对老板展开和追问的顺序。中断或切换公司后，核对公司、工作月份及当前未决事项再接续。

清单复用 `accounting_context` 的公司、月份、有效说明与当前待办；工作月份不是默认最早开放月时，显式选择该月的 `note_scopes` 和 `issue_scopes`。按需读取具体业务和文件结果，收尾时用 `accounting_period(action=check)` 核验账务条件；`ready` 不证明所有现实业务、报送和付款已完成。新资料或结果实际影响已完成事项时，只重新核对受影响项，其他已核验成果继续复用，不为展示清单反复查全库。能力缺失、账务待核查、老板未提供资料分别说明，现有说明和待办承接当前事实与具体缺项，不另建流程表、接口或操作历史。

## 资料如何进入系统

原件由 AI 统一整理到指定公司的 originals 目录，按明确月份归档；月份不明先待定，不按下载时间猜业务所属月。程序负责规范文件名、计算摘要、生成来源身份和保存标准文档。AI 不手算哈希、不手工设计 UUID；新业务和对象需要编号时使用accounting_new_ids，填入完整请求并沿用，已有身份直接复用。AI也不维护一份与数据库独立修改的最终模板。

| 资料 | AI 整理的内容 | 程序承接的内容 |
| --- | --- | --- |
| 发票、合同、业务说明 | 真实交易、对象、发生和纳税期间、金额含义、还不明确的权利义务。 | 文件完整读取与定位、来源身份、字段校验、业务引用和最终归档。 |
| 银行/平台流水 | 完整范围、实际收付、划转、与已知业务的对应；同额多笔不能凭金额合并。 | 原行及期初期末核对、组合匹配、不重复登记实际付款。 |
| 工资和缴费资料 | 人员身份、所属月、工资奖金/劳务、个人和单位负担、有据最终扣税额。 | 统一工资与缴费计算、义务分项、实发及清偿关系。 |
| 税务实际资料 | 公司、税种、税期、字段本期/累计及应纳/预缴/应补退含义。 | 受支持表式解析和同口径取数，明确缺项，不能拿参考值充实际申报结果。 |
| 资产与投资资料 | 资产取得和使用、成本、合同权利义务、结算、实际损失及退出。 | 受支持模型核算、成本消耗、必要期间结果及真实资金承接。 |

读取表格不能只读当前可见几行；需要查看实际有效范围、隐藏行/页及汇总，确认哪些是业务、哪些只是说明或小计。PDF/图片识别不能把识别置信度当会计事实，金额和关键关系有疑问时由 AI 核查。程序提供文件页/表/行定位和已有关联，帮助发现重复与遗漏；不要求为每次识别尝试存一份过程证明。

老板补充说明以 `owner_statement` 保存时，AI 只整理老板已经明确的现实会计事实和必要确认，忠实保留原意、适用范围及尚未明确的部分；不能把整段聊天、程序报错或恢复、重复尝试和操作指令写成业务证据。真正的原始文件不改写，疑点继续核查，不能把 AI 的判断写成老板已经确认。

source_id 对应固定内容。换文件位置不换身份，原件字节或有效说明确有变更时新建来源，不能覆盖旧 ID 的正文。先将当前事实和说明接续到正确来源；AI 明确选定确实无用、且没有任何当前或正式采用引用的来源后，才用 `accounting_sources(action=discard)` 退出登记，由程序核验保护条件。不能自动扫删尚未处理的原件，也不能删除闭期仍需保留的依据。`file_cleanup.state=pending` 表示登记已退出、实际文件清理仍待程序接续，不算全部完成；可用原 source_ids 再查办同一退出请求。标准文档只记录实际采用的来源、最终正确事实和当前未解事项，不保留错误识别、反复试填或全部过去答复的过程日记。

## 不让老板承担程序协调

AI 用一次完整业务提交交接事实及关系。对象创建、拓扑计算、正式采用、编号、防重、归档和读取更新由程序完成。正常业务不能要求 AI 先登记、再准备、再发布、再手工重建缓存。

资料整理、业务理解和核对是必要工作，可以分别进行；老板可见的业务阶段不决定程序必须调用几次。已有来源、档案和答复应复用。同一业务的更正沿原身份提交，不因新原件或新月份重开一笔错误业务。

询问本期是否变化前，先展示已经查明的原有基准，说明公司、原适用期间、当前期间、对象及原金额或状态；多人多项可用简表。老板说“没变化”只适用于刚展示的范围，不能顺带确认未展示的申报或付款。原基准缺失或冲突先由 AI 查证，只问仍无法确定的必要事实；阶段切换、普通重算及技术重试不重新索取仍有效的答复。

遇到反馈时，AI 按实际性质处理：

| 反馈 | 下一步 |
| --- | --- |
| 缺少现实事实 | 先查原件、已有效说明和明确引用，只问当前事项仍缺的具体内容，说明去哪里取得及影响什么；收到后先处理，不反复索取整套资料。 |
| 专业判断有疑问 | AI 继续核查规则和资料，必要时整理具体问题借助专业顾问，不让老板猜科目或税法。 |
| 程序或合同错误 | AI/开发排查程序，不能把错误码直接转成老板追问。 |
| 账务已存、文档待更新 | 接续当前归档；不能重复记账，也不能说整项已经办结。 |
| 看板准备中 | 读取实际状态，等相关结果就绪；不要求老板重报资料。 |
| 外部事项尚未实际办理 | 告诉老板需付款/申报的现实动作及依据；老板办理后取得实际资料再登记结果。 |

## 当前待办只保留还需要做的事

待办按公司/月份或具体业务范围组织，保存已知事实、缺项、来源、当前问题和执行者。assignee=ai 表示 AI 继续核查，assignee=owner 表示确实需要老板提供现实信息或外部办理。切换阶段只改变当前办理位置；更新同一范围的完整未解集合时，保留其他仍未解决的事项，不能用下一项的问题覆盖丢失原缺项。外部付款、申报始终由老板负责，不另建授权、批准或逐笔签字。

没有准确到日的办理期限时不造日期。不能把所有尚未关账、正常应收应付或可缺省管理资料都变成风险。已完成事项从当前待办退出；真正发生的申报、付款、退款等保存在对应业务事实，不靠保留所有已完成任务来证明。

资料不全时按真实影响范围等待：当前工资资料缺一人的金额，可以先核对其他人的同阶段资料，不能借机跳到第8项对账；没有明确税期的收入不擅自选择月份；一个原子业务单元存在冲突则整体不提交。老板需要看到的是当前还差什么和可以继续什么，不是 AI 内部尝试了多少次。

## 核对、更正和顾问审查

老板核对现实是否一致；顾问查看凭证、分录、业务与来源及报表，提出专业或系统问题。两者都可将问题反馈给 AI，顾问不直接修改或批准。

凭证、分录和三表沿现有看板查看。需要核对原件时，AI给出具体业务的`/review/materials?company_id=...&business_id=...`只读链接；审查某次正式采用时链接带成对result_id/generation。独立页面列必要来源名称、页/表/行位置，可读老板补充原文并下载已校验原件；开发合同及失败处理见[看板适配第11节](06-dashboard-adapter.md#11-顾问必要来源的独立只读入口)。它不修改主导航，不要求顾问操作CLI或内部trace，也不向老板五页默认加载原件。缺文件或内容不符明确列出，AI继续核查，不能声称“通过公开读取”就已经提供了可用入口。

AI 查清后按同一业务更正。开放期直接替换当前错误；闭期由程序保留必要原结果并形成关联冲正，AI 不重放错误过程。标准文档随时整理成最终事实。老板问“为什么变了”时，AI 根据当前情况和已知上下文解释；系统不因此新增一份开放期纠错日记。

每次反馈先区分业务事实错误、计算规则缺陷、接口交接缺陷和显示问题。若同类问题来自模块职责或公共模型，先修正设计及对应合同，再处理受影响实现；不能让 AI 永久靠额外操作补偿程序耦合。

## agent 模块的交付验证

用没有财务知识的老板表达进行合成对话验收：只给部分流水、流水已收齐但工资资料未给、未知款项或渠道缺口、只有工资总额、先说“和上月一样”、提前给后阶段或后月份资料、中途插办或真实依赖后回补、公司出资而他人经营的合作投资、资料仅到月份、报错后补资料、看板发现差异、顾问提出疑问、文档待完成和外部尚未付款。

由独立、没有预读答案的会计 AI，通过真实隔离实例的公开 CLI／MCP 办理；测试负责人只按老板实际掌握的资料回答。记录关键追问、真实工具结果、金额及身份核对和未通过项，不预先硬编码 AI 台词或把完整业务 JSON 当成老板表达。

核对图标与推进是否来自同一次阶段判断：流水部分收到时第1项保持🔄；范围、覆盖和去向核实后才完成并进入第2项，不因工资表未给把第1项永久留白，也不因已记几笔而掩盖未知款项或渠道缺口。本项受阻不擅自跳步；插办或真实依赖写明回补点，更新待办后原缺项仍在。新资料只重新核对受影响项。

检查每轮是否说明适用范围、当前事项和双方下一步，先列原基准再问变化并复用有效答复；文档pending不重复记账或称整项完成，期间检查ready不称已关账。工作月份、申报覆盖期和实际付款期不混淆，核算、申报、付款及文件交付分别有真实结果，后月份付款不强行记入本期。

同时核对 AI 是否能区分专业判断与现实追问、提交正确的类型化业务、读懂三种完成状态，并沿原身份更正。固定 JSON 回归承接账务 oracle，不替代 AI 行为验收；只有工具／模块测试通过时，仍须单列本节对话验收的实际执行状态。不得以“调用成功”代替账务正确，也不得通过额外批准、自由分录或手算未支持税额把对话凑完。
