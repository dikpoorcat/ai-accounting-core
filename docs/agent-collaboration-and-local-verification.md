# 多 Agent 协作与本地质量验证手册

## 1. 适用范围

本文沉淀工资模块多轮开发与验收中的可复用经验。它约束本地、本人拥有的软件项目质量检查，不授权访问外部目标、获取凭据、操作第三方数据或生成外部利用自动化。

建议在涉及数据库完整性、并发或错误边界的任务开头使用以下范围声明：

```text
这是对我本人拥有的本地财务软件项目进行防御性质量审计。
仅验证数据库约束、并发一致性、数据不可变性和异常信息脱敏；
不连接外部目标，不获取凭据，不生成漏洞利用或攻击自动化代码。
目标是发现实现缺陷、编写负向回归并完成修复。
```

这段声明用于准确描述任务，并不能改变平台对请求是否合规的判断。

## 2. 网络安全自动审查的处理经验

OpenAI 的自动安全检查可能在请求执行前增加检查、延迟或阻止响应。看到提示本身并不代表账号或请求已经被认定违规。对于被误判的本地防御性工作，应保持事实范围清晰、只携带完成当前任务所需的上下文，并聚焦防御结果。[OpenAI 官方说明](https://help.openai.com/en/articles/20001326-additional-safety-checks-for-biological-and-cybersecurity-requests-in-api-and-codex)

使用准确的工程措辞：

- “验证数据库约束能否拒绝非法状态”，而不是泛化描述外部系统行为。
- “检查是否存在不变量失效路径”。
- “构造边界或负向回归用例”。
- “验证异常信息已经脱敏”。
- 明确数据库、文件和进程均属于本地授权项目，不访问默认库之外的任何外部目标。

如果同一长会话连续触发检查，新建干净任务，只交接必要的文件、问题编号、预期结果和授权范围。不要为了规避检查而改变任务实质；措辞调整不能让原本不允许的请求变成允许。

合规任务仍反复被阻止时：

1. 使用产品中的差评入口反馈。
2. 联系 OpenAI 支持，提供准确提示、产品/模型、发生时间与时区、请求 ID 和经过脱敏的最小任务描述。
3. 不在反馈中提交密码、验证码、密钥、真实财务数据或商业敏感内容。

## 3. 多 Agent 分工

总设计与验收 Agent 负责需求裁决、稳定契约、文档、跨模块审计和最终门禁；执行 Agent 负责边界明确的实现包及其单元测试。不要把实现者报告的“全部通过”直接视为验收结论。

可以并行的工作应显式拆分：

- 不同文件且接口已经冻结的实现包可以并行。
- 只读代码审查、迁移审查、MCP 契约审查和测试矩阵设计可以并行。
- 同一高冲突文件，如 `models.py`、`service.py`、`mcp_server.py` 或同一迁移，只允许一个写入负责人；其他 Agent 在该阶段只读。
- 每个工作包都要写清问题编号、允许修改的文件、必须保持的稳定错误码、最低测试和禁止扩大范围的事项。

所有 Agent 共享同一工作区，文件修改会即时可见。测试者应在写入负责人宣布检查点后再固定文件哈希或开始长测试；若测试期间文件变化，结果作废并重新执行。任何 Agent 都不得暂存、回滚、清理或提交其他 Agent 的工作。

## 4. 独立验收方法

功能路径通过只证明正常输入有效，财务内核还必须证明非法状态在最终提交点被拒绝。总验收者应独立补充：

- 直接数据库负向回归，验证服务预检遗漏时数据库约束仍生效。
- 两连接并发回归，验证幂等、编号、累计税态和开放项守恒。
- 正常冲正回归，证明保护规则不会阻止唯一合法的更正路径。
- 真实 STDIO 生命周期，写入由 MCP 子进程完成，断言由父进程新 Session 读取，避免同事务自证。
- 历史迁移回归，使用真实旧版本 Schema 升级，不用 head 模型预先创建新列或约束。

失败报告只保留最小业务事实、预期稳定错误码、实际结果和精确文件位置。先区分夹具错误、测试环境错误和产品缺陷，再决定是否修改实现。

## 5. PostgreSQL 与测试进程纪律

- 迁移、升级污染预检、降级和提交点负向回归只使用唯一命名的临时 PostgreSQL 17 容器、端口和卷。
- 每条 Alembic 命令显式传入临时 `DATABASE_URL`；不要依赖 `alembic.ini` 的默认连接。
- 默认 Compose `finance` 数据库视为用户数据，只允许未经修改的只读版本核对，除非用户明确授权迁移。
- 清理容器或卷前解析并核对精确名称，不使用宽泛匹配。
- 收口时按“非 PostgreSQL → PostgreSQL → 完整覆盖率 → Ruff/依赖/编译/diff”顺序执行。
- 避免多个覆盖率进程同时写 `.coverage`；只终止自己启动并记录 PID 的进程，不做广泛进程清理。

迁移 revision 名称必须适配 `alembic_version.version_num` 的实际长度；本项目使用不超过 32 个字符的 revision ID。迁移链、`alembic check`、真实历史升级和安全降级必须作为一个整体验收。

## 6. 文档与交付

任务书使用稳定编号，例如 `R7-001`，并为每项记录：业务不变量、实现文件、数据库提交点、单元测试、集成测试、残余风险和最终结论。旧轮任务书保留为历史证据，但新 Agent 默认只读取最新规范和当前未关闭项。

提交前依次检查：

1. 当前分支、remote、upstream、ahead/behind 和远端默认分支。
2. 工作区全部差异、未跟踪文件、凭据、大文件和运行产物。
3. 精确暂存范围以及暂存后的 diff、测试和提交信息。
4. 推送后本地 `HEAD`、上游哈希和 GitHub 远端哈希完全一致。

提交信息遵循仓库 `AGENTS.md` 的中文标题、空行和编号正文格式。最终报告必须区分“已经验证”“尚未执行”和“需要用户授权”的事项，不能把本地通过写成远端已部署。
