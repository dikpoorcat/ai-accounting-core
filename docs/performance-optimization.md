# 看板性能优化方法与审查规范

本文供开发会话审查和优化老板看板使用。目标是保持正确的业务结果和已定用法，减少当前路径实际执行的读取、核验、组装和渲染工作。500ms是指定规模下的整页热刷新目标，不是所有内核命令的统一时限。

## 使用指令

在本仓库会话中使用：

> **看板优化**
>
> **看板优化：最近5个提交**

收到指令后先读本文，再读 [FRONTEND.md](../FRONTEND.md) 与范围内的实际代码、调用方和历史证据。未指定范围时，先根据当前任务确定范围；无法确定时只询问审查范围。用户限定“只审查”时只交付问题和证据；允许修复时，技术缺陷自行决定，改变业务用法或体验的取舍交给用户。

指令不自动授权真实业务写入、换库、重建大型样本、重启现有服务或 Git 提交。当前资料与服务按本次授权处理；本机 Python 使用仓库 `.tmp-kernel-venv`。测试范围按改动风险确定，不机械重跑历史阶段的全部验收。

本文维护可复用方法；[第9阶段记录](kernel-refactor-stages/09-performance-and-release.md)与各轮记录维护实际结果。历史数字只属于记录中的源码、样本、环境和执行窗口，不作为当前代码已经达标的证明。

## 一、实际有效的方法和经验

### 1．从页面消费追到整条读取链

触发条件：页面不再显示某项信息，却仍请求、生成或预加载它；只需要摘要，却调用整个业务页或完整检查。

- 沿组件、请求、命令、查询、组装、响应合同，检查哪些工作仅服务该信息；同时查专用缓存的读取、写入、预加载和失效清理。展示与专用读取一起退出。
- 同一个公共函数仍服务 AI、工作流、关账或完整核验时，保留其业务职责，为不同消费者选择所需内容。不能先构造全部技术数据，再由页面丢弃。
- 单任务进度按任务主键读取必要状态，不为轮询展开来源或读取文件。下载入口继续独立完整核验产物。
- 先确认该路径是否参与默认刷新。只在面板打开后执行的读取退出，不能宣称默认刷新因此明显变快。

适用例子：只需要资金金额的简报不组装资金页对账展示；两关闭月窄读取的返回值字节28,784→5,266、结果解码6→0。移除文件进度后，报表保留单任务状态和下载核验。证据见[八组优化](kernel-refactor-stages/09-performance-and-release.md#实际完成的八组优化)及[任务面板移除](kernel-refactor-stages/09-performance-results/jobs-panel-removal-20261006.md)。

### 2．限定实际查询范围，检查索引驱动

触发条件：先取全部数据再由 Python 筛选；循环内逐条查询；SQL条件精确但扫描仍大；为少量分类键扫描全部业务历史。

- 用实际期间、账户、对象、事实身份及精确采用范围定位；没有期间筛选就不生成假期间条件。公共批量读取接通全部调用方，避免只修一个页面。
- 检查执行计划、SQLite VM步数、返回行与装载量。`SEARCH`仍可能扫描很大的范围；小型固定集合的`SCAN`也不必强改。
- 保留合适的稀疏子表驱动；不要为了减少目录键，改成扫描大量无关事实。历史旧修订、缺失来源和异常采用仍进入必要核验。
- 当期冻结采用由不可变关账内容及精确采用关系确定，不能用当前修订代替。目录用于定位和可修复读取，目录命中本身不能补造采用结论。

历史例子：直接采用索引使主120月资产路径VM下降11.5%，返回行和解码不变；报表命名头处理的VM266,763→222,267。最近未来分类键修复虽减少目录输入，仍增加部分SQL工作，见[第9阶段](kernel-refactor-stages/09-performance-and-release.md#实际完成的八组优化)及[集中修复](kernel-refactor-stages/09-performance-results/recent-five-commit-performance-20261006.md)。不能由这些例子推导“加索引总有效”或“子表扫描已消失”。

### 3．分开完整汇总、定位和分页详情

触发条件：只列身份或算总数，却装载完整结果、人员历史、资产批次上游；请求小页但实际先组装全量明细。

- 完整金额和计数覆盖完整业务范围，与默认20条明细分开。优先对适用的已核贡献做SQL聚合；未知仍为未知，不能只汇总已加载页或把未知当零。
- 对完整范围先筛选，再定位`limit + 1`候选，批量装载本页必要事实、结果和依据；关系读取按必要键批量执行。确实需要扫描的状态筛选如实记录成本。
- 身份枚举、结果元数据选择和完整正文装载分别处理。精确直跳直接读取目标，不串接所有分页找对象。布尔存在性先复用本页已核内容能够证明的肯定结果，只有未确定主体继续完整查询；不由类型或金额猜否定结果。存在性阶段少读正文不代表整个入口少读正文，后续完整金额路径的必要装载须分别记录。
- 汇总仍保留实际入账期、更正、冲正、独立期初、无凭证结果及资产成员语义。员工未付不能用本月应付减本月付款替代；不同对象的应收与应付不能互相抵消。

当前读取边界见[看板读取合同](bounded-dashboard-queries.md)。资产负债和用工摘要恢复时复用窄摘要而非整个资金、员工和资产页，见[恢复记录](kernel-refactor-stages/09-performance-results/summary-restore-20261006.md)。

### 4．同一快照内复用成功核验，按精确键查缺

触发条件：同一请求重复核验相同来源或依赖；已经有缓存，却每次遍历全部缓存月份或集合查找。

- 先证明实际调用核验了同一批内容与相同范围，再复用。按来源身份、摘要、核验范围及读取快照区分成功结果；整批成功后才发布复用结果，失败不缓存。
- 缓存查找直接按需要的键查缺；批量取缺失项，复用同次已核金额、精确定位和基准。不能一边缓存，一边反复遍历已有全集。
- 业务证明和成功数据不跨请求快照缓存。页面已加载列表、上下文pending promise和受保护连接的SQL准备程序，与后端业务证明缓存分开判断；它们仍遵守各自失效边界。
- 正文摘要、独立不可变封签、结构、父依赖和来源绑定承担不同职责，不能因为函数相似就删除其中一项。完整核验与页面局部核验也不能混用范围。

历史精确key与唯一目标哈希复用使描述遍历119,186→59,847、目标哈希12,119→239，见[第9阶段](kernel-refactor-stages/09-performance-and-release.md#实际完成的八组优化)。这些数字不证明所有核验都可以合并。

### 5．减少重复汇总、解码、编码和临时投影

触发条件：已核金额再次展开结果计算；JSON在Python、SQLite和输出之间反复转换；构造未消费的事件字典、分页序号或展示统计。

- 共同金额汇总与领域明细组装分开，复用同快照已有资金效果、期末金额和精确基准；只处理真正变化的键。
- 公共职责确实相同时集中修复；领域规则不同就分别处理，不为统一代码增加通用业务框架。
- 缩小单列或解码次数前，检查是否增加其他扫描、临时对象和返回字节。测完整入口，不能只测一个转换函数。
- 异常形状、未知、非受保护连接和固定历史规则保留必要退路；不能把原可确定金额改成未知来取得收益。

资金摘要退出JSON→SQLite往返及未用事件组装，报表复用期末和基准，见[第9阶段](kernel-refactor-stages/09-performance-and-release.md#实际完成的八组优化)。贡献复用的失败反例见第三部分。

### 6．收敛内部重复响应校验和序列化

触发条件：服务、HTTP适配和页面内部对同一明确类型载荷重复校验、复制或序列化。

- 看板受控服务读取边界统一校验一次，立即按同一模型序列化；HTTP可以直接发送已生成bytes。客户端不能提交“已校验”标记，独立未校验入口仍严格校验。
- 前端继续使用后端模型生成的类型和Ajv校验器，校验最终请求URL与响应的公司、期间、对象、筛选和快照关联。类型断言不能代替校验。
- CLI/MCP使用原生整数分；HTTP使用规范的int64整数分字符串，前端用`BigInt`展示。省略、null、未知、零、版本和错误语义保留；不恢复字段名猜金额或重复分页载荷。
- 按合同拆分校验模块、按需加载附属组件时，比较初始、各页及总构建体积，防止重复依赖膨胀。

历史热态序列化诊断约0.1–0.3ms，见[第9阶段](kernel-refactor-stages/09-performance-and-release.md#实际完成的八组优化)。这是减少重复处理的做法，不能写成当时500ms瓶颈的主要原因。

### 7．局部刷新、增量续页和页面内精确索引

触发条件：展示切换重读整页；上下文变化触发相同选择重复请求；每续20条复制累计数组或整个凭证Map；悬停已加载凭证又请求简报。

- 同公司期间共享已加载上下文或pending promise；需要刷新上下文时，与主请求并行，确认两者及当前选择有效后展示。watcher比较实际选择，避免无关响应对象变化造成重复请求。
- 筛选、展示切换和分页只更新对应区域；同范围刷新可保留隐藏挂载组件，不能把旧结果当新结果。公司、期间、快照或错误失效时清空重读。
- 取消请求之外，仍核对generation、选择与当前请求身份；成功、catch和finally都防止旧响应覆盖新选择，包括A→B→A。
- 续页通过范围和快照校验后，重新取得当前集合，只追加本页并更新分页信息。凭证按精确版本放入稳定响应式Map，只加入新增版本；无关续页不写索引、不清浮窗。首屏或范围失效时重建。
- 已加载凭证直接展开，复用首屏及业务页分录，不请求、预取全月凭证或推进独立凭证分页。浮窗只渲染当前一项，关闭态先判空再读取累计集合；后台续页不禁用已加载条目的局部操作，主刷新及范围失效守卫保留。
- 保留选中模块自动续页、失败重试及用户允许的已展开详情后台续读。简报的本月发生和应收应付按服务端完整分类组数判断当前分类是否读齐，读齐后停止根集合续页，切到尚缺组的分类继续原游标；不能把未选分类续读加入当前分类的刷新等待链路。不为已展开详情新增模块切换或刷新暂停门禁，页面模块原有的切走取消规则保留。当前默认概览通常为两个请求，不能要求所有展开状态也固定两个请求。

业务与交互以[FRONTEND.md](../FRONTEND.md)为准；实际证据见[浮窗](kernel-refactor-stages/09-performance-results/activity-voucher-popover-20261006.md)、[自动续页](kernel-refactor-stages/09-performance-results/auto-pages-20261006.md)和[增量修复](kernel-refactor-stages/09-performance-results/recent-five-commit-performance-20261006.md)。增量追加减少旧记录复制，但computed、筛选和vnode遍历仍可能随累计列表增长。

### 8．检查临时对象与异步生命周期

触发条件：缓存容器查找层层展开；基准反复遍历；闭包捕获形成自引用；请求结束后对象、监听器、定时器或定位任务仍存活。

- 保持原优先序整理嵌套容器；同快照基准只遍历一次。检查递归闭包与容器关系，用合适的显式结构消除自引用。
- 用业务等价和请求结束后的对象释放验证收益；前端结合实际组件挂载、隐藏、卸载、取消与迟到回调检查。用户明确允许继续的后台任务不能直接列为遗留错误。
- 不靠关闭GC或强制回收获得计时。减少数组复制后，仍单独测实际渲染、筛选和分组；不能宣称整个页面工作已线性化。展示模式只渲染当前的无状态摘要，但保留承担原生展开状态的详情节点；用真实Vue渲染工作量及浏览器节点、焦点验证，不以脚本模式变量代替显示结果。

历史ChainMap和闭包生命周期修正保留业务输出及释放测试，见[第9阶段](kernel-refactor-stages/09-performance-and-release.md#实际完成的八组优化)。旧慢样本是否由GC引起未获证明，不能补写成已知根因。

## 二、统一审查流程

按组推进：**确定范围和基线 → 归类根因 → 全局排查 → 列出处理决定 → 集中修改 → 定向验证 → 固定代码后统一验证 → 记录结果。**

1. **确定范围和运行状态。** 明确提交或未提交改动、入口、公司期间范围、默认与已展开场景、前后端实际进程及已有证据。修改前保留可比较基线。先列不依赖真实资料写入的低成本检查。
2. **归类根因。** 写明触发条件和多余工作，如重复核验、无界筛选、逐条查询、扫描范围过大、仅需摘要却展开全文、缓存查找遍历全集、累计复制或重复刷新。不能只写“某函数慢”。
3. **全局排查再定范围。** 沿公共函数、调用链和同类实现，检查下表。代码相似只作为线索，用实际消费者、执行计划和工作量判断必要读取与重复读取、小集合筛选与无界筛选。
4. **集中修复同一根因。** 修改前列位置、调用方和处理决定；公共位置适合就共同修，领域不同就分别修并接通调用方。不要修第一个发现点后宣布整类问题解决。
5. **成组验证。** 修改期间使用必要定向测试尽早发现错误；相关修改收敛后固定代码，统一运行受影响回归、五页关联检查与必要测量。没有新修改、新失败或新风险证据，不重复同一大套。
6. **留下防退化和收口记录。** 用业务结果及真实工作量覆盖增长；报告净收益、剩余成本和未验证项。同类问题再次出现，先查以前排查范围和判断哪里遗漏，再补齐整组。

| 排查范围 | 要确认的内容 |
| --- | --- |
| 五页及共享上下文 | 上下文、主数字、默认明细、附属内容、核对摘要的实际读取边界、按需详情及刷新等待链路；无消费项是否仍生成 |
| 筛选、直跳、续页与浮窗 | 完整范围筛选、本页批量装载、增量追加、精确索引、重复请求、快照及迟到响应保护 |
| 公共读取调用方 | CLI、MCP、工作流、期间检查、关账、完整核验、修复、备份恢复及固定版本历史是否受影响 |
| 核验与缓存 | 各证明职责、成功范围、精确键查缺、失败处理和失效；有无未经证明的跨请求复用 |
| 生命周期和测试消费者 | 连接、容器、监听器、定时器、异步定位、真实Vue显示、当前后端合成响应及测试harness依赖 |

每组先填一张表并随结果直接更新：

| 触发条件／根因 | 位置与调用方 | 证据及必要性判断 | 处理决定／修复位置 | 验证结果与剩余成本 |
| --- | --- | --- | --- | --- |
| 明确是哪类重复或超范围工作 | 包括同类路径 | 实际调用、范围、执行计划、扫描／装载／解码 | 修复、保留，或等待业务用法决定 | 已验证范围、未解决、未验证 |

“未发现”仅描述本次排查结果；没有实际证据的地方写“未验证”，不能写“已排除”。

## 三、失败经验与判断边界

### 前提变化后重新判断实验价值

把以下三类分开维护：

- **不得采用的做法**：破坏信任链、削减必要核验、改写冻结历史、把未知改零或擅自删除已定业务功能。审查第24项等用户明确不重试的方案继续遵守，不因重新测速绕过决定。
- **当时没有净收益的实验**：记录源码、消费内容、调用链、数据分布、工作量、前后耗时及撤回原因。前提没变时不重复；看板精简、调用路径、分布或成本占比已变时，先说明哪些旧证据失去参考性，再做低成本对照决定是否值得重试。旧资金汇总窗口排序实验也按此规则判断，不能一概认定永远无收益。
- **尚未证实的猜测**：网络、GC、RSS、磁盘等线索先测，再决定；不能把推测写成根因，也不能把未验证写成无问题。

| 实际反例 | 应得出的结论与证据 |
| --- | --- |
| 贡献复用减少479次结果解码，却使简报VM868,000→1,290,300，返回值字节约翻倍，候选撤回 | 优化一个计数可能转移成本。核对完整读取，而非只看解码；见[历史归档](kernel-refactor-stages/09-performance-history.zip)，内含`09-performance-results/journal-contribution-withdrawal-20261004.md` |

## 四、验证与结果模板

### 工作量检查与低成本防退化

先用合成资料验证正确性和增长，再决定是否需要计时。针对修改选择指标，不为了凑齐表格增加昂贵插桩；没有测的指标明确留空并标注原因。

| 层次 | 建议记录 |
| --- | --- |
| 请求与SQL | 实际请求、SQL次数、执行计划、VM步数、扫描证据、返回行／值字节及临时排序或分组 |
| 来源与核验 | 事实／结果正文装载与解码、直接采用证明、目录键、摘要／描述遍历、哈希、资料解析及重复汇总 |
| 前端 | 请求关联、追加本页工作量、旧记录复制、Map写入、筛选／computed／实际渲染、组件及异步任务生命周期 |
| 资源与输出 | 构建初始／各页／总体积、Python分配峰值、进程RSS、请求结束后对象存活；各自写清测量窗口 |

SQL少不等于更快；VM步数不是磁盘I/O或耗时；返回值字节不是磁盘读取；Python分配峰值不是RSS；有限RSS观察不代表绝对峰值。全量摘要、历史清偿和闭期资料复核可能有必要增长，不一律要求固定成本。

防退化场景按根因选择：

- 增加无关对象、未来月份、历史月份或修订，确认本页没有无必要地扩大正文装载、上游解码或候选范围；保留冻结旧修订与异常来源检查。
- 使用100／200／400条分页响应，检查本页新增写入、旧集合复制和实际Vue显示；新增凭证精确版本只入索引一次，无关续页不清浮窗。测行为和工作量，不用SQL文本、私有函数名等实现细节充当正确性断言。
- 覆盖完整汇总、未知与零、期初、同／不同对象往来、开放期替换、闭期连续更正、无影响复核、无凭证与资产成员；以及首末页、筛选、精确直跳、快照失效、失败重试和公司／月份切换。
- 公共修改验证其受影响的CLI/MCP、关账、完整核验、修复、备份恢复及固定历史路径；不能把页面通过结果借给这些入口。
- 使用当前后端合成响应检验消费者，覆盖金额边界及严格合同。真实Vue测试验证浅响应式数组和Map；测试harness要提供新增依赖，每次模拟HTTP返回独立对象。

相关修改收敛后，按仓库实际命令统一运行受影响后端回归、前端测试、合同检查、类型检查、构建与改动范围静态检查。前端命令以[package.json](../frontend/package.json)为准，已有`contracts:check`、`test`、`type-check`及`build:release`；构建已包含合同与类型检查，不无故重复。检查不暗中生成合同或修改源码，不调用项目没有的检查命令。

### 前后计时与场景边界

修改前保存基线代码／构建和读取范围。前后使用可比较的数据库、公司、期间、分布、构建模式、授权及可见内容，记录实际执行代码的服务进程。Vite已更新不代表常驻Python进程已加载新实现；无法按授权重启现有服务时，可用隔离只读服务，但必须说明适配差异，不能把旧进程结果记成新代码通过。

纯计时不与建库、回归、构建、完整核验或插桩并行。记录环境和忙闲状态，分开执行工作量统计和耗时对照。局部候选尽量同库交替前后测量完整入口；整页比较保持相同场景，不将不同源码、窗口和分布差异归因于单项改法。

| 场景 | 完成边界 |
| --- | --- |
| 默认概览热刷新 | 点击“刷新数据”至上下文、主数字、默认20条及全部默认可见附属内容完成更新，并连续两帧稳定渲染 |
| 已选模块／已展开详情的刷新 | 保留既有可见状态，明确本次必须更新的内容及允许继续的后台续页；不人为收起内容取得更短耗时 |
| 筛选、直跳、详情首次展开与续页 | 对应区域实际完成显示及范围关联；与整页热刷新分列 |
| 自动续页全部读完 | 完整集合读取及显示完成；首屏完成不代表全部记录已读完 |
| 冷启动、首次打开、公司切换 | 单独保存样本，不混入热刷新结论 |

接口返回、首个文字出现或loading消失都不能代替整页终点。保留逐次有效样本、失败、超时、慢样本及实际退出状态；准备错误单独记录，不删掉已经开始计时的失败。报告样本数量、P50、P95、最大值和≥500ms数量，失败不算完成。沿用历史nearest-rank口径：30次时P50取排序第15项、P95取第29项；前后口径相同。

### 两级结论与历史证据

**低成本检查**使用小型合成业务／响应、工作量回归和已获授权的现有开发库只读对比。它证明本次业务行为、增长边界及已测场景；不要求每次重建10年大库，也不证明未测规模已经达标。若用户暂不做规模验收，记录“本次未做”，不设置重复的大库核验门禁。

**规模验收**仍为50人、每月1,000笔业务，12／48／120个月，包含独立业务与累计依赖，正常资料处置、开放与冻结月份及适用核对状态。正式前端构建、隔离常驻服务，五页各预热3次、测30次，验收样本必须全部成功且小于500ms；失败、超时和超线完整报告，不算通过。200人／每月5,000笔压力样本仅诊断，不能混入主规模承诺。当前合同是否draft与前端是否正式构建是两件事，性能验收不授权正式版冻结或换库。

完整样本的递增构造、边界复制、独立核验及五页烟雾检查使用[测试准备入口](dashboard-performance-test-preparation.md)。准备报告全部成功才标为`ready`；它不包含正式30次热刷新，也不继承历史达标结论。

历史[c063主规模](kernel-refactor-stages/09-performance-results/current-three-scale-browser-c063-20261005.md)450次全部<500ms、最大456.2ms；[独立三档](kernel-refactor-stages/09-performance-results/current-four-distribution-browser-c063-20261005.md)另450次全部<500ms，压力档150次中120次超线。当时测试副本有限复用了既有完整核验资格并重新核对适用条件，非重新完整核验或生产缓存；详见各原记录。最近同库30次对比和增量回归不能继承这些规模结论。
