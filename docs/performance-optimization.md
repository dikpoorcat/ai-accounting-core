# 看板性能优化方法与审查规范

本文用于当前 3.0 看板与后台的性能审查。优先保持核算正确、模块边界清楚和代码简洁，减少无必要的读取、解析、计算及数据改写。看板打开、刷新和交互应流畅；后台整理允许稍慢，但状态明确、失败能够接续。未经老板确认的数字不作为交付硬门槛。

## 使用指令

使用“看板优化”或“看板优化：<范围>”启动本流程。先阅读本文、[前端规范](../FRONTEND.md)、[看板读取设计](design/06-dashboard-adapter.md)及相关代码。未指定范围时根据当前任务确定；只有确实无法判断时才询问。带“只审查”时不修改。

技术缺陷自行修正，涉及显示内容、业务用法或体验取舍时说明具体影响。该指令不自动授权真实写账、换库、重建大型样本、重启现有服务或 Git 提交。Python 使用仓库 `.tmp-kernel-venv`，验证范围按当前改动风险确定。

## 从整体判断是否值得优化

每次动手前先反向质疑：问题能否通过明确职责、统一取数来源或缩小实际范围解决？新增缓存、目录或特殊分支是否只是局部补丁？去掉耗时目标后，这些设计是否仍值得维护？有界范围、一次读取内的复用和可重建模型服务实际工作；收益不足的重复层应合并或退出。

与当前业务无关的历史增加，不应触发额外扫描或重算；确实涉及累计工资、跨月清偿、资产摊折或税费累计时，可以承担与实际涉及范围相称的工作。不能把“分页只加载20条”说成整个查询没有扫描成本。

## 按完整调用链检查

| 问题 | 检查和处理方式 |
| --- | --- |
| 已移除信息仍在后台处理 | 从页面追到请求、查询、组装、缓存和失效，删除仅为该信息服务的整条链；仍被AI、关账或其他页面使用的能力保留。 |
| 查询精确但扫描过大 | 核对实际期间、账户、对象与业务范围，检查执行计划、返回行和装载量；SQL中的SEARCH不保证读取少，小型固定集合的SCAN也不必强改。 |
| 先装全部明细再分页 | 完整金额及计数与分页详情分开；先筛完整范围，再定位本页身份，批量装载必要结果和来源。总额不能累加已加载页。 |
| 同一请求重复查同一来源 | 仅在同一ReadContext、来源、内容摘要和核验范围相同且成功后复用；失败不缓存，查缺直接按精确键，不遍历全部缓存。 |
| JSON及金额重复转换 | 消费共享正式结果和已核摘要，减少重复解码、编码及临时字典；同时核对是否增加了SQL扫描或返回字节。 |
| 内部重复校验和复制 | 受控读取边界使用同一生成合同；输出校验与序列化各在明确位置完成。独立输入和浏览器响应仍校验，不能以类型断言或客户端标记绕过。 |
| 展开、续页带动整页刷新 | 局部请求只更新相关区域；完整范围、筛选、公司、期间和快照共同校验，续页只追加新记录并更新精确索引。已加载凭证本地打开，不预读全月。 |
| 异步响应串入新选择 | 取消之外，成功、catch和finally都校验当前请求和选择，覆盖A→B→A；切公司、期间和刷新正确清理失效内容。 |
| 临时对象不断保留 | 检查组件挂载、隐藏、卸载、监听器、定时器、闭包和连接；用释放及实际Vue渲染验证，不靠关闭GC或强制回收制造成绩。 |

模块只调用公开端口。阅读提速不能迫使消费者理解别的模块的私表、结果JSON或内部版本。共同职责集中，领域语义不同就分别维护，不为减少行数搭建通用业务框架。

## 保持业务和必要核验

- 未知仍是未知，不能用零值、空业务或旧结果掩盖失败；金额精度、完整资金和债权债务不变。
- 开放期只保当前正确事实和结果；闭期金额、关联冲正及必要采用依据保持原义，不能用今天的公式或来源覆盖冻结内容。
- 页面局部读取、完整核验、关账、修复和备份恢复承担不同职责，不能混用范围。派生目录只能定位，不证明正式采用。
- 政策、生效期间、科目、清偿限制和真实后续收付款分别检查，不能因金额相同就认定等价。
- 缓存与索引的失效依据必须明确。一次读取的成功证明不扩散成跨快照永久缓存，普通连接不全库自动回填。
- 页面内容、原生展开状态、键盘操作和用户允许的后台续页按前端规范保持。优化不能擅自删主数字、强制收起详情或改变业务含义。

## 集中修正与复核

按“确定范围和可比基线 → 归类根因 → 全局同类排查 → 反向质疑 → 集中修改 → 定向验证 → 完整自读与简化 → 再验证”推进。

一处问题触发相关公共调用链和同类路径检查，覆盖CLI/MCP、页面、期间核对、文件和恢复消费者。先列出多余工作及证据，再决定共同修复或分别处理。修改收敛后统一验证；没有新改动、失败或未解决风险，不重复运行大套测试或追逐耗时数字。

优化一个指标可能把成本移到别处：解码次数减少但扫描和返回量增加，不一定有净收益；局部函数变快，也不证明页面变快。网络、GC、磁盘和内存只是待验证线索，不能凭猜测下结论。实验前提变化后先做低成本对照，保留有实际用途的方案，撤去收益不足的层。

## 验证与计时

先用合成业务检查结果和工作量增长，再决定是否需要计时。按改动选择SQL次数、访问范围、返回行、装载/解析次数、重算槽数、改写量、请求数、页面节点或内存释放；没有测的项目明确说明，不为了填表增加昂贵插桩。

看板验证使用真实模块和真实Vue页面。分别检查默认首屏、热刷新、筛选、首次展开、续页、全部读完、公司切换和失败重试；接口返回或loading消失不能代替实际显示完成。后台另分核算提交、标准文档、读取准备、文件生成和备份，不把登录等待或样本构建混入业务计时。

比较耗时时固定构建来源、数据分布、起止点和工作内容，前后按相同预热及统计方法记录原始样本、失败、P50、P95和最大值。构建、全量测试、插桩和正式计时分开运行；未测场景写“未验证”，不能继承另一个构建的旧成绩。

合成样本的构建与独立核对位于 `tests/modular/acceptance/performance/`，可使用12、48、120个月等范围。样本规模、次数和辅助压力测试按实际风险选择，不要求每轮重建十年大库或执行全组合。检查脚本通过只证明其覆盖范围，不能代替真实页面或未测规模的结论。

## 结果与清理

结论写清实际问题、全局处理、业务验证、工作量变化、已测耗时及剩余成本。区分确定收益、条件性收益、没有明显收益和未验证；不把尾部波动归因单个改动，不额外设数值门槛。

文档直接维护当前方法和最终事实，原始合成结果按本次验证需要保存，不堆积开发日记。结束时核对绝对路径后清理本轮无用样本、临时产物和专用缓存；保护其他任务及仍使用的正式资料、身份、原件和备份。公开文件不包含真实公司身份、金额、响应正文或凭据。
