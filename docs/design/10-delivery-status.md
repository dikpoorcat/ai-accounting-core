# 当前 3.0 体系交付状态

当前实现使用模块化体系 `ai-accounting-modular/1`，唯一 CLI 为 `finance-modular`。项目 MCP、记账 Skill 和看板使用同一目录库，各公司分别保存业务数据库。这里维护稳定能力与结果入口，不保存开发过程、历史测试数量或已经过期的公司业务数量。

## 正式资料保存在哪里

| 内容 | 正式位置及作用 |
| --- | --- |
| 负责人和公司目录 | `data/accounting/catalog.sqlite3`，保存负责人身份及公司位置。 |
| 公司资料根 | `data/accounting/companies/<信用代码>/`，每家公司独立。 |
| 公司账本 | 公司资料根的 `runtime/company.sqlite3`。 |
| 原件 | `originals/`，按归档月份保存原字节；仍有效的负责人陈述、模板及业务依据按来源合同承接。 |
| 标准业务文档 | `standard/current.json`、其引用的 `parts/` 和 `README.md`，表达当前最终事实。 |
| 公司备份 | `backups/<信用代码>.finance-company.zip`；当前版及按滚动规则保留的上一版均须完整验证。 |

公司清单、工作月份、关闭范围和当前待办通过 `accounting_context` 读取；标准文档通过 `accounting_documents` 核对就绪状态。当前公司状态以这些入口和实际资料为准，不在源码文档复制真实公司身份、数量或金额。

## 功能与使用边界

合同、存储、身份、业务领域、账务、完整办理、档案、文件任务、读取、看板和运行装配各有公开边界。支持类型明确的业务核算、整单原子保存、防重、开放期保号更正、闭期冲正及后台接续。具体业务范围以[业务规则](05-business-rules.md)及运行时 `accounting_schema` 为准。

- 会计 AI 依[专业核查与办理](13-accounting-review.md)判断当前动作真正需要的事实，复用资料和明确答复，查清后办理；程序问题不转为老板问卷。
- 八项月度清单共用[内部规则](work-checklist.json)。实际文件、申报、付款和核算分别判断，不增加逐项批准或流程日记。
- [银行代发表](12-work-checks-and-payments.md)使用当前正式可付金额、真实收款资料及本公司模板；生成文件不登记付款，不需要代发时不索取模板。
- 单笔或指定多笔撤回保留原件；整月撤销通过 `accounting_cancel_month` 办理，保护跨月、长期安排、模板及冻结所需来源，明确报告不能清除的保留项。
- [公司说明](11-company-note.md)与具体业务事项说明各只保留当前正文，随标准文档保存；纯说明不重复核算，不保存编辑日记。
- 三表和税费共用正式核算及取数结果。缺少细分的字段明确未知，不能把部分报表称为完整定稿；实际申报、实际扣款和账务核差独立接续。
- 投资理财支持货币基金及合同范围内的合作项目记账。合作只是投资方式，不另建经营管理系统或合作详情页；合同未定时不默认补款或风险承担。

## 数据结构与接续

目录结构为1，公司结构为3，均由当前完整合同一次定义。系统只读取、创建和恢复这一基线，不携带开发期结构升级链。数据库、标准业务文档和备份分别核对自己的完整格式、结构与来源；业务历史中的必要冻结和冲正仍是正式账务，不因技术结构整理删除。

准确恢复保持备份的一致状态；简化重建只使用标准业务文档和必要来源重新核算。两者都不覆盖已有目标。普通启动不创建新库、不自行重放，也不把开发中的合成验证当作真实账套已切换。

## 验证与运行结果

可执行验证要求见[开发与验收](07-delivery-acceptance.md)，运行方法见[安装与接入](09-runtime-and-ai.md)。源码合同检查、合成业务测试、真实页面、文件恢复和正式环境核验分别说明，不能彼此替代。

当前正式环境使用上列统一目录，原负责人、公司和数据库身份保持不变，账务事实、凭证、余额与关账依据完整保留。每家公司均有当前结构的独立备份，并已通过实际恢复核对。CLI、项目 MCP 连接及两家公司五页看板均已分别核验；安装包也经过独立安装和恢复验证。

看板保持流畅，后台状态明确且失败可接续。性能验证按实际工作范围检查扫描、解析、计算及改写量，不因无关历史增长增加工作，不追逐未经确认的耗时数字。
