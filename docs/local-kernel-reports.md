# 本地内核季度三表

新 SQLite 内核提供小企业会计准则季度资产负债表、利润表及直接法现金流量表。
金额按整数分计算；XLSX 复用仓库已固定 SHA-256 的税务模板、行次及纯 XML 渲染器。
共享模块 `financial_statement_template.py` 不导入 ORM、旧服务或数据库；旧报表模块继续重导出原模板接口。
这是经营核对与材料准备能力，生成文件不表示已经实际申报。

## 准备与办理

希望使用三表的公司，应通过 `save_fact` 确认适用的报表口径：新设企业使用 `report_profile`，
明确公司名称、小企业会计准则、建账月份及零期初依据；接续企业使用 `continuation_report_profile`
引用有来源的期初包，必要时明确选择 `report_carry_forward` 的前期三表结转。不接受自由分录式期初导入。
已有建账月份之前的凭证时，不能用零期初声明隐藏它们。
没有配置报表口径的公司可以使用记账和关账，但不能据此导出季度三表。

`report_classification` 只引用已经存在的不可变凭证版本与行次，不接收科目或借贷方向。
它可以保存三类具有依据的报表明细：

- 普通管理、销售、财务费用的利润表明细。分类金额必须完整覆盖原行金额；明确银行手续费、利息、工资等沿用业务来源的确定分类。
- 无法从核算依赖唯一确定的往来交易方。资产负债表按账户和交易方分别重分类，不在不同交易方之间抵销。
- 无法确定类别的现金流分配。可将一条实际现金行分配到多个受控报表行次，分配合计须等于原现金行金额。员工或负责人偿还混合代垫、退抵税明细等不靠猜测归类。

季度所得税已通过 `income_tax_assessment` 的 `computed_provision` 正式采用时，三表直接核对该季度的不可变计算版本与账面所得税费用，包括有据的零结果，不要求再登记 `report_income_tax_confirmation`。计算使用有来源的 `income_tax_policy`、`income_tax_prepayment_basis` 和共享税前财报快照；暂计结果尚未正式采用、过期或与账面不一致时仍须处理。

其他已有口径仍可使用 `report_income_tax_confirmation` 明确 `not_applicable`、`zero` 或 `assessed`，提供说明与证据，金额与当年累计所得税费用核对。`assessed` 必须引用该季度有效的 `income_tax_assessment` 不可变计算版本。此事实不会自行生成所得税分录，也不表示已经申报。真实办理用 `external_completion` 保存，办理后的账务核对用 `external_basis_review`。

报表口径、分类、结转及内部确认通过 `save_fact` 保存即可，不需再调用 `preview/confirm` 发布零分录；所得税暂计仍需正式核算采用。
已配置报表口径时，每月关账在同一只读快照中调用同一报表计算，检查本月及累计范围的分类。
季末所得税采用有效的计算暂计或有据的内部确认；缺项会给出 `fact_issues`，补齐后重新预览关账。
`Registry.register_snapshot_readiness` 只负责查询适配，不在通用关账器中硬编码报表业务。
财务报表报送在覆盖期核算与报表检查通过后可使用含所得税暂计的开放期报表，默认先核对、报送，取得实际税额后沿原所得税事项调整并正式采用，再收尾关账。
银行开始收集完整原行并识别业务，收尾再核对完整覆盖、匹配与余额。办理、复核和关账分别留痕，
默认工作顺序不新增外部办理或核对的关账硬门槛；完整安排见[八步会计流程](local-kernel.md#工作清单外部办理与恢复)。

## 统一税务取数

记账、三表、税费核算和申报准备复用内核的固定字段及精确采用来源，不由 AI 自行选择收入范围、月份或重新计算税额。字段口径同时包含公司、期间、含税与不含税、本期与累计；同含义字段使用相同金额，不把不同含义的数据互相替代。

`tax_filing_data(company_id, year, quarter, source=open|closed)` 在同一只读快照返回固定字段、规则和表式版本、精确来源摘要及 `fact_issues`。每个字段的 `definition` 固定说明含义、业务范围、含税口径、舍入和表行。财报季度本期收入、成本和税前利润标为 `financial_statement`；企业所得税预缴字段只取本年累计，分别将 A200000 的第1、2、18行对应到小企业利润表第1、2、30行。适用来源为[税务总局2025年第17号公告](https://tianjin.chinatax.gov.cn/11200000000/0300/030004/03000418/20250714094006730.shtml)，不是旧表第3行。税前字段已有必要来源时，不先要求所得税计提确认；其他会影响这些字段的待处理业务仍须完成。完整财报、所得税费用和净利润保持其原必要检查。

增值税和附加字段直接读取完整已采用税期的 `tax_assessment.filing_fields`，不另算一次税。普通3%及减按1%业务的字段按[2026年第6号公告](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5247507/content.html)映射：减按1%的销售额进入3%栏；按完整季度归集普通应税销售额，计算3%应纳税额并四舍五入至分，填入第15栏；适用减按1%的销售额另按2%计算减征额并四舍五入至分，填入第16栏；第20栏直接用两项已舍入金额相减，不能改为销售额直接乘1%，也不能累加逐笔或逐月舍入的税额。免税销售额和免税额分别展示，不从第20栏重复扣减。

不同业务征收率分别取原来源，不用税期政策替代来源征收率。期间税费计提采用申报字段的最终舍入金额，同一计算器同时生成对应的凭证调整，保持增值税账面应付、正式税费义务和取数结果一致。三项附加税分别按该应纳增值税和已采用政策计算至分，再汇总；看板待缴事项展示正式税费义务，业务汇总、明细及凭证业务金额展示该税期已采用的增值税与附加税合计。前端只格式化整数分，不另算税额。开放期已有税期采用结果需通过原身份的 `preview`、`confirm` 重新采用，保留凭证编号和审计历史；刷新看板不会重算税期，已关账结果不得套用新公式改写。

关账核对按已保存的 `presentation_contract` 验证金额和标签。旧 `close-review/1` 保留当时的业务金额规则，新核对使用 `close-review/2` 展示增值税及附加合计；合同缺失或未知时仍报错。更新当前看板展示不改写冻结核对内容，也不改变其批准摘要。

季度企业所得税支持查账征收按实际利润预缴。`income_tax_policy` 保存生效版本和首要官方来源，`income_tax_prepayment_basis` 明确同年度、同季度的预缴方式、普通或小型微利企业适用资格、累计弥补以前年度亏损和其他特殊调整。普通税率与有据的小型微利企业优惠由内核采用；亏损为零、没有其他特殊调整也须明确有据，不能从空资料推断。弥补以前年度亏损非零时须有对应亏损依据；本轮不支持的其他调整、优惠返回具体缺项。

`income_tax_assessment` 以 `assessment_basis="computed_provision"` 引用 `policy_id` 和 `basis_id`，不填 `cumulative_assessed_fen`。内核读取与取数入口一致的税前财报快照，计算本年累计应纳和扣除此前计提后的本期计提，再通过 `preview`、`confirm` 正式采用。缺少会影响计算的事实时返回具体缺项，不推断优惠资格或零金额。个税、年度汇算以及未支持的所得税方式继续采用有来源的已确认税额。

损益来源新增或修订时，先通过原业务入口正式采用上游结果，再单独预览和采用所得税暂计；不把尚未采用的上游和暂计一起预览。已采用暂计的精确来源依赖保留，上游办理不被待重算暂计挡住，暂计及依赖它的后续事项继续显示待处理，重新采用前财报和税务取数不把旧税额当作有效结果。闭期调整按实际入账月进入后续报表，较早季度仍核对该季度末原采用与冻结金额。

财报生成使用正式暂计，无须等待税务机关实际结果。实际税额返回后，登记 `income_tax_declaration_actual`，沿原 `assessment_id` 重新预览并采用；实际金额优先，计算值保留供核对。暂计、实际申报、应补退与缴款分别说明，原提交文件和采用版本不回写。专票与普通票分栏、其他计税类别或试点表式尚未支持时，不能由 AI 补数。

季度增值税本期列只取该完整季度的核算结果，不用三个月度核算拼成季度；累计列汇总各完整季度的已采用金额，不重算累计免税限额。`open` 根据实际税期读取已正式采用的最新结果，允许该税期在次月入账，并保留真实入账期及采用版本；`closed` 只使用季度末已经冻结的来源，不借用后月份结果。

未采用税期、待重算、来源缺失、覆盖不完整或不支持的字段返回 `value_fen=null` 和具体缺项；明确零必须有完整采用依据。增值税第21、22栏和附加应补退第23至25栏缺少预缴、已缴或其他减免依据时分别标缺项，有据的销售额、应纳增值税和附加计提额仍可读取。附加计提额不冒充应补退额。原冻结结果缺少新字段时不套用当前公式补写。变更来源后重新读取并核验版本，原导出文件、真实申报和冻结历史保留。

## 税点来源

普通服务收入、客户预收及履约可直接登记业务来源明确确认的 `tax_obligation_period`／`tax_obligation_date`。合同、发票和 `tax_point_basis` 不作为普通入账或关账的统一必填。税期仍须有明确业务来源，不从收入月份或银行到账月份自行推定；月精度足够时不补日期，真实收款和月中规则等需要日精度时明确要求。

需要解析复杂税点时，使用 `tax_point_basis` 保存实际采用的合同付款、履约、收款和开票来源事实及精确位置；资产出售按其入口确定税点。共享解析器确定税月、必要的实际日和计税范围。收款候选必须引用已有 `payment`、`cash_payment` 或 `platform_payment` 事实中分配给本业务的金额；解析只读事实，不等待收款凭证计算。银行原行和普通资料原件可复用为来源、完整核对、合同及发票依据，不能独自决定收款归属。相同收款业务、相同原行的不同位置或历史版本不能重复消费。使用解析器时核对更早候选，不能由次月银行到账推定次月才纳税。部分回款按有据分配范围处理，多次收款累计拆税，合同、发票与收款对同一金额的触发合并为最早税点，不重复转税。税点前退回后，覆盖原销售全额的税点沿用原计提减明确红字结果的剩余净额及税额，不重拆剩余含税额；仅覆盖部分原销售范围且缺少退回归属时返回核算缺项，不推定退回发生在区间尾部。后续退回按此前已采用的税前退回和完整转税结果确定原税月，不改写原采用。普通服务与先收款再分期或分次提供服务分别按其明确事实采用适用规则。分期服务预收发生独立税点时，通过 `service_tax_point.sale_id` 引用原客户预收并完整转税；后续履约只确认对应收入，退款复用原税源及原申报采用版本，不重复计税。

复杂税点解析的规则依据为[增值税法第二十八条](https://fgk.chinatax.gov.cn/zcfgk/c100009/c5237365/content.html)、[实施条例第三十九条](https://fgk.chinatax.gov.cn/zcfgk/c100010/c5246349/content.html)及[2026年第13号公告](https://tianjin.chinatax.gov.cn/11200000000/0300/030004/03000418/20260203100537459.shtml)。仅登记真实来源，不把未知合同情况、履约或收款日补为默认事实；未提供的申报字段保持未知，不填零。原税月、采用与冻结内容按原版本读取，不自动迁移事实或更正真实账务。

## 查询和导出

公共命令均明确绑定 `company_id`：

| 命令 | 主要参数 | 行为 |
| --- | --- | --- |
| `report` | `year`, `quarter`, `source=open/closed` | 返回三表、勾稽结果、结构化缺项、来源关账摘要和模板版本 |
| `tax_filing_data` | `year`, `quarter`, `source=open/closed` | 在同一快照读取固定申报字段、对应财报字段、表式版本、精确来源及字段级缺项；不接收自由金额或公式 |
| `preview_report_export` | `year`, `quarter`, 可选 `carry_forward_fact_id` | 根据期末是否已关账自动选择开放或闭期来源，检查三表及资料、核算就绪情况 |
| `confirm_report_export` | 上述期间、`preview_digest`, `epochs`, `request_id`，可选 `output_directory` 父目录 | 原子写入冻结文件任务，不在 SQLite 写锁内渲染文件 |
| `run_report_jobs` | 可选 `limit` | 渲染、核对并原子发布冻结文件；`run_jobs` 也包含报表任务 |

开放查询使用当前开放凭证与已闭月份的冻结凭证；闭期查询只通过 `period_close.manifest.vouchers` 选择不可变版本。
报表口径和分类取 `readiness.financial_reports.facts` 中冻结的事实版本，不能用后来的名称或分类覆盖历史。
闭期冲正使用 `reverses_id` 指向的原核算与原行分类；替换凭证使用新的分类。
当前投影被重建、未来期间发生业务或后补管理资料，都不会改变已冻结报表的金额及内容摘要。
导出入口按期末是否已关账自动选择 `open` 或 `closed`；开放期复用资料与核算就绪检查，
仅财报用途不要求税务清单覆盖，不等待后续实际所得税额、关账批准、外部办理或复核完成。税务资料缺项仍保留在工作清单和关账检查，不能改记为无业务。其他资料覆盖、内部转账流水关联、银行对账及报表分类、所得税采用、期初和勾稽检查继续有效。
预览和确认核对同一 `digest` 与三条 lane 的 `epochs`，确认事务还检查准备时的读取修复版本；
发生变化须重新预览，不直接使用过期计划。内容摘要本身不含实时 epochs。

`confirm_report_export` 可省略 `output_directory`，默认使用公司内部 `exports`；提供时只表示导出父目录，新任务的独立成果目录由程序分配。页面的 `confirm_browser_report_export` 不接收此参数，程序按请求编号管理公司内部下载目录，成果以任务返回路径为准。旧任务继续使用原保存的精确输出路径，重试不改写原载荷。按任务结果定位成果目录，其中包含：

- `财务报表报送与信息采集（小企业会计准则）月季报_YYYYQn.xlsx`。
- `manifest.json`：完整冻结报表、公司/数据库身份、关账来源摘要、模板版本、文件摘要和任务 ID。

文件生成后按同一冻结数据重新渲染逐字节核对；原子目录发布前逐文件刷新到磁盘。
只有 `jobs` 成功且产物核验通过后，才用会计 Skill 的桌面复制脚本交付报表和 manifest；相同内容复用，不同内容自动另名保留。
任务在发布文件后崩溃，可以识别同一任务成果继续完成，不能覆盖其他任务或损坏的已有目录。
后台按任务原保存的 `plan` 输出，不重新读取后来的账务替换计划；改变账或公司名称不会改变
已经排队任务的内容。任务 payload 不可修改，失败记录与重试次数独立更新。

## 实际报送与复核

文件生成只表示交付准备完成。实际提交后，用 `evidence` 保全真正提交的系统导出任务
`manifest.json` 与原 XLSX，再由 `external_completion.adopted_evidence_digests` 引用其不可变摘要。
办理回执独立保全并作为该事实的证据，不能用提交文件自身冒充回执。
实际日期、记录月份与申报覆盖期分别保存；精确采用计算及真实补报接续仍遵守外部办理合同。

完整财报复核需要真实提交的 manifest 与 XLSX，以及本次核对所用的经验证 manifest。
核对公司、数据库、季度、文件摘要、模板及冻结计划，并验证原 XLSX 与原计划一致；
本次依据未变时复用已保全的原 manifest，变化后重新导出，保全并核对新 manifest。
通过 `external_basis_review` 的既有证据和精确引用保存核对依据，不为继续、结果确认或重复阅读另造来源。

原报送资料可以先保存；人工形成且没有结构化可核验依据的资料，只说明复核依据尚未建立，
不能凭文件名、人工文字或空计算集合猜测 `matched`。实际报送仍保留完成状态，等待补齐可核验的复核依据。

复核过期判断覆盖报表口径、分类、期初、全年累计、规则与模板及核算源。
原提交快照、XLSX、采用依据与回执保持不可变；后续变化使核对待复核，不覆盖实际报送。
版本变化没有影响报表时，可用精确的新依据重新核对为 `matched`；存在实际差异时记录差异，
不能把复核当成已经补报。相关快照元数据存于既有 JSON 与计算上下文，不新增物理数据库结构。

## 验证及性能边界

`tests/kernel/test_reports.py` 覆盖真实现金出资、费用、现金付款生成三表及模板缓存数值；
